# Hand-off: i197a

## Problem

The outcome gate sends a run back to a step for two failures that no step of the run can change: a spec the base branch changed since the run started (`ts-spec-fresh`) and a verification command that fails for the machine (`ts-verify`, which the outcome check, unlike the code gate, does not compare with the run's base commit). The specs now say that these two failures pause the gate with the cause named, also when a failure a step could repair stands beside them, that the outcome judge starts no session on such a pause, and that a failing command is compared with the run's base commit and counted at the base as the code gate does. The engine already has the mechanism for each rule (HUM-B7, CHK-B14, CHK-B18, CHK-B20) and the code gate's rows state the comparison; what changes is the outcome check, which the plan designs from these specs.
