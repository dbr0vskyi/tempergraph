# Hand-off: t-30e1f2509b

## Problem

A loop whose reviews failed looked like a loop that found nothing: in run r3-t8-4 all 16 reviews ended on a usage limit and the summary read `18 recorded, 0 filed` ([research `does-the-improvement-loop-find-what-a-reviewer-finds`](../../plugins/tempergraph/docs/research/does-the-improvement-loop-find-what-a-reviewer-finds.rsrch.md) F7). The task makes `loop_summary` and `attention` count the failed reviews by error class, and has the loop child run a review that failed on a usage limit once more after the limit resets, before the loop is called done. The documents say what the code does after the change; no code, test or plan was touched.

## Decisions

- A class that names a spent allowance needs a fact only an executor has. Every existing class would have been wrong or silent: `classify` gives an error `result` `model` and a stream with no `result` after a rate limit retry `throttled` (`claude.py`), and EXI-B7 forbids reading the text. SSN-B11 therefore adds two fields to the session result, `usage_limit` and `usage_limit_resets_at`, and ECC-B17 fills them from the last `rate_limit_event` of the `claude` stream when its status is `rejected`. `infra_cause` and `error_kind` are left as ECC-B12 gives them, so the gate, the ladders and BUD's counters are untouched; whether a step of a run should also wait for a reset is left open (see Open questions). Other executors return false and null until their own specs name a structured fact.
- The reset is read as an epoch in seconds. The recorded 2.1.330 streams carry an `allowed` event with `resetsAt` 1795317000, which is 2026-11-22T03:10:00Z, the day they were recorded; a third-party declaration comments "epoch ms". Read as seconds, a value that is really milliseconds lies far ahead and is not waited for, so the mistake fails safe. No recording of a rejection exists, and ECC says so in an open question; the research note has the findings and confidence marks. A rejection with `errorCode` `credits_required` gets a null reset, since the reference says the session cannot continue until credits are bought.
- The class words are the executor's own (the `infra_cause` and `error_kind` words of SSN-B5 and the stop shapes `timed_out`, `stalled` and `partial`) plus three of the loop's: `usage_limit`, `unparsed` (the answer held no readable block after the re-ask) and `error` (the review raised). The issue names "error class" with no vocabulary; this is a choice of this step. Precedence is in SRV-B29.
- The retry is in SIL, the failure class and the end at once are in SRV. The wait is the loop child's flow, which SIL-B17 owns, and spec `session-review` is at about 30,030 bytes of the 30,720-byte cap of `tests/test_spec_budget.py` (measured by a character-count probe, 30,000 to 30,029 characters and two 3-byte characters), so it has about 690 bytes left; a later edit of it should move a behaviour out first. Specs `self-improvement` and `executor-claude-code` are under 24 KB and specs `engine-cli` and `session-contract` under 27 KB.
- The retry is recorded by a field, not a new record kind. Every record a retry writes (`review_session`, `review_done`, `review_failed`, `review_skipped`) carries `retry` true, so the lists of loop record kinds in SIL-B17 and SRV-B22 stay true and are not edited.
- A review counts as failed in the summary when the latest `review_done` or `review_failed` record of its session is `review_failed`, so a retry that succeeds clears it and a retry skipped for budget leaves it failed. `child.process` also writes a `review_failed` record with no session key when the whole review raises (`child.py` lines 283 and 284); SIL-B24 counts it as one review of class `error`, so a review that crashed is not silent either.
- The wait is bounded and the retry happens once. `review.retry_wait_hours` is 6 with provenance `default_no_data`: it covers the five-hour window and leaves out a weekly one. Each failed review qualifies on its own reset time; the group waits for the latest of the qualifying ones, runs in plan order under the money caps of SRV-B21 and SRV-B25, and a retry that fails again is not run a third time. A reset that is unknown or later than the bound leaves the review failed, with no wait.
- A run in the foreground never waits: a person's `improve review` and the loop run with `TEMPERGRAPH_LOOP=inline` return at once (SIL-B26). `runner.py` runs `drain` inside the exit of the run in inline mode, and `cmd_review` calls the review in the person's own process, so a six-hour wait there would hold the person or the run. A person reruns the review after the reset (SRV-B23).
- `attention` shows a loop with failed reviews as a summary block in `loop[]`, as CLI-B20 already shows findings, and not as an item waiting on a person: CLI-B6 keeps `items` to what waits on a person, and a summary waits on nobody. The command stays `tempergraph improve review show <thread>`; the summary of a thread with no finding, no observation and no failed review still shows nothing.
- Not edited: RDD-B7 and RDD-AC6 (the `loop` block is the thread's whole newest `loop_summary` record, so the new field reaches `status --detail` unchanged), SRV-B20 (SRV-B30 states the one case where its re-ask does not apply), SRV-B22 and SIL-B17 (see the record kinds above), ECC-B11 and SSN-B7 (`rate_limit_event` still maps to no normalized event; SSN-B7 stays a closed list), BUD and the gate, the guides and the README.
- Left for the plan and code steps, where the code differs from the documents today: `improve/review.py` (`_ask` re-asks any session that is not ok, where SRV-B20 names only an unparsable block and SRV-B30 forbids it for a usage limit; `run` writes `review_failed` with no class; `repeat.record` runs once after the plan, so a retry's `review_done` must reach it; `show` lists `failed` from every `review_failed` record, so after a successful retry it would list a review that finally succeeded, and SRV-B23 does not name that list, so the plan keeps it consistent with SIL-B24 or says it did not), `improve/child.py` (where the wait runs and in what order with the proposal and the trial is the plan's choice, but the summary comes after the last retry, nothing waits when `mode()` is `inline`, and the clock must be replaceable for a test), `improve/loop_summary.py` (`review_failed`), `observe/attention.py` (`loop_summaries` skips a summary with no `recorded` and no `top`; `loop_line`), `executors/claude.py` and `executors/launcher.py` (the launcher pushes every event the line mapper returns to the sink, so the report must reach the result without a new event kind, for example a line mapper that keeps the last report), `contracts.py` and `executors/session.py` (two result fields), `executors/standins.py` (`answer` builds ok results only, so the fixtures need a failed scripted session carrying `usage_limit`), `improve/params.py` (the parameter), and the tests named in the reading list. The cost of the retries must reach the review cost that `process` sums into the `loop` ledger row (SRV-B21 keeps review spend in `loop.jsonl` and in that row).

## Open questions

None blocks planning; each has the default the documents use.

- Is six hours the right bound for the wait (`review.retry_wait_hours`)? Options: (a) six hours, the default in SIL-B25, which covers a five-hour window; (b) 24 hours, the reach of Claude Code's own wait ([research `dynamic-workflows-as-orchestration-model`](../../plugins/tempergraph/docs/research/dynamic-workflows-as-orchestration-model.rsrch.md) D13), which also covers a weekly window that resets within a day and holds the child and its ticket longer; (c) never wait, which is SIL-B26 for every limit. Recommended: (a) until overnight runs show how long resets take.
- Should a step or judge session of a run that meets a spent allowance wait for the reset too, as BUD's open question on a `throttled` session asks? Today it is classed `model` or `throttled`, so the run spends a retry or an infra try, and the 10, 20 and 40 second backoff cannot outlast a five-hour window. Options: (a) leave it, this task changes only the loop's reviews (the default); (b) a later task that pauses the run on `usage_limit` until the reset. Recommended: (a) here, and an issue for (b) if the owner wants it.
