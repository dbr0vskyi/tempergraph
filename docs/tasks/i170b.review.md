# Review: i170b

## Findings

1. `plugins/tempergraph/engine/src/tempergraph/improve/child.py:282` blocking: the heading of each segment section takes its reason from the segment's `run_exit` record (for example `budget` or `escalation`). Criterion 6 says "exit code and pause reason", and SIL-B45 says "the first pause's reason". The pause's reason is a different value (`retries_spent`, `unresolved_gap`; `causes.py` maps exit reason `budget` to `retries_spent`). The new test asserts `reason budget` and `reason escalation`, so it checks the wrong value.
2. `plugins/tempergraph/engine/src/tempergraph/improve/issue_context.py:144` not blocking: `## Run` names the pause's reason (ISS-B14, criterion 7) only through the facts line. That line exists only for a candidate that has a pause row (friction candidates). For any other finding of a paused segment, `## Run` shows only the run_exit reason, which is not the pause's reason, so the criterion 7 statement is met only partly.
3. `plugins/tempergraph/engine/src/tempergraph/run/runner.py:1187` not blocking: `take_pause_mark` reads and deletes the marker as an argument, before `attach_workspace` runs and before any later refusal in `_resume`. If the resume is then refused, or the runner dies before the next pause, the marker is gone. The next resume falls back to the `last_head` comparison and reports the run's own commits as `external_change`, which is the false "workspace changed" that criterion 2 forbids.
4. `plugins/tempergraph/engine/src/tempergraph/workspace.py:521` not blocking: the status comparison matches whole porcelain lines. A person's further edit to a file that was already modified at the pause leaves the line unchanged (` M a`), and a person's deletion adds no extra line. The first case gives `reused`, so "workspace unchanged" is told after a change. The second gives `external_change` with `external_changed` 0.
5. `plugins/tempergraph/engine/tests/test_pause_findings_at_final_exit.py:481` not blocking: `test_the_guide_names_every_exit_that_is_final` only checks that the words "exit 0", "exit 4" and "exit 5" appear in the guide paragraph. It does not check that the paragraph lists the reasons SIL-B9 makes final (a stop by request, the attempt cap, a person's stop), which is what criterion 9 asks.

## Earlier review

1. `plugins/tempergraph/engine/src/tempergraph/improve/pause_facts.py:81` not blocking: the decision is the first ledger row for the paused unit at or after the pause's time, with no upper bound at the segment's end or at the next pause. A pause with no recorded answer can pick up a later answer to a later pause at the same unit and show it as that pause's decision, caller and touch.
2. `plugins/tempergraph/engine/src/tempergraph/run/runner.py:1187` not blocking: `take_pause_mark` deletes the marker as soon as the resume reads it. If the resume dies before the next pause or exit, nothing is left to compare with, and the next resume falls back to the old `last_head` comparison (`workspace.py:535`), which the change was meant to replace. The marker is also written only after `run_exit`, so a kill between the two leaves no marker.
3. `plugins/tempergraph/engine/src/tempergraph/improve/issue_context.py:64` not blocking: `log_lines` and `environment` (line 103) take a `facts` parameter that they never use. The docstrings say it is "accepted for the same call shape". This is dead surface.
4. `plugins/tempergraph/engine/tests/test_pause_findings_at_final_exit.py:481` not blocking: the guide test looks for any paragraph that holds "final exit" and "exit 5", then checks for the substrings "exit 0", "exit 4" and "exit 5". It does not check that each exit SIL-B9 makes final is listed (the stop-by-request and attempt-cap reasons, the lost runner), so criterion 9's guide clause is only loosely proven.
5. `plugins/tempergraph/docs/specs/runs-without-a-final-exit.spec.md:26` not blocking: the sentence of SIL-B37 asks for eight results in one `WHEN … SHALL` (reason, decision, caller kind, feedback, ruling, touch class, workspace change, next gate), which goes against the spec rule "one behaviour, one result". The row is the single observable result, but the sentence is close to the 500-character limit.
