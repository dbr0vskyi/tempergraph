# Hand-off: i71

## Problem

The code step's prompt and the phase step's prompt tell their sessions to "mark each row you built", and the plan rule says a row is marked when its change is in its file and the phase's tests pass. No document says in how many edits the marks of a phase are written, so sessions wrote one edit for each row: 30 to 44 edits in a code session, and ten failed in a row in one run when the cells the session guessed were not there (research `does-the-improvement-loop-find-what-a-reviewer-finds`, F7). Each edit is a model turn that reads the session's context again. The task asks that the two prompts and the plan rule say that the marks of the rows built in one phase are written in one edit of the plan, after that phase's tests pass, that the installed copy of the rule files stays the same as the package's, and that a test fails when a prompt lacks the sentence.

## Gaps closed

- G1: `plugins/temperspec-tgraph/docs/specs/phase-coding.spec.md` (PHC-B3 third scenario, PHC-AC3) and `plugins/temperspec-tgraph/docs/specs/kept-marks.spec.md` (KMK-B9, KMK-AC16, KMK-AC17): the brief of a phase session tells it to write its marks in one edit of the plan after the phase's test files pass. The rule is stated once, in KMK-B9; PHC-B3 and PHC-AC3 say what the phase brief tells and link it
- G2: `plugins/temperspec-tgraph/docs/specs/kept-marks.spec.md` (KMK-B9, KMK-AC16, KMK-AC17): the same rule for the prompt of the code step, which builds the whole plan phase by phase on the arm `single` and builds any row left without a mark after the phases, and for the plan rule. `code.spec.md` has no behaviours and is not edited (see Decisions). The quick lane writes no marks, so the rule does not reach it
- G3: `plugins/temperspec-tgraph/docs/specs/kept-marks.spec.md` (KMK-B9's clause on when a mark is written, KMK-AC17): the timing the plan rule states and the prompts imply, extracted as a behaviour. A row is marked after its change is in its file and the test files that its phase's rows name pass. What a marked row must look like at the end is already specified (PHC-B6 and `ts-code-changed` in `code.spec.md`)

## Decisions

- The triage note lists no owner decision, so no option was chosen on an answer or taken by default.
- Where the rule lives. Stated once, in KMK-B9, because it holds for three texts at once (the prompt of the code step, the prompt of a phase session and the plan rule), and KMK already holds the briefings on marks for the code step and the plan rule (KMK-B5 to KMK-B7). PHC-B3 already links KMK-B7 for the phase session in the same way. PHC-B3 and PHC-AC3 keep their own statement of what the phase brief tells, now with the one edit, and link KMK-B9.
- `code.spec.md` is not edited. It is a unit spec in the earlier layout: no behaviours, and the text of each of its criteria must equal the text in `outcome.json` (the engine's docs check, `docs_check.py` lines 53-106). A new or reworded `ts-code-*` row would force a new revision of `outcome.json` and a new stamp for no gain, since KMK-AC16 and KMK-AC17 already name the prompt of the code step. This is how KMK-B5 to KMK-B7 were placed. The rows `ts-code-rows` and `ts-code-once` stay true.
- The Purpose of `kept-marks.spec.md` got one sentence so that the spec does not say it is only about a trip back. The overview's line about it ("which completed marks of a plan survive a trip back to plan") stays true and is not edited: an edit there would be collateral.
- "One edit" is one change to the plan file that marks every row of the phase, whatever the number of rows. The unit is the phase, not the plan: a code session that builds two phases writes two edits, one after the tests of each phase (KMK-B9 third scenario). The wording of the prompts and the rule is the plan's to write; the three texts need one shared phrase for one test to match them.
- A row the session did not build (the plan or a spec is at fault, or its change is not in its file) stays unmarked and is not part of the edit; KMK-B9 says "all the rows it built".
- The quick lane has no plan and no marks: its rows are the report's Rows table (`checks.py` lines 1492-1496 and 1502-1504, where `ts-code-changed` is not applicable). The trigger of KMK-B9 ("the rows of a plan's phase") leaves it out. The triage note's mention of the quick lane in G2 is closed by saying so.
- The second half of the task's criterion 2 (the installed copy of the rule files equals the package's) needs no spec text. It is held by the test `test_the_copy_of_the_rules_installed_beside_the_package_is_the_same` and by the command `python plugins/temperspec-tgraph/skills/setup/install_rules.py --update`, which the plan runs after it edits the rule. The plan template is generated from the rule's fenced example only, which the change does not touch.
- The task's criterion 3 (a test fails when a prompt lacks the sentence) is proved by tests that carry KMK-AC16 and KMK-AC17, and PHC-AC3 for the phase prompt. No behaviour was written for it.
- No criterion in `outcome.json`, as for KMK-B5 to KMK-B7. Whether the gate's `PROMPT_SAYS` also reads the new phrase is the plan's call.
- No contradiction with the specs KMK-B9 and the PHC edit touch: PHC-B3 (only the test files its rows name), PHC-B6 and PHC-B12 (marks as an end state, the code step builds only unmarked rows), KMK-B7, `ts-code-once` and `ts-code-rows`. A search of the package's specs for "one edit", "per row", "row by row" and the forms of "mark each row" found only PHC-B3 and PHC-AC3, and a scenario of KMK-B4 that uses "marks" for another purpose.
