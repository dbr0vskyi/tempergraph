# Triage: i203a

## Task

`batch-queue/tasks/i203a.md`: first slice of GitHub issue #203. A script unit after `code_join` regenerates the files a repository declares as generated (stamp, authoring record, diagram) when their inputs changed in the run, commits them, and sends a failed regeneration back to the code step as numbered findings within a budget of one trip. Two engine needs are expected: `author verify` in a linked worktree (register rung), and a judge-less gate that can send the run back with findings.

## Acceptance criteria

1. A spec of the package states the unit: where it sits, what it reads to know which regenerations a repository has and what the inputs of each are, when it runs one (an input of it is among the paths the run changed since its base), that it starts no session, and that it commits what it wrote on the run's branch with the step's commits. A repository that declares no regeneration, and a run that changed no input, pass the unit with nothing run and nothing written; a fixture run for each proves it.
2. The declaration is the repository's, in a file the package's spec names (the commands file or one beside it); a regeneration command is run through the engine's command runner under the launch rules (SEC-B5), never through a shell, and a command the declaration does not hold is refused. The prepare step does not invent regenerations for a repository.
3. This repository declares its own: the stamp and diagram of each workflow package under `plugins/` whose files, or whose engine inputs, changed, and the authoring record where `author verify` writes one. After a fixture run in a linked worktree whose code step changed a unit's summary and a brief of a fixture package, the package's stamp, authoring record and diagram are the ones the two engine commands write, the main checkout's registry entry and files are unchanged (a tree digest before and after), and the run did not pause.
4. `tempergraph author verify <path>` run in a linked worktree, while the workflow's name is registered from the main checkout, passes its model-free rungs with the default home. The engine spec that owns the register rung states what the rung does for a path that is another checkout of the registered package; an engine fixture proves it and proves that a different package claiming a registered name is still refused `name-taken`.
5. A regeneration that fails sends the run back to the code step once, with one numbered finding for each thing the command reported (for the two engine commands: the rung or check, the finding's code, the unit and the message, as their JSON output gives them), and the code step's visit is told to fix those and nothing else. The four failures of run i173 are the fixture: a summary over 60 characters, a check with no pass case and no fail case, a blocker no case verifies, and a blueprint difference each come back as a finding that names the file to change; the stand-in code step fixes them, the regeneration passes on the second visit, and the run reaches the outcome gate with no pause.
6. The trip back has a budget of one: a regeneration that still fails after it pauses the run, and the pause shows the findings left. A regeneration that fails for the environment (the command does not start, a timeout) pauses at once and sends nothing back. A fixture for each.
7. On the arm `phases` the trip back runs the code step (the join) and not the phases again, unless the run shows in its plan why that cannot be had with the engine's back-edges; then the spec says what runs again and the fixture of criterion 5 counts the sessions.
8. The plan and expand prompts, and the plan rule if it must, say that a generated file the repository declares gets no task row and that `outcome_revision`, digests and diagrams are never edited by hand; the phase and code checks do not count a declared generated file the unit wrote against the scope of a phase or of the change (`ts-phs-scope`, `ts-code-scope`), and the code gate's reading list leaves them out.
9. If an engine capability of need (b) is built: a workflow declares it on a gate with no judge, validation refuses it on a map's gate (MAP-B11 stands) and on a gate that has a judge, the loop budget bounds it (BUD), the visit reason holds the findings' criterion, place, message and fix and nothing else, and an engine fixture with a script unit that fails once proves the trip back, the second pass and the budget. The engine specs changed say it without naming any workflow.
10. `outcome.json` carries a new revision, the package's README, overview spec and diagram show the unit, the specs changed stay within the spec budget, and each new test carries the id of the spec criterion it proves. The package's own stamp, authoring record and diagram at the end of this run are written by the unit this run built, in this run's worktree, or the report says why not and names the files left for the operator.
