# Triage: i197a

## Task

`batch-queue/tasks/i197a.md`: the outcome gate of the temperspec workflow sends no run back for a fact no step can change (a moved base branch under `ts-spec-fresh`, a verification command that fails for the machine under `ts-verify`). First slice of GitHub issue #197.

## Acceptance criteria

1. A failing `ts-spec-fresh` never sends the run back. The outcome gate pauses with the cause: the pause shows each spec that changed on the base branch, the base commit and the head it was compared with, and the one action that clears it (bring the base branch's head into the run's branch, then answer `retry`; SBS-B2 already passes a run that merged the head). `side-by-side-runs` states it, and the criterion's fix line says the same. A stand-in run whose base branch gains a commit to a spec the run edited ends its first invocation paused at the outcome gate with no step entered again, and after a merge of the head made by the test and a `retry` it reaches the finalizer.
2. The outcome check compares a failing verification command with the run's base commit exactly as the code gate does (the same function, the same four cases: exits 0 at the base, fails the same, fails differently and names a changed file, fails differently and names none; not compared when there is no base or the command does not finish). A failure that is environmental by that comparison never sends the run back: the gate pauses with the command, its exit at the gate and at the base and the reason, as the code gate's pause does. `outcome-gate` states it. A stand-in run whose command fails the same at the base ends paused at the outcome gate with no step entered again.
3. A verification command that exits 0 at the outcome gate is never run at the base, and a failing one is run there once per visit of the gate; a test counts the started commands (as the test of `ts-code-spend` does).
4. A failure the change caused still goes back as today: a stand-in run whose command exits 0 at the base and 1 at the head is sent to the step OGT and `serves` name today, with the command's output in the reason.
5. When a fact no step can change fails beside a failure a step could repair, the run pauses and goes nowhere: a trip back cannot make the gate pass while the first fact stands. The pause lists both, the unchangeable one first. A stand-in run with a moved base and a failing `ts-traced` proves it. After the operator clears the first and answers `retry`, the gate runs again and the second failure is routed as today.
6. The outcome judge is not started when the check paused the run for criteria 1, 2 or 5 (CHK-B1 holds for the outcome gate); a test counts the judge sessions.
7. `outcome-gate` states, as one behaviour, which final criteria name a fact no step can change and what the gate does for each; the wording of `ts-spec-fresh` and `ts-verify` in `outcome.json` and their `check_method` say the same; `outcome.json` carries a new revision.
8. The specs changed stay within the spec budget, each new test carries the id of the spec criterion it proves, and the tests of OGT-AC, SBS-AC and the code gate's base comparison still pass, changed only where a criterion above changes the fact they assert.

## Intent

- Goal: a run whose outcome gate fails on something no step of the run can change stops at once with a clear pause, instead of re-running about 85 percent of the run and then stopping on a budget.
- In scope: `ts-spec-fresh` and `ts-verify` failures that are environmental at the outcome gate pause with no retry; the same base comparison as the code gate for `ts-verify`; the unchangeable-plus-repairable mixed case pauses; the judge is skipped on those pauses; specs `outcome-gate` and `side-by-side-runs`, `outcome.json` wording and revision (29), tests.
- Out of scope: choosing the latest owning step as a back target; narrow return visits; targets unable to make the fix; the engine fact that the judge's `place` and `fix` do not reach the step; the workflow merging the base head by itself; the outcome check reusing the code gate's base run (#189). Also the same fault at the review gate and the code gate: named in the report as follow-ups unless the fix is the same line. Running `author verify`, `upgrade-check --stamp`, or editing a digest.
- Assumptions:
  - A1: the engine pauses on a check result marked environmental before it routes back (HUM-B7), so no engine change is needed. If wrong: an engine change to OUT-B16 with an engine fixture, stated without the workflow.
  - A2: i173 is merged before this run (the task's order line), and the outcome record is at revision 28 so this run writes 29. If wrong: a hand merge of `outcome.json`, `outcome-gate.spec.md` and `checks.py`.
  - A3: the environmental mark may be set on a result that also holds a repairable failure. Today `_result` marks environmental only when no other finding fails (`checks.py:617`), the code gate's `ts-code-mixed` retries instead. If wrong: criterion 5 needs a different way to pause (see U1).
  - A4: the code gate's behaviour stays as it is; only the outcome check gains the comparison and the mixed-case rule. If wrong: the code gate's `ts-code-mixed` row and its tests change too, which widens the change past the two specs and the outcome check and breaks the budget of criterion 8.
