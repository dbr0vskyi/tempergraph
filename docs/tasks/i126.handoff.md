# Hand-off: i126

## Problem

A clean code visit pays for each verification command twice: once in the session, once at the gate. The gate cannot take the session's result because the session runs the commands in its own shell, which records nothing, and because the reuse key names the commit and the status listing, which the commit that follows the session changes. The task makes the session's one run go through the engine's check preview, makes the key name the tree's content so that it survives the commit, and makes the gate's evidence say for each command whether it was reused or run.

## Decisions

- Criteria to rows: AC 1 is `ts-code-once`; AC 2 is `ts-code-preview` (what the prompt and the step say) and `ts-code-previewed` (what the preview does); AC 3 is `ts-code-session` with CHK-B13 and CHK-AC8; AC 4 is `ts-code-rerun` with the same two; AC 5 is `ts-code-evidence`.
- The key names content (ADR above). This is an assumption the task leaves open, taken because the owner is away: every file git tracks and every untracked file git does not ignore, outside the state root, by path, bytes and executable bit; no commit, index or status listing. It leaves CHK-B5 and CHK-AC6 true as written; CHK-AC8 proves the case CHK-AC6 had never been shown for (a commit between the preview and the gate).
- The commit between session and gate is made by the workflow's own commit script, which the engine runs as an `after` script of the step (`nodes.py` lines 593-595; `routing.py` lines 136-151); it is not made by the engine. So the engine cannot re-key a stored run at the commit, and the key has to survive any commit. The engine spec and the ADR say this without naming a workflow.
- Both the preview and the gate read and write one store: the preview's context is built by the same function as the gate's and carries the same store path (`nodes.py` lines 545-548 and 1504; `check_worker.py` line 39). No engine change is needed for that, only for the key.
- Outside a git repository the old key held no file content (`git()` prints nothing there, `git.py` lines 34-44), so every call after the first was a hit. The new key covers every file under the workspace outside the state root. Recorded in the ADR because the new definition has to say what it does there.
- `08-code.spec.md` is in the earlier layout (numbered sections, `- [ ] ts-…` rows), which the spec rule says to leave as it is. It has no behaviours section, so each row states one observable result, as the rows of the earlier tasks do. The code step mirrors each new or edited row into `outcome.json` with the same text as revision 9: a rescaffold rebuilds the criteria from that file and would drop a row that is not there, and each row needs a check or a test. The earlier task's test pins the file at revision 8 (`test_spec_budget_and_moved_ids.py` lines 273-277) and compares the text of its rows with their spec rows (lines 260-293), so the plan updates that pin and keeps what it proves: the entry for issue 114 exists.
- `ts-code-once` no longer says "before it writes the report". A file written after the final run changes the tree's content, and then the gate runs the commands again (`ts-code-rerun`), so the saving needs the plan marked, the report written and the final run last. The prompt row says so; the exact wording of the prompt is the plan's.
- The preview cannot see the unit's own artifacts: its context holds the artifacts as state held them when the attempt began (CHK-B17, `selfcheck.py` lines 40-48), and `artifact_path` reads only those (`check_helpers.py` lines 17-23). So on a first attempt `code_check` cannot read the code report in a preview, records "the code report cannot be read", and returns before it runs any command (`checks.py` of the package, lines 848-868). The report's folder differs by package, so a fixed path will not do. `ts-code-previewed` therefore asks that a preview run the commands and report no failure for a report not yet handed over or for the commit that follows the session (`_committed`, line 886, fails on an uncommitted tree). How the check does it, for example a branch on `ctx.preview`, is the plan's. The marks still come first in a preview: it runs nothing on an unfinished plan, which saves a full run.
- The quick lane has the same two problems: its rows are read from the code report (lines 860-864), so a preview skips them too.
- The evidence: the preview prints at most 2,000 characters of it (`selfcheck.py` lines 28 and 100-101), and `_result` puts up to 120 changed paths in it (`checks.py` of the package, line 250). Put the per-command lines first, or a session will not see them. A command that did not start has no result: the plan decides its word (`not run`).
- The preview runs on the executor `claude` only (the open line of the engine spec's last section stays as it is). On another executor the session cannot run it, runs the commands in its shell, and the gate runs them again: the old cost, never a wrong answer.
- A session may call the preview three times in an attempt (`self_check_limit`, default 3). A call after any change runs every command again, so the prompt should say to call it once, when everything else is done.
- No spec carries a "Not built yet" line for this issue (searched the package's specs, its docs README and the engine's spec 75); the one in spec 75 is about other executors and stays.
- No research note is written: the unknowns are answered by reading the code, cited above and in the ADR. The package's research note `speedup-runs-command-reuse.rsrch.md` described the key before this change; its F2, F4, F5, F6 and its open question become false when the code changes, so the plan lists it under Docs to update.
- Not edited, on purpose: `00-overview.spec.md` (its line 41 lists the criteria checked model-free; the plan decides whether `ts-code-preview` joins that list), `rules/task-notes.rule.md`, `prompts/code.md`, `outcome.json` and the engine's guides (the one sentence on `self_check` stays true).

## Open questions

- What does the code report's Verification section say when the report is written before the final run? It cannot hold the final run's result. Options: (a) the report is written before the final run, names each command and records what the phase runs showed, and the final run's result is the gate's evidence; the saving is kept, the judge already treats the report's results as claims and takes the commands' results from the check's evidence (`judges/code.md` lines 3 and 7), and the pull request body shows the first six lines of the section (`summary.py` line 110). (b) The report is written after the final run with its result; it is complete, the tree changes, the gate runs every command again, and the saving of this task is lost. (c) A new engine capability lets a workflow name paths its commands do not read, so that the key leaves them out; the saving is kept and the report complete, but a command that reads documents (the engine's own suite does) could then be answered stale, and nobody has asked for it. Until answered: (a). It does not block planning.
- Should a live check prove that a real session's preview run is reused by the gate? The resolved program is part of the key and is found on the `PATH` of the process that runs the check, and the preview runs in the session's shell; L-29 proved only that the preview runs. Options: (a) add a row to the owner's live checks plan; (b) rely on the `reused` or `run` word of the gate's evidence in the first runs. Until answered: (b). It does not block planning.
