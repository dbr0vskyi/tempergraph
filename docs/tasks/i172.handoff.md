## Problem

The loop's cause codes read a pause shape the gate never writes (a tool-access pause is kind `escalation` with reason `tool_access`, not kind `tool_access`). They name no trip back, no stop at the attempt cap, no last stage that delivered nothing and no session refused for the usage limit, class an ask unit's pause a fault, and make `tool_repeat` from repeated calls that never failed. ## Decisions

- The triage note lists no owner decision (`Owner decisions: None`), so none is listed here as answered or as taken by default. The conversation value and the owner's answers of this run were placeholders: the step took the run as unattended, closed each question that only the owner could settle on the option that changes the least, and listed it under open questions with the default taken.
- The task names the self-improvement spec as the one that states the causes. The five live in a sibling spec with its own prefix because of the size above; the self-improvement spec keeps the rules for how a finding is judged and filed.
- Names, taken from the nearest existing codes: `trip_back:<unit>`, `attempt_cap`, `finalizer_undelivered:<outcome>`, `usage_limit`, `input`. The `<unit>` and `<outcome>` parts are the one detail part a code may carry (`plugins/tempergraph/engine/src/tempergraph/improve/causes.py` lines 3-4).
- Classes and sides: the three fault causes are `fault` and `workflow`, as `loop_budget_spent` and `check_repeat` are; the usage limit is `infra` and `host`, as `auth` is, so it is recorded and never filed (SIL-B11); the ask pause is `designed` and `workflow`, as `approval` is.
- What a count is: the trip back's count is the sessions started in the visits it began (CMP-B12), the attempt cap's is the trips back, and the others are one for each occurrence (for `usage_limit`, for each session). A count can be 0 for the first two, and the finding is still made.
- A trip back is a gate whose verdict is `BACK` routing the run back. A person's `back:<unit>` decision at a pause and a switch's re-arm also send a run back, but neither is a gate's verdict (open question 4).
- A repeat that did not fail makes no cause (G7).
- Whether any new cause fires the friction lens in stable mode is left as it is (open question 1): SIL-B10 is not edited.

## Open questions

- Should a trip back, a stop at the attempt cap and an undelivered last stage fire the friction lens in stable mode (SIL-B10)? Options: a) none of them; b) all three; c) the attempt-cap stop only, since SIL-B10 already lists a stop. Until answered: a (the stable list is unchanged; the causes are recorded and judged in dev mode).
- A pause of a `wait` unit (kind `event_wait`) and an operator's breakpoint (kind `breakpoint`) also reach the last branch of `derive` and become a fault `escalation:<reason>`, the defect the ask pause had. Should they be `designed` too? Options: a) leave them; b) class them `designed` like the ask pause. Until answered: a (the task names the ask unit only).
- Task criterion 8 asks the remedy of every new or corrected code to name a kind of change that fits a unit with no step and no prompt. FRC-B4 (`usage_limit`, infra) and FRC-B5 (`input`, designed) have nothing in the workflow to change and say their remedy proposes no change, as every existing infra and designed code does. Options: a) as written; b) give `usage_limit` a remedy that names the account's allowance (resume after the reset, or raise it) and `input` one that names the ask unit's defaults. Until answered: a.
- A switch's re-arm routes `BACK` to the safer arm's entry with `entered_from` `rearm:<unit>` and starts new visits as a trip back does. Should it be a trip back for the loop? Options: a) no, only a gate whose verdict is `BACK` (as written); b) yes, with the arm's entry unit as the detail. Until answered: a.
