## Decisions

- The triage note lists no owner decision (`Owner decisions: None`), so none is listed here as answered or defaulted. The conversation value and the owner's answers of this run were placeholders: the step took the run as unattended (`never`), closed each question that only the owner could settle on the option that changes the least, and left none blocking.
- The task names `self-improvement` as the spec that states the five codes. The five live in a sibling spec with its own prefix because of the size above; a new prefix, not new `SIL-B` numbers, because other tasks of this batch may also edit `self-improvement.spec.md` and a second branch could take the same number.
- Names, taken from the nearest existing codes: `trip_back:<unit>`, `attempt_cap`, `finalizer_undelivered:<outcome>`, `usage_limit`, `input`. The `<unit>` and `<outcome>` parts are the one detail part a code may carry (`improve/causes.py` lines 3-4).
- Classes and sides: the three fault causes are `fault` and `workflow`, as `loop_budget_spent` and `check_repeat` are; the usage limit is `infra` and `host`, as `auth` is (so it is recorded and never filed, SIL-B11); the ask pause is `designed` and `workflow`, as `approval` is.
- What a count is: the trip back's count is the sessions run again, the attempt cap's is the trips back, the others are one per occurrence (sessions for `usage_limit`). A count can be 0 for the first two, and the finding is still made.
- Trips back are gate routes of `BACK` only (CMP-B12). A person's `back:<unit>` decision at a pause is not one.
- A repeat that did not fail makes no cause (G7 above).
- Whether any new cause fires the friction lens in stable mode is left as it is (open question 1): SIL-B10 is not edited.

## Open questions

- Should a trip back, a stop at the attempt cap and an undelivered last stage fire the friction lens in stable mode (SIL-B10)? Options: a) none of them; b) all three; c) the attempt-cap stop only, since SIL-B10 already lists a stop. Until answered: a (the stable list is unchanged; the causes are recorded, and judged in dev mode).
- A pause of a `wait` unit (kind `event_wait`) and an operator's breakpoint (kind `breakpoint`) also reach the last branch of `derive` and become a fault `escalation:<reason>`, the defect the ask pause had. Should they be `designed` too? Options: a) leave them; b) class them `designed` like the ask pause. Until answered: a (the task names the ask unit only).
- Should the trip back's count also include units that ran only in an earlier invocation of the thread? Options: a) no, the records of the one invocation decide, as written; b) yes, count every unit the trip back clears (CMP-B12), which needs the earlier invocations' records. Until answered: a.
- Task criterion 8 asks the remedy of every new or corrected code to name a kind of change that fits a unit with no step and no prompt. FRC-B4 (`usage_limit`, infra) and FRC-B5 (`input`, designed) have nothing to change and say their remedy proposes no change, as every existing infra and designed code does; an ask unit is itself a unit with no step and no prompt. Options: a) as written; b) give `usage_limit` a remedy that names the account's allowance (resume after the reset, or raise it) and `input` one that names the ask unit's defaults. Until answered: a.
