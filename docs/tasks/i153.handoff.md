# Hand-off: i153

## Problem

A step, retry or judge session that the account's usage limit ends (`usage_limit` true, not ok) is counted as a model error or an infra failure: it spends a retry or an infra try, and a few of them end the thread with exit 5 and reason `budget`. The run never reads the field the executors already return. The specs now give that case a cause of its own that spends nothing, a pause with its own reason that carries the reset instant, a plain resume that reruns only the session the limit ended under the attempt number it had, and the keys on the run log, the status row and the detail document that tell it from a model error.

A session that ends not ok with `usage_limit` true spends no retry and no infra try, whatever its `error_kind` or `infra_cause`; its scenarios show a `model` error and a `throttled` infra cause both left uncounted, and a session with `usage_limit` false still spent as BUD-B1 says. BUD-B1, BUD-B2 and BUD-B11 are not edited: BUD-B17's "whatever" clause and its scenarios give it precedence over them.

The pause is HUM-B14, nothing spent is BUD-B17, and the resume that reruns the judge without the step is DUR-B12 (its second scenario and DUR-AC10).
- G6: `plugins/tempergraph/docs/specs/durability-and-resume.spec.md` (new DUR-B12 and DUR-AC10). A resume with no decision reruns only the session the usage limit ended, in its unit, under its attempt number and with every counter as it was; a resume before the reset instant is accepted and pauses again when the limit still holds. DUR-B9 and DUR-B2 are not edited.

## Decisions

- The triage note lists no owner decision (`Owner decisions: None`), so none is answered or defaulted. The prompt carried no value for the conversation setting (a placeholder stood in its place); the step took the run as unattended, closed every question on the option that changes the least and left none blocking.
- The pause is kind `escalation` with reason `usage_limit`, not a new kind. The task asks for "a pause reason of its own", and `tool_access` (HUM-B7, BUD-B11) is the existing case of an environment cause that pauses as an escalation with a cause of its own, so every reader that counts pauses by kind keeps its kinds.
- The reset instant has no format of its own. Every new key holds the value the session's result holds (SSN-B11; the dataclass holds epoch seconds as a float, `contracts.py` lines 717-718), so a test compares equal values and no conversion is specified.
- The criterion "the run's `status` row carries `usage_limit_resets_at`" is read as one key of the row (DUR-B13), not a key of a pending gate, so a reader finds it where it finds `resume_count`.
- A sampled audit judge (JDG-B7) does not grade the attempt, so BUD-B17 names "a judge session that grades the attempt" and not every judge-kind session; JDG-B7 stands (an audit changes no verdict, route or counter).
- Sentences over 500 characters: none written; the longest new behaviour sentence (JDG-B14) has about 415 characters. BUD-B1, BUD-B11, HUM-B7, EVT-B13, EVT-B16 and DUR-B11 are already over 500 characters and are not edited, so each new rule is a behaviour of its own and no existing list grew.
- Values taken from the task's fixtures (a retry budget of 2, a reset one hour ahead, the first run and two resumes) sit in the criterion BUD-AC15 and in scenarios of DUR-B12; no behaviour sentence carries them. No added line names the task, an issue or a workflow.
- Ids start at the next free number of each spec (BUD-B17, HUM-B14, JDG-B14, DUR-B12 and DUR-B13, EVT-B26 and EVT-B27, RDD-B21; criteria BUD-AC15, HUM-AC10, JDG-AC9, DUR-AC10 and DUR-AC11, EVT-AC9 and EVT-AC10, RDD-AC11). The queue of this batch holds requests that edit specs of the same capabilities, so a second branch may take the same number; the structure check then names the duplicate at the merge.

## Open questions

- HUM-B6 appends one ledger row for every accepted resume, with its decision, and DUR-B12 accepts a resume that carries none; the runner writes a row only when a decision is given (`plugins/tempergraph/engine/src/tempergraph/run/runner.py` lines 1155-1156). Should the plain resume of a usage-limit pause write a row? Options: a) the row HUM-B6 describes, its decision empty and its touch class that of the pause's kind; b) no row, as for the plain resume of an unfinished thread. Until answered: a (HUM-B6 as written; the plan decides the empty decision's spelling).
- Should `proceed` be refused at a usage-limit pause, since no session of the attempt produced or judged anything? HUM-B12 accepts it at any escalation, and the guide already says not to `proceed` after an infrastructure failure. Options: a) accepted as at any escalation; b) refused with exit 2 as a wait refuses it (HUM-B4). Until answered: a (nothing refused, no new rule).
