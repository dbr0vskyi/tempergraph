# Hand-off: i153

## Problem

A session that the account's usage limit ends (`usage_limit` true, not ok) is counted as a model error or an infra failure: it spends a retry or an infra try, and a few of them end the thread with exit 5 and reason `budget`. The run never reads the field the executors already return. The specs now give that case a rule that spends no counter, a pause with a reason of its own that carries the reset instant, a decision-less `resume` that reruns only the session the limit ended under the attempt number it had, and the keys on the run log, the status row and the detail document that tell it from a model error.

## Decisions

- The triage note lists no owner decision (`Owner decisions: None`), so none is listed here as answered or defaulted. The prompt's conversation value and the owner's answers were placeholders; the step took the run as unattended (`never`), closed every question on the option that changes the least and left none blocking.
- The pause is kind `escalation` with reason `usage_limit`, not a new kind. The task asks for "a pause reason of its own", and `tool_access` (HUM-B7, BUD-B11) is the existing case of an environment cause that pauses as an escalation with a cause of its own, so every reader that counts pauses by kind keeps its kinds.
- The reset instant has no format of its own. Every new key holds the value the session's result holds (SSN-B11; the dataclass holds epoch seconds as a float, `contracts.py` lines 717-718), so a test compares equal values and no conversion is specified.
- The criterion "the run's `status` row carries `usage_limit_resets_at`" is read as one key of the row (DUR-B13), not a key of a pending gate, so a reader finds it where it finds `resume_count`.
- A sampled audit judge (JDG-B7) does not grade the attempt, so BUD-B17 names "a judge session that grades the attempt" and not every judge-kind session; JDG-B7 stands (an audit changes no verdict, route or counter).
- HUM-B14 names the resume command in prose, as EVT-B13 and DUR-B11 do, because HUM-B2 calls the payload field `resume_command` while `gate.py` line 270 and `status.py` line 87 write the key `resume`. That mismatch is older than the task and is left alone.
- DUR-B12 changes only a resume that carries no decision. RRN-B19 still refuses feedback with no decision on a paused thread, and a `--set` on such a resume is applied by DUR-B7; neither is edited.
- The behaviours that meet a rule about infra failures (JDG-B5 "never pausing", CNL-B15 and CTS-B9 on members and slots that fail on infrastructure, HUM-B11) are not edited: BUD-B17 and JDG-B14 say "whatever its `infra_cause`" and a session the usage limit ends is never an infra failure, so each of those rules keeps its meaning for the failures it names.
- No behaviour sentence carries a value of the task's fixtures (its retry budget, its reset one hour ahead, the number of resumes); the scenarios take their own illustrative values and the criteria say "more sessions than the retry budget" and "a reset instant". No added line names the task, an issue or a workflow.
- Ids start at the next free number of each spec (BUD-B17, HUM-B14, JDG-B14, DUR-B12 and DUR-B13, EVT-B26 and EVT-B27, RDD-B21; criteria BUD-AC15, HUM-AC10, JDG-AC9, DUR-AC10 and DUR-AC11, EVT-AC9 and EVT-AC10, RDD-AC11). The queue of this batch holds requests that edit specs of the same capabilities, so a second branch may take the same number; the structure check then names the duplicate at the merge.
