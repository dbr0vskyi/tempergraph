# Hand-off: i203a

## Problem

A run that changes a workflow package's outcome record, a unit, a brief or an engine input of a diagram leaves the package's stamp, authoring record and diagram stale, and no step session may run the two engine commands that refresh them. The task adds a unit with no session after the code step that runs the commands a repository declares for its generated files when their inputs changed, commits what they wrote, and sends a failure back to the code step once as numbered findings. Two engine needs came with it: `author verify` in a linked worktree, and a gate with no judge that sends the run back with findings.

## Decisions

- Owner decisions of the triage note: none. The note lists `None`, so no answer and no default was taken
- The declaration is `tempergraph.regenerations.json` at the repository root, beside the commands file and read only by the package (decision record of the package). The commands file stays the engine's: a regeneration's command never becomes a command a session may run
- Criterion 5 cannot be met with no engine change. Read in the engine: a check FAIL of a gate with no judge derives RETRY with the findings as blockers and an environmental one escalates (`run/nodes.py` lines 1512 to 1528); a BACK is produced only for a judge's `defect_in` (`run/judging.py` line 286), a confirmed upstream claim (`run/nodes.py` lines 1559 and 1589), the outcome gate's serving unit (`run/nodes.py` line 1447) and a re-arm (`run/gate.py` line 348); a route reaches forward units only (`model/validate.py` lines 1038 to 1041) and a script unit takes no route (`api.py` lines 165 to 176); a failed `after` script of a step retries that step under its own retry budget with `script_failed:<name>` as the whole reason (`run/nodes.py` lines 734 to 735 and 1485 to 1490). So the engine gets `on_fail: back` (decision record of the engine; HUM-B15 to HUM-B18). The expected need (b) is built; need (a) is SCF-B24 and SCF-B25
- A second failure after the trip back reaches the loop budget (HUM-B17) and not the repeat rule of BUD-B16: that rule compares a step's attempts of one visit (`prior_failing`, `run/nodes.py` lines 588 and 601 to 605), and the record of a script unit holds none (`run/nodes.py` lines 1295 to 1296 and 1571 to 1577)
- Where the unit sits: after the code step and before the independent review and the outcome gate, in every lane (RGN-B1). The overview lists it between `code` and `code_join`, so `code_join` and its route are unchanged and no route unit is added (a script unit takes no route). The task says "after `code_join`"; see the first open question

## Open questions

- Where does the unit sit against `code_join`? The task says after `code_join`. Options: a) between `code` and `code_join`, as the overview lists it: `code_join` keeps its route to the review or the outcome gate and the new unit needs no route; b) after `code_join`: `code_join` then goes to the new unit for every run, and a route unit after it has to pick the review or the outcome gate, because a script unit takes no route. RGN-B1 holds under both. Until answered: a
- Should a declaration that exists and cannot be used pause the run (RGN-B4), or declare none as CHK-B11 does for the commands file? Options: a) pause at once naming the file; b) declare none and pass. Until answered: a
- RGF-B3 meets "a finding that names the file to change" only where the command's own message or remedy names the file: the engine's report for `summary-too-long` and for a missing check case names one, the report for `blueprint-difference` and `outcome-unverified-blocker` does not. Options: a) keep the command's words unaltered and have the fixture's stand-in report name its files; b) let a regeneration in the declaration list the files its findings are fixed in, and name them in every finding of it. Until answered: a
- A fix of a regeneration finding in the quick lane may touch a file the triage note does not name, and the code gate's lane guard (`ts-code-lane`) then sends the run to triage. Options: a) no exception; b) the guard leaves out the files of a visit whose reason is a regeneration's findings. Until answered: a
- Candidate issue, not a behaviour: SCR-B5 says a script's `call` takes a `ScriptContext` and returns a `ScriptResult` (`ok`, `produces`, `environmental`, `message`), but `run/nodes.py` lines 1236 to 1245 calls it with a `CheckContext` and reads a mapping of artifacts, with `ok` false only when it raises. The regeneration unit must not rely on `ScriptResult`. Until answered: the unit reports its findings through the gate's check, which the engine does support
- Candidate issue, not a behaviour: `_result` and `_reading_lines` in `workflow/temperspec/checks.py` (lines 448 and 486) drop every path under `.claude/rules/` from the changed paths, whoever changed it, and no test pins it, so no spec states it. Until answered: left as it is
