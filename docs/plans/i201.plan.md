## 2. Phases

### Phase 1: A stand-in session that opens a named path

Goal: a scripted stand-in judge or step session can be told to open named paths and reports each as a `read` call with the workspace-relative path, so a fixture run builds the digest's reads from the journal it wrote, and the SRV-AC22 test no longer writes a judge's journal by hand.
Weight: light

### Phase 2: The gate field `judge_may_skip`

Goal: a gate declares `judge_may_skip` through `Gate(...)`, and validation refuses an absolute pattern, a pattern that leaves the repository and a list on a gate with no judge, each with a finding code of its own.
Weight: light

### Phase 3: The judge's own list of changed paths and its record

Goal: the judge node builds its changed paths for the judge only (no deleted path, names as the workspace holds them, declared file artifacts and the gate's patterns left out, then the cap of 200), writes `changed_base`, `changed_base_reason` and `changed_left_out` on the judge's `agent_run` record, and leaves the lists of checks, git facts, the session's own record and the suites unfiltered.
Weight: medium

### Phase 4: The digest and the findings read the new record and the item key

Goal: a digest of a judge with a null `changed_base` carries no `changed_total` or `changed_read` and makes neither finding, and `passed` and `gave` are keyed by unit and item so each item's judge is read from its own judgements.
Weight: medium

### Phase 5: Thresholds, privacy and the shape of the specs

Goal: the seven recorded shapes, the one-of-five and two-of-five judges and the canary fixture with a declared artifact path and a gate pattern are proved by tests, `digest.judge_read_share` keeps its value with its source, and the spec form and budget checks still pass.
Weight: light
