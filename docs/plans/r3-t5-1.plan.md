# Plan: the engine's `schedule` command, first phase (R3-T5.1)

## 0. Hand-off

- Triage note: `docs/tasks/r3-t5-1.triage.md`; hand-off: `docs/tasks/r3-t5-1.handoff.md`
- Specs read: `plugins/tempergraph/docs/specs/83-schedules.spec.md` (SCH-B1 to SCH-B33, SCH-AC1 to SCH-AC12, open questions). Read for the boundary only: the hand-off's reading list names spec 84 (TCK), ADR-0095 to ADR-0099, ADR-0132, R-150 and R-095; the code step reads them as the list gives them.
- Extra files opened beyond the reading list, and why: `plugins/temperspec-tgraph/rules/plan.rule.md` (the plan format; the machine-wide copy was also given in the instructions); `plugins/tempergraph/engine/tests/test_cli.py` lines 90-110 (to find tests that pin the bare `schedule` verb: `test_usage_refusals_exit_2` expects `["schedule"]` to exit 2 with a message, which stays true when `schedule` takes a sub-verb, so the verbs phase keeps a bare `schedule` a usage error); a search of `tests/` for ADR-0129 (it found `test_workflow_packages.py`, `test_run_skills.py` and `conftest.py`, which already check that the engine names no workflow package).
- Why this design: one new package `tempergraph/schedule/` holds pure, clock-injected modules (rule model and slots, exact formats and canonical form, word grammar, policies) and one store module for the entry and fire log; `cli/schedule_cli.py` joins `COMMANDS` the way `audit_cli` does and reuses `cmd_run`'s settle step for the check. Slots come first because the echo lists them, and the policies are pure functions over an entry, its fire log, live-run facts and a fake clock, so R3-T5.2's tick only calls them. The phases follow the dependency order. No decision is added beyond SCH-B29 to SCH-B33 and the assumptions in R-150 F50; the open `parse --count` question has its default in spec 83 (it bounds the recurrence, the echo lists three slots) and the plan follows it.
