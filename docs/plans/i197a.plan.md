- Design settled for the rows:

## 2. Phases

### Phase 1: The outcome check pauses for a fact no step can change

Goal: the outcome check, run on its own with scripted command runs and a scratch repository, returns a result marked environmental for a stale spec and for an environmental `ts-verify` command, also beside a failing `ts-traced`, with the unchangeable fact first in the evidence, the base run counted, and a failure the change caused still unmarked and routed back.
Weight: medium

### Phase 2: Stand-in runs prove the pause, the retry and the routing

Goal: stand-in runs of the loaded package, with the real outcome check and a recording finalizer, end the first invocation paused at the outcome gate with kind `escalation`, no step entered and no outcome judge session for a stale spec, a command that fails the same at the base and a stale spec beside a failing `ts-traced`; after a merge of the head made by the test and `retry` the run reaches the finalizer or goes back for `ts-traced`; a command that exits 0 at the base and fails at the head goes back to the step the criteria name.
Weight: medium

### Phase 3: The criteria file and the tests that pin the old facts say the same

Goal: `outcome.json` words `ts-spec-fresh`, `ts-verify`, their `check_method` and the old assumption as the specs do and carries revision 29, and the two existing tests that pin an old fact (the old fix line of `ts-spec-fresh`, and that the outcome gate asks for no run at the base) assert the new fact; the two changed specs are within the spec budget.
Weight: light
