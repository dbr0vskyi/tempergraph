- Why this design: a gate with no judge cannot send a run back today (the hand-off's Decisions), so the engine gets `on_fail: back` first (HUM-B15 to HUM-B18) and the unit uses it. The unit is a script unit between `code` and `code_join`: its script runs the due regenerations through the engine's command runner and commits, and its gate's check turns what the script recorded into findings, so that the gate sends the run back to `code` with them, once (loop budget 1), and `code_join` and its route stay as they are. The answers taken for the hand-off's open questions are its defaults: the unit sits between `code` and `code_join`; an unusable declaration pauses; the stand-in command of a fixture names the files in its own findings; no exception to the quick lane's file guard. The unit's `call` is handed a `CheckContext` and returns a mapping, and it does not use `ScriptResult` (hand-off, last candidate issue but one).
- The code step cannot run the engine's two commands, and the unit this run builds does not run in this run, so the package's `stamp.json`, `authoring.json` and `diagram/` are left for the operator to refresh with the unit's declared commands; the code report names them (AC 10).

## 2. Phases

### Phase 1: The engine's gate with no judge goes back with its findings

Goal: a gate with no judge and `on_fail: back` sends a failing check back to its one back target with the numbered findings, within the loop budget, and validation refuses the declarations HUM-B18 lists.
Weight: medium

### Phase 2: The register rung accepts another checkout of the registered package

Goal: `author verify` of a package folder in a linked worktree of the checkout its name is registered from passes rung 7 with the default home and the registry unchanged, and a different package that claims the name still fails with `name-taken`.
Weight: light

### Phase 3: The repository's declaration and the regeneration unit

Goal: a script unit between `code` and `code_join` reads `tempergraph.regenerations.json`, runs the due regenerations through the engine's command runner, commits their files or restores the workspace, is declared in the blueprint with its criteria in the outcome record, and this repository declares its packages' stamps, diagrams and authoring records.
Weight: heavy (large-context)

### Phase 4: A failed regeneration goes back to the code step as numbered findings

Goal: the unit's gate declares `on_fail: back` to `code` with loop budget 1, turns each failure a command reported into one finding, pauses at once for a failure of the environment, pauses after the one trip, and the code prompt tells the visit to fix those findings and nothing else, on both arms.
Weight: medium

### Phase 5: The gates, the reading list and the briefs know a generated file

Goal: the phase gate and the code gate list a file only the unit's commits changed as written by the regeneration and not among the changed paths, the code gate's reading list and the quick lane's file guard leave it out, and the plan, expand and code-judge briefs say what RGN-B13 to RGN-B15 state.
Weight: medium

### Phase 6: The package's records and the contract spec

Goal: the outcome record carries a new revision, the README shows the unit, the tests that pinned the old order of units hold the new one, the contracts spec lists `back`, and every new test names the id of the criterion it proves.
Weight: light
