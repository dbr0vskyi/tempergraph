- Extra files opened beyond the hand-off's reading list: `tempergraph.commands.json` (the declared verification commands: only `claude plugin test` fits the mod; `bun` is not declared, so the model tests cannot be proof commands); `plugins/tempergraph-monitor/docs/research/claude-code-mods.rsrch.md` and `plugins/tempergraph/docs/plans/t10-monitor.plan.md` (searched for how the test kit passes plugin options: neither says; row 1.1 tells the code step to take it from the kit's own types and help); `plugins/tempergraph-monitor/docs/specs/data-sources.spec.md` lines 1-30 (the sources table, which the new probe extends).
- Why this design: the mod has no host call that reads the environment or the home folder (research F6), so MAC-B6's `TEMPERGRAPH_HOME` or `~/.tempergraph` is learned the way the Processes tab learns `ps`: one constant POSIX probe argv (`sh -c 'printf %s "${TEMPERGRAPH_HOME:-$HOME/.tempergraph}"'`), run only when the setting and `PATH` have both exited 127, so the idle poll budget of MDS-B1 and the existing session tests are untouched when the engine is on `PATH`. The probe is a constant that builds no engine verb and writes nothing; the read-only guard accepts it by exact match, as it accepts the `ps` listing, and the one `$.process.run(` call site stays behind the guard (MDS-AC-2). The first program that does not exit 127 is kept for every later verb (MAC-B5); the pane's not-installed text reads the places the failed lookup recorded in the engine state. Open questions of the hand-off (the "until the person runs the installer" clause, the bare `tempergraph` in prompt fills) keep their defaults (a) and no row serves them.
- The test kit's way of passing plugin options (`engine_path`) is not documented in the repository and could not be read in this step; the code step finds it in the kit's types before writing row 1.1. If the kit takes no options, that is reported as a deviation and the setting cases are proven by the model tests of row 1.4.
