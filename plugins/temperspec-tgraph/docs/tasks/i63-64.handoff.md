# Hand-off: i63-64

## Problem

The conversation setting of temperspec has two values and neither pauses for the owner: `blocking` sorts no gap and ends blocked on a question that blocks planning, `never` is the only working unattended mode, and `always` is refused. Issues #63 and #64 add the value `always`, make `blocking` sort gaps and pause once after triage for the owner decisions, give the pause answers by terminal, by file or from the agent that started the run, and let a passed deadline take each open question's default. All ten gaps are closed in the specs; the units, prompts, checks, summary, README, tests and `outcome.json` follow in the plan.

## Decisions

- The run's conversation value was not given to this step: the prompt carried the unfilled placeholder `⟨missing:settings.conversation⟩`. The task itself says that what the specs leave open is decided and recorded as assumptions, and the triage note's one owner decision (G4) carries a default, so this step took the default, ended blocked on nothing, and lists below what the owner may want otherwise. Nothing here blocks planning.
- Where the behaviours live. The conversation spec keeps what the setting means and what the description lists (edited in place, ids kept). The pause is a capability of its own, so it is a new spec, `owner-questions.spec.md`, with the prefix `OWQ`. The three unit pages stay in the earlier layout, as the engine's docs check needs a page `NN-<unit>.spec.md` for each unit in the workflow's order (`docs_check.py` lines 20-24 and 86-88) and ties rows of such a page to `outcome.json`; they hold no gate criteria and point at the behaviours, as `code-mode.spec.md` does. The two-digit number is the check's; the unit name keeps the file name from colliding with another branch's.
- G4, closed on triage's default a). The pause holds the owner decisions and, under `always`, one question on the reading of each findable gap (OWQ-B4); with no owner decision it still pauses on the readings; with no gap at all it makes no pause (OWQ-B2). This is also the task's own assumption. Three points the option leaves open are taken as follows, each the smallest change that gives the question an effect:
  - A reading question is asked only for a gap row that says findable and does not say `Covered by`. A covered gap writes no document and takes the short visit, which the pause does not precede; asking it would need a second route after the pause. See the fourth open question.
  - The choices are `right` (the default) and `wrong`. A typed choice cannot carry a corrected reading, so `wrong` has one effect: the pause stays open, naming the gap, until it is answered `right` or the run is stopped to correct the task (OWQ-B5). The ask's own answers check does it, so no step runs on a reading the owner rejected, and a deadline cannot take it (ASK-B11).
  - Owner decisions come first in the pause, then readings (OWQ-B4, OWQ-B6).
- `blocking` and `always` sort gaps as `never` does (CONV-B2 to CONV-B4); the triage check applies to all three values, and a check given no value still passes an unsorted note, which keeps the met seeds of the triage judge passing. A step that meets a question the note does not list ends blocked under `blocking` and `always` (CONV-B5); an owner decision the note lists is never a reason to end blocked under any value, since it has an answer or a default.
- The flow, so that the plan builds what the unit pages name. `triage` routes a discovery-route note that is not `covered: yes` to `owner_questions`, a script with no model session that lists the questions for the conversation value; `ask_route` sends a run with a question to `ask_owner`, the engine's ask unit, and any other to `read_gap`; after `ask_owner` the order goes on to `read_gap`. The three units sit between `discovery_short` and `read_gap` in the order. The short visit is never entered after a pause: an owner decision, or a findable gap with no `Covered by`, makes `covered` `no`. A return from a later gate to discovery goes straight to discovery and asks nothing again; a return to triage that yields a new note with questions pauses once for that note.
- Names the owner types. A question is named by its gap's id in lower case (`g2`), so `--decision answer:g2=b` and a file `{"g2": "b"}` are what an answer looks like; the choices of an owner decision are its option labels (`a` to `d`). Question wording gives the gap's id, the question and the options; the cost of a wrong default stays in the triage note, which the pause names as context (ASK-B5).
- Limits of the engine's ask that a note can pass: at most 20 questions and 500 characters of wording (ASK-B5, `asking.py` lines 19 and 34-53). OWQ-B6 keeps the first 20, owner decisions first; an owner decision left out is closed on its default and listed as a default taken (OWQ-B9, OWQ-B10, CONV-B7). OWQ-B3 shortens option wording, never a label, rather than let the engine stop the run.
- The deadline is the engine's unit key `ask_owner.deadline_s` (RST-B19, `settings.py` lines 218 and 869-873) with the workflow's default of 86,400 seconds, and the ask declares `on_deadline: defaults` (OWQ-B7, OWQ-B8). The task says "a workflow setting"; no engine mechanism hands a workflow-declared setting to an ask's deadline, so a second declared setting would need an engine change. See the second open question.
- Decided and assumed, with no model. The description reads the `answers` file the ask leaves: a decision is answered when the file holds its name and the file does not list it under `defaulted`; a decision the file lacks (left out of a pause of 20) or lists as defaulted (a deadline took it) is an assumption (CONV-B7, CONV-B8). An unreadable file makes every decision an assumption, the safe side. `Decided` goes before `Assumptions to confirm`, and neither is clipped.
- Discovery records, in the hand-off's `Decisions`, each owner decision as answered or as a default taken (OWQ-B10); the description already lifts `Decisions` into "Decisions taken", so the owner sees both lists.
- Prompt criteria are package tests, not gate rows, as in run i60: OWQ-AC9 and OWQ-AC10 are proved by tests that read the discovery prompt, CONV-AC2 and CONV-AC6 by tests that read the triage and discovery prompts. The only gate row that changes is `ts-tri-owner` in `triage.spec.md`, whose text `outcome.json` repeats word for word (the test at `tests/test_conversation.py` lines 355-363 compares them), so the plan changes both in one step, raises the revision and adds a line to the revision list.
- No decision record and no research note: the triage listed spec gaps and spec updates only, and its one owner decision is closed on its default.
- Facts of the engine the plan must handle, found while closing the gaps:
  - A script's callable is built with a context that holds `unit`, `workdir` and `request` only (`nodes.py` lines 1154-1155), though SCR-B5 says it gets `artifacts` and RST-B25 says code gets the resolved settings. `owner_questions` needs the triage note and the conversation value, so the plan's first row is an engine fix of that context, a general capability the engine's specs already state (engine ADR-0129: the need goes first into the README's "What it asks of the engine", the fix is tested with an engine fixture). The fallback is the triage check, which has both, recording the number of questions as a fact and the triage step writing the list as a second file; that changes the rule "Triage writes this note and nothing else" in `task-notes.rule.md` and is not chosen here.
  - A route's view has `settings={}` (`gate.py` line 57), so `ask_route` cannot read the setting; it reads the value that `owner_questions` produces. No fix is needed for it.
  - An ask accepts `proceed`, and the pause payload offers it (`gate.py` lines 275-281); it stores the defaults of the open questions without marking them (`runner.py` lines 1273-1291), unlike a deadline (`runner.py` line 1319, ASK-B12). See the first open question.
  - The discovery prompt names the answers as `{answers}` and its judge references `answers` as optional, so a run that skipped the pause still renders (VAL-B3, ASK-B3 in `ask-unit.spec.md`).
- Every run on the default value `blocking` now sorts gaps, so each stand-in triage note and fixture that is run with a conversation value and has no sort fails `ts-tri-owner`; fixtures that the engine's rung runs with no value keep passing (CONV-B4, last scenario). The plan checks `tests/` and `evals/` for notes that are run with the default.
- The research note `next-features.rsrch.md` says in its status row that `always` is not declared; the plan updates that row under Docs to update (this step leaves the note as it is, and the test at `tests/test_conversation.py` lines 343-349 reads only the phrase "conversation mode `never`").

## Open questions

- Should a `proceed` at the pause count as an answer? An ask accepts `proceed` and takes the defaults of the open questions, and the answers file does not mark them, so the description would list those decisions as decided. Options: (a) leave it: `proceed` is the owner's word to go on with the defaults, and the description lists them as decided; (b) extend the engine's ASK-B12 so that `proceed` marks what took its default too, a change any workflow gains from. Until answered: (a). It does not block planning: (b) changes the engine's spec and one line of its code, and nothing in CONV-B8.
- Should the deadline be a declared workflow setting, as the task words it? Options: (a) the unit key `ask_owner.deadline_s` with the default 86,400 seconds (chosen); (b) a declared `duration_s` setting of the workflow, which needs an engine binding from a setting to an ask's deadline. Until answered: (a). It does not block planning: only OWQ-B7 and its criterion change under (b).
- May the agent that started the run answer the pause? The task says it answers what it can and takes the rest to a person; the engine's `run` skill tells the agent never to answer a pause itself (`SKILL.md` lines 14-15) and its pause page does not mention an `input` pause. Options: (a) the README says how the starting agent answers what it can and takes the rest to a person, and the engine's skill stays as it is (chosen); (b) the skill changes for `input` pauses, a general engine capability. Until answered: (a). It does not block planning: the engine records who answered (`person` or `agent`, ASK-B8) either way.
- Should `always` also ask the reading of a gap that a spec already answers? Options: (a) no (chosen, see Decisions); (b) yes, which needs a second route after the pause so that the short visit stays reachable, and one more place that ends blocked on a reading called wrong. Until answered: (a). It does not block planning: OWQ-B2, OWQ-B4 and the unit page `ask-route.spec.md` change under (b).
