# Hand-off: i173

## Problem

The workflow has no step that reads a run's change without the run's own reasoning: the units before the outcome gate are graded by judges that are given the step's products and account, and two runs that passed every gate each carried a defect that an independent reader found afterwards. The task adds a review after the code step: a read-only reader that is given the change and the task's acceptance criteria, numbered findings in a document on the branch, one trip back for a blocking finding, a pause when one is left, and the findings that block nothing in the pull request's description. No spec stated any of it, nor what the description holds.

## Decisions

- The triage note lists no owner decision, so no owner decision was answered or took a default. The conversation value of this run was not given to the step (the placeholder was never filled), so every choice below was taken as under `never`: the option that changes the least of what exists, listed under Open questions with `Until answered`.
- The unit is named `independent_review`, so that its spec is `independent-review.spec.md`: the package's test of the units' specs asks for a spec file named after each unit in `order` (`tests/test_code_mode.py` lines 578-579), and the spec rule asks every new spec to hold behaviours, so a thin unit spec in the earlier layout cannot be added. A unit the plan adds beside it, such as a route that skips the review, would need a spec of that name too; the join `code_join` might be that route itself, since the engine's check of `joins_at` names no unit kind (`plugins/tempergraph/engine/src/tempergraph/model/validate.py` lines 696-707), which the plan confirms.
- The bound under which the review does not run is the quick lane (IRV-B2), the reason in [the decision on the quick lane](../adr/a-quick-lane-run-takes-no-review.adr.md).
- Which step a blocking finding goes back to is read from the finding's file against the change: a file the change touches goes to the code step, a file it does not touch to the plan step, the plan step when both occur (IRV-B9, IRV-B10). The reader marks no kind, and the rule needs no model.
- The trip back, the budget and the pause are the engine's own, so the spec states what a person sees and not how the engine counts (IRV-B11 to IRV-B13).
- The independence of the reader is held by what the unit hands over and by a check of the session record, not by a refusal, because the engine has none; the needs are written in [the decision on independence](../adr/review-independence-is-held-by-inputs-and-the-session-record.adr.md) as general capabilities, no engine change is built, and the report of the code step says so.

## Open questions

- Should the lane be the bound under which the review does not run, or a size of the change in lines and files? Options: a) the quick lane; b) a size bound of the diff. Until answered: a (the lane's own limits are the bound and the code gate already measures them; the reasons are in the decision on the quick lane)
- Should a first review's findings carry a result for each point of the visit? The engine gives none, so RVF-B7 records the whole visit's result for each blocking finding, and `Visit: refused` is reached only when the run goes on past a visit that did not pass its gate (a person's decision at a pause). Options: a) the whole visit's result for every blocking finding; b) leave the record out until the engine gives a per-point result. Until answered: a
- Does a person's pause for a blocking finding left after the trip back also hold for a run whose conversation value is `never`? The pause is the budget pause of a gate, as the pauses of the plan and code gates are, and the task asks for it. Options: a) the pause holds under every value; b) a run on `never` stops instead. Until answered: a
- Should the rule files `rules/documents.rule.md` and `rules/task-notes.rule.md` list the review note (`.review.md`, in `docs/tasks/`) beside the triage note, the hand-off, the code report and the setup note, with a fill-in template generated from the rule? Options: a) the spec alone states the note's name and form (RVF-B1 to RVF-B5); b) the rule files list it too. Until answered: a
- Should a blocking finding that a person lets through at the pause also be listed in the pull request's description? PRD-B9 lists the findings that block nothing only. Options: a) not listed; b) listed under its own heading. Until answered: a
