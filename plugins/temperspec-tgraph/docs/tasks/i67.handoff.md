# Hand-off: i67

## Problem

The first step of every run, prepare, writes a fixed block into `CLAUDE.md` that names a root `docs/` this repository does not have (the first write of run r3-t1-1b went to a root `docs/tasks/`, and this run's own block names `docs/specs/`, `.claude/rules/temperspec/` and `docs/templates/`, none of which exists in its worktree), copies the rule files into a repository that already ships them (the spec 35 run), and leaves a change that operators delete by hand before each pull request (#67). The outcome check does not see that another run changed a spec on the base branch while this run was editing it, although parallel runs are normal here (#61). The task asks for a block built from the repository's real folders, rule files counted as installed where the repository or the machine has them, a `CLAUDE.md` left alone when it already says where the specs live, and an outcome check that fails, naming the spec, when a spec the run edited has changed on the base branch since the run started.

## Decisions

- Where the behaviours live. Two new specs in the engine's layout, named by the overview, as `judge-reading.spec.md` was in run i55. The unit spec `01-prepare.spec.md` is in the earlier layout, which has no behaviours section, and the engine's docs check ties the rows of the overview and of the unit specs to `outcome.json` (`docs_check.py` lines 20-24 and 66-113), so a behaviour cannot be written there. The one row added is the gate criterion, because every finding of the outcome check names a criterion of `outcome.json` (`tests/test_temperspec.py` lines 65-66).
- The criterion `ts-spec-fresh`. The row reads "No spec the run edited has changed on the base branch since the run started". The code step mirrors it into `outcome.json` as a final criterion of revision 12 with the same text: `verified_by` `check`, `verifier.check` `tgwf_temperspec.checks:outcome_check`, severity `blocker` (the task says the check fails, and two runs overwriting each other's spec edits is a defect), a `check_method`, and no unit criterion that serves it (see What a failed guard does). Models: `ts-spec-moved` and `ts-spec-parent` (`outcome.json` lines 62-89) and the tests at `tests/test_spec_budget_and_moved_ids.py` lines 292-311. A criterion the outcome gate verifies by its check counts as covered (OUT-B14), which the engine's package test requires (`test_workflow_packages.py` lines 29-40).
- The folders the repository really uses (criterion 1). A specs folder is the folder of an overview spec, found as `has_overview` finds it (a file named `overview.spec.md`, with or without a number prefix, outside the folders of copies and fixtures: `routing.py` lines 23 and 103-109); with no overview spec, the folders of the other specs; with no spec, `docs/specs/`, where the setup step writes the overview (`prompts/setup.md` lines 16-17). Beside a specs folder go `adr/`, `research/`, `plans/` and `tasks/`, because `documents.rule.md` keeps the folder names and lets a repository keep its place under a plugin's `docs/`. They are named whether or not they exist yet, since plans and task notes are written there later. A repository with several overview specs gets all of them, in path order, with no cap (this repository has five outside its fixtures). The wording of the block, for example that each docs folder belongs to its own part of the repository, is the plan's.
- "Already describes where its specs live" (criterion 3) is an assumption: the criterion does not say how a script with no session decides. It is read as a test of the text. The file, leaving out any temperspec block, names by its whole path from the repository root a specs folder or the folder that contains it. A path counts when it starts and ends at a path boundary, and it may continue (`plugins/a/docs/{specs,adr}/`, `plugins/a/docs/plans/x.plan.md`); the tail of a longer path does not count (`plugins/b/docs/guides/` does not name `docs/`). This repository's `CLAUDE.md` names `plugins/tempergraph/docs/` and `plugins/tempergraph-monitor/docs/` in its Layout lines, so prepare leaves it alone and the block that operators deleted by hand from this file is not written again. The block is left out of the test so that a block prepare wrote earlier does not count as the file's own description (last scenario of PNR-B6). Rejected: a model reading the file (prepare has no session and must answer the same way twice), and any mention of the word `docs` (it would match a file that only says to update the docs).
- The rule files (criterion 2). They are held when the repository's own `.claude/rules/temperspec/` exists (as today), or a folder of the repository holds every rule file the plugin ships, or `~/.claude/rules/temperspec/` exists (as today: `routing.py` lines 89-91). Every rule file, not any: with a partial set a step would miss a rule, so prepare installs the full set as it does now. A folder inside the skipped folders does not count, so a fixture's copy cannot hide the install. The block names the first of three, in the order the repository's own folder, the folder the repository ships, the machine's: the first is loaded by Claude Code in this repository, the second is what the repository chose to ship, the third is the fallback.
- Templates. Prepare installs nothing when the rules are held, and the code writes no template then either (`routing.py` lines 89-91 return before the templates). The block's present sentence says the templates are in `docs/templates/`, which is false today for a machine-wide install, so PNR-B5 names them only where they exist. It is the one behaviour about templates and follows from "copies no rule file".
- The engine side of the guard. `GitFacts` declares `base_head`, CHK-B10 lists it, and the check worker and the preview pass it on (`check_worker.py` lines 46 and 69, `selfcheck.py` line 83), but nothing says what it holds and `git_facts` never sets it (`run/checks.py` lines 44-51), so it is always empty. A check cannot learn the base branch any other way: its context holds the run's base commit and the run's own branch, not the base branch's name (`run/checks.py` lines 70-95), so a check would have to guess it. So the need is written in the package first (the Purpose of the new spec) and the engine states it as a general capability without naming the workflow (CHK-B22, CHK-AC13), as the run at the base was in run i54b. The engine reads the ref as its local branch, else its remote-tracking branch on `origin`, with no fetch, because a check is pure and does no network; this is how the engine already reads the local copy of the default branch at a start (`workspace.py` lines 246-253).
- What the check compares (criteria 4 and 5). Two conditions together, so that the answer does not depend on how the base branch's ref is kept. The head holds commits that the run's base commit lacks: a head behind the run's base, for example a local copy never updated after a start from the remote's default branch, is no change since the run started. And the spec reads differently at the head than at the run's base commit: different text, or present at one and absent at the other. So a spec the run created at a path the base branch has since filled, and one the base branch deleted, fail; a change that was restored passes. The package already allows the commands for both (`git log`, `git diff`, `git show`: `__init__.py` lines 51-53); how they are used is the plan's. A run that merged the base branch into its own branch still fails, since its base commit is the one it started from; a rerun starts from the new base.
- What a failed guard does. No criterion of any unit serves `ts-spec-fresh`, so the engine escalates the run at the outcome gate (OUT-B3, OUT-B16), which is right because no step can repair it. The research note's wording, "sends the run back to discovery to edit the newer text" (`next-features.rsrch.md` line 67), cannot be built as written: discovery works in the run's worktree, which holds the old text of the spec, and its tools have no git, so the newer text is out of its reach. A person reruns the task from the base branch's head; the finding's `fix` text should say so, in the plan's words. See the second open question.
- Not applicable. A run with no base branch, and a run that edited no spec, report the criterion not applicable with the reason, as `ts-spec-links` does for no spec (`checks.py` lines 1140-1141). The existing outcome fixtures have no git facts, so they keep passing (`tests/test_temperspec.py` lines 47-66); the failing case needs a scratch repository, built as `_edited` builds one (lines 1052-1061).
- The paragraph of `01-prepare.spec.md` is rewritten because the task makes two of its statements untrue as written; the edit is not collateral. The file stays in its earlier layout.
- No decision record and no research note. The triage listed no `decision needed` or `research needed` gap; each choice above is answered from the code and the specs cited, and the options are in the open questions.
- No "Not built yet" line names #61 or #67 (searched the package's specs, README, rules and docs); the one in the engine's spec 75 is about other executors and stays. The research notes mention the guard as a proposal (`next-features.rsrch.md` lines 60, 67 and 134, `plan-format-review.rsrch.md` line 60); they are history and are not edited.
- Linked specs. The new specs link the overview and the unit spec and contradict none of their statements. The overview row says what must hold, and the new spec says what the check reports, so neither restates the other. CHK-B22 defines the field that CHK-B10 lists and leaves CHK-B10, CHK-B18, WTR-B21 and WTR-B24 as they are.
- Not edited, on purpose; the plan lists them under Docs to update: the prepare row and the Rule files paragraph of the README (lines 13 and 49), the sentence on what a run installs in `skills/setup/SKILL.md` (line 10), `outcome.json` (revision 12), and the prompts below. The rule files change nowhere.
- The prompts. Six prompts name a fixed `docs/tasks/` or `docs/plans/` path for the notes (`triage.md` line 24, `discovery.md` line 27, `discovery_short.md` line 21, `plan.md` line 27, `setup.md` lines 16-18, `code.md` line 23), and seven say the rule files are in `.claude/rules/temperspec/` (the same six and `expand.md` line 10). A true block does not change what a prompt says, so the symptom of the issue, a first write to a root folder, can remain unless the prompts defer to the block (`triage.md` already says to use the repository's own docs folder). The five criteria do not require it; the first open question asks it. Whatever the plan changes keeps the phrases that `PROMPT_SAYS` checks (`checks.py` lines 69-86).

## Open questions

- Where does a step learn the rule files' location and the notes' folders when no block is written, which criterion 3 makes the case for a repository like this one? Options: (a) the prompts say to use the folders the project note names when it exists, else the folders beside the repository's specs, and to find the rule files by searching for `*.rule.md` when `.claude/rules/temperspec/` is absent; (b) prepare hands the folders to the steps as values that the prompts read; (c) prepare writes a block of two lines, the rule files' location only, even when the file describes the specs, which conflicts with criterion 3. Until answered: (a). It does not block planning.
- Should a failed guard send the run back to discovery, as the research note proposes, instead of escalating? Options: (a) escalate, which follows with no serving criterion (OUT-B16) and is what a person must do anyway; (b) add a discovery criterion that serves `ts-spec-fresh`, which would send the run back to a step that cannot see the newer text unless something brings it into the worktree, for example a step that merges the base branch, which the engine does not offer in a run. Until answered: (a). It does not block planning.
- Which ref is the head of the base branch? Options: (a) the local branch, else its remote-tracking branch (chosen, as the engine reads the local copy at a start); (b) the remote-tracking branch first, which sees what a `git fetch` brought and ignores local merges; (c) the later of the two when one holds the other. Under (a) a base branch that moved only on the remote is seen only when no local branch exists. Until answered: (a). It does not block planning: the choice sits in one engine function and the spec's scenarios hold for (a) and (c).
