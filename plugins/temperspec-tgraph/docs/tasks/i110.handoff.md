# Hand-off: i110

## Problem

temperspec lists only the triage note as a deliverable of its final gate, because release 1 of the engine required every listed deliverable on every path; the discovery hand-off, the plan and the code report were left out, so the gate neither checks them nor shows them to its judge. It also never says whether the run's branch is pushed, because release 1's git facts did not report it. Release 2 requires a deliverable only on a path that produces it and sets the push in the git facts, so the task lists the three documents and has the outcome check report the push, and the two open questions that stated the workarounds close.

## Gaps closed

- G1: `plugins/temperspec-tgraph/docs/specs/outcome-gate.spec.md` (OGT-B1, OGT-B2, OGT-B3, OGT-AC1 to OGT-AC10): the hand-off, the plan and the code report are each required on the path that writes it and not on any other, and the outcome judge is shown the ones the run wrote
- G2: `plugins/temperspec-tgraph/docs/specs/outcome-gate.spec.md` (OGT-B4, OGT-B5, OGT-AC11 to OGT-AC13): the check's evidence says whether the branch is pushed, and a push never decides the check's result
- G3: `plugins/temperspec-tgraph/docs/specs/00-overview.spec.md` (open questions 2 and 7 removed, the new spec named beside the units) and `plugins/temperspec-tgraph/docs/specs/08-code.spec.md` (the `ts-code-commit` row, line 16, loses "with no commit on a remote"); the matching `outcome.json` assumptions and the text of `ts-code-commit` are data, not a spec, so the code step changes them to the exact texts under Decisions

## Changed documents

- `plugins/temperspec-tgraph/docs/specs/outcome-gate.spec.md`: new, five behaviours (OGT-B1 to OGT-B5) and thirteen criteria (OGT-AC1 to OGT-AC13)
- `plugins/temperspec-tgraph/docs/specs/00-overview.spec.md`: line 19 names the new spec, which the overview must do; the second and the seventh open question are removed, nothing else changes
- `plugins/temperspec-tgraph/docs/specs/08-code.spec.md`: one row, `ts-code-commit`, now reads "Every file the code step changed is committed"

## Decisions

- Where the behaviours live. A new spec in the engine's layout, `outcome-gate.spec.md` (prefix OGT, used nowhere else), named by the overview as `judge-reading.spec.md` is. The unit specs are in the earlier layout, and their rows are generated from `outcome.json` and compared with it by the docs check, which the engine's suite runs in stable mode (`docs_check.py` lines 66-113, `selftest.py` lines 295-298), so no behaviour can be written there. No final criterion is added to `outcome.json`: the deliverable check is the engine's built-in check (OUT-B15), and the push line is evidence, not a result the gate passes or fails. So no row is added to the overview or to a unit spec, and the OGT criteria are proved by the package's tests that carry their ids, as the judge-reading ones are.
- The three deliverables. Keys `handoff`, `plan` and `code_report`, kind `file`, the artifact keys the units already declare (`__init__.py` lines 127, 134, 141, 154). The engine requires a deliverable when the run's path took a unit that declares it (`outcome.py` lines 184-199 and 218-223): the hand-off after `discovery_short` or `discovery`, the plan after `plan`, the code report after `code`. By the package's routes (`routing.py` lines 53-75) the paths are: the quick lane (triage, code) has the code report; a task with no gap (triage, plan, code) has the plan and the code report; a task with a discovery visit, short or full, then the plan and code has all three; a docs-only run (triage, discovery, last stage) has the hand-off only. The triage note stays required on every path. The blueprint already lists these keys as `produces`, and it has no `outcome_ref`, so a new `outcome.json` revision does not trip the authoring ladder's compare rung (`compare.py` lines 119-121).
- The outcome judge. Its default references are the deliverables, each optional when a route can skip the unit that produces it (`outcome.py` lines 157-163 and 202-206), and a run's reference is read from state when the run recorded it and skipped otherwise (`nodes.py` lines 1567-1576). Because the package has routes, no unit is on every path, so all four are optional references. Listing the deliverables is therefore all OGT-B3 needs: no judge reference is written into a criterion and the outcome judge's stance is unchanged.
- The push is a line of evidence, never a verdict (OGT-B4, OGT-B5). The gate runs before the last stage, the only place that pushes (`routing.py` lines 136-151 and 173-200), so a fresh branch is not pushed at the gate. A failing finding for an unpushed branch would fail every run, and the engine's own helper `git_pushed` does fail an unpushed branch (`check_helpers.py` lines 91-92), so it is not used. A branch an earlier run pushed (the last stage's `reused` outcome shows this happens) is pushed at the gate, and failing on that would fail every later run on it. The report is one line of the outcome check's evidence, placed early: the engine keeps 8,000 characters of the evidence (`run/checks.py` line 275) and the judge's prompt keeps 4,000, head and tail (`judging.py` line 156), and the changed-paths line can take 120 paths. It is added in the outcome check only: the result builder `_result` is shared with the discovery and code checks, whose evidence (the code judge's reading lines, JRD-B1 and JRD-B2, and the code seeds' copies of it) does not change. The wording is the plan's; the tests find it by the words `pushed` and `not pushed`, and the line says no more than the engine's git facts report.
- When the line appears. The engine runs a package's own outcome check only when every required deliverable exists (`outcome.py` lines 234-241), so a run that fails on a missing deliverable ends with that finding and no push line. OGT-B4 is worded "grades a run against the final criteria" for that reason. The engine's built-in check is not changed: this is a package change on a release 2 capability, and the engine stays free of the workflow.
- What `pushed` means. CHK-B10 says it means the head commit is on a remote-tracking ref; the code (`git.py` lines 118-126) tests that a remote-tracking ref with the branch's name exists on any remote, with no network. The two differ for a branch that was pushed and then committed to again. The spec says "the branch is pushed" as the engine's git facts report it and nothing more (see Open questions).
- `ts-code-commit`. Its text becomes "Every file the code step changed is committed", in `outcome.json` (line 993) and in the row of `08-code.spec.md` (done here). The clause "with no commit on a remote" was never checked: the check reads only that the worktree is clean (`checks.py` lines 61-62, 987 and 1002), and an assumption said so (`outcome.json` line 1243). The push is now reported at the outcome gate instead. The two texts must stay identical, or the engine's suite fails on the docs-drift check.
- The assumptions of `outcome.json`. Delete the second (line 1238, "The plan, the code report and the discovery hand-off are not listed as deliverables because the engine requires every listed deliverable on every path, ..."). Replace the seventh (line 1243, "Whether a commit is absent from every remote is not checked: ...") with: "The outcome gate reports whether the run's branch is pushed and never grades it: the last stage pushes after the gate, and a branch an earlier run pushed is already pushed at the gate, so no gate fails a run for the push." The reason is an assumption the owner did not settle, so it stays recorded. The overview's open questions 2 and 7 are the same two statements and are removed (done). No test reads either old assumption (`tests/` finds assumptions by "one file per 50" and "30,720" only).
- The next revision. The issue's "Done when" names revision 5; the file is at 10 and later changes passed 5, so the next is 11 (the triage note reads it so). The new entry in `revisions` has `origin` "authored" and a note that carries the phrase "issue 110", as the notes of issues 111, 112 and 113, and 114 do (the tests find an entry by its note), and `revision` equals the last entry's, which existing tests assert (`test_judge_reading.py` lines 177-179). Rung 10 of the authoring ladder takes a newer outcome revision as the owner's re-approval (`stamp.py` lines 112-115 and 143-152), so `stamp.json` and `authoring.json` are not edited, as in issues 112 and 114, and the pull request says that the owner was away.
- How AC 4 is met. The engine's suite (`python -m pytest` from `plugins/tempergraph/engine/`) runs, for every package, its generated tests (the stand-in run, the docs check in stable mode, the check fixtures and the diagram) and the package's own tests (`test_workflow_packages.py` lines 29-59). `tempergraph author verify` is not on the package's command list, so a plan cannot list it; the plan names the engine's suite, `ruff check src tests` and `mypy` from the engine folder and, from the package folder, `python -m pytest tests`. Expected, not yet run: the stand-in run reaches the outcome gate by triage, discovery, plan, expand and code, so all four deliverables are on its path, and each is a file the stand-in steps write (`selftest.py` lines 153-179 and 186-273); a failure there is a finding for the plan, not for the spec.
- Proving OGT-AC1 to OGT-AC8 and OGT-AC11 to OGT-AC13. A test builds the gate's check settings the way the engine does at run time (`nodes.py` lines 1502-1514: the deliverables, their producers, the path's units and the package's own check) and runs the compiled outcome gate's check on a scratch workspace, as `test_temperspec.py` does with an empty deliverable list (lines 931-940). With no `path_units` the engine requires every deliverable, so each path test sets the units the path took. A docs-only path needs the value `route` = `discovery-only`, which the fixture `2-docs-only/values.json` shows. OGT-AC11 and OGT-AC12 set the pushed flag of the git facts the context gets.
- Proving OGT-AC9 and OGT-AC10. What the judge is told is read from the compiled outcome gate's judge references (all four keys, the three documents optional) and, for the docs-only path, from the prompt of a scripted outcome judge in a stand-in style run (`selftest.py` lines 186-273 is the model). If OGT-AC10 cannot be proved without an engine change, the plan says so and goes back to discovery; it does not weaken the criterion.
- The outcome seeds. The four seeds under `evals/calibration/outcome/` hold a copy of the check's evidence (`check.json`) and the judge's references (`references.json`, the triage note only). The plan decides whether the copies follow the new evidence and references; a seed edit changes no verdict, and rung 8, which grades the seeds, needs the owner's signed-in `claude`.
- Left unchanged. The research note `stages-against-engine-releases.rsrch.md` (F1 says the release 2 capabilities are not used yet; it records what was true when it was written, and the task's gaps do not name it). `docs/README.md` of the package, the package README and `diagram/` (nothing in them names the deliverables or the push). No engine file changes.
- No "Not built yet" line. None names issue 110 or its backlog row (searched the package's specs, README and docs, the root README and CLAUDE.md); nothing to remove or update.
- No contradiction with the linked specs. The new spec links the overview (no behaviours, an earlier layout), OUT-B15 (per-path deliverables, which OGT-B1 and OGT-B2 apply to this package's three documents) and CHK-B10 (the git facts, whose push flag OGT-B4 reads). It contradicts none of them. OGT-B3 relies on OUT-B15's rule that an off-path reference is optional and does not restate it.

## Open questions

- Should the code gate also fail a branch that is already on a remote, which is what the dropped clause of `ts-code-commit` asked for? Options: no, report the push at the outcome gate only (chosen), because a run on a branch an earlier run pushed would then never pass the code gate; or yes, restore the clause with a check, which needs a way to tell a push made during this run from an earlier one, and the engine's git facts do not give it. Dropping the clause removes words from a blocker's text, which weakens nothing the check did, but it is the owner's to confirm. It does not block planning: the plan builds the first option.
- CHK-B10 says the push flag means the head commit is on a remote-tracking ref, and the engine's code tests the branch's name on a remote-tracking ref, so a branch pushed and then committed to again reads as pushed. Options: leave it, since this task reports what the engine says (chosen); or file an engine issue so the spec and the code agree. It does not block planning: the evidence line claims no more than "pushed" or "not pushed".
