# Hand-off: i58

## Problem

temperspec allows its verification commands from one list written into the workflow (`VERIFY` in `workflow/temperspec/__init__.py`: pytest, ruff, mypy and read-only git), so it runs on Python repositories only, although since release 2 the engine lets a workflow take a repository's own commands from its `tempergraph.commands.json`. The task makes every check that reads a verification command, and the code step's shell, take the repository's commands from that file; has `prepare` write today's Python commands into it for a Python repository that has none; and removes the overview's open question that says the list is fixed. No spec said where the commands come from, and none said that `prepare` writes the file. The plan step then sent the unit back for a fourth gap: the engine's host audit, which rung 6 of the authoring check runs, takes the entry that asks for the repository's commands for a program and reports it missing, and no engine spec said how the entry is read, so criterion 5 could not pass and the plan could not include the engine change (G4).

## Decisions

- The conversation value of this run reached the step unfilled (`⟨missing:settings.conversation⟩`; the workflow's default is `blocking`). The triage note lists no owner decision. Every choice below is answered from the task, the research notes and the code, and none blocks planning; the one that is a person's to weigh is the open question.
- Where the behaviours live. A new spec in the engine's layout, named by the overview's "Beside the units" paragraph. G1 and G2 are one capability (where verification commands come from, and the file that gives a Python repository its default; `docs/research/stages-against-engine-releases.rsrch.md` line 25 frames them together), so they share it. The unit specs and the overview are in the earlier layout, which has no behaviours section, and the engine's docs check ties their criterion rows to `outcome.json` (`plugins/tempergraph/engine/src/tempergraph/package/docs_check.py` lines 20-24 and 66-113), so a behaviour cannot be written there; run i67 made the same choice for `project-note.spec.md`. The paragraph of `01-prepare.spec.md` is rewritten because the task makes its list of what prepare does incomplete; that edit and the overview's line naming the new spec are not collateral. No criterion row is added: `ts-verify` and `ts-exp-commands` are true as written.
- The workflow's own list shrinks to what is no toolchain. The Python commands leave it; what stays is read-only git (RCM-B3, and what the code session always gets), the last stage's commands (`git remote`, `git push -u origin`, `gh pr list`, `gh pr create`, `gh pr edit`), and the entry that makes the checks and the code step read the repository's file. Reasons: criterion 2 means something only if the file is where a Python repository gets its commands (the stages note says prepare writes it "so today's behaviour is the default"); with the list kept, a repository that is not Python would still be offered pytest, ruff and mypy, and the engine's host audit would still ask for those programs on the machine (`audit/host.py` lines 72-94; the comment at `__init__.py` lines 75-77 says the list holds one toolchain for that reason). The alternative is to keep `VERIFY` beside the repository's commands: it changes less code and no existing test, but it reads criterion 1's "instead of the fixed list alone" as "in addition to it", leaves RCM-B2 untrue for `pytest` in a repository that is not Python, and makes the written file change nothing. Cost of the choice: a test that resolves a Python command in a scratch folder needs a `tempergraph.commands.json` there (81 mentions of pytest, ruff or mypy in 11 test files; 15 places in 10 test files build a check context from `SPEC.allow_commands`). Among the check fixtures under `evals/checks`, `git --version` or `git status` appear in 42 files, and they stay accepted; the only fixture of the plan, expand, triage, code and outcome checks that lists a Python command is `expand/must-fail/chained-command/phases.md` (`pytest -q && ruff check .`), which is refused for its `&&` chain whatever the allow-list holds.
- What the file declares (RCM-B6): `pytest`, `python -m pytest`, `python3 -m pytest`, `ruff check`, `ruff format --check` and `mypy`, the six Python commands of `VERIFY`, in that order. The five read-only git commands of `VERIFY` are not in it: the workflow allows them in every repository (RCM-B3), so writing them too would change nothing a plan can list. The content is the same for every repository, so two runs side by side that each write it merge without a conflict.
- What a Python repository is (RCM-B6, RCM-B8): one that holds a `pyproject.toml`, `setup.py`, `setup.cfg`, `requirements.txt` or `Pipfile` at its root or in any folder that is not a folder of copies or fixtures, the folders prepare already skips (`routing.py` lines 25 and 123-132; the Purpose of `project-note.spec.md`). The search goes below the root because this repository has no root `pyproject.toml`: its Python projects are `plugins/*/engine` and `plugins/*/workflow`, and the others sit in `evals/` fixtures, which do not count. The list errs towards Python: a repository wrongly taken as Python gets a file that declares commands it does not use, which its owner edits; one wrongly taken as not Python has its plans refused until its owner writes the file, which the finding names. Rejected: any `.py` file (a scripts folder in a Node repository would count) and the root alone (it would leave this repository without a file).
- The file's form (RCM-B6): `schema_version` 1 and a `commands` list. The engine reads a file only with `schema_version` 1 and takes any other as declaring none (`run/commands.py` lines 41-51; `tests/test_i2_26.py` lines 93-100), while the example in CHK-B11 shows only `{"commands": [...]}` and so would write a file the engine ignores. The engine's spec is not edited here: no behaviour of this task changes it, and a spec edit with no such change is collateral. The plan may list it under Docs to update as a fix of the engine's text.
- RCM-B9 is part of G2, not an extra. Prepare commits the file on the run's branch after the run's base commit, so it is among the changed paths the code gate reads, and no triage note or plan names it. In the quick lane that fails `ts-code-lane` on the first run in any Python repository that has no file (`checks.py` lines 1096-1103: a changed file that is not Markdown, not a test and not named by the note's Change section), and the code judge would count the file as a changed source file (lines 400-414). The block prepare writes into `CLAUDE.md` has this treatment today (lines 352-365 and 437-443; the test at `tests/test_temperspec.py` lines 1134-1148), the rule files are skipped by path, and the templates are Markdown. A step's later edit still counts, so the file stays visible in the pull request.
- What a declared command can do. The engine hands the code session each plain command the file declares, as written. The plan check refuses `git push` and `gh` in a plan before it resolves a command (`checks.py` lines 884-886), so a plan never lists a publishing command, but a file that declares one would let the code session run it. That is the file owner's declaration, as with every user of the file; whether a run may change the file itself is the open question.
- The host audit reads the entry as the target's declared commands (G4; AUD-B17 to AUD-B19). What I read in the code: `prefixes()` returns the allow-list and each step's commands, and `commands()` looks up the first word of each with `shutil.which` and raises `check-program-missing` (error) for one it does not find (`audit/host.py` lines 72-94), so the entry is reported as the program `@repository`; `author verify` runs the `definition` and `host` layers against the working directory (`cli/author.py` line 243: `target=env.cwd`) and fails rung 6 on any `error` finding that is not ignored (`author/verify.py` lines 168-183, SCF-B18); validation accepts the entry when the allow-list holds it too (`model/validate.py` lines 816-824), and the engine's own test of the entry validates a workflow with it and never audits it (`tests/test_i2_26.py` lines 121-135). Nothing else reads a prefix as a program: `shutil.which` appears elsewhere only for a reuse key of an already resolved command (`run/checks.py` lines 209 and 222) and for binaries that are no command prefix. This step has no shell and did not run the audit.
- The options for how the audit reads the entry (G4): (A) the audit skips the entry. It is the smallest engine change, but once `VERIFY` leaves the workflow the workflow's own prefixes are `git` and `gh` only, so `toolchain-not-covered` (warning) would fire for every repository whose root documents a toolchain (`pyproject.toml`, `package.json` with scripts, `Makefile`, `go.mod`, `Cargo.toml`), file or no file; silencing it as well would hide the one case where it is right, a repository that documents commands and declares none. (B, chosen) The audit takes the prefixes of the target's file in the entry's place, as a run does: `check-program-missing` still names a program a repository's own command needs and the machine lacks, and `toolchain-not-covered` is raised only when the file does not cover what the repository documents. (C) An `audit.ignore` of `check-program-missing` in `tempergraph.json`, or a `command_resolver` (which the audit skips): either passes rung 6 with no engine change, but the first blinds the package to a missing `git` or `gh` and the second is not the engine's `@repository` entry that criterion 1 names.
- The cost of option B and the size of the specs it touches (G4): the result of rung 6 depends on the working directory's file and programs. In this repository the root holds no `tempergraph.commands.json`, so the entry stands for nothing when the check runs here; where a file exists, its programs must be on `PATH`, as the programs of `VERIFY` had to be (the comment at `__init__.py` lines 75-77 says so). The finding points at the file because the fix is there, not in the workflow's declaration (`Host.add` takes a `file`). Spec 75 is not edited: by my estimate from line lengths it is about 29 KB, near the 30 KB cap that `tests/test_spec_budget.py` enforces, so a plan row that edits it (the `schema_version` below) must run that test; specs 55 and 56 have room (about 20 KB and 18 KB by the same estimate). An open point for the plan, not a question: the written behaviours say nothing about a workflow that lists the entry, has no gate with a check and whose file is missing, where the audit has no prefix to compare and raises no `toolchain-not-covered`.

## Open questions

- May a step change `tempergraph.commands.json`? The commands the engine gives a step and a check are read from the file as the working tree holds it, and the plan, expand and code steps can write files, so a step can add a command and have it accepted later in the same run (by a retry of the code step, the code gate and the outcome check). Options: (a) accept it: the file's diff is in the pull request for the owner to review, and RCM-B9 makes a step's edit count as a change of the run; (b) add a check that fails a run whose file differs from the base commit's or from what prepare wrote, so that only a person changes the file; (c) ask the engine to read the file at the run's base commit, a general capability that this workflow would then use. Until answered: (a). It does not block planning.
