# Hand-off: i72

## Problem

Issues #72, #73 and #74 ask that temperspec's checks hold what the session record shows: a step opens the rule file its prompt names, the expand step opens each file a row names, and the code step writes each phase's tests before its source. No spec answered any of this, and the engine gave a check nothing of what the session did. The task needs one general engine capability (the attempt's tool calls as a check input, or none) and three checks and their prompts on the temperspec side.

## Decisions

- The check confirms the rule file was read; no prompt carries rule text. Criterion 1 allows either; the rule text stays in the rule files, `specfmt.py` parses it and a repository's own rules stay authoritative (decision above). Each prompt that names a rule file also tells the session to open it with the read tool (SRC-B2).
- Read means a call of the read tool that ended without an error and whose target ends in the file's name, in any folder; a search or a listing never counts; a partial read counts, the record keeps no range. Named means the file name is in the step's prompt file, which the check reads as `_prompt_says` already reads the package's prompts. Only a rule file the repository holds under `.claude/rules/temperspec/` is asked for; with none there, the rules are installed for the whole machine and the criterion is not applicable with a message. Assumption: the prompt's five rule files for the full discovery are all asked for, though a discovery that writes no decision never needs `decision.rule.md`; the decision record names the alternative (ask only the types written) and what would reopen it.
- Each attempt is checked on its own session. A retry is a fresh session ([PRM-B5](../../../tempergraph/docs/specs/04-prompt-rendering.spec.md)), so reads of an earlier attempt of the visit do not count, which answers the "earlier attempt" part of G6.
- The engine builds `session` from the attempt's activity journal after the session ends, from the last start of the session (an infra try appends to the same journal and restarts its line count), and gives `None` (never an empty list) for no step session, a stand-in that reports names only, a session with no call, a journal that dropped a tool line, and the check preview. `CheckContext.session` therefore defaults to `None`, and every context the package's tests build has no record, so the new criteria are not applicable there and the existing tests stay as they are. The preview gets no record because its context is stored when the attempt begins and the journal is written in batches; refreshing it at each call (as the preview refreshes git facts) is the alternative the engine decision names.
- EVT-B21 is not edited: the record is a copy for the check and is written to no stored record, and SRC-B9 keeps a finding from quoting a call (a finding names the rule file, row, path and phase from the prompt and the plan). CHK-B9 is edited because the sameness it states cannot hold for a record that follows what each session did; the edit adds one trace obligation, below.
- A phase's test files are the files of its `test` rows and its source files those of its `code` rows; a file counts for the first phase that names it; a change is a successful edit or write; the phase fails when the first change of its source comes before the first write of any of its test files. A phase whose test files the session never wrote is not measured for order, which is what keeps a retry that only repairs source from failing; the gate's other criteria find a test never written. The quick lane has no phases, so the criterion is not applicable there.
- The new behaviours are one new spec in the layout of the spec rule, listed beside the units in the overview as `judge-reading` and `outcome-gate` are, and not rows in the step specs 04 to 09: those are in the earlier layout, which the spec rule says to leave, and one concept across seven steps would be seven near copies. The new criteria are check-verified, since a judge never sees a session (`UNSEEN` in `tests/test_temperspec.py` bars the words from a judged criterion); each gate's list in `outcome.json` needs its own criterion id so that a finding is attributed (CHK-B14), and the plan names those ids.
- No research note: each unknown was answered by reading the code, cited in the decision records. No spec carries a "Not built yet" line for this issue (searched the package's docs and the engine specs 25, 30 and 75; the one in spec 75 is about other executors and stays), so there is none to remove or update.
- The short discovery prompt limits the visit to 10 files; SRC-B2 says the rule files it names do not count in that limit, since the check now requires two of them.
- Not edited on purpose: the step specs 03 to 09, the rule files, the prompts, `outcome.json`, tests and code; `30-run-events.spec.md` and `25-session-contract.spec.md` (the record uses their journal and events as they are).
- Trace obligations for the plan (`ts-traced`, which asks a test that is not skipped for each added or reworded criterion and for each old one that proves an edited behaviour): SRC-AC1 to SRC-AC12; CHK-AC14 to CHK-AC18; CHK-AC7, which a test in `test_check_at_base.py` already carries; and CHK-AC3, which names CHK-B9 and which no engine test carries, so the plan adds the test that proves it (the one shared `resolve_command`, a source scan) or another proof of it.
- The worktree of this run has no `.claude/rules/temperspec/` folder (a search of `.claude/` with the file tools found no file), so the rule-file criterion would be not applicable in a run like this one; the rule files here are in `plugins/temperspec-tgraph/rules/`.

## Open questions

- Should a failed test-first criterion send the code step back? Options: (a) fail the check, as the task says: the retry is a fresh session that cannot undo the order and can only write the phase's tests first or leave the source alone, so a violation costs one retry session; (b) report it as a `maybe` finding, so the judge sees it and the code report records it, with no retry; (c) fail it on the first attempt only. Until answered: (a), as SRC-B6 states. It does not block planning.
- Should the quick lane be checked as one phase made of its note's `Tests` and `Files`? Options: (a) not applicable, since it has no phases (SRC-B7); (b) one phase. Until answered: (a). It does not block planning.
- Should the rule-file criterion bind where the rules are installed for the whole machine? Options: (a) not applicable there, as SRC-B3 says; (b) have `prepare` put the rule files into the repository even when the machine has them, which makes the check bind but changes where rules live. Until answered: (a). It does not block planning.
