# Hand-off: i57

## Problem

In run r3-t5-1 a spec of about 34 KB, over the 30 KB budget, passed the discovery check, which counts lines only. The code step's suite caught it, and a code step cannot split a spec, so the run escalated `upstream`. The split that fixed it then failed the structure check: an acceptance criterion that stayed in the old spec named `SCH-B15`, a behaviour that moved with its id to the new spec. Discovery now states the budget in lines and bytes at the step that writes specs, and states how the ids a split moved are read.

## Decisions

- Both specs are in the earlier layout (numbered sections, `- [ ] ts-…` rows), which the spec rule says to leave as it is. That layout has no behaviours section, so each new row states one observable result, as the rows of the speed-up task did. The code step mirrors each of the four rows into `outcome.json` with the same text (revision 8), because a rescaffold rebuilds the criteria section from that file and would drop a row that is not there.
- The budget is the one the engine's docs README states and its budget test enforces: at most 400 lines and at most 30 KB, with 30 KB read as 30 × 1,024 = 30,720 bytes and "over" meaning strictly more. No setting names a budget per repository, and the task names none, so the figures are fixed like the 400-line cap already is (the overview's note on the fixed command list is the same convention). This is an assumption; see the first open question.
- "Every spec the step wrote" is the set the check already reads: the specs the git facts show changed, plus those the hand-off lists. A spec in the earlier layout is measured too, as the line cap does today, although its form is not checked.
- "Goes back to discovery" needs no change to the workflow's routing or to the engine. The discovery check runs at the discovery gate, and a failed check sends the step round again with each finding in its retry prompt (CHK-B1, CHK-AC5). The check already fails a spec over 400 lines there, under `ts-dis-form`. What is new is the byte figure, a criterion of its own, and a finding that says to split by capability. With `ts-dis-budget` the line figure moves out of `ts-dis-form`, so one overrun is one finding.
- A split is recognised from the files, not from the run's history. A behaviour moved by a split keeps its id (docs README, Ids; spec-migration plan, Over the cap), so a spec that defines ids with another spec's prefix was split from that spec or split into it. A criterion therefore may name an id that exactly one other spec defines when the id carries a prefix the criterion's own spec defines, and the check reads it as defined in that spec. This is an assumption the task leaves open. Two other readings were rejected: recognising a split from the run's base commit, because the allowance would lapse in the next run that edits either spec and the same finding would come back; and accepting any id that exactly one spec defines, because that is wider than the task and drops the check that catches a criterion naming a wrong behaviour.
- Boundaries the plan keeps: a criterion that names an id of a spec outside the split stays a finding ("names … which this spec does not define"); a criterion still names at least one behaviour of its own spec; an id defined twice or by no spec stays a finding of `ts-spec-links` and `ts-dis-links`, which already read a moved id as defined where it now is.
- The discovery check reads moved ids the same way, with no row of its own: `ts-dis-form` is `ts-spec-form` on the step's files (its check method in `outcome.json`), and both gates call the same function. Without that, a split decided at discovery would fail the discovery check, and the way out `ts-dis-over` offers would not work. The plan tests both gates. The setup check calls the same parser and keeps its own line-only cap, which this task does not touch.
- `rules/spec.rule.md` is not edited here: discovery writes specs, records and notes, and the speed-up task left its rule edits to the plan in the same way. The plan lists the rule under Docs to update: Length gains "30 KB (30,720 bytes)" beside the 400 lines (the rule-against-parser test holds the phrase "at most 400 lines"); Behaviours and Ids and links say that a behaviour moved by a split keeps its id, so a spec may define ids with the prefix of the spec it was split from, and that a criterion may name the ids of that spec.
- The outcome gate's `ts-spec-cap` is not touched: the task names the discovery check. It stays at 400 lines; the byte figure is measured once, at discovery.
- No spec of the package carries a "Not built yet" line for this issue (searched its specs, README and rules), so the plan has none to remove or update.

## Open questions

- Should a repository set its own budget? Options: (a) fixed figures for every repository, 400 lines and 30 KB, as the line cap is today; (b) a setting that the check reads. Until answered: (a). It does not block planning.
- Should the outcome gate's `ts-spec-cap` count bytes too? Options: (a) leave it at 400 lines, so a spec that grows past 30 KB after discovery is caught by a repository's own suite, as before; (b) count both figures there, one more criterion edit. Until answered: (a). It does not block planning.
