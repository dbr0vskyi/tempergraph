# Hand-off: i112

## Problem

In run r3-t5-2 the code judge of a 2,100-line change read one file, graded four blockers PARTIAL or UNVERIFIABLE at confidence 0.4 and escalated with no defect named, and across four runs judges graded MET from grep fragments (`judge_shallow`, kept 19 times). No spec says how much the code judge is to read, which files it must open, or what a judge must quote behind a MET. The task asks for a reading budget sized to the diff for the code judge (or one judge per phase), the list of changed source files with an instruction to open each before grading alignment, and the quoted line behind every MET in every judge brief, with PARTIAL when the only evidence is grep lines.

## Gaps closed

- G1: `plugins/temperspec-tgraph/docs/specs/judge-reading.spec.md` (JRD-B2, JRD-B4, JRD-AC3, JRD-AC5): the budget is one source file per 50 changed source lines, rounded up, floor 10, ceiling 50; a listed file beyond it is named as unread and what rests on it is UNVERIFIABLE; one judge per phase is not chosen (see Decisions)
- G2: `plugins/temperspec-tgraph/docs/specs/judge-reading.spec.md` (JRD-B1, JRD-B3, JRD-AC1, JRD-AC2, JRD-AC4): every changed source file is listed, the largest change first, and the judge reads them before it grades the alignment criteria
- G3: `plugins/temperspec-tgraph/docs/specs/judge-reading.spec.md` (JRD-B5, JRD-B6, JRD-AC6, JRD-AC7): the quoted line behind every MET, and PARTIAL for search lines alone, in all eight judge texts

## Decisions

- Where the behaviours live. A new spec in the engine's layout, `judge-reading.spec.md` (prefix JRD), named by the overview. The unit specs (`NN-<unit>.spec.md`) are in the earlier layout, which has no behaviours section, and their rows are generated from `outcome.json` and compared with it by the engine's docs check (`docs_check.py` lines 66-113), so a behaviour cannot be written there and a row added there must be mirrored in `outcome.json`. No row is added to `08-code.spec.md` and no criterion to `outcome.json`: the budget and the file list are evidence the gate gives its judge, not a result the gate passes or fails, and the brief wording is proved by the package's tests that carry the JRD ids, as the briefs' open-question wording already is by a test with no criterion (`tests/test_temperspec.py` lines 959-963).
- "The brief" of the task's criterion 2. A judge brief is a fixed file and cannot list the files of one run. Run facts reach a read-only judge through the check's evidence (JDG-B11), so the code gate lists the files and states the budget (JRD-B1, JRD-B2) and the brief tells the judge to read what the evidence lists (JRD-B3). Together they are the code judge's brief of the criterion. The engine hands a judge the branch and a count of changed paths as workspace facts (`nodes.py` line 1587), not the files, so the evidence is the only list it gets.
- A budget, not one judge per phase. The code step is one session with one gate (`plugins/temperspec-tgraph/README.md` line 43; per-phase coding is issue #122), so there is one judge to size and no phase gate for a second one to sit on. The budget is a statement in the evidence, not a session cap: the engine sets a judge's turn cap and time limit per gate, not per attempt, and the one setting it raises by diff size is the judge's model or effort (JRK-B6), which does not change how much a judge reads. Revisit when #122 is built.
- How criteria 1 and 2 meet. All changed source files are listed; the judge reads them in order, largest change first, up to the budget. The budget covers every file of an ordinary change: any change of up to 10 source files is read in full, and so is a larger one whose files average 50 changed lines or more, up to the ceiling of 50 files. A change with more files than its budget gets the unread files named and the alignment criteria that rest on them graded UNVERIFIABLE (JRD-B4), which the engine escalates (JDG-B13), not a MET from a sample. PARTIAL was not chosen for them: a PARTIAL on a blocker sends the code step back (JDG-B13) for a fault it cannot fix.
- Terms, defined in the spec once. A source file is any changed file that is not a Markdown document, tests included, because the judge reads them for `ts-code-tests`. Changed lines are lines added plus lines removed since the run's base, the measure the quick lane's 200-line limit already uses (`checks.py` lines 735-763). The alignment criteria are `ts-code-aligned` and `ts-code-related`.
- No base commit. A gate run with no base to count from (the package's check fixtures build their context without one) cannot count changed lines. The spec states no such case; the plan chooses between the floor with a stated reason in the evidence and an `n_a` finding. The quick lane takes the same rule, so a small change gets the floor.
- Values. One file per 50 changed lines, floor 10, ceiling 50 are first values with no run behind them, as the quick lane's limits are (`outcome.json` assumptions). The floor reads any change of up to 10 source files in full; the ceiling bounds the judge's reading cost and time; 50 lines per file is a guess at the average changed lines of one source file that no run has measured (r3-t5-2's 2,100 lines would have given a budget of 42). The measure to tune them by: the share of code judge sessions that read every file within the budget (the session review records how many changed files a judge read, `changed_read`).
- Which judges. JRD-B5 and JRD-B6 cover eight texts: the seven briefs in `judges/` and the stance of the outcome judge in `outcome.json` (lines 13-16), which has no brief file. The engine's own brief for an upstream claim is the engine's and stays out. The check holds the budget's arithmetic, so no brief carries a rule-like branch (JDG-B6).
- Search lines. They are lines a search (grep) printed, as against a file read. A MET stays possible when the judge searched, then read the file around the line, and quotes that line from the file (the second scenario of JRD-B6).
- No engine change. Everything is package-side: the check's evidence and the brief text. One engine limit bears on JRD-B1 and JRD-AC2: the judge's prompt keeps 4,000 characters of the check's evidence (`judging.py` line 156), and the gate's existing changed-paths line (up to 120 paths) and criterion-test line share that room. A list of 40 files with counts must be compact and early in the evidence, or the existing lines shortened. If it cannot fit, the cap is the general capability to change, as a separate engine task.
- The judge's time. The package sets no `timeout_s` on any judge, so the code judge has the engine's 600 s (`nodes.py` lines 80 and 1605), and a judge timeout escalates (JDG-B4). Whether a budget of up to 50 files fits in 600 s is for the plan to size; a `timeout_s` on the code judge alone, with its reason, is the means the package has, and the spec states no time.
- Seeds and the live check. The task's "judge seeds still pass rung 8 (TS-L1)" needs the owner's signed-in `claude`, which a cloud container does not have. The plan lists no verification that needs a model, and the code report says TS-L1 is not run. The code seeds embed a copy of the check's evidence (`evals/calibration/code/*/fixture/check.json`); when the evidence gains the file list and the budget line, those copies follow, so rung 8 grades with the evidence a run would give.
- The model-free authoring check (task criterion 5). `tempergraph author verify plugins/temperspec-tgraph` runs rungs 1 to 7 and 10 with no model (`verify.py` lines 1-4 and 19-20), and rung 10 writes `stamp.json` and `authoring.json`. `tempergraph` is not in the package's verification list (`__init__.py` lines 51-53), so the gate cannot run it as a plan command. The engine's own suite covers rungs 1, 4 and 5 for every package (`test_workflow_packages.py` lines 29-40). The plan decides how criterion 5 is verified; a run by hand is the fallback, which the code report states. A change to the outcome judge's stance changes `outcome.json`; each earlier change to it added an entry to its `revisions` list (seven so far), and rung 10 takes a newer revision as the re-approval (`stamp.py` lines 112-115).
- No "Not built yet" line. None names #112 or #113 (searched the package's specs, README and docs); nothing to remove or update.
- No contradiction with the linked specs. The new spec relies on the two alignment criteria of `08-code.spec.md` and on the overview's statement that alignment is judged once, at the code gate, and contradicts neither. The overview says a judge never sees the gate's command runs; the evidence is the check's own text, which the engine hands the judge (JDG-B11).

## Open questions

- Are one file per 50 changed source lines, a floor of 10 and a ceiling of 50 the right first values? Options: keep them (chosen), or one per 100 lines with a ceiling of 40, which costs less and reads fewer files of a large change. It does not block planning: each value is one constant of the check.
