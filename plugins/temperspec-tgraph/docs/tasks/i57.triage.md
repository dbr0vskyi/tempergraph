# Triage: i57

## Task

GitHub issue #57, "temperspec: spec splits do not send the run back (budget check at discovery, moved ids)". In run r3-t5-1 an over-budget spec was caught only by the code step's suite, which cannot fix it, and the run escalated `upstream`; the split itself then failed the outcome check (`SCH-AC1 names SCH-B15`). Was backlog rows B42 and B43.

## Acceptance criteria

1. B42: the discovery check measures every spec the step wrote against the repository's spec budget (lines and bytes). An over-budget spec goes back to discovery, where a split by capability is decided.
2. B43: the outcome check reads ids moved by a split (the docs rule keeps a moved behaviour's id) as defined in the spec they moved to. An acceptance criterion may name an id of the spec it was split from.

## Existing documents

- `plugins/temperspec-tgraph/docs/specs/discovery.spec.md`: discovery criteria (form, names, links, commit, gaps, behaviour, scope, narrow, reading); none mentions a size budget or a return to discovery for an over-budget spec
- `plugins/temperspec-tgraph/docs/specs/overview.spec.md`: `ts-spec-cap` (no spec the run edited is over 400 lines) and `ts-spec-links` (every linked id resolves to exactly one definition) at the outcome gate; neither mentions bytes or ids moved by a split
- `plugins/temperspec-tgraph/rules/spec.rule.md`: Length (at most 400 lines, split by capability or compress); Ids and links (an id is defined once and never renumbered); says nothing of bytes or of an acceptance criterion naming the id of the spec it was split from
- `plugins/temperspec-tgraph/workflow/temperspec/checks.py` (`_spec_form`, line cap) and `specfmt.py` (`SPEC_CAP_LINES`, "names X, which this spec does not define"): current code; the discovery form check counts lines only, and a criterion naming an id the spec does not define is a finding
