# Triage: i65

## Task

GitHub issue #65: temperspec per-phase coding. The `phases` arm of the switch `code_mode` becomes `expand`, then a sequential map `phase` over the plan's phases (a fresh session, a gate and a commit through the `after` script per item), then `code` as the join. The map's gate has no line back, so the quick-lane guard and the plan's upstream line move to the join.

## Acceptance criteria

1. On the `phases` arm, after `expand`, a sequential map runs one item per phase of the plan, in plan order; each item is a fresh session that builds only that phase's rows (tests first) and commits through the `after` script.
2. A phase item whose check fails retries alone; the phases already committed are not rerun.
3. The `single` arm is unchanged: one code session builds the whole plan.
4. The join after the map checks the whole change: the quick-lane guard, the plan's upstream line (trips back to plan, discovery, triage) and the proof table's commands run there, as the code gate does today.
5. The specs say what is true now: the overview, code-mode, the code step and a unit spec for the new map unit; the README's "Per-phase coding is not built yet" line is removed. Offline tests prove criteria 1 to 4 with stand-in executors.
6. The package's model-free authoring check (`tempergraph author verify plugins/temperspec-tgraph`, rungs that need no model) passes, and the package tests pass through the engine suite.
