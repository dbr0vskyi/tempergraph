# Hand-off: i68

## Problem

A trip back to plan rewrites the plan in place and leaves the run's files as they are, but the plan and expand checks refuse every completed mark, and the plan prompt, the expand prompt and the plan rule tell the steps to leave every Completed cell empty. A trip back therefore relabels or rebuilds finished rows (`row 3.2 is already marked completed`; R-160, row B23). No spec said what becomes of a mark across a trip back. The task asks that a row whose text, file and file history are unchanged keeps its mark and is accepted, that a changed row loses its mark and a mark on it is refused, and that the code step after the trip builds only the rows without a mark, with the code check asking no new change to the file of a kept row.

## Decisions

- Where the behaviours live. A new spec in the engine's layout, `kept-marks.spec.md`, as the judge-reading task did. The unit specs (`NN-<unit>.spec.md`) are in the earlier layout, which has no behaviours section, and their criterion rows are compared with `outcome.json` by the engine's docs check (`docs_check.py` lines 53-113: ids and whitespace-normalised text). Three rows were false once the behaviours exist, so they are reworded in place, each pointing at the new ids. The code step mirrors the same text into `outcome.json` (`ts-plan-form`, `ts-exp-rows`, `ts-code-changed`), updates the `check_method` of the first two, which still say that the Completed cell of each row is read against the rule, and adds a revision to its `revisions` list (the next is 11). Until it does, the docs check reports drift between the three specs and `outcome.json`.
- `ts-code-rows` is not edited. After a trip back a kept row carries a mark with the date of the visit that wrote it, which is a mark with its date, so the end state it states still holds. Only `ts-code-changed` was written in a way that could be read as asking this visit to change every marked row's file.
- The code check needs no new behaviour in code. `ts-code-changed` compares each marked row's file with the paths changed since the run's base commit (`checks.py` lines 989-996; `outcome.json` check method; `git.py` lines 219-232), and the run's base commit is fixed when the run starts, so a file that an earlier visit changed already passes. KMK-B8 says so in the spec and the plan adds a test row that pins it; it adds no code row for it unless that test fails.
- What "kept" means. A mark carries a date and nothing else (`DONE_MARK`, `specfmt.py` line 30), and "the file was not changed since the row was marked" needs a point in time. The spec therefore defines the row's marking commit, the earliest commit of the run in which a row with that id carries the mark the plan now carries. The check reads history with the read-only git commands the workflow already allows (`git log`, `git show`), as `_at_base` reads a file at the base (`checks.py` lines 1018-1029). The engine's `commits_since_base` fact is never filled (`run/checks.py` lines 43-50), so the check lists the commits itself.
- Two roles. The plan and expand steps have no shell (`__init__.py` lines 138-150), so they cannot read history: they keep or empty a mark from the plan file in the working tree, which a trip back leaves in place (BUD-B4). The check holds the mark against history and refuses one that history does not back, including a row whose file a later commit changed. The refusal names the row, so the retry empties that mark.
- A row's text. For this task a row is the same when its id, kind, requirement, file, proof and change are the same; the phase heading is not part of it. How spacing is compared is the plan's choice. A row the trip renumbered is a changed row (first open question).
- Accept, not require. Criterion 1 says the check accepts a kept mark. No behaviour requires it: a step that empties the mark of an unchanged row is not refused, and the code step then builds that row again (second open question).
- No history, no mark. With no base commit, or with no commit of the run that carries the mark on that row, the mark is refused, which is today's behaviour. The first plan of a run, and the two fixtures `row-already-marked` (plan and expand), which have no history, therefore keep failing as they do.
- Which trips. KMK-B1 to KMK-B4 read only the marks and the history, so they hold whichever gate sent the run back to the plan step (the expand gate, the code gate or the outcome gate, whose trip R-160 records as H4) and when the trip went through discovery first.
- Complex plans. The plan step writes the phases of a complex plan and no rows, and the expand step writes the rows. For a mark to survive there, the plan step must edit the plan in place on a trip back and leave the task table of every phase it does not change, and the expand step must keep the marks of the rows it leaves and fill only the phases or rows that lack them. KMK-B5 and KMK-B6 state what each prompt and the plan rule tell; how they say it for a complex plan, beside the plan rule's line that a complex plan is written with phases, goals and weights only, is for the plan to write.
- The status stays `planned` after the plan and expand steps, as `ts-plan-form` and `ts-exp-rows` still say; the code step sets `in-progress` and then `completed`.
- A kept mark skips the building, never the verification. The code gate runs every verification command of the plan and reads each criterion's test (`ts-code-verify`, `ts-code-proof`), so the tests of kept rows still run.
- The briefing behaviours (KMK-B5, KMK-B6, KMK-B7) get no criterion in `outcome.json`. The package's tests carry the KMK ids and read the prompts and the plan rule, as `tests/test_judge_reading.py` does for the briefs. Whether to also add their phrases to `PROMPT_SAYS` (`checks.py` lines 69-80) so that a gate reads them is the plan's call.
- What the change makes false, for the plan's Docs to update and code rows: `rules/plan.rule.md` lines 118-119 and 85 (every Completed cell empty; a complex plan is phases only), the three prompts (`plan.md` line 27, `expand.md` lines 16 and 24, `code.md` lines 22 and 29), the `outcome.json` rows above, `stamp.json` (the docs digest and the outcome revision, which rung 10 stamps again), and in code `mark_problems` and its messages (`specfmt.py` lines 472-491), the fix text in `_marks` (`checks.py` lines 623-626) and the call in `plan_check` and `expand_check`. `tests/test_temperspec.py` line 136 calls `mark_problems(plan, done=False)` on the plan rule's example, so the new signature keeps that call valid or the test changes with it.
- No contradiction with the specs it links. The new spec relies on BUD-B4 (a trip back leaves workspace files untouched), on `ts-code-changed` measuring from the run's base commit, and on the plan rule's status values; it contradicts none, and the three reworded rows agree with it.
- Left as they are: `judges/code.md` line 15 (the check confirms each marked row's file changed, which stays true for a kept row), and `docs/research/plan-format-review.rsrch.md` rows 4 and 21, which record a review of the plan format and are not behaviour.
- No engine change. Everything is package-side, and the engine's specs say nothing about marks.
- No "Not built yet" line names #68 (searched the package's specs, README, rules and docs); nothing to remove or update.

## Open questions

- Should the plan check require the mark of an unchanged row instead of only accepting it? Options: (a) accept only, so a step that empties such a mark causes a rebuild and no more (chosen: criterion 1 says "accepts"); (b) require it, so finished work is never rebuilt, at the cost that a step cannot deliberately redo a row without changing it. It does not block planning: (b) adds one finding to the check.
- Should a row the trip renumbered keep its mark when its text and file are unchanged? Options: (a) no: the id is part of the row, so a renumbered row is a changed row (chosen: the safe reading, and the planning prompts can tell the steps to keep ids); (b) yes: match rows by their text and file when the id moved. It does not block planning.
