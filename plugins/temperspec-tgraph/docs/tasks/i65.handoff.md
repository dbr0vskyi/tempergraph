# Hand-off: i65

## Problem

Issue #65 splits the arm `phases` of the switch `code_mode` into the expand step, a sequential map `phase` with one item for each phase of the plan (a session, a gate and a commit each), and the code step as the join, whose gate checks the whole change; the arm `single` stays as it is. No spec of the package said so: the overview, the README and the code-mode spec said that per-phase coding is not built and that `phases` ends in one code session, and no spec covered the map or the join. The engine already has the sequential map (MAP-B1 to MAP-B11), so the specs rest on it; three points it does not settle are open questions with defaults.

## Decisions

- Layout, which the plan's rows follow: the arms stay `single` to `code` and `phases` to `expand`, and `joins_at` stays `code_join`, because the engine refuses a `joins_at` that is the entry of an arm (`model/validate.py` lines 696-698) and `code` is the entry of `single` (the reasoning of the plan of issue #59, `docs/plans/i59.plan.md` line 17). The map `phase` goes in `order` between `expand` and `code`, so on `phases` the unit after the map is `code`: the join of the map, as the issue says. `single` and the quick lane skip the map. No unit is added besides `phase`. The map's list is the plan that `expand` produces (`items_from` `expand`, key `phases`), which precedes the map on every path into it (`validate.py` lines 515-522).
- One code step with two jobs and one prompt. Its prompt gains the key of the phases' notes, which the engine renders as one line for each item or `none` when no item holds it (VAL-B9; `run/nodes.py` lines 1095-1117), so on `single` and in the quick lane the brief says no phase ran. KMK-B7 already makes the step build only a row with no mark, so after the phases it builds nothing, sets the plan `completed`, writes the report with the notes' deviations and makes its one run of the commands. The `ts-code-*` criteria stay as written, which is why `code.spec.md` changed in prose only: their text is mirrored word for word in `outcome.json` and the docs check compares it.
- A phase's gate is a model-free check of its own rows and one judge session (a model step needs a judge, `validate.py` line 762). The check runs none of the plan's verification commands: the task puts them at the join. The criteria are the seven of `phase.spec.md`; the plan copies their text word for word into a `phase` entry of `outcome.json` (`package/docs_check.py` lines 97-101). The lint of `outcome.json` wants a scale and two seed names for each judged criterion (`author/criteria_lint.py` lines 142-150); `read_gap` has names and no seed fixture (`outcome.json` lines 616-660), and that is the model.
- Two specs for the unit: `phase.spec.md` in the earlier layout, since the docs check wants `NN-<unit>.spec.md` and the gate criteria as `- [ ] <id> <text>` lines, and a capability spec in the new layout with the prefix PHC for the behaviours, as `read-gap.spec.md` and `parallel-reading.spec.md` are. The earlier layout is not checked for form (`checks.py` lines 324-326).
- What a phase item is told: the phase's heading, goal and weight, the plan's path and the triage note's path. `{item}` takes at most 4,000 characters (MAP-B7) and a phase's rows can be longer, so the session reads its rows from the plan. The `Read:` and `Produces:` lines of the research note (`stages-against-engine-releases.rsrch.md`, F3 point 2) belong to a change of the plan format; the plan rule is not touched here, since the change in flight (#106) edits the rule files.
- Item ids are `p<n>` from the number in the phase heading (PHC-B1). A heading with no number, or a number used twice, needs a fallback such as its position; the spec leaves it to the code, and the plan should state it in a row.
- Not edited, and why: `code-mode.spec.md` and `code-join.spec.md` (they say where the arms go and meet, which is still true); `expand.spec.md`, `kept-marks.spec.md` and `session-record-checks.spec.md` (their behaviours hold; PHC-B8 applies the rule of SRC-B6 to the phase check by link); the rule files, prompts, judges, code, tests, `outcome.json`, the blueprint and every engine spec (not documents of discovery).
- Checked against the specs PHC links, none contradicts: MAP-B3, MAP-B5, MAP-B7, MAP-B10 and MAP-B11 (the same retry, pause, trip-back and refusal rules), KMK-B7 and KMK-B8, SRC-B6 and SRC-B8, JDG-B1, and CDM-B1 to CDM-B11 as edited. CXR-B4 is not touched: the map and its key sit before `joins_at`, and no unit after it reads them.
- Trace obligations (`ts-traced`): each of PHC-AC1 to PHC-AC15 needs a test that is not skipped and carries its id in its name or a comment. CDM-AC11 and CDM-AC12 prove behaviours that changed, so the test that carries them (`tests/test_code_mode.py` lines 341-351) is edited in this run. Tests that pin what changes: `tests/test_code_mode.py` line 205 (the order of units), line 243 (`UNITS`), lines 351, 381, 400 and 421 (the units entered on `phases`), and lines 458 and 478 (the units `report --switch` counts, which now include the map, since it lies between the switch and `joins_at`).
- Documents this makes stale, each a docs row of the plan and not a gap: `README.md` line 20 (the `code` row says both arms end in one session), line 31 (the full lane) and line 47 (the per-phase line, which the task says to remove); the module docstring of `__init__.py` lines 16-21; `diagram/model.json`, `diagram/workflow.md` and `stamp.json`, regenerated. The overview names the unit's summary, "Build one phase of the plan, tests first, and commit it" (55 characters), so the step's summary and the blueprint must say the same.
- A phase prompt that names a rule file would bring the rule-file check to the phase step; SRC-B1 and SRC-B2 list the seven steps, and nothing in this change asks to widen them, so the phase prompt may name no rule file, its procedure being short enough to hold in the prompt.
- The conversation value of this run was not filled in the prompt (`⟨missing:settings.conversation⟩`), so the default `blocking` was taken. No question below blocks planning: each has an `Until answered` default, and the triage note lists no owner decision.

## Open questions

- How should the commit of a phase name its phase? Options: (a) the message names the step and the task and the marks inside the commit tell the phase, which is what the engine's script context allows today, since it gives the commit script the step's name and not the item's id (`run/nodes.py` lines 1152-1156); (b) the package's commit script finds the phase whose rows the commit marks and names it, a package change with no engine change; (c) ask the engine to give such a script its item, a capability stated without temperspec (ADR `the-engine-names-no-workflow`). Until answered: (a). Not blocking.
- How many phases may a plan have? Options: (a) keep the map's default of 20, so a plan of more phases stops the run at the map, naming the count, before any phase starts (MAP-B5); (b) raise the map's limit to the engine's 50; (c) cap phases in the plan rule and the plan check, which touches the rule files that #106 edits. Until answered: (a). Not blocking.
- What should a phase do when the plan or a spec it rests on is at fault, since it has no line back (MAP-B11)? Options: (a) it leaves the row unmarked and names the row and the conflict in its note, the check fails the row, and when the retries are spent the run pauses at the phase for a person; (b) it ends with a `BLOCKED:` line, so the engine escalates the phase at once with no wasted retry (JDG-B1), which looks better to the author of this hand-off; (c) give a phase a line back, which MAP-B11 forbids on purpose and the engine would have to change. Until answered: (a). Not blocking.
