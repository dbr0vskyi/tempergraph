# Hand-off: i59

## Problem

Issue #59 asks that the route after the plan step be the engine's complexity switch, named `code_mode`, with the arms `single` and `phases` (`phases` the safe arm), measured on the plan check's facts, with its rules in `routing/code_mode.json`, the owner's override at start from `--arm`, and a new trial run that passes. No package spec stated the route after the plan. The plan check records no engine facts today, so the switch would have nothing to measure. The engine's rules for a complexity switch (an arm's entry may not be the join, the arm is chosen once per run) fix limits on the layout and on what a trip back does.

- G1: `plugins/temperspec-tgraph/docs/specs/code-mode.spec.md` (CDM-B1 to CDM-B7 and CDM-B9; CDM-AC1 to CDM-AC12 and CDM-AC15): the switch, the facts the plan check records, the arm chosen from them, the limits in `routing/code_mode.json`, the safe arm, what each arm runs, and the quick lane taking no arm

## Decisions

- One new spec in the layout of the spec rule, listed beside the units in the overview as `kept-marks` and `session-record-checks` are, and not rows in `06-plan.spec.md` or `07-expand.spec.md`: those are in the earlier layout, which the spec rule says to leave, and the route is one concept. Not edited on purpose: the step specs 06 to 08, `kept-marks.spec.md`, the rule files, the prompts, `outcome.json`, tests and code, and every engine spec (the need is stated in the engine's CXR-B8 already, ADR-0129). CDM-B1 to CDM-B11 were checked against CXR-B1, CXR-B6, CXR-B7, CXR-B9, CXR-B10, CXR-B13, CMP-B7, SWM-B5, CHK-B6, CHK-B14, SCF-B20, `ts-plan-size` of the plan spec and `ts-code-rows` of the code spec: none contradicts. The second scenario of KMK-B1 (expand again after a trip back) holds under `phases`; under a kept `single` no expand step runs, so that scenario does not arise (open question 1).
- The layout is the plan's choice and the spec holds for each. The engine refuses `joins_at` equal to the entry of an arm (`model/validate.py` lines 689-691, `complexity-joins`, though CXR-B7 words it "the first unit every arm path reaches"), and an arm's target must come after the switch in `order` (lines 1004-1013). So `code` cannot be both the `single` arm's entry and the join. Options: (a) arms `single` to `code` and `phases` to `expand`, with `joins_at` a new model-free script unit after `code`; (b) `joins_at` = `code`, with a pass-through script unit as the entry of `single`; (c) change the engine so an arm may be the join. Recommended: (a). `report --switch` counts first-pass yield over the gates between the switch and `joins_at` (`cli/observe_cli.py` lines 252-256, `observe/switch_report.py` lines 38-45), so under (a) the figure covers the code gate of each arm, while under (b) it covers `expand` for `phases` and only the pass-through unit's own gate, which always passes, for `single`. Under (a) the order becomes `plan`, `code_mode`, `expand`, `code`, the new unit; `plan` goes on to the switch by order and loses its `route` and `route_targets`; the quick lane (triage to `code`) never meets the switch and passes the new unit with no effect. (c) is an engine change the task does not need. A script unit needs a summary of 1 to 60 characters (`package/selftest.py` lines 38-46), and with no check and no produced key it needs no fixture: the generated scripted run writes nothing for it (lines 153-179). In that run the plan is the first must-pass fixture of the plan gate (`evals/checks/plan/must-pass/1-complex`), so once the plan check records facts the run takes `phases`.
- Facts and measures. `CheckResult.facts` exists (20 slug keys, values up to 200 characters, CHK-B14; `contracts.py` lines 829-836) but `checks.result` takes no facts and the plan check never sets any (`checks.py` lines 420-454, 869-929): the plan check sets `res.facts` from the signs that `simple_overruns` computes (`specfmt.py` lines 514-521), ideally one helper used by both, so the facts equal what `ts-plan-size` measures (CDM-B2, CDM-AC3). A measure takes the name of its fact (`phases`, `rows`, `test_rows`, `files`, `commands`, `reading_bytes`, `heavy_phases`) and reads `stock.fact("plan", <name>)` (`api.py` lines 225-257), because a repository's override file and the `route` record name measures (CXR-B10, CXR-B13). The seven names and the file path are the exact names someone outside depends on, which is why the behaviours state them.
- Rules file `routing/code_mode.json`: `schema_version` 1, `arms.single.when` = phases at most 3, rows at most 12, test_rows at most 6, files at most 10, commands at most 3, reading_bytes at most 200000, heavy_phases at most 0; no `margin`; no entry for `phases` (the schema refuses bounds on the safe arm, `run/complexity.py` lines 56-57). The numbers are `SIMPLE_MAX` (`specfmt.py` line 47) and the plan rule's table. `tests/test_temperspec.py` lines 129-149 holds the table to `SIMPLE_MAX`; a test of the same kind holds the file to it (CDM-AC7). Assumptions: `mode` stays `route` (the rules are the old rule, so there is nothing to measure before trusting them; the engine only warns in `local-stable`, CXR open question), no `explore`, no `rearm` (not asked; `phases` still ends in one code session, so a re-arm would change only who writes the rows, until per-phase coding, issue #65), and `size` is `phases` (`rows` is 0 for a complex plan before the expand step, while `phases` is at least 1, `checks.py` lines 882-883; the report divides cost by the sum of the size measure, `observe/switch_report.py` lines 60-62, 73).
- The fault behaviour changes. The old route took `code` for any `complexity` value but `complex`, so an unreadable value took the cheaper path (`routing.py` line 62); the switch takes `phases` on any fault (CXR-B1). No spec stated the old behaviour; CDM-B5 states the new one.
- The `complexity` value stays. The plan step still produces it and `ts-plan-size` still holds it to the signs (`checks.py` lines 911-924); the plan check still asks rows of a `simple` plan only (lines 887-895). The route reads no step value (CXR-B9), so with the plan check passed, `simple` and `single` go together, as do `complex` and `phases`. `route_plan` and its import (`__init__.py` line 38) go, the two asserts that pin it (`tests/test_temperspec.py` lines 317-318) go with it, and the plan unit loses `route=route_plan, route_targets=[...]` (`__init__.py` lines 142-144).
- Blueprint. `blueprint.json` gets a unit `code_mode` of `kind: switch` and `flow.code_mode.switch` = `{arms: {single: <unit>, phases: <unit>}, default: phases}`, the new script unit of option (a) with `kind: script`, and loses `flow.plan` (lines 239-244). `blueprint check` builds a plain switch from the blueprint (`author/blueprint.py` lines 297-300), so the complexity declaration is validated at rung 1 on the built workflow, not at `blueprint check`.
- Task criterion 3 (the workflow validates, `blueprint check`, the model-free rungs of `author verify`, the package tests, `ruff check src tests`, `mypy`) is verification, not behaviour, so no spec states it. `tempergraph blueprint check` and `tempergraph author verify` are not on the workflow's allowed command list (`VERIFY`, `__init__.py` lines 51-52), so the plan cannot list them as verification commands. The engine's suite covers, for the package, the load and its outcome coverage, the generated self-tests (diagram digest, summaries, check fixtures, the scripted run, compatibility, docs) and the package's own tests (`engine/tests/test_workflow_packages.py` lines 29-40 and 53-59), not rungs 2, 3, 6 and 7. The plan lists `python -m pytest` from `plugins/tempergraph/engine/`, `ruff check src tests` and `mypy`, writes the blueprint so that rung 2 compares equal (arms and default of the switch, `author/compare.py` lines 98-102), and says in its assumptions that the two CLI checks are run by whoever merges.
- What each arm runs, today: `single` the code step on the plan as written (a simple plan carries its rows); `phases` the expand step and then the same code step in one session. Issue #65 splits `phases` per phase later and would update this spec then; README line 43 says so already.
- Trip back. The measures are evaluated once per run (`run/nodes.py` lines 1187-1189), `clear_from` leaves the pick alone (`run/gate.py` lines 25-40) and `_switch_pick` reuses it for the run (lines 113-115). The old route chose again after every plan. ADR-0003 refused a switch for discovery for the same reason (lines 11 and 34); here the issue chooses the switch, and `phases` is the safe arm. Stated as open question 1 in the spec, with its default.
- A forced `single` on a plan with no task rows reaches the code check, which fails with `ts-code-rows` ("the plan has no task row", `checks.py` lines 1203-1204); that is the default of open question 2, since the operator's arm wins over every zone (CXR-B6).
- Live check. Proposed row for `live-checks.plan.md`, added as a docs row of the plan with no result (a result is written only from a run on the owner's machine, the file says so; the orchestrating agent runs it after the merge and writes the result then): `TS-L3` | trial run of the route after the plan | in a scratch Python repository with `pytest` and `ruff` on PATH, `tempergraph author verify <path to plugins/temperspec-tgraph> --trial --case missing-config --cap 15` | rung 9 `passed`: the trial run reaches the outcome gate with a verdict other than `not_reached` and no pause (SCF-B20, `author/verify.py` lines 233-265), its `route` record names `code_mode` and an arm with the seven measures, and `tempergraph report --switch temperspec/code_mode` lists the run under that arm; rung 10 then stamps the new shape. The arm is not named in the criterion, since the model writes the plan. `ts-traced` counts a text mark such as `@pytest.mark.skip` or `xfail` as skipped (`specfmt.py` lines 581-591), so CDM-AC18 and CDM-AC19 are carried by an offline test that reads the live checks file, and the trial itself carries no criterion.
- Documents the change makes stale, each a docs row of the plan: `README.md` lines 11-23 (the plan row's Then cell), 25-33 (the full lane), 43 and 60-67 (add the override `--arm code_mode=<arm>` and the report); the module docstring at `__init__.py` lines 11-13; `diagram/model.json` (digest) and `diagram/workflow.md` (line 11) and `stamp.json`, regenerated by `tempergraph upgrade-check <workflow> --stamp` (`package/selftest.py` lines 22-35); the stamp's audit baseline (`stamp.json` lines 58-93) may need a refresh if the new shape adds a finding. `plan.rule.md` is not edited: its Complexity table stays the source that CDM-B4 holds the rules file to.
- Trace obligations (`ts-traced`): each of CDM-AC1 to CDM-AC19 needs a test that is not skipped and carries its id in its name or a comment. No old criterion proves an edited behaviour, since no behaviour of another spec is edited. Suggested: a new `tests/test_code_mode.py` for CDM-AC1 to CDM-AC17, with scripted runs modelled on `package/selftest.py` lines 186-273 and `engine/tests/test_complexity.py` lines 67-137, the override as `flags={"code_mode.arm": ...}` (`engine/tests/test_measured_switches.py` lines 162-171), and plan fixtures under `evals/checks/plan/`; CDM-AC18 and CDM-AC19 by a test that reads the live checks file.
- This worktree has no `.claude/rules/temperspec/` folder (a search of `.claude/` with the file tools found no file), so the five rule files the prompt names were opened with the read tool from `plugins/temperspec-tgraph/rules/`, where the project note in `CLAUDE.md` places them (`spec`, `decision`, `research`, `task-notes`, `documents`).
- No "Not built yet" line concerns this issue: a search of the engine's and the package's specs for `Not built yet:` found none about the plan route, so none to remove or update. No research note and no decision record: each unknown was answered by reading the code, cited above; the layout is the plan's choice, and the two choices only a person can take are below.

## Open questions

- Should a run that comes back to the plan step choose its arm again? Options: (a) keep the arm of the first pass for the run, which is what the engine does (the spec's default); a plan that outgrows `single` after a trip back then goes to the code step with the rows it has, and the code gate decides; (b) ask the engine for a complexity switch that is evaluated again when the run returns to a unit before it, a general capability for which CXR-B7 (sticky for the run) and the one-way re-arm would be reopened, and ADR-0003's "revisit when" would be met; (c) run the expand step on every plan, which costs one session on a simple plan. Until answered: (a). It does not block planning.
- What should `--arm code_mode=single` do when the plan has no task rows? Options: (a) leave it to the code check, which fails `ts-code-rows` and costs the code step's retries before the gate's policy applies (the spec's default); (b) refuse at the switch, with a check on its gate that fails `single` for a plan with no task row, which is a package change and a new behaviour; (c) take `phases` instead, which contradicts "the operator's arm wins" (CXR-B6). Until answered: (a). It does not block planning.
