# Hand-off: i60

## Problem

temperspec cannot run unattended on what only the owner can decide: nothing sorts a task's gaps into what the code or the documents can answer and what only the owner can, and discovery ends blocked on a question that blocks planning. #60 asks for a conversation setting with the value `never` for pipelines and night runs: triage sorts each gap and writes a default for each owner decision, no step or gate stops on one, and the draft pull request lists each default as an assumption to confirm, while every other value keeps today's behaviour. All four gaps are spec gaps, closed by one new spec; the code, prompts, rules and checks follow in the plan.

## Decisions

- Where the behaviours live. One new spec in the engine's layout, named by the overview's "Beside the units" line, as `project-note.spec.md` was in run i67. The unit specs are in the earlier layout, which has no behaviours section, and the engine's docs check ties their rows to `outcome.json` (`docs_check.py` lines 20-24 and 66-113). The file is named for the capability and not for the value, since the setting has room for more values. The prefix `CONV` is used by no other spec.
- The values are `never` and `blocking`, and `blocking` is the default (assumption). The research note lists `never`, `blocking` (the default, the owner's ruling of 2026-11-22) and `always` (`next-features.rsrch.md` lines 38-44), and the task says the other values keep today's behaviour. `always` means "ask every owner decision", which needs questions that nothing in the workflow asks yet; a value that is accepted and does nothing would mislead whoever sets it, so it is not declared, and the engine refuses it before any spend, listing the two values (RST-B7). `blocking` is today's behaviour: triage sorts nothing, a step ends blocked on a question only a person can answer when it blocks planning, the description lists no assumptions. See the first open question.
- How the setting reaches each reader, with no engine change. The workflow declares `conversation` as a `choice` setting with default `blocking` through `Setting(...)` and the `settings=` field of `Workflow(...)` (`api.py` lines 109-112 and 409-424; RST-B25). A prompt names it as `{settings.conversation}` (VAL-B8). A check finds it as `ctx.settings["conversation"]`, by its bare name (`nodes.py` lines 1509-1517, `settings.py` lines 915-917). Per run it is `--set settings.conversation=never`; per repository it is an entry of the engine's project settings file (RST-B22, RST-B24), which the engine's own test builds with `ConfigFiles(project=...)` (`test_settings.py` lines 47-60 and 183-195) and which is the model for the CONV-AC1 test.
- The last stage cannot read the setting, so the description reads the note. The finalizer's context holds values, artifacts, facts and a `run_options` with the workspace mode only (`run/finalize.py` lines 81-87), no settings. CONV-B7 therefore keys on the triage note: an `Owner decisions` section means the run was `never`, and `None` there means it took no default. This needs nothing from the engine, as the research note says of `never` (line 48). Handing the value to the finalizer would be an engine capability for any workflow (ADR-0129); the task does not need it.
- A check that is given no conversation value reads `blocking` (CONV-B4, last scenario). The package's tests build a check context with no settings (`test_temperspec.py` lines 40-44), and `test_a_met_seed_passes_the_check_of_its_gate` (lines 69-90) runs the triage check on the met seeds of the triage judge, which criterion 4 says must keep passing. A check that demanded the sort when the value is absent would fail them.
- The engine's fixture rung gives every check no settings either (`package/selftest.py` lines 123-125), so each fixture under `evals/checks/triage/` runs as `blocking`. A `never` fixture in `must-fail/` would pass the check and fail the rung, so the `never` cases of CONV-AC3 and CONV-AC4 belong to package tests that set `ctx.settings` themselves (as `test_temperspec.py` line 61 does for the outcome check). A new must-pass fixture with a well-formed section is harmless, and the engine asks for no fixture per criterion (it asks for one pair per check, `selftest.py` lines 133-150).
- The note's shape is the rule's and the plan's to fix. The spec says what the note says, not its markup. Shape assumed, so that the rule, the parser, the prompt and the tests agree:
  - A new subsection of `task-notes.rule.md` after "The quick lane", with its own example, the way the quick lane's `## Change` section is described; the standard triage example, and with it the installed fill-in template, stay as they are. The parser reads the section as optional, as it reads `## Change`.
  - A section `Owner decisions` between `Gaps` and `Route`, required under `never`, holding `None` or one list item per owner decision.
  - Each gap row ends with `Findable` or `Owner decision`; a row that ends `Covered by <ids>` is findable with no extra word, since a spec already answers it.
  - An entry names its gap id and the question, then nested items for the options (labelled `a)` to `d)`), the default (a label) and the cost, for example:

    ```
    - G2: Which exit code does a missing config file give?
      - Options: a) 2, as the other usage errors; b) 1; c) 78
      - Default: a
      - If wrong: a script that tests for 1 sees another code; one constant and one spec line change
    ```
  - The sections in a note stay `Task`, `Acceptance criteria`, `Existing documents`, `Gaps`, `Owner decisions`, `Route` and, in the quick lane, `Change`; `headings_missing` already ignores a heading it does not ask for (`specfmt.py` lines 95-104).
- The default is the safe option (assumption). The research note has triage write "the default it would take" (line 30) and has `blocking` ask only "when a decision has no safe default" (line 41). The spec requires only that the default is one of the options. The prompts should say: the option that changes the least of what exists and is the cheapest to undo, for triage's defaults and for the question discovery meets that the note does not list (CONV-B5 words it the same way).
- The new gate criterion `ts-tri-owner`. Every finding of the triage check names a criterion of `outcome.json` (`checks.py` lines 1-4), and a row of the triage spec must equal its criterion's text in `outcome.json` (`docs_check.py` lines 97-101), so the check's findings need the new row, which is in `triage.spec.md` line 17. The code step adds the same text, word for word, to the triage criteria of `outcome.json` after `ts-tri-covered` (lines 398-408), with `verified_by` `check`, `verifier.check` `tgwf_temperspec.checks:triage_check`, severity `blocker` (an incomplete sort lets an unattended run guess without saying so), a `check_method` and `source` `created`, raises `revision` to 15 (line 3) and appends its entry to the end of `revisions` (the last entry, revision 14, is at lines 1411-1416). The row is added in this step, as `ts-spec-fresh` was in i67; between the two steps the docs check reports drift as a warning, as it did then.
- No judge criterion and no new seed. The task asks that the triage judge's seeds keep passing. The judge criterion that the research note suggests (each question could not be answered from the repository, line 31) would need seeds graded by a signed-in judge (README lines 60-67, rung 8), which a cloud run cannot do. See the second open question.
- The prompt criteria are package tests, not gate criteria. CONV-AC2, CONV-AC6 and CONV-AC7 are proved by tests that read the prompts and briefs, as JRD-AC4 to JRD-AC8 are, each test carrying its criterion's id. They are not added to the gate's `PROMPT_SAYS` list (`checks.py` lines 69-86), which would need a criterion of `outcome.json` for each; the plan may add one if it wants a guard at every run. The prompts name the value as `{settings.conversation}` and put the `never` instructions under "only when it is `never`", since a prompt cannot be cut by its value.
- A default is an assumption, not a decision. `decision.rule.md` (line 46) leaves a decision only a person can take to the person and has no record written for it, so under `never` discovery writes no decision record for a defaulted owner decision. It writes the default's behaviour into the spec and holds no open question for it in the spec, because the plan step stops early on a spec with an open question the design depends on (`prompts/plan.md` line 20). The run lists the default for the owner to confirm.
- A task with no acceptance criterion still ends blocked under `never` (third scenario of CONV-B5). It is not an owner decision: the task states nothing to take a default of (`task-notes.rule.md` line 42, `prompts/triage.md` line 18).
- A question that a later step meets and the triage note does not list (second scenario of CONV-B5). Discovery takes the option that changes the least and writes the question, the options and the option taken among the hand-off's open questions with `Until answered: <option>`, the form earlier hand-offs already use. The description already lists the open questions of the hand-off (`summary.py` line 104), so the default is visible, under that heading and not under `Assumptions to confirm`. See the third open question.
- The description's block. `Assumptions to confirm` lists each owner decision of the triage note with its question, default and cost, built with no model like the rest of the description. It is not clipped: the other sections keep their first 14 lines (`MAX_LINES`, `summary.py` lines 17, 93, 99 and 107), and a block that cut owner decisions would hide guesses, which is why CONV-B7 has 16. With `None` the description says the run took no default, so that the owner of a night run can tell a run with no guess from a run on `blocking`. Where the block sits is the plan's; the owner acts on it, so right after the task's acceptance criteria is suggested.
- Not graded here: that the sort is right (a question wrongly sorted as an owner decision becomes a default in a spec instead of an answer found), and that discovery followed the default. The guards are the check (the shape), the description (every default is listed) and the owner reading the pull request.
- No decision record and no research note. The triage listed four spec gaps and no `decision needed` or `research needed`; each choice above is answered from the documents and code cited.
- No "Not built yet" line names #60 (searched the package's specs, README, rules and docs), so there is none to remove. The status line of `next-features.rsrch.md` (line 8) lists what is built and will not name `never`; it is history, and the plan may update it under Docs to update.
- Linked specs. The new spec links the overview, `triage.spec.md`, `discovery.spec.md` and the engine's spec on settings, and contradicts none of their rows: an owner decision is a gap and routes to discovery, so `ts-tri-gaps` and `ts-tri-route` hold; a gap closed on a default has its document, so `ts-dis-gaps` holds. The engine's specs are not changed.
- Files that change in the code step, all outside this step: `rules/task-notes.rule.md` (the subsection and example above; the hand-off bullet on open questions gains that under `never` each open question carries `Until answered` and none ends a step blocked), `prompts/triage.md`, `prompts/discovery.md`, `workflow/temperspec/specfmt.py` (the parser), `checks.py` (`triage_check`), `summary.py`, `__init__.py` (the setting), `outcome.json`, tests and fixtures under `tests/`, `README.md` (the triage row and the description paragraph), and `stamp.json` through `tempergraph author verify plugins/temperspec-tgraph`, whose model-free rungs the README names (lines 60-67); a changed prompt or `outcome.json` leaves the `stamp` rung stale until that runs again.

## Open questions

- Should `always` be declared now? Options: (a) declare `never` and `blocking` only, and refuse `always` (chosen); (b) declare `always` as well and let it behave as `blocking` until questions are built, which keeps the research note's three values and makes the setting accept a value that does nothing. Until answered: (a). It does not block planning: (b) is one more choice in the declaration and one changed sentence and scenario of CONV-B1.
- Should a judge criterion ask whether each owner decision could have been answered from the repository (the research note's guard against triage asking too much, line 31)? Options: (a) not in this task (chosen); (b) add it, with a met and an unmet seed, once a signed-in judge can grade them. Until answered: (a); the triage judge's brief and seeds stay as they are. It does not block planning.
- Should a default that a later step took be listed under `Assumptions to confirm` with triage's? Options: (a) no, among the hand-off's open questions, which the description already lists (chosen); (b) yes: discovery marks such a line in the hand-off's `Decisions` and the description lifts it into the block, which adds a second source and a mark to parse; (c) discovery adds an entry to the triage note's `Owner decisions`, which edits a note the triage gate has already passed. Until answered: (a). It does not block planning: only the last scenario of CONV-B7 and one criterion change under (b).
