# Hand-off: i106

## Problem

A step session starts with the repository's own settings only, so rule files that only the machine holds (`~/.claude/rules/temperspec/`) are neither in its instructions nor readable by it: they lie outside its working directory. Prepare copied nothing when the machine held them, and the step prompts said such files were already in the session's instructions; the TS-L3 trial failed the form checks at four steps that way and passed with the rule files in the repository. The task takes option 1 of the issue as an assumption: prepare copies the rule files into the repository whenever the repository lacks them, even when the machine has them, which reverses PNR-B3.

## Decisions

- Option 1 is taken as the task states it: an assumption, because the owner has not chosen between the issue's options. Prepare copies the rule files into `.claude/rules/temperspec/` whenever the repository lacks them, even when the machine has them (PNR-B7), and copies nothing into a repository that holds them, also when the machine holds them too (PNR-B3). This answers the third open question of the i72 hand-off in favour of its option (b). The conversation value of this run was not given (the placeholder in the prompt was unfilled), so the only owner choice closed on a default is the one the task names.
- What "the repository holds them" means is unchanged: its own `.claude/rules/temperspec/` folder (kept as it is, even when partial), or a folder outside the folders of copies and fixtures that holds all six. Only the machine's folder stops counting. The third scenario of PNR-B3 puts a partial own folder beside a machine that holds the full set, so that an implementation cannot complete a repository's own folder from the machine.
- What is copied is what prepare copies today: the plugin's own rule files and the templates written from their examples (PNR-B7 says "every rule file temperspec ships"). A machine's copy that differs, for example one with local edits, is not carried over; see the second open question.
- The block (PNR-B4): prepare copies before it writes the block, so the block names `.claude/rules/temperspec/` or the folder of all six and never the machine's folder; the "(installed for the whole machine)" form no longer exists. PNR-B5 and PNR-AC7 are not edited: in the machine case prepare writes the templates, so the block names `docs/templates/`, which PNR-B5 already says.
- The prompts (SRC-B10): the claim that machine-wide rule files are already in the session's instructions goes, and so does the instruction not to open a machine-wide copy, which existed for that claim (the `tool_access` pause recorded in `plugins/temperspec-tgraph/docs/plans/live-checks.plan.md` line 30). The prompts name only the repository; no warning about the machine's folder takes their place, since the rule files are in the repository and the block names them. SRC-B2 keeps its one result (open with the read tool, not by a search, when the repository holds the file) and the short discovery prompt's limit.
- The rule-file criterion (SRC-B3) is not widened. A repository that keeps all six rule files in a folder of its own and has no `.claude/rules/temperspec/` leaves the criterion not applicable, as before; its WHEN now says "whose `.claude/rules/temperspec/` folder holds none" in place of the false reason "installed for the whole machine". A repository whose rule files were only on the machine now gets the folder, so the criterion binds there, which is the point of option 1.
- The decision record is edited in place, not replaced: its decision (a check confirms from the session record that the rule file was opened) stands and only a premise it recorded changed. `decision.rule.md` leaves an earlier record unedited when a later record replaces it, and nothing is replaced here; `documents.rule.md` has a change that makes a document false change that document. No new record is written: the choice among the issue's options is the owner's, and the task records it as an assumption. The line numbers the Context bullet gives for the prompts are older than the prompts; they are not part of this change and were left.
- Not edited on purpose, for the plan's rows: the seven prompts, `README.md` (lines 13 and 55), `skills/setup/SKILL.md` (lines 8 to 14), `routing.py` with its docstrings and the tests below. Records stay as they are: the i67 and i72 notes and plans and `live-checks.plan.md`. `outcome.json` and the other specs name no machine-wide rule file (searched `plugins/temperspec-tgraph` for "whole machine", "machine-wide" and "already in your instructions"), so they need no row.
- Trace obligations for the plan: a test that carries the id and is not skipped for each of PNR-AC4, PNR-AC5, PNR-AC6, PNR-AC10, SRC-AC4, SRC-AC5 and SRC-AC13 (each is added, reworded, or proves an edited behaviour). The test at `tests/test_project_note.py` line 124 holds the old behaviour (nothing copied, the block names the machine's folder). It is replaced by the two cases of task criterion 3: the machine holds the files and the repository lacks them (PNR-AC10 and PNR-AC6), and the repository holds them while the machine does too (PNR-AC4).

## Open questions

- The owner has not chosen between the options of the issue. Taken: option 1, as the task states. Until answered: option 1. Another option would rewrite PNR-B3, PNR-B7, PNR-B4 and SRC-B10. A cost to know: in a repository that lacks the rule files, the run's own prepare commit, and so its pull request, now carries the rule files and the templates even when the machine already has them. It does not block planning.
- Which copy does prepare write when the machine holds the rule files? Options: (a) the plugin's own rule files, as prepare copies today; (b) the machine's files, which keeps local edits made to the machine-wide rules. Until answered: (a), the smaller change. It does not block planning.
