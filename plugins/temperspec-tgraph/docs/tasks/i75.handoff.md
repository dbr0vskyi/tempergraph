# Hand-off: i75

## Problem

Discovery and setup read one gap or one component after another in one long session, so they are the slowest document steps. The task makes each of them first start one read-only reading session for each gap or component folder, three at a time on the engine's concurrent map, and then run the step's one writing session on what they found; with no gap or one gap none starts, and no gate gains a second judge. The engine as built cannot hand the writing session what the reading sessions found, so one engine behaviour is specified first (VAL-B9).

## Decisions

- No way to give the writing session the findings of a read-only map, so VAL-B9. A read-only item hands on one line, a `value` (VAL-B5), kept as `<key>[<item id>]` (`nodes.py` lines 654-658). When the map ends the plain key holds the last item of the list (`nodes.py` lines 1026-1030). A template names `name` or one dotted pair (`template.py` line 16), the dotted pair only for a sub-workflow unit (`validate.py` lines 917-922; CON-B8, SWF-B12), and a script's callable gets the unit, the folder and the request only (`nodes.py` lines 1116-1119). So acceptance criteria 1 and 2 ("from the items' findings") need a capability the engine lacks; the task's "Engine status: Ready" is true of the concurrent map and the cap (R3-T3.2 and R3-T1.1 in `third-release.plan.md`) and not of this. VAL-B9 says that a later template that names `{<key>}` gets one line `<item id>: <value>` for each item in list order, or `none`. It leaves CON-B8, SWF-B12 and the plain key in the state as they are; the decision record compares it with a dotted field, a script or check that composes a file, writing items and the state root. A search of `plugins/` and of the engine's tests found no workflow, built-in workflow or test that names a map's key in a later template, so the old rendering (the last item) breaks nothing known. Per decision 0129 the need is written in this package first (PRL-B11) and the plan adds a line under "Limits" in the README; the engine change is general, names no workflow, and is tested by an engine fixture (VAL-AC5). The code step builds it first, because the package's units depend on it.
- A component is a component folder (PRL-B4). The writing session decides the components of the specs after it has read, so a survey per final component is not possible; the survey is per top-level folder that is not hidden, a dependency folder, a build-output folder or the documentation folder, which is also the unit `ts-set-cover` counts. The writing session may join or split folders.
- The lists are made by rule, with no model. A map's list is a file that an earlier unit produced (MAP-B7), and `prepare` produces values, so a model-free script unit writes each list: for discovery from the gap rows of the triage note (`specfmt.parse_triage(...).gap_rows` is only their count, so the plan adds a function beside it that returns the rows, read with `GAP_ROW` at `specfmt.py` line 57), for setup from the folder names. The lists are generated files: write them under `.tempergraph/` in the workspace with a `.gitignore` of `*`, because `commit_step` excludes that folder (`routing.py` line 139) and the root `.gitignore` ignores it, so no generated file is committed. Item ids are the gap numbers `G<n>` and the folder names cut to the engine's id pattern (`mapping.py` line 26), the exact name in the item's text.
- One gap, no reading session (PRL-B2, PRL-B5). Acceptance criterion 4 allows one item for one gap; with one subject nothing can run at the same time, so none is the cheaper reading. The list script returns no item for fewer than two subjects and the map has `on_empty: skip` (MAP-B7), so it passes with no session. Setup follows the same rule, which criterion 4 does not mention; without it a repository with one folder would stop the map, the default `on_empty` being `stop`. A triage note with more than 50 gap rows, or a repository with more than 50 component folders, meets the engine's own stop (MAP-B5; `max_items` is at most 50); the second open question of the new spec records it, and a task that large is split first.
- A return to discovery runs the writing session alone (PRL-B3). The plan, expand and code gates name `discovery` as a back target (`__init__.py` lines 138-161). It stays the name of the writing step and the reading unit gets another name, so the map is not entered again; BUD-B4 clears only the target and the units after it, so the findings stay and the writing session is briefed with them again (PRL-B11), PRL-B12 telling it to confirm them. The map's list must come from a unit on every path into the map (`validate.py` lines 508-515 and `_dominates` at lines 1078-1097), so the routes after triage and after the short visit name the list script as the entry to the full discovery, and `setup_route` names the list script of setup. The short visit starts no reading session (decision 0003).
- Three at a time and 1,500 characters. Three is the engine's default `concurrency` (MAP-B7) and 1,500 characters is the first value for a finding (PRL-B9); neither has a run behind it. The cap reserves for the sessions in flight (BUD-B12).
- Each reading session has a judge of its own (PRL-B13). The validator refuses a model step whose gate has no judge or no criterion (`validate.py` lines 754-757), a map's step included (lines 439-441), and a map gates each item on its own (MAP-B7). So a visit with N reading sessions holds N judge sessions beside the judge session of the writing session. They are the narrow judges of per-item gates that decision 0005 names for keeping judging cheap; their criteria are the form of the findings (a check first, JDG-B1) and whether they answer the subject. A session that ends with no findings line fails the output contract (VAL-B5, VAL-B6); a failed item runs again alone within its own retry budget (MAP-B10), and `on_budget_spent` is `stop`, as in every step of the package.
- Judges of one gate (acceptance criterion 3). A gate holds one judge (`contracts.py` lines 155-167; JDG-B10) and decisions 0005 and 0063 defer a panel of judges. Each of the seven step gates of the package declares one, and so does its outcome gate. Both conditions of the criterion hold, so the first open question of the new spec records the default and no judge of an existing gate changes (PRL-B14). The judges of the reading gates follow from the engine's rule above, not from a change to how a gate judges. No decision record is written: the task states the outcome.
- Tools of the reading sessions (PRL-B6). Read tools only. Discovery's sessions also hold web search and fetch, because a `research needed` gap is answered from public sources and the engine counts both among the read-only capabilities (`contracts.py` lines 566-567); the reading prompt limits the web as the writing prompt does, to reading a public source a research note cites. This is an assumption (open question 6).
- The earlier-layout specs keep their layout. `discovery.spec.md` and `setup.spec.md` have criteria rows and no behaviours, and no row became false, so each got one sentence and a link; the behaviours and their criteria are in `parallel-reading.spec.md`.
- What `ts-dis-narrow` binds. `PROMPT_SAYS` matches `prompts/discovery*.md` (`checks.py` line 70), and `test_every_discovery_prompt_says_to_read_narrowly` (`test_temperspec.py` lines 280-288) iterates the same glob and also asserts the text `## reading list`. A reading prompt named `discovery_*.md` would have to carry that heading, which a session that writes no hand-off cannot use. Name the reading prompts outside the glob (for example `prompts/read_gap.md`) and give the discovery one the three phrases anyway, because the criterion says "every discovery prompt"; or change the glob and the test.
- Sizing. Each new unit states a model, an effort and a reason (decision 0002). First assessment, with no run behind it: `medium` and `medium` for both reading units and for their judges, because each reads one subject, writes nothing and is confirmed by the writing session (PRL-B12). The discovery writing session stays at `max`. The sizing tests loop over `kind == "step"` only (`test_temperspec.py` lines 496-525) and `UNITS` in `test_judge_reading.py` (line 25) lists the seven judges by name, so the plan extends both for the map units.
- What the engine's generated tests ask of new units (acceptance criterion 5). `docs_check` wants a spec `docs/specs/NN-<unit>.spec.md` (two digits, 10 and up are free) for every unit in the order, the unit's outcome criteria as `- [ ] id text` rows, and every relative link under `docs/` resolving (`docs_check.py` lines 66-113). `diagram_current` wants `diagram/model.json` and `diagram/workflow.md` regenerated after the units change (`selftest.py` lines 22-35). `standin_run` answers each session at most once by the unit that asks and holds no reply for a map unit (`selftest.py` lines 186-273; SCF-B16). Its path here runs through setup (the stand-in `prepare` returns both values) and then the full discovery (the stand-in triage takes its first choices), so both reading maps are reached: either each list script's must-pass fixture holds an empty list, so each map passes with no item on `on_empty: skip`, or the engine's stand-in learns maps as a general capability stated in SCF-B16 first. Also, the blueprint states only `over` for a map (`blueprint.py` lines 151-153; `compare.py` lines 103-106), so `mode`, `concurrency`, `on_empty` and `max_items` live in `__init__.py` alone and the package's tests pin them; `outcome.json` takes a revision entry with each change to it.
- No "Not built yet" line names issue 75 (searched the package's specs, README, docs and rules; line 43 of the README is about per-phase coding), so none is removed. No research note is written: the unknowns are answered by the code cited above.
- Not edited on purpose: `plugins/temperspec-tgraph/docs/specs/discovery-short.spec.md`, `triage.spec.md` and `setup-route.spec.md`, `outcome.json`, the prompts and the judges (the plan and code steps own them), and the overview's open questions.

## Open questions

- Is the engine capability (VAL-B9) acceptable to the engine's owner? Options: (a) the plain field renders every item's value (chosen; VAL-B9 and its decision record); (b) a dotted `{<map unit>.<key>}`, which changes CON-B8, VAL-B8 and SWF-B12 and their tests to keep an old meaning nothing uses; (c) a script or a check composes a findings file, which needs a change to the context of scripts anyway and puts a generated file in the repository. Until answered: (a). It does not block planning; it is the first phase of the code step.
- Should reading sessions start for two gaps, or only for three or more, as the research note's table of case A suggests? Options: (a) two (chosen: acceptance criterion 4 excludes zero and one only); (b) three, which saves two sessions for a task of two gaps and which the acceptance criteria do not forbid, changing PRL-B1, PRL-B2 and PRL-B5. Until answered: (a). It does not block planning.
- How coarse is a component folder? A repository whose code sits under one top-level folder gets a reading session that reads nearly everything; this repository is one, with its code under `plugins/` beside an `assets` folder of images, so setup here would start two sessions and one of them would read it all. Options: (a) top-level folders only (chosen); (b) also open a folder whose subfolders each carry a build file. Until answered: (a). It does not block planning.
- Should a reading session be judged at all? The engine says yes for every model step (PRL-B13). Options: (a) one judge session for each reading session, with the form of the findings and their answer to the subject as criteria (chosen; no engine change, N more judge sessions for a visit, run beside their own items); (b) an engine capability that lets a read-only step's gate hold a check and no judge, which changes the engine's rule that an independent judge grades every model step (decision 0005) and needs the engine's owner; PRL-B13 would then say no judge session starts for a reading session. Until answered: (a). It does not block planning.
- Does the owner want the judges of one gate to run side by side once the engine can? The first open question of the new spec holds the default (one judge for each gate) and what reopens it. It does not block planning.
- Should the reading sessions of discovery hold the web tools? Options: (a) yes (chosen; the research of a `research needed` gap runs beside the other gaps); (b) no, and the writing session does all the web reading, which keeps the readers to the repository and costs the time that the web reading takes. Until answered: (a). It does not block planning.
