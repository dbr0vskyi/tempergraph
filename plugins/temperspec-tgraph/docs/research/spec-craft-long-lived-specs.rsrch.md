# How do spec-driven tools with long-lived specs write a spec, and what should temperspec take?

## Problem statement

temperspec keeps one living spec per capability and edits it in place (spec-anchored, in Böckeler's terms; see [sdd-tools-comparison.rsrch.md](sdd-tools-comparison.rsrch.md), comparison 1). The owner found that its runs write specs as literal descriptions of a task instead of general rules, and asked what other tools do about the craft of the spec itself: what a spec holds, how it is worded, at what level of detail, how it stays general and durable, how it is created and updated, and which checks keep its quality. The owner asked to weigh most the tools whose specs live on after a change, as temperspec's do.

The earlier comparisons looked at features ([sdd-tools-comparison.rsrch.md](sdd-tools-comparison.rsrch.md)) and plans ([plan-format-review.rsrch.md](plan-format-review.rsrch.md)), not at how a spec is written. Two open pull requests cover neighbouring ground and are not repeated here: #118 (`specs-state-durable-meaning.rsrch.md`, why task text gets into specs, and a "General rules, not cases" section, a discovery extract step, the `ts-spec-literal` check and a judge criterion) and #121 (`spec-extraction-from-existing-code.rsrch.md`, extracting specs from existing code). Where a finding below supports one of their proposals, the conclusion says so and points at it.

## Key findings

### F1 The long-lived tools keep two kinds of document: the truth, and the change `confirmed`

OpenSpec splits `specs/` ("Source of truth. How your system currently works") from `changes/<name>/` (proposal, design, tasks, delta specs). The why goes in the proposal; the delta says "(Previously: 30 minutes)" and a removed requirement carries "**Reason** and **Migration**", but only the requirement text is merged into the main spec at archive. Tessl's spec-as-source tile keeps history in `.handoff/HISTORY.md`, one line per state change, never in the spec. cc-sdd's steering rule says the same for project memory: "Steering files are project memory, not exhaustive specifications." temperspec already has this split (triage note and hand-off against spec, documents rule 1 and 7); #118 F5 and F7 found the same and its "General rules, not cases" section acts on it.

### F2 A spec is named and bounded by a durable capability, never by the work `confirmed`

OpenSpec's proposal instruction: "Name each capability for a durable system behavior (for example, `user-auth`), not the work in this change (for example, `add-login-endpoint`). Choose a cohesive boundary that can own related requirements as the system evolves; avoid broad catch-all capabilities." cc-sdd's guide makes the boundary the main value of a spec: "what this spec owns, what it explicitly does not own, which dependencies are allowed, what downstream work may need revalidation if this spec changes." Tessl: "One spec per logical unit of functionality — don't combine unrelated features." temperspec's rule says "A spec states what one capability does" but gives no naming test and asks for no boundary; the Purpose is "what the capability is for and who depends on it".

### F3 Before writing, the tools look up the whole capability inventory and reuse an owner `confirmed`

OpenSpec tells the agent to "Research existing specs before filling this in": list every capability, read each related one's purpose and requirement texts without scenarios, "Reuse an existing capability's exact path instead of introducing a near-duplicate name", then "read each relevant spec in full, including scenarios" before deciding what is covered. cc-sdd's discovery routes each request to one of five outcomes: extend an existing spec, implement with no spec, one new spec, several specs, or a mix. temperspec's triage searches for each concept and its discovery reads what the triage note names; nothing gives either step a cheap view of every capability and its rules, so the owner of a rule is found only if a search happens to hit it. #118 F1.2 (one rule written twice, in MAP and CTS, while WSP owns it) is what a missing inventory produces.

### F4 "If behaviour did not change, no spec changes" is stated, and checked both ways `confirmed`

OpenSpec rejects a change with no delta unless the change declares `skip_specs: true`, which is allowed "only when no spec-level behavior changes (pure refactor, tooling, docs)", and adds: "Do not invent a requirement just to satisfy validation." It also rejects `skip_specs` when spec files exist. Its quick test for content: "If implementation can change without changing externally visible behavior, it likely does not belong in the spec." cc-sdd's golden rule for steering: "If new code follows existing patterns, steering shouldn't need updating." temperspec has the first half (`ts-collateral` fails an edit to a spec in which no behaviour or criterion changed; the quick lane needs no spec change). It has no counterpart to "do not invent a requirement to satisfy" a check, and discovery's line 4 ("Every acceptance criterion of the task that a gap concerns must be provable from the behaviours you wrote") pushes the other way, as #118 F3 found.

### F5 Requirement text is short and single; examples and edge cases go to scenarios `confirmed`

OpenSpec warns at 500 characters of requirement text (`MAX_REQUIREMENT_TEXT_LENGTH = 500`; `--strict` fails it): "Move examples and edge cases into scenarios, or split it into separate requirements that each state one behavior." Every requirement must contain SHALL or MUST and have at least one scenario with a WHEN or GIVEN step and a THEN step. cc-sdd's EARS rule: "testable, verifiable, and describe a single behavior." temperspec has "One behaviour, one result", but no length limit on the sentence.

Measured on this repository (first line under each behaviour heading): the engine's 1,392 behaviours have a median of 339 characters and a 90th percentile of 1,023; 499 are over 500 and 471 hold a semicolon or two or more ", and". The longest, SCH-B27 "Verbs" (`83-schedules.spec.md` line 150, 2,229 characters), lists every `schedule` sub-command with its options in one sentence: a contract table written as one behaviour. temperspec's own 107 behaviours have a median of 206, a 90th percentile of 328 and none over 500. So the long sentences come mostly from the migration of the engine's contract sections (R-150), not from temperspec runs, but nothing stops a run from adding to them.

### F6 Long-lived tools use more than one requirement pattern `confirmed`

cc-sdd (and Kiro, whose format it copies) uses all five EARS patterns: event (`When`), state (`While`), unwanted behaviour (`If … then`), optional feature (`Where`) and ubiquitous (`The <system> shall`). OpenSpec needs only SHALL or MUST and RFC 2119 strength words. temperspec allows only `WHEN … THE … SHALL`, so a state rule or an invariant has to be bent into an event. #121 left this as an open question for invariants.

### F7 Scenarios are a few key examples that illustrate a rule `confirmed`

OpenSpec: scenarios "provide concrete examples that can be verified … testable … cover both happy path and edge cases". Specification by Example asks for key examples that cover the main concepts and each important boundary, not every case, and warns against over-specifying. Gherkin's `Rule` keyword groups scenarios under the business rule they illustrate. In the engine specs 1,081 behaviours have one scenario and 68 have four or more. #118 already proposes at most three scenarios, never a test fixture; these sources support it and add one point: the examples should sit on the rule's boundary (29 against 31 minutes in the rule's own example), which is what makes them key.

### F8 Tessl ties each spec to its code and its tests, and checks the tie mechanically `supported`

A Tessl spec's front matter lists `targets`, the files it describes, and its body puts `[@test]` links next to the requirements they prove. `spec-verification` checks that targets and test links exist, runs the linked tests, and looks for drift both ways: "Behavioral changes in code not mentioned in the spec", "Newly added tests without matching requirements (or vice versa)", "New code paths in target files that aren't covered by any requirement". The spec-as-source tile adds a rule that a change to a target file needs a change to its owning spec in the same commit or pull request, enforced by `check-target-ownership.sh` (excerpts only). temperspec links the other way (a test carries a criterion id, `ts-traced`) and its code gate judges changed paths against specs; it has no map from a code path to the spec that owns it, and so no cheap signal that a code change touched a capability whose spec did not change.

### F9 The checks that look at wording are separate from the checks that look at code `confirmed`

Spec Kit calls its spec checklists "unit tests for English": they test "whether the requirements are well-written, complete, unambiguous" and "NOT whether the implementation works". Its `analyze` pass looks for near-duplicate requirements, "vague adjectives (fast, scalable, secure, intuitive, robust) lacking measurable criteria", unresolved placeholders (`TODO`, `TKTK`, `???`), underspecification and "terminology drift (same concept named differently across files)", each with a severity. Kiro adds a requirements analysis step before design that flags acceptance criteria open to several readings, contradictions and gaps (excerpts only), and turns requirements into correctness properties tested by property-based tests that point back to the requirement they validate (IDE only). temperspec's discovery judge grades coverage, observability and scope (`judges/discovery.md` lines 10-12); the outcome gate judges agreement between specs. No check or criterion looks for an ambiguous or vague behaviour, a placeholder, a near-duplicate of another spec's behaviour, or a term named two ways. The vague-word ban in `spec.rule.md` covers acceptance criteria only; measured, 8 engine behaviour sentences and none of temperspec's use such words, so this matters less than F5.

### F10 Long-lived specs rot where no change touches them `supported`

The earlier comparison cites a study that found 81.5% of spec files are never touched after their first commit. Tessl runs `spec-verification` "periodically as a maintenance check", not only after a change. Spec Kit's `converge` and OpenSpec's `verify` are per change and do not block. temperspec checks alignment only for the specs a run changed or links.

### F11 GSD 2 keeps one project-wide requirements contract, rendered from records `confirmed`

GSD 2's `.gsd/REQUIREMENTS.md` is "the explicit capability and coverage contract for the project" and lives across all milestones. Its guidelines: "Keep requirements capability-oriented, not a giant feature wishlist", "atomic, testable, and stated in plain language", "one accountable primary owner". Three points bear on spec craft:

1. **The file is generated.** Requirements are saved as records with a tool and the file is rendered from them; the decisions register says "Do not edit this file … to reverse a decision, save a new one that supersedes it." This is documents rule 3 (an index is generated) applied to the contract itself.
2. **Where a requirement came from is recorded.** Each has `Source: user | inferred | research | execution`, and "Research may suggest requirements, but research does not silently make them binding": candidates from research or inference are shown to the person to confirm, defer or reject. The discuss prompt adds "Codebase facts are context, not decisions."
3. **What is out is written down.** An `Out of Scope` group holds requirements that are explicitly excluded, each with "what scope confusion this prevents".

GSD 2 also keeps status (`active`, `validated`, `deferred`), "why it matters" and owning slices in each requirement. temperspec rejects all three in a spec (documents rule 1, no status; a reason goes to a decision record), and the owner ruled that out, so they are not taken. The source of a behaviour is the same idea as #121's evidence ranking (`tested`, `read`, `stated`), extended from code to the task.

### F12 What temperspec already does that the others do not `confirmed`

No other tool has a one-line fixed pattern plus scenarios plus separate numbered criteria with test traceability, a size cap per spec, links by id only, or a check against collateral edits. OpenSpec's MODIFIED delta copies the whole requirement block, so a change cannot quietly drop a scenario, but it pays for that with a merge step; temperspec's direct edit is reviewed in the diff instead. None of the findings argues for deltas, front-matter metadata or an interface section, all of which the owner ruled out (`temperspec-principles`).

## Conclusions

Each recommendation names the finding it rests on and whether #118 or #121 already covers it. All of them change only the temperspec package (ADR-0129).

1. **Already covered by #118, supported here, no second version:** truth and change kept apart (F1); scenarios as illustrations, not fixtures, at most three (F7); no history or reasons in a behaviour (F1); replace discovery's "provable from the behaviours you wrote" (F4); the owning capability named in triage (F3). One addition to #118's scenario wording, from F7: a scenario sits on the rule's boundary, one case each side where the rule has one.
2. **Capability inventory, new (F3).** A generated, never hand-edited index (documents rule 3 allows it) of every spec's path, Purpose and behaviour headings, without scenarios, that triage and discovery read before they decide which spec owns a rule. Triage reuses an existing capability over a near-duplicate, as OpenSpec does. This gives #118's owning-capability column its source; build it with that column. Whether it is written to a file or printed by `specfmt` for the prompt is a plan choice.
3. **Name and bound a spec by its capability, new (F2).** Add to the spec rule: a new spec is named for the capability it owns, never for the task (no task id, issue number or work verb such as add or fix in its file name or title), and its Purpose says in one sentence what it does not own when a neighbouring spec could be mistaken for its owner. No new section: the boundary sits in the Purpose, which keeps the owner's ruling that every section beyond behaviours and criteria is in question. A model-free check on new spec file names can enforce the naming half.
4. **A length limit on the behaviour sentence, new (F5).** Add to the spec rule: the WHEN … SHALL sentence is at most 500 characters; detail goes into scenarios, and a sentence that lists several results or options is split. A model-free check warns on lines a run adds or changes (the engine's 499 existing long sentences would otherwise fail every run that edits their spec), and the existing ones are left to a separate cleanup, like #118's.
5. **Wording checks on behaviours, new (F9).** Extend the vague-word ban from criteria to behaviours and add placeholders (`TODO`, `TBD`, `???`, `<…>` left from the template), as warnings in the same model-free check as conclusion 4. Add to the discovery judge one criterion for ambiguity: a new or changed behaviour that an implementer could read two ways, or that names one concept by a term another spec defines differently, is a defect. This sits next to #118's judge criterion on general rules and could be the same criterion's second clause.
6. **Do not invent behaviour to satisfy a check, new wording (F4).** Add one line to the discovery prompt and the spec rule: a task with no behaviour change changes no spec, and no behaviour is written only to make a criterion or a check pass. It completes #118's change to discovery line 4.
7. **More requirement patterns, open (F6).** Admitting `WHILE <state> THE … SHALL` and `THE … SHALL always` (EARS state-driven and ubiquitous) would let state rules and invariants be written without bending them into events. It touches `specfmt`, the rule, the template and the tests, and #121 already left the same question open, so it is the owner's choice, asked once for both notes.
8. **Code-to-spec ownership, later (F8).** Tessl's target ownership is the one mechanism here that catches a code change whose spec was left alone. temperspec could build a similar map without front matter, from the plan's file rows and `ts-traced`'s test-to-criterion links, and warn when a run changes a file that tests of an untouched spec cover. It needs design and real runs to set its noise level, so it belongs in a GitHub issue (`area: temperspec`), not in #118's build.
9. **Say where an unrequested behaviour came from, new (F11).** A behaviour discovery writes that neither the task's criteria nor the owner's answers ask for (inferred from the code, from research or from a neighbouring spec) is listed in the hand-off with its source, not marked in the spec, so the judge and the owner see which rules were inferred. This is GSD 2's "research does not silently make them binding" in temperspec's form, and the task-side companion of #121's Evidence section; it fits #118's discovery changes. GSD 2's `Out of Scope` group supports conclusion 3's "does not own" sentence; a list of excluded behaviours inside a spec is not taken, since a spec states what the capability does.
10. **Periodic spec review, later (F10).** A scheduled docs-only run that checks one area's specs against the code and the tests, outside any task, is the only answer the sources give to rot in specs nobody touches. The engine already has schedules; this is a GitHub issue too.
11. **Not taken:** deltas and an archive step, front matter (`targets`, status), GSD 2's per-requirement status and rationale, Spec Kit's per-feature specs, success criteria as metrics, one question at a time in clarification (temperspec batches its one pause by design), and Kiro's property-based tests from requirements (a code-step matter, not spec craft). F12 explains why.

## Open questions

- Should the behaviour sentence limit be 500 characters (OpenSpec's) or set from temperspec's own measured 90th percentile (328)? Until answered: 500, as a warning on new and changed lines.
- Should the rule admit the EARS state and ubiquitous patterns (conclusion 7)? Same question as #121's; until answered: one pattern.
- Should conclusions 2 to 6 and 9 be built inside #118's build, or after it merges as a second pull request? Until answered: after, because 2, 6 and 9 extend what #118 changes and should start from its merged text.
- Should the 499 long engine behaviours be split in a separate cleanup, and in which order? Not settled here; it is engine documentation work and follows the engine's own process.
