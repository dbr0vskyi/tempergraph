# Plan: the outcome gate lists the hand-off, the plan and the code report, and reports the push

## 0. Hand-off

- Triage note: `docs/tasks/i110.triage.md`
- Hand-off: `docs/tasks/i110.handoff.md`
- Specs read: `docs/specs/outcome-gate.spec.md`, `docs/specs/00-overview.spec.md` (open questions after the two removals), `docs/specs/08-code.spec.md` (the `ts-code-commit` row, already reworded).
- Extra files opened beyond the hand-off's reading list, each for what the list did not answer: `rules/plan.rule.md` (the plan format); `tests/test_code_base.py` and `tests/test_spec_budget_and_moved_ids.py`, found by searching `tests/` for code that pins the deliverables, the assumptions, the text of `ts-code-commit` or a revision (none pins the first three; both only assert that the top revision equals the last entry's and is at least 8); `tests/test_temperspec.py` lines 80-90 (how a seed is run); `workflow/temperspec/checks.py` was searched for `_result(` callers. The other files of the list were read at the ranges it names.
- Why this design: the engine's release 2 already requires a deliverable only on a path that declares a unit producing it, and already puts `pushed` in the git facts, so no engine file changes. The three keys `handoff`, `plan` and `code_report` are what the units already produce, so listing them in `outcome.json` is the whole of OGT-B1 to OGT-B3: the engine's built-in check does the per-path requirement and the outcome judge's references come from the same list. The push is one line of the package's own outcome check, added through a new keyword of the shared `_result`, so the discovery and code checks and the seeds copied from them do not change; the line is evidence and never a finding, so a push cannot decide the result (OGT-B5).
- Assumptions recorded here and in `outcome.json`: (1) the outcome gate reports the push and never grades it, because the last stage pushes after the gate and a branch an earlier run pushed is already pushed at the gate; the owner did not settle it. (2) The four outcome seeds under `evals/calibration/outcome/` keep their copy of the evidence and their references (the triage note only): the push line and the new references change no verdict a seed expects, and grading the seeds again (rung 8 of the authoring ladder) needs the owner's signed-in `claude`, which a cloud run has not. (3) "revision 5" of the issue is read as the next revision, 11, as the triage note says. (4) `tempergraph author verify` is not on the repository's command list, so it is not listed; the engine's suite runs the same model-free rungs for the package (generated stand-in run, docs check, fixtures, diagram) and the package's own tests.
- Wording of the push line, fixed here because the spec leaves it to the plan: `The run's branch is pushed.` and `The run's branch is not pushed.`; a test for the pushed case therefore checks for `is pushed` and for the absence of `not pushed`.
- Not changed: the research note `stages-against-engine-releases.rsrch.md` (a record of what was true when written), the package README and `docs/README.md`, `diagram/`, `stamp.json` and `authoring.json` (rung 10 takes a newer outcome revision as the owner's re-approval; the pull request says the owner was away), and no "Not built yet" line exists for this issue.
