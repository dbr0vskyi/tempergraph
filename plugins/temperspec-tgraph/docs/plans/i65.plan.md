- Why this design: the discovery step fixed the layout and this plan follows it. The arms stay `single` to `code` and `phases` to `expand`, and `joins_at` stays `code_join`, because the engine refuses a `joins_at` that is the entry of an arm. The map `phase` sits in `order` between `expand` and `code`, takes its list from `expand`'s plan (`items_from` `("expand", "phases")` with an extractor), runs sequentially with the engine's default limit of 20 items, and each item commits through the `after` script. The code step is the join and keeps one prompt and one gate, so the quick-lane guard, the plan's upstream line and the proof table's commands stay there with no new gate.
- Item ids are `p<n>` from the number in the phase heading (PHC-B1). The map refuses a duplicate id (MAP-B8), so a heading with no number or with a number already used takes an id made from its position in the plan; the extractor's row states it.
- Owner questions with their defaults from the specs, none blocking: the commit message names the step and the task, not the phase; the map keeps the engine's limit of 20 phases (a longer plan stops the run at the map, naming the count); a phase that finds the plan at fault leaves the row unmarked and says so in its note.
- This change is kept to coding. The rule files and the prepare step are untouched (issue #106 edits them), so the phase prompt names no rule file and the phase step is not added to the rule-file check (SRC-B1, SRC-B2).
- The model-free authoring check `tempergraph author verify plugins/temperspec-tgraph` is not a plan command: the code session's allow-list holds no `tempergraph` command. The engine's suite loads the package and runs its rungs 1, 4 and 5 and its tests, and the generated diagram and stamp are written by that command's own run (never by hand); a row that cannot regenerate them stays unmarked and the code report says why.

## 2. Phases

### Phase 1: The phase items and the phase check

Goal: an expanded plan gives one item for each phase in plan order with the id `p<n>` of its heading's number (a position-based id when the number is missing or repeated, so no id repeats and the list never holds fewer items than phases), the text of each item holds the heading, goal and weight with the plan's and the triage note's paths, and the phase check reads only the rows of the item's phase (marks with dates, files changed in the run with kept marks left alone, each proved criterion carried by a test that is not skipped, no source file changed before the phase's test file, with the order criterion not applicable when no session record is given); proved offline on plan fixtures by tests carrying PHC-AC1 (the names and the order), PHC-AC6, PHC-AC7 and PHC-AC8.
Weight: light

### Phase 2: The phase session's brief and judge

Goal: the phase prompt briefs a session on one phase (its heading, goal and weight, the plan's path and the triage note's path) to build only the rows with an empty Completed cell, tests first, run only the test files its rows name, change no file no row names, mark each built row with `✓` and the day's date, run no `git commit`, name no rule file, and end with a one-line note of at most 1,500 characters; the phase judge grades whether each row's change is in its file and no file outside the phase's rows changed; proved by tests that read the two files and carry PHC-AC2 (the brief names one phase and the paths), PHC-AC3 and PHC-AC4.
Weight: light

### Phase 3: The map is wired into the workflow

Goal: the workflow orders `expand`, `phase`, `code`, declares `phase` as a sequential map over the plan the expand step produced with the phase extractor, the phase check, its judge, the commit script in `after`, no line back, a model tier and effort with their reasons, and the summary "Build one phase of the plan, tests first, and commit it"; `outcome.json` holds the `phase` entry with the seven criteria of `15-phase.spec.md` word for word, a scale and two seed names for each judged criterion; the blueprint's units and flow name the map; the workflow validates and the engine's docs check finds no drift between the unit specs and `outcome.json`; the tests that pinned the old order, the units entered on `phases` and the units the report counts are rewritten and carry CDM-AC11, CDM-AC12 and PHC-AC14 (the validation half), and a scripted run of passing phases carries PHC-AC1, PHC-AC2, PHC-AC5, PHC-AC9 and PHC-AC11.
Weight: light

### Phase 4: The join and the failure paths

Goal: the code prompt gains the key of the phases' notes and the statement that, when the notes list the phases, the session builds only a row with no mark, sets the plan `completed` and writes the report with the notes' deviations, while on `single` and in the quick lane it lists no note and says no phase ran; scripted runs with stand-in executors prove a failed phase runs again alone with the earlier commits kept, a spent phase pauses at `phase.p2` before phase 3 and the code step, the code gate fails a command that exits 0 at the base and fails at the gate and reruns only the code step, the code gate keeps no finding about the files the phases changed and records the quick-lane guard not applicable, a plan not `completed` fails before any command, a claim against the plan, discovery or triage step goes back to that step, and a trip back to the plan runs every phase again with kept marks building nothing; they carry PHC-AC10, PHC-AC12, PHC-AC13, PHC-AC14 and PHC-AC15.
Weight: heavy (many-tests)

### Phase 5: The package says what is true now

Goal: the README's run table has a `phase` row and its `code` row and full lane say the code step is the join after the phases, the per-phase line is gone, the module docstring and the generated diagram (`model.json`, `workflow.md`) show the map, the stamp is the one the authoring check writes, and a test that reads the README, the docstring and the diagram carries AC 5; the package's own tests and the engine's suite pass with the engine's docs check finding no drift.
Weight: light
