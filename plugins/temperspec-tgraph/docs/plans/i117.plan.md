Searches, to find what pins the change: a grep of `judges/` for the open-question sentence (CONV-AC7), a grep of `tests/` for `revision`, `ts-tri-covered` and `ts-tri-gaps`, a grep of the engine's tests for `stamp` (only the engine's own stamp tests match), line counts of `checks.py`, `specfmt.py` and `outcome.json` by length band to estimate the bytes of the files the rows will name, and a grep of `docs/plans/` for how earlier plans (`i110`, `i112`, `i125`) treat `stamp.json`.
- Why this design: every behaviour is built in the package with no engine change, as the hand-off decides. The setting is a `choice` setting declared in `workflow()`; prompts read it as `{settings.conversation}`, the triage check reads it as `ctx.settings["conversation"]` and treats a missing value as `blocking`, and the last stage keys on the triage note's `Owner decisions` section because the finalizer holds no settings (CONV-B7). The note's shape (section `Owner decisions` between `Gaps` and `Route`; each gap row ends `Findable` or `Owner decision`; each entry has `Options:`, `Default:` and `If wrong:` items) is fixed by the hand-off's assumptions and written into the task-notes rule, the parser and the prompt so that the four agree.
- Why `complex`, by the signs of the plan rule. Measured on this plan: 4 phases, over the limit of 3 for `simple`; 3 verification commands; no heavy phase. Expected of the rows the expand step writes: about 14 task rows (7 code, 4 test, 3 docs or more), over 12; 10 or 11 files; and about 235 KB in the files and specs the rows name (`checks.py` about 68 KB, `outcome.json` about 68 KB, `specfmt.py` about 29 KB, the README, the task-notes rule, `__init__.py`, the two prompts, `summary.py`, the two specs), over 200,000 bytes. The phase count is the sign that this plan shows without rows. The first attempt packed the same work into 3 phases and called it `complex` on counts that only the rows would show; the four phases below are four goals, each with its own test row, not a split made to reach a number. The expand step writes the rows and the proof table.
- `stamp.json` is not a row. It is written only by rung 10 of `tempergraph author verify plugins/temperspec-tgraph`, a command that is not on the workflow's allowed list (`VERIFY` in `__init__.py`), so the code step cannot run it, as in runs i110, i112 and i125. A changed prompt and `outcome.json` revision 15 leave the stamp stale; the owner runs the command, which takes the newer revision as a re-approval, and the pull request says the owner was away. The code report says that the command was not run.
- Assumptions taken from the hand-off, all kept: values `never` and `blocking` only, with `blocking` the default and `always` refused (first open question, option a); no judge criterion and no new seed (second, option a); a default a later step took is listed among the hand-off's open questions with `Until answered`, not under `Assumptions to confirm` (third, option a); the new gate criterion `ts-tri-owner` is added to `outcome.json` with the text of the row in `04-triage.spec.md`, word for word; the `never` cases of the check run in package tests that set `ctx.settings`, because the engine's fixture rung gives a check no settings.
