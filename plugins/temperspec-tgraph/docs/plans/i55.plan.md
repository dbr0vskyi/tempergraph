# Plan: a reading budget and a quoted line for the judges of temperspec

## 0. Hand-off

- Triage note: `plugins/temperspec-tgraph/docs/tasks/i55.triage.md`
- Hand-off: `plugins/temperspec-tgraph/docs/tasks/i55.handoff.md`
- Specs read: `plugins/temperspec-tgraph/docs/specs/judge-reading.spec.md` (JRD-B1 to JRD-B6, JRD-AC1 to JRD-AC7), `plugins/temperspec-tgraph/docs/specs/00-overview.spec.md` (the line that names the new spec; it is already there), `plugins/temperspec-tgraph/docs/specs/08-code.spec.md` (the two alignment criteria; unchanged). No spec is edited by this plan: the new spec already states every behaviour below.
- Files opened beyond the hand-off's reading list, each for one fact: `plugins/temperspec-tgraph/rules/plan.rule.md` and `documents.rule.md` (the format; this repository keeps the rules there, not under `.claude/rules/temperspec/`); `plugins/tempergraph/engine/src/tempergraph/api.py` lines 115-127 and `contracts.py` lines 138-151 (to confirm that `Judge(...)` takes `timeout_s`); `plugins/tempergraph/engine/src/tempergraph/security/scrub.py` line 50 (`head_tail`, which keeps the first and last 1,980 characters of the 4,000 the judge gets); `plugins/temperspec-tgraph/docs/plans/live-checks.plan.md` lines 1-30 (the rows that the brief change makes stale); `plugins/temperspec-tgraph/README.md` (a search for "judge" and "brief"; nothing in it becomes false).
- Why this design: everything is package-side. The code gate (`code_check` in `checks.py`) puts the changed source files and the reading budget into its evidence, which is the only channel for run facts to a read-only judge (JDG-B11); the code brief tells the judge to read what the evidence lists; the quote-and-PARTIAL sentences go into the seven briefs and the outcome judge's stance. One judge per phase is not chosen: the code step is one session with one gate, so there is one judge to size (hand-off, Decisions).
- Plan choices on points the hand-off left to the plan, each a package-side value or format and not a new behaviour:
  1. A gate run with no base commit, or a `git diff` that fails, cannot count lines. The evidence then says so, states the floor of 10 files as the budget, and lists the source files from the changed paths with no counts, in the order the engine gives them. The quick lane's guard already treats a missing base the same way.
  2. The reading lines come right after the first evidence line and before "Changed paths since the run's base", and the file list is one compact line (`path count`, joined by `; `). The judge's prompt keeps the first 1,980 and the last 1,980 characters of the evidence, so the list sits in the kept head. The test of JRD-AC2 uses 40 paths of about 35 characters. A list that does not fit the head of a larger change is the engine's cap to change, as a separate engine task; the code report states it if it happens.
  3. An implementation choice, not a requirement and not a behaviour (no spec states a judge time limit, and this plan states none): the code judge's declaration gets `timeout_s=1800` (the gate check's own limit) and no other judge changes. Its reason is to support JRD-B3: a read of up to 50 files may not fit the engine's default of 600 s, and a judge timeout escalates (JDG-B4). It is one argument of the code unit's judge, with a comment that gives this reason, and it adds no check and no spec line.
  4. The constants (one file per 50 lines, floor 10, ceiling 50) are named once in `checks.py`. They are first values with no run behind them, so `outcome.json` gets an assumption line that says so, as for the quick lane's limits.
  5. The outcome judge's stance changes `outcome.json`, so its `revisions` list gets entry 8, as each earlier change did. Rung 10 takes a newer revision as the owner's re-approval (`stamp.py` lines 112-115); the pull request must say that the owner was away.
  6. Follow-through that is a plan choice and no requirement, each tied to the requirement whose change makes it needed: (a) the ten code seeds' copies of the check evidence (`evals/calibration/code/*/fixture/check.json`) follow the new evidence format, so that rung 8 grades with the evidence a run would give (serves R1, R2); (b) the new brief sentences are kept clear of the vague words and the accepting-brief rule of the engine's prompt lint, which the engine's suite already runs (serves R4, R5); (c) the `live-checks.plan.md` row for TS-L1 says rung 8 is to run again (serves R3, R4, R5; see Docs to update). None adds a behaviour.
- Not verified here: `tempergraph author verify plugins/temperspec-tgraph` (rungs 1 to 7 and 10 need no model) is not on the package's verification list and cannot be a plan command; the engine's suite already runs rungs 1, 4 and 5 for every package. The code report states whether the code session ran it by hand. Rung 8 (TS-L1) needs the owner's signed-in `claude` and is not run; `stamp.json` is written only by rung 10 and is not edited by hand.
- Open question carried on, which does not block: whether one file per 50 changed lines with a floor of 10 and a ceiling of 50 are the right first values (the alternative is one per 100 with a ceiling of 40). Each value is one constant.
