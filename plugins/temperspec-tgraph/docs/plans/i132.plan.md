## 2. Phases

### Phase 1: The engine renders a map's items in a later template

Goal: a template of a unit after a sequential or a concurrent map that names a key the map's step produces renders one line `<item id>: <value>` for each item in list order, and `none` for a map that ran no item, proved by an engine fixture that names no workflow (VAL-AC5).
Weight: light

### Phase 2: Discovery reads one gap at a time in parallel

Goal: a stand-in run of the full discovery step on a triage note of three gaps runs three reading sessions at most three at a time, then one writing session briefed with their findings in gap order; a note of no gap or one gap, the short visit and a return to discovery start none; the units, routes, prompts, judge, check, sizing and every package record the generated tests read agree.
Weight: heavy (large-context)

### Phase 3: The setup survey reads one component folder at a time in parallel

Goal: a stand-in run of the setup step on a repository with the folders `src`, `tests`, `docs`, `node_modules` and `.github` runs reading sessions for `src` and `tests` only and then the one writing session briefed with their findings; a repository with fewer than two component folders starts none; the list script, the reading unit, its prompt, judge, sizing and records agree.
Weight: medium

### Phase 4: One judge for each gate, and the README says what the package does

Goal: a package test pins that every gate holds one judge, the reading gates included, with one judge session for each attempt, and the README names the reading sessions and the engine need under Limits.
Weight: light
