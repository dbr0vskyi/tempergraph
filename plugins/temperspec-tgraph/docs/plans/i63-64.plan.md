## 0. Hand-off

- Files opened beyond the reading list, and why: the two rule files `.claude/rules/temperspec/plan.rule.md` and `documents.rule.md`; `plugins/temperspec-tgraph/docs/plans/i60.plan.md` and `i75.plan.md` (the format of an earlier change to this package and how it handled generated records); `plugins/tempergraph/engine/src/tempergraph/run/checks.py` (the fields of `CheckContext`, which the script's context is built from); `plugins/tempergraph/engine/tests/test_ask_wait.py` and `test_script_cache.py` (harnesses for an engine fixture and for a stand-in run with a pause and a deadline); `plugins/temperspec-tgraph/tests/test_parallel_reading.py`, `test_temperspec.py` and `test_code_mode.py` (what pins the routes and the unit order); `plugins/temperspec-tgraph/rules/task-notes.rule.md` (lines 76-105 and 139, the sort described only for `never`); `plugins/temperspec-tgraph/authoring.json` (its decisions).
- Why this design: the hand-off fixes the flow and the plan keeps it: `triage` routes a discovery-route note that is not `covered: yes` to a script `owner_questions`; the route `ask_route` sends a run with a question to the engine's ask unit `ask_owner` and any other to `read_gap`; `ask_owner` declares `on_deadline: defaults` and its check refuses a reading called `wrong`; the `answers` artifact reaches discovery and the last stage. The script needs the triage note and the conversation value, which the engine does not give a script's callable today (`nodes.py` `_run_script` builds its context with `unit`, `workdir` and `request` only), so Phase 1 is a general engine fix of that context, as SCR-B5 and RST-B25 already state, tested with an engine fixture that names no workflow (ADR-0129). The deadline is the unit key `ask_owner.deadline_s` with a default of 86,400 seconds (OWQ-B7), not a second declared workflow setting, because no engine mechanism binds a setting to an ask's deadline; AC 5 holds either way. The four open questions of the hand-off are taken on their option (a).
- Tests that the change makes false and that the expand step gives rows: in `plugins/temperspec-tgraph/tests/test_conversation.py` the two-value setting test, the refusal of `always`, the triage prompt phrases ("only when the value is `never`", "sort no gap", "no such section"), `test_a_note_with_no_sort_passes_unless_the_value_is_never` (its `blocking` case), the discovery prompt phrases for `blocking`, `test_no_unit_asks_a_person_and_no_gate_requires_a_sign_off`, and the README test; in `test_temperspec.py` lines 304-314 (`route_triage` returns `owner_questions` where it returned `read_gap`); in `test_parallel_reading.py` lines 100-103 and 660-661 (the triage route and its flow entry). `test_parallel_reading.py` runs the workflow on the default `blocking` with stand-in notes that list no owner decision, so those runs skip the ask and go on unchanged.
- Why `complex`, measured on this plan: 7 phases (limit 3) and 4 verification commands (limit 3). Expected of the rows the expand step writes: about 30 rows, about 12 test rows, 20 or more files, and over 200,000 bytes in the files the rows name (`checks.py`, `outcome.json`, `specfmt.py`, `test_conversation.py`, the README, the task-notes rule, `blueprint.json`, `diagram/model.json`). No phase is marked heavy.
- `stamp.json` is not a row: rung 10 of `tempergraph author verify plugins/temperspec-tgraph` writes it and the command is not on the code step's allowed list, so the owner runs it, as in runs i53, i55, i60 and i68. The model-free rungs are proved here by the engine suite (rungs 1, 4 and 5 through `tests/test_workflow_packages.py`) and by a package test that compares `blueprint.json` with the workflow (rung 2), as `test_parallel_reading.py` does.
