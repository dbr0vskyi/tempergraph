## 2. Phases

### Phase 1: The plan check records the plan's measured signs

Goal: the plan check sets seven facts on its result, from one helper in `specfmt.py` that `simple_overruns` also uses, each equal to the number the check measures for that sign, with `phases` the number of phases and `rows`, `test_rows` and `files` 0 for a plan with no task rows; proved on the plan fixtures of `evals/checks/plan/` and on plans built for the heavy and the reading-bytes signs.
Weight: light

### Phase 2: The switch replaces the hand-written route

Goal: `routing/code_mode.json` bounds `single` by the plan rule's limits, the workflow declares the switch `code_mode` with the join unit `code_join` after `code`, the plan unit routes to it by order, `route_plan` and its asserts are gone, and `blueprint.json` says the same; scripted runs show `single` in the zone `simple`, `phases` in the zone `complex`, a plan over exactly one limit taking `phases`, the fault arm for a missing fact and for an override file that is not JSON, the expand step skipped or entered first, and the quick lane taking no arm.
Weight: heavy (many-tests)

### Phase 3: The operator's arm and the report by arm

Goal: scripted runs started with the arm override take the arm named in both directions with `chosen_by: operator` and `would_choose` in the `route` record, and the report over runs of both arms counts the operator's run under the arm it took and divides a cell's cost by the sum of its phases; the package's README tells the operator the override and the report.
Weight: light

### Phase 4: The package says what the route does now

Goal: the README's run table and lanes, the module docstring and the generated diagram (`model.json`, `workflow.md`) describe the switch; the live checks hold the trial row TS-L3 with its command and pass criterion and no result, and an offline test holds the row to CDM-AC18 and CDM-AC19.
Weight: light
