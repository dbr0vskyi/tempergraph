## 2. Phases

### Phase 1: The engine's audit reads the entry for the repository's commands

Goal: the `host` layer takes `@repository` in an allow-list or a step's commands as the commands the target declares, with tests that carry AUD-AC8, AUD-AC9, AUD-AC10 and AUD-AC11 (a fixture workflow and fixture targets with an injected `which`, and a scaffolded package through `author verify`); no existing engine test pins the entry as a missing program, found by a search of the tests for `check-program-missing`, `toolchain-not-covered` and `prefixes`.
Weight: medium

### Phase 2: Steps and checks take their commands from the repository

Goal: the workflow's allow-list and the code step's commands name `@repository` and read-only git, the refusal text names `tempergraph.commands.json`, and the code step's own commands go to the repository's file, with tests that carry RCM-AC1 to RCM-AC5 over a fixture repository that is not Python (a `package.json`, its own commands file, a `check.sh` that exits 0 or 1) and with the existing tests that resolved a Python command in a scratch folder given a commands file.
Weight: medium

### Phase 3: Prepare writes the file and the gate does not count it as a change

Goal: `prepare` writes the Python commands file once for a Python repository that has none, leaves every existing file and every repository that is not Python alone, and the code gate lists a file prepare wrote apart from the run's changes, with tests that carry RCM-AC6 to RCM-AC9 (scratch repositories as `test_project_note.py` builds them, a quick-lane gate context as `test_temperspec.py` builds it).
Weight: medium

### Phase 4: The documents say where the commands come from

Goal: the README, the setup skill, the three prompts, the code judge's brief, `outcome.json`'s assumption and the audit ignore's reason in `tempergraph.json` say what is true after phases 2 and 3, and a test of the package keeps the overview free of the fixed-list question.
Weight: light
