This plan is written at `plugins/temperspec-tgraph/docs/plans/` because the repository keeps its specs, tasks and plans under the plugin's `docs/`.
- Open question of the hand-off, answered by its default: "the commit at which the phase was entered" is the commit at which the phase step was entered (option a), so the first list of a later phase also holds the files of the phases before it.
- Why this design:
  - Engine: the attempt record already carries `session_key`. It gains the list of the session keys of the attempts of the current visit of the same item: carried over from the previous attempt record when the attempt is not the first of its visit (`first` in `nodes.py`), plus its own key. `_check` reads each key's record with `read_session` and gives the check `visit_session`, the calls of those attempts in order. `visit_session` is `None` when the attempt's own record is `None` and when the check is a preview, and an earlier attempt with no record adds no call (VSR-B1, VSR-B2). The check worker's context document carries the new field.
  - Workflow, the steps' names: the only commit a step makes is `commit_step`, whose subject is `<type>(temperspec): <step> for <task>`. A step's entry is the newest commit of `base..HEAD` whose subject does not name that step (the base when there is none), so the commits the step made in this visit, and no other, count as made since the step was entered. The phase check and the join read the history with one `git log --name-only` over `base..HEAD` and one `git diff --name-only <entry>`. Both are read-only git commands, which the check already runs for `_kept_marks`. When the history cannot be read no path is known to be one that only earlier steps changed, so the first list holds every changed path and the second states that it holds none.
  - Evidence lines: `Changed since the phase step was entered: <paths>` and `Changed only by earlier steps: <path> (<step>, <step>), <path>`, each in ascending order of path and each ending `none` when it holds no path. The join writes the same two lines with `the code step`. The join uses them when a commit of the run names the step `phase`; any other run keeps its one line `Changed paths since the run's base`, which other tests pin.
  - The expand check reads `visit_session`, skips a row whose mark is kept (`_kept_marks` returns `""` for it), and makes one finding for all unopened rows. The engine clips a finding's message to 200 characters and the evidence to 8,000, so the finding names the rows and paths in its message as far as it fits and the evidence lists every row and path in full.
  - A changed criterion text is a new revision of `outcome.json`; the file's `revision` follows the last entry (`tests/test_spec_budget_and_moved_ids.py` line 278).

## 2. Phases

### Phase 1: The engine gives a check the calls of the visit

Goal: a check run after a retry attempt sees `visit_session` with the calls of the first attempt and of the retry in order, and `session` with the retry's calls only.
Weight: light

### Phase 2: The expand check reads the whole visit

Goal: `ts-exp-opened` fails once, naming every row and path that no session of the visit opened, and passes a retry that opens only the file the first session missed.
Weight: medium

### Phase 3: The phase check hands its judge the changed paths sorted

Goal: the evidence of a phase check holds the paths changed since the phase step was entered and the paths that only earlier steps changed with their steps, and the phase judge grades `ts-phs-scope` on the first list.
Weight: medium

### Phase 4: The join is handed the same two lists

Goal: the code gate after the phases hands its judge the two lists counted from the code step's entry, and a stand-in run of two phases with an earlier step's document passes every phase gate with no pause.
Weight: medium
