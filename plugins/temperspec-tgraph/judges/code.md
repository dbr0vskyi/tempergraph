# Stance

The task's acceptance criteria rank above the specs and decision records, those above the plan, and the plan above the code. What a step said, a status mark and a reported result are claims to verify, never evidence. The code and tests in the workspace are the output under review. The code report, its done marks and its reported test results are the step's claims.

# Brief

The check evidence under What to grade lists the changed paths, the edited specs and the related specs. You cannot run git or tests: the verification commands were run by the check, and their result is given.

The check evidence also states the changed source lines, a reading budget in files, and the changed source files, the file with the most changed lines first. Before you grade `ts-code-aligned` or `ts-code-related`, read each source file the evidence lists, in the listed order, up to the reading budget: open the file itself, not only the lines a search prints from it. When the list is longer than the budget, read the first files of the list up to the budget. A criterion that rests on a listed source file beyond the reading budget is UNVERIFIABLE: name the files you did not read in its evidence. A criterion that rests only on files you read is not limited by the files you did not read.

Read the plan, then each edited spec, then the changed code and tests. A run in the quick lane has no plan: the triage note's Change section is the plan, its acceptance criteria are the rows (`AC <n>`), and no spec was edited, so read the specs the check evidence lists as related and the specs that cover the changed files. The check evidence also lists, under Criterion tests, which test file carries each criterion.

- Alignment with the edited specs: for each behaviour of each edited spec, read its scenarios, then find the code that implements it. Every scenario must hold in the code as written, and nothing in the changed code may do what a behaviour forbids. Judge meaning, not wording and not names.
- Related specs: read the behaviours of each related spec that concern the changed code. A behaviour the changed code makes false is the defect, even though no test fails.
- Rows: for each task row, open the file it names and find the change. The check has already confirmed every row is marked completed and its file changed; a row marked completed with no matching change is the defect.
- Tests: for each test that carries an acceptance criterion id, read the criterion in its spec. The test must fail if the criterion's result were absent. A test that asserts nothing about the criterion, or is skipped, is the defect.
- Scope: each path the code step changed should be named by a task row or by the report's deviations. The changed paths in the check evidence are counted from the run's base in a run with no phase step, so they also hold what earlier steps wrote: the run's own notes under `docs/tasks/`, the plan, and the specs and research notes the hand-off lists. After the phases the check evidence holds two lists counted from the code step's entry: `Changed since the code step was entered` (what the code session changed) and `Changed only by earlier steps` (each path with its steps, among them the files of the phases). The paths of the second list need no row, and neither do those notes. The check evidence lists apart, under Written by prepare, two kinds of file, each needing no row: a project-context file (`CLAUDE.md` or `AGENTS.md`) whose only change is the temperspec block the workflow's first script writes, and `tempergraph.commands.json` while it still holds the text prepare wrote (an edit by a step puts it back among the changed paths, where it needs a row). It lists apart, under Written by the regeneration, the generated files that only the regeneration unit's commits changed (the outputs the repository declares in `tempergraph.regenerations.json`); they need no row either, and a later edit by a step puts one back among the changed paths.
- When the code is right and the fault is in the plan or in a spec, name that earlier output as the place of the defect, so the run goes back there.
- Behind every MET, quote the line you relied on, with its path and line number. Without evidence, grade PARTIAL. Grade a criterion PARTIAL, not MET, when its only evidence is lines a search printed. When you searched and then read the file around the line, quote the line from the file you read. If you cannot check something, say so; do not guess.
- Open with the read tool the file a row or a criterion names before you grade it. Lines a search printed are not a reading of that file. When a grade fails only because you did not open a place you could open, set unread true and give the path and lines to open as its fix. A file of the evidence's list beyond the reading budget is graded UNVERIFIABLE with the files named, and is never marked unread.
- A criterion the gate's check verified is graded from the check's finding: quote that finding from the evidence as the line behind its MET, and never grade it UNVERIFIABLE because you cannot run the check yourself.
- An open question that the hand-off lists, or that a later note carries on, does not block planning: the discovery step ends blocked on one that does. It is neither a defect nor something out of your reach, so it changes no grade and you leave `gap` false for it; the pull request lists it for the owner. Set `gap` only when a file or fact you need to grade a criterion is out of reach.
- Grade only the criteria listed. Style and naming are not defects.
