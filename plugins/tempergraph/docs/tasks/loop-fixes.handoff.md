# Hand-off: loop-fixes

## Problem

In release 3's first dev-mode run the improvement loop found only part of what a reviewer found by hand ([R-160](../research/R-160-does-the-improvement-loop-find-what-a-reviewer-finds.rsrch.md)). The task makes the loop find it unaided: reviews read the sessions of units in trouble first and are paid for from the spend reported so far, a review category kept in several sessions of one unit becomes a finding, a short loop summary reaches `attention` and the thread's detail, and a check that fails twice with the same evidence stops the retries at once. The documents say what the code does after the change; no code, test or plan was touched.

## Decisions

- R-160 F3 named the wrong cause. Reading `plan` and `run` in `plugins/tempergraph/engine/src/tempergraph/improve/review.py` shows the six skipped targets came from the count cap of 12 sessions (`review.max_sessions.full`) applied at plan time, in run order. The money cap (3.46 USD, a quarter of 13.84 USD) was never reached, since the 12 reviews cost 0.66 USD. Criterion 2's example (no target skipped at 12 reviews, 0.66 USD, 3.46 USD) cannot hold for 18 targets while that count cap stays, so SRV-B21 drops the count cap in `full` and keeps 3 in `signals`; the money caps decide. R-160 was corrected for that reason, and a backstop count cap is an open question.
- A "unit in trouble" (SRV-B24) is read from criterion 1 as written: its gate failed its check at any attempt of the run, sent the run back, escalated or paused. All its sessions of all attempts and visits join the first group. A designed approval pause counts as a pause. Inside each group the session that started later comes first, which puts later attempts before earlier ones and a judge before its own step.
- The budget decision (SRV-B25) estimates the next review as the mean reported cost of the run's finished reviews, or, before one has reported, the price of its view by size as today. It stops at the first target that does not fit and skips every later one. Today's `run` skips one target and goes on with the next, which could read a lower-priority session. The spend counts over the run, so earlier plans of the thread count too, since SRV-B21 and SRV-B23 state their caps per run; today's `run` starts its spend at 0 on each call, so the code step reads the thread's review records or says in its report that it kept the per-call figure.
- The repeat finding (SRV-B26) has the cause `review_repeat:<category>` and counts distinct sessions in which the category was kept (it passed the citation check) on the same unit, three by default as the parameter `review.repeat_sessions` with provenance `default_no_data`. It is a fault of the workflow, except that `environment_fault` is `infra`, as SRV-B19 already records it, and `request_ambiguous` is `designed`, a choice of this step, since SRV-B19 only routes it to the outcome lens and no workflow change fixes it. Those two therefore do not appear in `improve backlog`, which lists only fault findings. If the owner wants every repeat in the backlog, SRV-B26's last clause and its fourth scenario change; the recommendation is to keep them out.
- The finding corroborates only its own category on its own unit (SRV-B27). The `review_done` records are written one session at a time, before the count is known, so SRV-B22's `corroborated` in those records cannot be final. SRV-B22 is not edited; the plan step chooses between a reader-side join of findings and review records and a later record. Today `improve review summary` reports 0 corroborated.
- The decision record answers R-160's second open question: one run is enough to record the finding, and no number of runs is enough to file on a review alone, as criterion 3 says. R-160's conclusion 2 ("counts as corroboration for filing") and that open question are left as the snapshot they were, and the record is the place that overrides them. ADR-0119 stays as it is; its decision stands and the new record links it. The decisions index `plugins/tempergraph/docs/adr/README.md` is kept by hand, so it was not edited, as the documents rule says an index is generated; the new record has no number, status or date.
- The child orders its work as friction judge, filing, review, then the loop's own proposal, so the repeat finding exists only after filing and cannot file in the same child. SRV-B28 states it for any later run too.
- The loop summary (SIL-B22) is written at every normal end of the child, a skipped one included. `recorded` counts the findings the thread holds, the repeat finding among them; `filed` counts the issues this child opened or commented on; `top[]` holds at most three kept observations of the thread by confidence, ties in plan order, with category, unit and confidence and no note text.
- `attention` shows the summary in `loop[]` beside `items` and not as an item (CLI-B20), because `items` is every item waiting on a person, each with a command that answers it (CLI-B6), and a summary waits on nobody. It shows the newest summary per workflow, and only when that summary holds a finding or an observation; it stays until a later loop child of the workflow ends (dismissal is an open question). CLI-B6 now says its sources are for the items, so `attention` stays read-only (CLI-B8). The detail document gains a `loop` block, `null` until a loop child has ended; it is additive at schema version 1, and the existing fixture test of RDD-AC1 reads selected blocks only, so it does not need the new one.
- The gate rule (BUD-B16) compares the failing findings by criterion, place and message, or the scrubbed evidence text when the check returns none, on two attempts in a row of one visit and item, the later step having changed files in the workspace. It takes precedence over the retry budget, infra tries and the ladder step; a check FAIL marked environmental already escalates at once (BUD-B11). It is deliberately exact: it must not treat a failure that changed as a repeat, since the ladders must not act on just any failure. A check whose message carries a changing duration never repeats, which is an open question. The pause has kind `escalation` and cause `check_repeat`; HUM-B7's list and LAD-B11's held causes are not edited, because BUD-B11 adds triggers the same way and no next attempt starts.
- The finding for `check_repeat` is in SIL (SIL-B23), as `tool_access` is (SIL-B14): a workflow fault with no evidence text, remedy that a person decides whether the check, the environment or the prompt is wrong. Today the cause table would class the pause as the generic `escalation:check_repeat`; the code step adds the specific cause.
- Not edited: SRV-B7 and SIL-B16 (they concern model-free findings, which are unchanged), SRV-B15 (the plan record keeps its plan-time skips; the run-time skips of SRV-B25 are the `review_skipped` records of SRV-B22), PRP-B12 (the backlog already lists fault findings and shows `review_weight`), and the guides and the README (their line on `attention` is about its items). RDD's Purpose names no loop log among the sources of the detail; it is not a behaviour and was left.
- Left for the plan and code steps, where the code differs from the documents today: `improve/review.py` (`plan` and `run`: order, count cap removed, budget decision; `plan` takes the digests and the ticket only, while SRV-B24 needs the run's checks, gates and pauses to name the units in trouble), `improve/params.py` (`review.max_sessions.full` removed, `review.repeat_sessions` added), `improve/child.py` (repeat finding, summary), `improve/causes.py` (the two causes and their classes), `improve/proposals.py` (`review_weight`), `observe/attention.py` and `observe/detail.py`, the gate and its check node for BUD-B16 (the plan step finds where the engine knows that the later attempt's step changed files), `tests/test_session_review.py`, which builds plans from digests alone, and any test whose check fails the same way on two attempts in a row while its stand-in step writes files, which the new gate rule would pause as an escalation (the suite shows which).
- The link check counts a line that opens with an id (after a heading mark, a list dash or a table bar) as a definition of that id. The first Open questions bullet of `plugins/tempergraph/docs/specs/improvement-proposals.spec.md` opened with PRP-B9, which its heading already defines, and SIL-B5 in the changed `plugins/tempergraph/docs/specs/self-improvement.spec.md` links PRP-B9, so the id read as defined twice. The bullet now opens with `Not built yet:`, as the same section of other specs does, and says the same otherwise. It is the only edit to spec `improvement-proposals`, a collateral edit the documents rule allows when it is reported, and the link in SIL-B5 is unchanged. No line of any spec now opens with a behaviour id outside a heading, and each id this task added has one definition.
- Size: spec `session-review` is about 27.5 KB against the 30 KB budget of the engine's spec budget test (measured from line lengths, since this step has no shell), so a later edit of it has about 2.5 KB. The other edited specs were not measured.

## Open questions

None blocks planning; each has the default the documents already use.

- Should a `full` review plan keep a count cap as a backstop for a run with very many sessions (SRV open question)? Options: (a) none, the money caps decide (the default); (b) a high count such as 40, which would skip the lowest-priority tail of a very long run. Recommended: (a) until a run shows a need.
- Should a person be able to dismiss a loop summary in `attention` (CLI open question)? Options: (a) no, it stays until the workflow's next loop child ends (the default); (b) a verb that hides it for a thread. Recommended: (a); the summary is one block per workflow.
- Should the comparison of BUD-B16 ignore durations and temporary paths in a check's message (BUD open question)? Options: (a) no, exact after scrubbing (the default), so a failure that changed is never taken as a repeat; (b) drop such tokens, which catches more repeats and risks stopping a run that is making progress. Recommended: (a), with the check author keeping messages stable.
- Should the repeat findings of `environment_fault` and `request_ambiguous` also appear in `improve backlog`? Options: (a) no, they are recorded as `infra` and `designed` (the default; SRV-B19 records the first as infra and routes the second to the outcome lens); (b) yes, as workflow faults with no remedy class. Recommended: (a).
