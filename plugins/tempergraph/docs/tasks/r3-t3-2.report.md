## Deviations

- **Row 2.6: no `merge_maps` reducer.** The plan changes the `maps` channel to a new reducer `merge_maps` and says no test pins the reducers. `tests/test_compiler.py::test_every_state_channel_has_a_two_writer_reducer` (CMP-AC9) does: it requires every unit-keyed channel except `replace` and `merge_run` to use `merge_units`. I kept `merge_units` and made the concurrent map's `maps` record safe a different way: every item writes only keys of its own (`n:<id>` for its attempt number, `st:<id>` for how it stands: started, parked, passed, stopped), so items finishing in one superstep lose nothing; the list order, `passed` (written once, when the map finishes) and `exit` are written by the map's own step node. The plan's document-level behaviour is the same. The plan's premise (that no test pins the reducers) was wrong for this one test.
- **Where the item helpers live.** `compiler/state.py` (row 2.6) also holds `fold` (a state as it reads after a write, through each channel's reducer), `item_view` and `slot_writes` (an item's record moved to and from the place the unit's own would be), `item_end` (the `maps` write of an item's turn) and the `Move` record a concurrent map's step node returns. The compiler must not import from `run/`, and `run/mapping.py` imports them from there.
- **Graph shape (row 2.7).** A concurrent map keeps the unit's four nodes and adds four item nodes `<unit>.item_step`, `.item_judge`, `.item_gate` and `.item_human` (`flow.item_node`). The unit's own step node reads the list, sends the next `concurrency` items that have not started (a wave) with `Send`, waits while items run, sends the items that wait for a person to `item_human` once nothing else can run, and when every item has passed merges, checks and goes to the unit's own judge. The unit's own judge, gate and human nodes are unchanged and give the map's PROCEED, the conflict pause and the failed-check pause. A passing item's gate record has token `NEXT` (the map's own gate record, with no item, has `PROCEED`). The cap on items at once is a wave: a slot is not refilled by an item that ends while others still run. LangGraph needs `destinations` on nodes it reaches only by `Command`; `diagram_model` (the committed diagrams) does not draw the item nodes, and no test compares it with a concurrent graph.
- **Row 4.2: "the other pause still pending" and when a retry runs.** A LangGraph superstep ends only when every task of it has, so with two pending item pauses, a `retry` named for one item is applied but the item runs again only when the other pause is answered too. The tests show it: after `retry` for `phase.p5` the run is still paused with `phase.p2` pending, no new session has started, and after `stop` (or `proceed`) for `phase.p2` the retried item alone runs one more session (its step and its judge) and the others none. The plan's "(one new session, the other pause still pending)" cannot hold at the same moment.
- **Files changed that no row names.** `durability/checkpoint.py`: `_gate_node` names a pause of an item by its slot (`<unit>.<item id>.human`), and `update_values` now declines a state write when more than one task is pending. Without the second change the runner's `update_state` call on a resume with two pending item pauses (the same node sent twice, so LangGraph does not call it ambiguous) silently dropped both pauses. `tests/test_zz_probe.py`: a throwaway file I used to read the installed LangGraph version (1.2.24) and to inspect a thread; the allowed commands cannot delete a file, so it is emptied to a docstring and carries no test. **Please delete it.**
