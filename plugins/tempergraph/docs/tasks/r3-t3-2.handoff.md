# Hand-off: r3-t3-2

## Problem

Release 3 phase R3-T3.2 replaces the `not_in_release` refusal of a map with `mode: concurrent`: items run up to `concurrency` at once, a writing map gives each item its own worktree merged at the join, and the joined result is checked once. The behaviours were mostly written ahead of the code (MAP-B6, MAP-B7, MAP-B9, MAP-B10, MAP-B11, WSP-B11, WSP-B12, BUD-B12), but no criterion stated the concurrent mode, WSP-B11, WSP-B12 and WSP-B19 spoke of branches and blocks, nothing stated a check after the merge, and spec `map-unit` still listed the mode as not built.

## Decisions

- Where each rule lives. The worktree, merge, conflict and checkpoint rules for items stay in WSP, which owns the shapes of parallel work, so WSP-B11, WSP-B12 and WSP-B19 are widened in place and no second spec states them again. MAP states only what is the map's own, the check after the merge. BUD-B12 already lists a parallel map, so BUD gets a scenario and a criterion and no new behaviour.
- A writing map item is an item of a concurrent map whose step declares `write` or `edit`, the test WSP-B11 applies to a branch (`shell` alone makes none). Its place in the merge is its place in the list. The merge happens when every item has passed, at the end of the map and before the next unit; the join of a map is that end, not the unit that follows. MAP-B10's last clause now says so, so that it does not contradict MAP-B13.
- "No worktrees" in MAP-B11 is read as WFM-B8 reads it for a branch: a workflow that declares `workspace: in_place`. The default `auto` resolves to a worktree for a writing item and an explicit `in_place` is refused before spend; spec `worktree-mode` already says both ("a writing map item"), so it needs no edit there.
- The check after the merge exists only for a writing concurrent map, the only one that merges. It is the gate's check run once on the run's worktree with no item (CHK-B10 gives `item` to a mapped item only) and it is model-free; each item's own check still runs in the item's worktree. A failure ends the map blocked and not retried (MAP-B13) for three reasons: the task says the check runs once, nothing runs between two runs of it so a retry would repeat its result, and JDG-B1 would otherwise turn the failure into RETRY. The merge stays on the run branch, since a conflict resets it because the merge itself failed and a failed check does not. This is the interim choice; see Open questions.
- A read-only item that changes the run's worktree fails with `branch_changed_the_workspace`, the error CMP-B13 and WSP-AC12 name for a branch: one rule, one error. The fingerprint is the worktree's, so a read-only sibling running at the same time can fail too, as in a block today; the scenarios say nothing about siblings.
- The executor rule, WTR-B25, gave "a writer" its own path while WTR-B20 names writer, slot and item worktrees apart, so an item's step would have stayed on the run's path and WSP-AC16 would have contradicted it. One phrase and WTR-AC12 close it. WTR-B20 (the `--i-<item>` names), WTR-B23 (cleanup lists item worktrees) and WTR-B24 (children) already name items and are unchanged.
- The checkpoint behaviour, WSP-B19, is retitled "The checkpoint before writers start" (the old title named writer branches only). No other title changed.
- Not edited: MAP-B6 (its scenario is the two pending pauses and MAP-AC7 is its criterion), HUM-B3 (written for gates of a block and extended to items by MAP-B6, as it was for the sequential form), HUM-B7 (it does not list the merge conflict either; the blocked pause is JDG-B1's ESCALATE with no judge session), CMP-B14 (already compiles a map as one subgraph per item), WFM-B8, BUD-B13 to BUD-B15, WSP-AC3, and the words "a parallel map" in BUD-B12 (the mode MAP-B7 calls `concurrent`).
- Left for the code step, because each says what is built and is true only once the code lands (as in R3-T3.1). The plan lists them under Docs to update:
  - `plugins/tempergraph/docs/plans/third-release.plan.md`: record R3-T3.2 and track R3-T3 as built (the Status line, the R3-T3.2 phase, and the end of R3-T3.1's Status, which leaves the writing map's item worktrees to R3-T3.2)
  - `plugins/tempergraph/docs/specs/budgets-and-failures.spec.md`: the Not built yet bullet says the reservations are not built for maps; drop "maps" (contests and councils stay). `test_reservations.py` pins its words at lines 209 to 222 (`maps`, `contests`, `councils`, `projection`, `BUD-B12`, `BUD-B15`), so the test changes in the same row
  - `plugins/tempergraph/docs/specs/worktree-mode.spec.md`: the Not built yet bullet says slot and item worktrees arrive with the units that need them; drop "item" (slot stays for the contest)
  - `plugins/tempergraph/docs/research/rationale-carried-from-the-engine-specs.rsrch.md`: the F44 "As built" bullet says the concurrent mode is refused `not_in_release`

## Open questions

None of these blocks planning; each says what the plan does until the owner answers.

- What should a failed check after the merge do? MAP-B13 states one outcome for now: the map ends blocked, not retried, the merge kept. Options: (a) as written; (b) the gate's usual path (JDG-B1 makes it RETRY, then the retry budget, then a `budget` pause), which runs the check again on an unchanged tree and breaks "runs once"; (c) stop the run naming the map; (d) go on to the join unit with the failing findings as a fact its judge reads, so the join's gate, which may carry `back_targets`, decides. Recommended: (a). Owner: owner.
- What happens when a trip back (MAP-B3) enters a writing concurrent map a second time? WTR-B20 fixes the item names, so the second visit meets the first visit's item worktrees and branches, whose work the first merge already took into the run branch. Options: (a) reuse them as R3-T3.1 does for a block, so an item starts from a tree cut at the first checkpoint; (b) cut them again at the new checkpoint, ending blocked and naming the branch when an item branch holds a commit the run branch lacks; (c) refuse at validation a back target that re-enters a writing concurrent map. Recommended: (b), as a task of its own. Until answered the plan treats the second visit as outside this task and the code report names it under Deviations; none of the six criteria visits a map twice. Owner: owner.
- Should a writing concurrent map outside git be refused `needs_git`? WSP-B18 lists writer branches, and a writing map needs worktrees too. Options: (a) widen WSP-B18 to writing map items, with a scenario, and add the map to the `needs_git` reasons; (b) leave it, so the run stops at the map's entry with a refused workspace after earlier units have spent. Recommended: (a). Until answered the plan adds no `needs_git` reason for a map and the code report names it. Owner: owner.
- What does the plain key hold after a concurrent map? MAP-B9 says it holds the item in hand; after a sequential map that is the last item's value, and no single item is in hand when items run at once. Options: (a) the last item of the list, one rule for both modes; (b) nothing, a later unit reading `<key>[<item id>]` (MAP-B9, VAL-B7). Recommended: (a). Until answered the plan keeps (a), which changes no sequential behaviour. Owner: owner.
