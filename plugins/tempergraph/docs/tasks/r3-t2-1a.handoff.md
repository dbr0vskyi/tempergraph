# Hand-off: r3-t2-1a

## Problem

Task r3-t2-1 lets a workflow declare `Subworkflow(...)`, makes validation refuse every bad one before any spend (SWF-B6, SWF-B7), and stops a run of a valid parent with one clear message until R3-T2.2 builds running a child. SWF-B6 and SWF-B7 were already written. The spec had no behaviour for the interim stop, the template grammar accepted no `{<unit>.<key>}`, and several readings the code would have to guess were unstated (the code of the built-in refusal, what a required input is, how depth is counted, the form of `requires`, what `summary` is).

## Decisions

- "The blueprint records each field" (criterion 1) is read as the unit record of the built workflow, not the authoring `blueprint.json`. SCF-B9 (`plugins/tempergraph/docs/specs/blueprint-and-scaffold.spec.md`) says the authoring blueprint states no sub-workflow. So authoring is untouched, and `blueprint check` must keep refusing `kind: "subworkflow"`, with the `not_in_release` it gives today. `author/blueprint.py` reads `LATER_KINDS` for that, which will no longer hold `subworkflow`, so a plan row must keep the refusal. No test pins it (`test_blueprint.py` line 102 pins `council` only).
- The built-in case gets the code `subworkflow-builtin`. SWF-B6 and criterion 2 name none. The name follows the other sub-workflow codes; renaming is one spec edit and one code edit.
- The interim stop (SWF-B11) is exit 2 `not_in_release`, the convention of ADR `first-release-is-simple-trusted-workflows-on-one-machine`, WFM-B10 and PRO-B6. It is the last refusal, so every other refusal stays observable: validation findings, settings, executor preflight and `needs_git` come first. It applies to `run` and to `run --check`, as WFM-B2 asks the two to refuse alike. It must not be a finding of `validate`, because a valid parent has to pass validation and its catalog row stays valid. In `run/runner.py` that means after the `needs_git` and carry checks and before `ensure_state_root`; `executors/preflight.py` runs earlier than `needs_git`, so it is not the place. It names the first sub-workflow unit. SWF-B11 and SWF-AC4 are removed, their ids retired, when R3-T2.2 builds running a child.
- A required input is every input the child declares, and `request` for a child that declares none. CON-B9 has no optional parameter, and VAL-B8 gives a parameterless workflow the one input `request`. `text.input_names` already returns this set.
- `requires` takes the range form of `requires_engine` (VER-B14). `_in_range` in `package/changelog.py` already parses it, and returns false for an unreadable range, which is the `subworkflow-version` refusal.
- `summary` is read as a step's `summary` is (CON-B6): at most 60 characters, for diagrams. No refusal is stated for it: `validate` refuses no long step summary, the blueprint check does (`summary-too-long`) but a blueprint states no sub-workflow, and the package self-test's 1-to-60 check (`package/selftest.py` lines 38-46) covers `step` and `script` units only.
- Depth: the parent's child is level one; three levels pass, four are refused (CMP-B14's "four levels deep" fails).
- `needs_git` is decided at start, by `needs_git()` in `run/runner.py`, because git is a property of the start directory and `validate` cannot see it. The plan extends that function over the child's units and the child's children.
- Not built here, as the task says: SWF-B8's validation warning `subworkflow-finalizer-skipped`. The plan's R3-T2.1 Goal line names SWF-B8, but the task puts SWF-B8 in R3-T2.2 and its criteria list only the SWF-B6 refusals. Acceptance criteria outrank the plan.
- The task text speaks of a "nesting depth table" in `model/validate.py`. The table there (`LATER_KINDS`, lines 54-57) holds the release in which each kind is built; `"subworkflow": 3` is release 3, not depth 3. No depth code exists anywhere in the engine, so `subworkflow-depth` is new.
- The "Not built yet" line in the spec's Open questions is left for the code step as a `docs` row, since it states what is built. Suggested final text: `- Not built yet: running a child (SWF-B1 to SWF-B5, SWF-B8, SWF-B10), which SWF-B11 refuses meanwhile, and measures and carrying (SWF-B9, SWF-AC3). Owner: engine owner.` The plan's R3-T2.1 status line is also a code-step edit, in the form of R3-T1.2's (`Status: built. ...`).
- The compatibility-changelog entry that WFM-B5 asks for a new spec field belongs to the release's own phase (R3-T10.2), not to this task.
- This step has no shell. The spec form (`test_spec_form.py`) was checked by hand with searches on the edited spec: 12 behaviours, each with a statement line and scenarios, all 31 scenario lines matching, five criteria naming every behaviour, no code block or checkbox. The suite was not run.

## Open questions

- Not blocking planning. Should validation also refuse an `inputs` value that is none of `request`, `<unit>.<key>` or a quoted literal, and a `<unit>.<key>` that no earlier unit produces? SWF-B6 and criterion 2 list no such refusal.
  - Option A, the default for the plan: no validation refusal in this phase. The builder reads each value into one of the three forms and a value of any other form fails when the declaration is built (a builder `TypeError`, as `Map` does for a bad `step`); whether `<unit>.<key>` names a real key is left to R3-T2.2, where the child reads it.
  - Option B: add a finding such as `subworkflow-input-invalid` for both cases, each with a scenario in SWF-B6 and a test. It catches the error before any spend, and adds a ninth refusal beyond the task's list.
