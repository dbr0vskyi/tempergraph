# Hand-off: i196

## Problem

A person who closes a loop issue as a duplicate names the issue it duplicates only in the closing comment, and the loop reads only issues that carry its label, so it keeps opening issues for causes a person already tracks while a close as a duplicate only mutes. Discovery wrote the capability that binds such a cause to the named issue, the target: the target is read from the closing comment by REST and kept in a record of the state root, later sightings comment there within the day bound of ISS-B13, and a closed target decides like a closed loop issue. It also made ISS-B3 and ISS-B17 true for a duplicate that names a target.

## Decisions

- The triage note lists no owner decision (`Owner decisions: None`), so none was asked, answered or taken by default
- The design in the task is the owner's and was taken as stated (assumption A3 of the triage note): the target comes from the newest comment of a person with standing on the closed issue, the record is a cache of what the host says, later sightings comment on the target within the bound, and a closed target decides by its close reason
- The record is one JSON document, `filing-bindings.json`, beside `filing-outbox.jsonl`: the task fixes its place and keys and no file name, so discovery chose the name (BND-B8, LOS-B7)
- "A person" for a closing comment is the account test of OUT-B25 only: the marker line of an agent comment in `CONTRIBUTING.md`, which `plugins/tempergraph/engine/src/tempergraph/improve/pr_later.py` applies to pull request reads, is not applied here, because the design and the first criterion name only the author kind (assumption A2 of the triage note)
