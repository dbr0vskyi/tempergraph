# Hand-off: i17-18

## Problem

A concurrent map whose step writes needs worktrees, but outside git nothing refuses it before spend: the run reaches the map after earlier units have spent and stops there with `workspace_refused` (#18). A trip back that enters such a map a second time meets the first visit's item worktrees and branches, which the cut reuses, so the second visit works on a stale base, its work lands on the first visit's branches, and a removed worktree folder with a surviving branch refuses the cut (#17). The specs named neither a writing map among what needs git nor what a second visit does with the first visit's items.

## Decisions

- Acceptance criterion 2's default is taken, because no document decides a second visit of a writing map. Searched `77-map-unit.spec.md`, `13-workspace-and-concurrency.spec.md`, `82-worktree-mode.spec.md` and `72-contest-unit.spec.md` for "second visit", "trip back", "item worktree", "item branch": MAP-B3 says only that the list is read again, WSP-B11 and WSP-B19 describe one cut and one checkpoint, WTR-B20 and WTR-B24 name and record item worktrees with no visit, WTR-B23 deletes no branch. The second visit cuts fresh item worktrees from the run branch's head after the checkpoint commit; the first visit's item branches and worktrees stay as they are; only the second visit's branches are merged.
- Names. The first visit keeps `--i-<item>` (`tests/test_map_concurrent_writers.py` pins it); the n-th visit, for n above 1, takes `--i<n>-<item>` on the folder and the branch. The visit number rises on every re-entry of a unit: a gate's trip back (`run/gate.py` lines 34-39 and 442-448), a person's `back` or `rewind` (lines 671-679) and a rerun (`run/rerun.py` lines 287-290). `--i-` can never equal `--i<digits>-`, so no name repeats. Rejected: a number after the item id (an item `x-2` of visit 1 would meet item `x` of visit 2); resetting or deleting the first visit's branch (criterion 2 leaves the branches as they are and WTR-B23 deletes none). No decision record: no gap asks for one and criterion 2 with WTR-B23 leave one workable option.
- Where each rule lives. MAP states the second visit (criterion 2 names MAP, and the visit is the map's own idea); WSP-B18 owns what needs git; WTR-B20 owns names, so it is edited in place. WSP-B11, WSP-B19, WSP-B12, WTR-B23 and WTR-B24 already hold for the second visit and are not edited. WSP-AC5 stays: its "every `needs_git` refusal" now includes the map, and WSP-AC21 to WSP-AC23 name the map case so that a test can carry them.
- The first visit's item worktrees stay in the run's workspace record (MAP-B15). The listing and `cleanup: on_finish` read the record (`workspace.py` lines 574-575), so a dropped record would leave those worktrees locked and unlisted. Today `cut_writers` replaces a record of the same slot when it cuts again (lines 415-416) and `_child_of` finds a child by its slot alone (`run/nodes.py` lines 173-190), so the plan has to tell the visits apart in both places, and in `_merge_children` (lines 252-276), which matches by slot too.
- A writing map is a concurrent map whose step declares `write` or `edit`; `shell` alone makes none (WSP-B11, `model/flow.py` lines 87-91). A child workflow's `needs_git` defers to WSP-B18 (SWF-B6 in `99-subworkflow-unit.spec.md`), so a child tree holding a writing map follows from the same reason and that spec is not edited. `running-workflows.guide.md` line 124 says "worktrees" and stays true.
- The run's conversation setting arrived unresolved. Nothing here needs a person before planning, so no question below blocks it.
