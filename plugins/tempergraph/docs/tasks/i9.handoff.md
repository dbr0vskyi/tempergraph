# Hand-off: i9

## Problem

GitHub issue #9: nothing reads whether a proposal's draft pull request was merged, so a proposal never leaves `opened`, the measure after release (PRP-B9) never starts and `regressed_after_release` is never recorded. The specs did not say how the merge is seen, what happens when the code host cannot be asked, or when a proposal's measure counts as worse. Spec 40 had room for all of it (about 26 KB and 232 lines after the edit, by my line-length count, since this step has no shell; the caps are 30,720 bytes and 400 lines), so nothing was split and no spec was created.

## Gaps closed

- G1: `plugins/tempergraph/docs/specs/40-improvement-proposals.spec.md` (PRP-B26, PRP-B27, PRP-B28, PRP-AC10, PRP-AC11): PRP-B26 says how `pr_state` is read: at each final exit of a workflow with an `opened` proposal, at autonomy `file` or above and outside a dry run, the loop asks the code host (the person's `gh` sign-in, read-only) for the proposal's draft pull request and keeps `open`, `merged` or `closed` (closed without a merge) on the proposal, `unknown` from the opening until a read succeeds. PRP-B27 moves an `opened` proposal to `merged`, with the host's merge time as `merged_at`. PRP-B28 is the fallback: when the host cannot be reached or no `gh` is installed or signed in, the proposal stays as it was (`unknown` when never read), nothing is recorded as merged and nothing fails. Task AC 1 rests on PRP-B26, PRP-B28, PRP-AC10 and PRP-AC11. Task AC 2 rests on PRP-B27 and PRP-AC10 (an opened proposal moves to merged) and on PRP-B28 and PRP-AC11 (the host unreachable)
- G2: `plugins/tempergraph/docs/specs/40-improvement-proposals.spec.md` (PRP-B9, PRP-B29, PRP-AC12, PRP-AC13, Open questions): PRP-B9 is rewritten in place. It names the exits that count (the first 10 final exits of real runs after the merge), the base (the proposal's `base_version` exits before the merge), the figures and margins that make a measure worse (cost per run up more than 15 %, `trial.guard_cost`; gate first-try pass rate or met share of outcomes down more than `measure.quality_drop`, 5 points), what is recorded (`regressed_after_release` with the figures before and after when worse, `held_after_release` when not) and what happens before 10 exits exist (nothing is compared or recorded). Its scenarios cover a 30 % cost rise, a 7-point pass-rate fall, a 5 % rise that is not worse, 9 exits, trial runs among the 10, a merge seen late and no second comparison. PRP-B29 is the old "reopen the issues" half of PRP-B9, now its own behaviour with an unreachable-host case. PRP-AC12 and PRP-AC13 are new. Task AC 3 rests on PRP-B9 and PRP-AC12. Task AC 4's first half is done: the "Not built yet" bullet of spec 40 is removed (the engine suite, `ruff check src tests` and `mypy` are the code step's)

## Decisions

- The home of `pr_state` is PRP (spec 40), which task AC 1 allows. FBK-B9 and its open question (spec 41, line 108) are about labels of a run's pull request for judge grades. They are not edited and stay true: those labels are still not derived. The field here belongs to the proposal record, so spec 78 (line 37, the finalizer's `opened` URL) is not edited either
- The read happens at every final exit of a workflow with an `opened` proposal, whether or not a lens fired (scenario 2 of PRP-B26 is a clean exit). The code starts the loop child only when it writes a ticket, and `hand_off` in `child.py` writes none for a clean exit (lines 124-125). A quiet workflow whose cost rises with no fault is exactly the one PRP-B9 must see, so the plan has to make such an exit run the read: a ticket for it, or the read in the exit's loop start. SIL-B1 says when the engine SHALL write a ticket, not that it writes one only then, so SIL-B1 is not edited; if the code step reads it as exclusive, it edits SIL-B1 in the same pull request
- The state is read at autonomy `file` or above and never in a dry run, as PRP-B25 does for the trial comment and SIL-B6 for filing. Trial child runs are dry runs with origin `trial`, so they neither read nor count. `improve show` stays read-only (PRP-B22): it prints the record and never asks the host. `open_pr` sets `pr_state` `unknown` when it records `opened`
- A pull request closed without a merge records `pr_state` `closed` and leaves the proposal `opened`, which keeps it live for PRP-B23 as today. This is the option that changes the least (open question 1)
- A merged proposal is no longer live: `LIVE_STATES` in `autonomy.py` (line 24) holds `opened` and not `merged`, so the loop may propose again for a cluster whose proposal merged, when the fault recurs. That follows from the move to `merged` and is intended
- What "worse" means (open question 2): the four figures of SIL-B5 with two margins, not the old words "on the trial's target and guards". Reasons: a proposal opened without a trial (autonomy `propose`, or a person's `improve open` of a drafted one) has no target or guards; the trial's guards count paired cases (outcome met -1 case, checks -1 case, escapes +1) and a window of runs has none, one run being 10 points of a 10-run share; `measure.compare` already finds quality drops, so the cost margin is the one addition; both margins are parameters with provenance. A figure is worse only when it is more than the margin (as `guard_states` and `compare` do) and only when both windows have it. Repeat share is compared and reported, with no margin, so it never makes a measure worse
- Which exits count: the base is the proposal's `base_version` final exits recorded before `merged_at`; the new side is the first 10 final exits (exit 0, 4 or 5) after it, leaving out the runs PRO-B8 leaves out (origins `trial`, `scenario`, `evals`, dry runs; `promotion.py` lines 23 and 83-94 is the model, read from the run log). The ledger row's `workflow_version` is the declared version, which a merge need not change, so the boundary is the merge time the host reports and not a version string (open question 3)
- The comparison runs once. `held_after_release` is the marker for a comparison that found nothing worse (the name `loop_report.py` and IMD-B22 already use for the figure, which the report does not read in this change); `regressed_after_release` is the marker for one that did. A proposal holding either is not compared again. The rule is level-triggered: a merge first seen when 10 or more exits already follow it is compared at once, so a missed exit or a down host loses nothing
- PRP-B29 reopens the cluster's issues that are in the pull request's repository, the set PRP-B24 had the merge close, and a host that cannot be reached leaves the record standing and the reopen in the SIL-B19 outbox, as PRP-B25 does for the comment. `_deliver` in `filing.py` handles only a comment and a create today, so the outbox needs a reopen payload. SIL-B5 is not edited: its comparison writes no file and keeps its own comment and its reopen after a quality drop, and the record on the proposal is PRP-B9's own write after it. On a quality drop both reopen the same issues, and reopening an open issue changes nothing
- PRP-AC2 stays true and the plan must keep its source test passing: `test_no_code_path_merges` rejects any string constant equal to `merge`, containing `/merge` or starting with `merge `, and any `merge`, `merge_pr` or `merge_pull_request` attribute of `MemoryCodeHost`. Read the pull request with a GET of the pull request (its `merged` and `merged_at` fields), never the `/merge` endpoint, and name the new method for what it does (for example `pull_state`), not with the word merge as a verb
- The funnel of `report --loop` (IMD-B22; `loop_report.py` lines 95 and 128) counts `opened` by `state == "opened"`, so a proposal that moves to `merged` would drop out of that count. The plan keeps the figure true by counting `opened`, `merged` and `closed` proposals as opened. The report's `merged` and `held after release` stay printed as not derived: wiring them is a later change, outside "the merge state and the regression record". IMD-B22, IMD-B9 and the open question at spec 43 line 163 ("release 1 reads none", about who reads state for the store) are not edited: the store's states are still not built
- `audit/owned.py` (lines 70-92) imports `tempergraph.improve.watch.prompt_moved_gates` when a module of that name exists, and spec 55 (line 120) says that watch is not built. Do not create `improve/watch.py` for this change, or the audit's rule would find a module without its function
- The decision record `a-closed-loop-issue-mutes-its-fingerprint-or-links-a-regression.adr.md` is not edited (a record is not). Its "Revisit when" names the merge being seen, which now happens; ISS-B4 still only links, as its own open question says
- The prompt gave no conversation value (`⟨missing:settings.conversation⟩`) and the triage note lists no owner decision, so the unattended rule applied: nothing here blocks planning, no decision record was written, and each open question below has its default in force and in the spec

## Open questions

None blocks planning.

- Should a proposal whose pull request was closed without a merge move to `closed`? Options: (a) no, it stays `opened` with `pr_state` `closed`; (b) yes, it moves to `closed` and stops being live for PRP-B23, so the loop may propose again for its cluster (a person's "no" could then meet a new proposal the next day). Until answered: (a). Changing it is one new clause beside PRP-B27 and one line of `LIVE_STATES`. It is also in the spec's Open questions
- Should the post-release measure be the trial's target and guards counted per run, not the figures of SIL-B5? Options: (a) the four figures of SIL-B5 with `trial.guard_cost` and `measure.quality_drop`, which works for a proposal with no trial; (b) the trial's target and guards over 10 exits before and 10 after the merge, with a run as a case, which needs 10 exits before the merge and the default guards for an untrialled proposal; (c) both. Until answered: (a). It is also in the spec's Open questions
- Is the merge time the right boundary for "after the merge"? Options: (a) the merge time the host reports; (b) the content version of the run log's `run_started` record (VER-B14), which marks exactly the runs of the merged package, since a machine that has not pulled the merge still runs the old package and its exits count as after under (a). Until answered: (a), which the spec's words "after the merge" already cover. Moving to (b) needs no spec change if the plan finds the version cheap to read; it is only a choice of how to tell the exits apart
