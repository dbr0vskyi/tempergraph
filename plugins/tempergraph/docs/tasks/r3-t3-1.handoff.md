## Decisions

- A writer branch is a parallel branch that declares `write` or `edit`, the test the refusal applied (`validate.py` line 246), now written in WSP-B11. `shell` alone does not make one: such a branch stays read-only and the fingerprint check fails it if it changes the tree.
- The phrase "a workflow without worktrees" in WFM-B8 is read as one that declares `workspace: in_place` (said in WFM-B8 now). It is the only reading under which a writer branch validates in the default case, as AC 1 asks. It comes from WTR-B18, ADR-0101 and R-150 ("A workflow author who wants a fixed mode declares `workspace: worktree` or `in_place`"), and MAP-B11 says "no worktrees" of a concurrent writing map in the same sense. A start with `--in-place` or a setting of `in_place` is refused by WTR-B18 (exit 2 before spend), since AC 1 needs a run branch to cut from; WTR-B18 is unchanged and WTR-AC1 covers it. `resolve_workspace` has neither the `writers` case nor that refusal today.
- The checkpoint commit gets its own behaviour, WSP-B19. WSP-B11 named it without saying what it commits or when. Taken before any branch starts, it cannot fail a read-only sibling by moving the head, and a block with no writer branch gets none, so existing read-only workflows are unchanged (WSP-AC14).
- "Declared order" is the order the parallel unit names its branches (CMP-B13: a unit "names its branches"). `order` may list them differently, since WFM-B8 only requires them to be adjacent before the join.
- The edit to CMP-B13 is not named by any triage row. It said every branch runs as a read-only step, which the task makes false for a branch that declares `write` or `edit`. It counts as a collateral edit in the sense of the spec rule and is reported here. Its first scenario said "a branch that edits a file", which a writer branch does without failing, so it now says "declares neither `write` nor `edit`". WSP-B11's first scenario had the same wording and is revised the same way.
- A writer's check and script get the writer's path as well as its step and judge, in WTR-B25. CHK-B10 already gives a check "the attempt's workspace", and a check of a writer's output run in the run worktree would see none of it before the merge. The second phrase covers a child's path in the `acceptEdits` condition; the code takes that condition from the run's mode (`nodes.py` line 385, `claude.py` line 108), so a writer's session gets it with no code change. The messages-api clause of WTR-B25 (the tool host's known workspaces) is left: that executor is release 4 (ADR-0132).
- A writer worktree is a worktree, so WSP-B2's bootstrap applies to it. What a failed writer bootstrap does to the run is stated nowhere; the plan reuses the start path's removal of the new worktree and branch and names the stop it chooses.
- Reservations (BUD-B12 to BUD-B15) need no change: a session reserves when its unit is a branch of a block, whatever its tools (`nodes.py` lines 166 to 176).
- Not edited: WSP-B12, WSP-B18, WTR-B18, WTR-B20, WTR-B23, WTR-B24, WTR-B27, WSP-AC3, WSP-AC5, WTR-AC1, WTR-AC2 and WTR-AC5. They already state what the task asks, and the new criteria sit beside them. A blocked join is JDG-B1's ESCALATE with no judge session, and the conflicting paths reach the person through the pause's `blockers` (see the reading list).
- Left for the code step, because each says what is built and is true only once the code lands (as in R3-T1.1 and R3-T2.3). The plan lists them under Docs to update:
  - `plugins/tempergraph/docs/plans/third-release.plan.md`: record R3-T3.1 as built (the status line and the phase)
  - `plugins/tempergraph/docs/specs/82-worktree-mode.spec.md`: the Not built yet line under Open questions says writer worktrees arrive with the units that need them; drop "writer,"
  - `plugins/tempergraph/docs/specs/08-budgets-and-failures.spec.md`: its Not built yet line says the reservations are built for "parallel read-only branches"; a writer branch reserves too. `test_reservations.py` pins that line (the words `maps`, `contests`, `councils`, `projection`, `BUD-B12`, `BUD-B15` stay, `check spend only` stays out)
  - `plugins/tempergraph/skills/author/references/steps-and-executors.md`: line 15 calls `parallel` "the join of two or more read-only branches"
  - the root README names "parallel read-only steps" only in its release 2 summary, which stays true; the guides and the other skill files name no writer branch and no read-only rule for branches (searched), so no other document is made false
- The concurrent map (R3-T3.2) is untouched: the map halves of WSP-B11 and WFM-B8 keep their wording, and WSP-B19 speaks of a parallel block only.

## Open questions

- What happens when a trip back runs a block with writer branches a second time? CMP-B13 says every branch runs again and WSP-B11 says each writer is cut from the run's branch after a checkpoint commit, but WTR-B20 fixes the names, so the second entry meets the first entry's writer branches and worktrees. It does not block planning: none of the task's five criteria enters a block twice. Options: (a) cut again under the same names, moving each writer branch to the new checkpoint in its existing worktree; nothing is lost when the first pass merged, but if its join was blocked by a conflict and a person then sent the run back, the unmerged commits stay only in the reflog; (b) as (a), but a writer branch that holds commits the run's branch lacks ends the step blocked, naming the branch, for a person to decide; (c) refuse at validation a back target that re-enters a block with a writer branch, as `not_in_release`, until (a) or (b) is built. Recommended: (b), as a task of its own. Until answered, the plan treats the second entry as outside this task and the code report names it under Deviations. Owner: owner.
