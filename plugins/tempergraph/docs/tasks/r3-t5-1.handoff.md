# Hand-off: r3-t5-1

## Problem

Task R3-T5.1 builds the engine's `schedule` command from spec `schedules`: the exact formats, the word grammar, slots with daylight saving, the entry and its fire log, ten verbs and the fire-decision policies as functions. The spec left four things open: how `--cron` maps onto the stored rule, which refusals the exact formats give, that the verbs of the next phase are refused, and what this phase builds and assumes. Discovery closed them in spec `schedules` and in R-150, and wrote no code, test or plan.

## Decisions

- Cron (no document stated it; chosen so that every result stays inside the stored subset): steps, ranges, lists and names expand to ascending lists and never to `INTERVAL`; a restricted month and both day fields restricted are `rule_unsupported`, since the stored rule has no month part and cron's "either day matches" cannot be written as one rule (R-150 cites POSIX and GNU Micron); macros, seconds, `?`, `L`, `W` and `#` are `when_malformed`.
- One new reason code, `rule_unsupported`, serves cron and `--rrule`; `interval_too_short` now covers every exact format and is read on the local clock, because cron steps and `BYMINUTE` lists can fall under 15 minutes without an `INTERVAL`.
- G3 is a behaviour with a criterion (SCH-B33, SCH-AC12), like PRO-B6, so a test can carry it. SCH-B27 keeps the synopsis of the verbs because spec `engine-cli` (line 100) sends the CLI to SCH-B27 for it, and its carve-out stands in the WHEN clause so that the sentence keeps the fixed pattern, `SHALL` followed at once by its result. The triage lists `add --orchestration` with the verbs of R3-T5.2, but ADR-0132 puts orchestration in release 4, so SCH-B33 and the "Not built yet" line give it that reason and name `add --program` (`program_target_reserved`) beside it.
- The release 3 plan's status line for R3-T5.1 (task criterion 8) is a plan edit and is not made here; the plan step lists `plugins/tempergraph/docs/plans/third-release.plan.md` under Docs to update.
- No decision record was written: no gap was of kind `decision needed`, and the reasons sit in R-150 next to the other schedule assumptions.
- The assumptions in R-150 that the owner may most want to veto: a slot found within one tick interval is on time under every `catch_up` (an inference from SCH-B21, so that `none` still fires on-time slots); an interval rule's first slot is `starts`, default now, so `--every PT2H` with no `--starts` is due at once (the RFC 5545 reading, and the one AC2's reference gives); an interval rule is `MINUTELY` or `HOURLY` with `INTERVAL` only, every other rule being a calendar rule, so AC2's reference is `dateutil.rrule` in UTC for the first and with a zone-aware start for the second (the dateutil half is inferred, and the first run of the test settles it); a fire counts in the budget period of its `started` event; the slot in a thread id is UTC.
- This phase leaves the person-only rule for `add`, `edit` and `resume` (TCK-B22), the credential check, the fire token and the ledger to R3-T5.2; the "Not built yet" line says so, and `executors_checked` and `token_digest` are written empty.
- The user guides in `plugins/tempergraph/docs/guides/` do not mention schedules, so the new verbs make none of them false and none was touched; the release plan gives a schedules guide to row R3-T10.1.
- The machine-wide rule files were outside the working directory (the read was denied), so the rules were read from `plugins/temperspec-tgraph/rules/`. The three external sources of R-150 were read through search excerpts, since fetching the pages was refused; R-150 says so.

## Open questions

- Should `schedule parse --count n` bound the recurrence (as `add --count` does) or set how many slots the echo lists? SCH-B27 lists `--count` for `parse` apart from `<when>`, which suggests the second; the first keeps the echo of `parse` equal to the echo of `add`. Default in spec `schedules` until answered: it bounds the recurrence and the echo lists three slots. Planning is not blocked.
- ADR-0095 to ADR-0099 still read `Status: proposed` (2026-11-20). The task builds from them and ADR-0132 (accepted) puts schedules in release 3, so planning is not blocked; accepting or editing them is the owner's call.
