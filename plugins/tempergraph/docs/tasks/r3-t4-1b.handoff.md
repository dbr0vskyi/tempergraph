## Decisions

1. Where the reservation rules live. BUD owns reservations and BUD-B12's trigger already lists council members, so BUD gets scenarios and criteria and no new behaviour; CNL-AC7 only points at BUD-AC13 and BUD-AC14.
2. WFM-B10's scenario names a field, not a kind. When this run and the contest run have both landed, no unit kind is left in `LATER_KINDS`; a field scenario stays true then, and `test_later_fields_not_in_release` (`tests/test_validate.py` lines 196 to 199) already proves it. `LATER` at line 164 loses `Council` and keeps `Contest` until the contest run lands. WFM-B13 keeps `contest` refused for the same reason.
3. BUD-AC10 and BUD-AC11 are left unused on purpose. The contest run adds criteria to the same list on its own branch and an id is defined once; skipping two numbers avoids a collision. Nothing else depends on them.
4. A member's reservation. BUD-B12 reserves the per-session cap, else the share. A member has no cap field (CNL-B9); a per-session cap reaches it from the step-side scopes, as it reaches a step (spec 80 line 17: `steps` covers "council members and chair"). `settings.py` line 43 is `SESSION_KINDS = ("step", "map")`, so a council unit gets none of those scopes today. The plan extends the settings resolution to member and chair sessions for `session_cost_cap_usd`, which BUD-AC13 and BUD-AC14 need, and for the executor and model of a member, which CNL-B9 calls "resolved on the step layer". Other step-side keys for councils are not needed by any criterion. The width of the share is the members of the round (BUD-B13's new scenario); a session that runs alone, the chair, has width 1.
5. Two caps, two outcomes. CNL-B8's `cost_cap_usd` is checked by the council before it starts a member session and ends the attempt `cap_reached`. The run's cap acts through the ledger: wait, refuse, drain `cost_cap` with exit 5 (BUD-B12 to BUD-B15). A catch for the plan: the ledger does not refuse a width-1 reservation when nothing else is in flight and spend is already over the cap, because the share is then negative and the sum equals the cap (`run/reserve.py` lines 20 to 22 and 53). The chair, or any council session run alone, must therefore also meet the check made before an attempt (`_boundary`, `run/nodes.py` lines 271 to 279), or the run cap would not stop a council between its last round and its chair.
6. Crash, drain and resume. ADR-0062 decides the subgraph with an engine-owned barrier "so a crash resumes only unfinished sessions", and the checkpointer keeps the pending writes of tasks that finished in an unfinished superstep (R-133 S5 and F2); CNL-AC4's test is the proof. A cost-cap drain mid-round is not a crash and CNL-B14 states resume only for a crash. The plan reuses the per-session checkpoints so that a resume after the cap is raised does not rerun finished members; no criterion proves it, so the code report says what was built.
7. The blueprint keeps stating no council. `author/blueprint.py` line 43 builds `BLUEPRINT_LATER_KINDS` from `LATER_KINDS` plus `subworkflow`, and `RELEASE_KINDS` (line 52) holds eight kinds without `council`. Dropping `council` from `LATER_KINDS` alone would turn the blueprint's `not_in_release` for a council into `blueprint-invalid` ("is not a unit kind") and break `tests/test_blueprint.py` line 102. The author skill (`skills/author/references/steps-and-executors.md` line 15) already calls council a later kind of the authoring surface, as it does a sub-workflow, which the engine builds and a blueprint does not state (SCF-B9). The plan lists `council` beside `subworkflow` in the blueprint's own list, so line 102 holds as written and the skill and SCF-B9 stay true. Open question 1.
8. The warnings of CNL-B16 and the audit. CNL-B16 says the engine SHALL warn on one model family, an even-count `majority` council and `rounds > 0` with `anonymize: false`. ARC-B15 (spec 56 line 79) names the first two as audit rules `council-one-family` and `council-even-majority`, which `audit/__init__.py` lines 173 to 178 skip with "the council unit is not built yet" and spec 55's Not built yet bullet names. The plan builds the three warnings with the unit, so that the skip reasons and the bullet stop naming the council (task AC 7); `Capabilities.families` (`contracts.py` line 570) gives the family of an alias. Every tier of the claude executor is `anthropic` (`executors/capabilities.py` line 23) and claude is the only executor in release 3 (ADR-0132 line 38), so a council on it will carry the one-family warning; that follows from the rule. Release 2 left `unbounded-wait` skipped after it built ask and wait, so building a kind has not always built its audit rules. Open question 2. The audit's two history rules read a `council` record that no spec defines (`audit/history.py` lines 10 to 14 and 345; EVT-B13 and EVT-B15 define `council_round` and `council_tally`); they stay as they are, and the plan writes only the EVT records.
9. Keys not stated. CNL-B14 gives session keys for `member` and `chair` sessions only. The plan chooses the keys of a re-ask and of a ranking pass (for example round `r + 1` for the pass) and keeps the member name and the round in the key, which RDD-B9 relies on. CNL-B16 holds nine groups of refusals with fourteen alternatives; the plan gives each different cause its own finding code and a fixture.
10. CNL-B7 is read as: under `retry_scope: chair`, every RETRY of the council's gate reruns only the chair. Every criterion of that gate grades `decision` (CNL-B4), so every unmet blocker concerns the synthesis, and the engine has no way to sort blockers by topic without a model. A defect the judge attributes to an earlier unit takes the gate's upstream path, not this retry.
