# Hand-off: r3-t8-2

## Problem

Release 3 phase R3-T8.2 builds three features that release 2 left behind: in-process observers (EVT), the worktree extras (WTR) and session review in stable mode (SRV). Their specs already state the behaviour, so the document work was narrow: two clauses in spec `session-review` (in SRV-B16 and SRV-B7) said "until stable-mode plans are built" and stop being true once the plans exist. Reading the code against each criterion also found that the observers already ship and that one code path disagrees with WTR-AC5; both are recorded below for the plan.

## Gaps closed

- G1: `plugins/tempergraph/docs/specs/session-review.spec.md` (SRV-B16, SRV-AC2): the clause "until stable-mode plans are built, a `signals` plan records `depth: none` with `deferred`" is gone. SRV-B16 now says a `signals` plan records `depth: partial` when a signal or the audit gives it a target and `depth: none` when none does, with one new scenario. SRV-AC2's statement now names the slices of SRV-B16 and the stable-mode money caps of SRV-B21, which are what the task's fixture plans prove
- G2: `plugins/tempergraph/docs/specs/session-review.spec.md` (SRV-B7, the "Not built yet" line under Open questions): the clause "until stable-mode plans are built, review results never file" is gone. The triage note places it in SRV-B28, but line 140 was SRV-B7; SRV-B28 and SRV-AC11 (a `review_repeat` finding never files, in any run) are unchanged and still true. Filing from reviews stays off in this phase and the new Not built yet line says what is left (see Decisions)

## Decisions

- Filing from stable-mode reviews stays off in this phase (G2). AC 3 names plans, saturation and the money caps, and AC 4 asks for a Not built yet line that "names only what is left". Corroborated filing and the proposer's reading of observations belong to the same moved item (X2-26, first-release plan line 239, R-150 F24) but the task does not ask for them. SRV-B7 keeps its design text, so the design stays (ADR-0119 stands); spec `session-review`'s Not built yet line now says it is not built. The code agrees: the loop child runs the review after filing (`child.py` 260-268), no module marks a model-free finding with `review:<category>`, and only `review_repeat` findings carry `review_weight` (`repeat.py` 72-73). SIL-B16 states the corroboration with no stable-mode condition and is unbuilt in dev mode as well; it is named in the Not built yet line, not edited. Open question 1 asks the owner to confirm
- A `signals` plan is `depth: partial` when it has a target and `none` when it has none. SRV-B15 lists `partial` and nothing said when it applies; the removed clause was the only place that said what a `signals` plan records
- Saturation (SRV-B5) counts the corroborated observations a cluster holds, which PRP-B12 reports as the cluster's `review_weight`. With model-free corroboration unbuilt, the `review_weight` of a cluster of a model-free cause stays 0 in a real run, so saturation can hold only in fixtures that plant it. AC 3 asks for fixture plans, so it is provable. The plan builds the check as: the cluster of the signal's finding (`proposals.cluster_key`), its member findings on the current workflow version, the sum of their `review_weight` at 3 or more gives `skipped: saturated`. It does not widen what counts
- The stable caps are the three money caps of SRV-B21 (`review.run_share.stable` of the run's cost, `review.run_cap_usd.stable`, and the day's room under SIL's daily cap, SIL-B20) plus `review.max_sessions.signals` (3 sessions per run, the rest `skipped: budget` in SRV-B24 order). Today `plan` sets `cap_usd` from the first two only (`review.py` 163-166), the daily room is read by the loop child, which skips the whole review at zero room (`child.py` 218-221) but does not lower the cap by what is left, and `review.max_sessions.signals` is defined (`params.py` 44) and read nowhere. SRV-B21 and SRV-B25 already say "shared"; the code is the defect, no spec change
- Tickets: `hand_off` writes a ticket whenever the review setting is not `off` (`child.py` 92-98), so every stable final exit would start a loop child. SIL-B1 writes a ticket when "its session review plan has a depth" and SRV-B4 says a clean first-pass run that is not the 20th plans `none` and spends nothing. The plan decides how `hand_off` learns the plan's depth; the specs are right
- In-process observers have shipped since release 1 (t7 plan row 7.1.10; the r2-t7 triage says "in-process observers already ship"), although ADR-0125, the second-release plan and ADR-0132 list them as moved to release 3. Nothing refuses them: `observe.observers` is read from the operator files (`settings.py` 438-452). What differs from EVT-B23 and EVT-B5 is: no preflight warning for a missing observer (EVT-B23 says "warn at preflight and record it"; the name is only listed as `observers_missing` on `run_started`), and the tests carry `AC-5` in a comment instead of `EVT-AC5` and put their observer in by patching the run log instead of registering it under the entry-point group. No engine code calls `ObserverHub.close`; EVT-B23 does not ask for a drain, so that is noted, not required. The plan's AC 1 work is the warning and the EVT-AC5 tests with a fixture observer registered in-test; nothing in EVT-B23 or EVT-B5 changes
- Worktree extras: WTR states every value and verb. The code refuses `in_repo`, `path:`, `default_branch` and `on_finish` in `settings.py` (159-172, 202-206) with `setting_not_in_release`, and a workflow's own `worktree.base` and `cleanup` reach the same checks as the `workflow:default` layer (`settings.py` 662-664). It places every worktree under the sibling root (`workspace.py` 66-67, 180; a rerun at `rerun.py` 327; carry at `carry.py` 524-527), calls `release_workspace` with no cleanup value (`runner.py` 540), and has only `worktree list` and `worktree path` (`main.py` 151-155, 851-863). `test_settings.py` 80 and 87 pins the `in_repo` refusal and must move to a value that stays refused. No test carries a `WTR-AC` id yet
- `workspace.py` 262-265 (`_remove_new`, the rollback that WSP-B2 and WTR-B22 require after a failed bootstrap) calls `git worktree remove --force` and `git branch -D`. WTR-AC5 forbids both on any code path and no test pins it yet. WTR-AC5 is read as written, and the plan re-implements the rollback without those calls; open question 2 offers the owner the other ways out
- `worktree prune --apply` "recording its caller" (WTR-B27): PRV-B17 lists where a mutating call's caller block goes and does not name this verb, and the `worktree` parser takes no caller options. Verbs outside that list put the block in their own result (`hooks add` and `hooks remove`, `main.py` 718-723). The plan does the same and adds the caller options to the `worktree` parser; PRV is not edited
- Left for the code step, because they say what is built and are true only once the code lands (AC 4): spec `worktree-mode`'s Not built yet bullet (line 188), to name only writer, slot and item worktrees and the probes P-WTR-1 to P-WTR-4; the R3-T8.2 record in the release 3 plan in the form R3-T1.1 uses (a Goal line and a `Status: built.` line naming the proved criteria, the test files and what remains; the header Status at line 40 lists built phases too); and the release-split sentence of R-150 F24 (line 256, "Until then a `signals` plan records `depth: none` with `deferred: signals_release_2`"), which becomes false. All three belong in the plan's Docs to update. Spec `session-review`'s Not built yet line is final as written: it names what stays unbuilt after this phase
- Not edited, on purpose: spec `worktree-mode` (it states all of AC 2), spec `run-events` (EVT-B23 and EVT-B5 cover AC 1), SIL-B1 and SIL-B16 (they state what the code should do), ADR-0119 (its sentence that corroborated filing "comes with stable-mode plans" is a release statement; the Not built yet line carries the present state), PRV-B17, and RST-B32 (it lists `setting_not_in_release` for the audit judge, council, contest, wait and ask keys only)

## Open questions

1. Does stable-mode review also file in this phase? It does not block planning. Options:
   - (a) No. Plans, saturation and caps only; corroboration and filing stay in spec `session-review`'s Not built yet line for a later phase.
   - (b) Yes. Build SRV-B7 and SIL-B16 with the plans. That means the loop child runs the review before filing instead of after (`child.py` 260-268), a kept observation marks a model-free finding of the same unit and run with `review:<category>` and `review_weight`, the issue body gains the category word and no note text, and saturation then has real corroboration to count. It needs a criterion of its own (SRV-B7's two scenarios have none beyond SRV-AC5's canary) and it changes what reaches a code host.
   - Recommended: (a) now and (b) as its own phase, because (b) changes what reaches an issue tracker and the task names no criterion for it. Until answered, planning reads (a).
2. WSP-B2 and WTR-B22 require a failed start to remove the worktree and branch it just made; WTR-AC5 forbids any code path from calling `git worktree remove --force`, `git branch -D` or `git branch -d`; the code's rollback does the first two. It does not block planning. Options:
   - (a) keep both texts and re-implement the rollback with other calls: unlock, remove the new folder, `git worktree prune`, delete the new branch's ref with `git update-ref -d`. WTR-AC5's scan passes as written; the engine still deletes the branch it made seconds earlier.
   - (b) edit WTR-B23 and WTR-AC5 to name the rollback of a start that has just failed as the one exempt path, and leave the rollback as it is.
   - (c) leave the new branch in place on a failed start and edit WSP-B2 to say so; a retry then meets `branch_exists` (WTR-B5) until a person deletes the branch.
   - Recommended: (a) or (b). Both keep ADR-0103's test, that no work is lost, because a worktree and branch with no run in them hold nothing of a person's. (c) changes WSP-B2 and costs the person a manual step. Until answered, planning reads (a).
