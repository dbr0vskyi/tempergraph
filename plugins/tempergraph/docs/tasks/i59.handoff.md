# Hand-off: i59

## Problem

The improvement loop starts only at a final exit that a runner reports itself. Three ends never reach it: a person's stop of a thread paused before a unit (`--pause-before`) writes no record at all, a person's stop at a gate makes a loop that reads only the stop's own segment and so misses the faults of the pauses before it, and a runner that was killed, crashed or cut off by a timeout writes no exit. The documents now say that each of these is handed to the loop, a lost runner once per thread and found by `status`, `stop` or `attention`; no code, test or plan was touched.

## Decisions

- Reading of "paused and then stopped": a person stops a paused thread with `resume --decision stop`. At a gate the stop is already exit 4 and a loop starts (HUM-B12), but the loop reads only the stop's own segment (the ADR cites the lines), so the paused segments' faults go unjudged and, in stable mode, no review is planned. Before a unit named by `--pause-before` the stop writes `exit.json` and returns, so nothing is recorded (`runner.py`, lines 949 to 957). "Marked unfinished while paused" is that breakpoint stop. FLX-B10 words its result as "stopped and resumable" and the code leaves the thread `unfinished`; SIL-B27 names only the exit code and the reason, on which both agree.
- A discrepancy outside the gaps, left alone: FLX-B10 says a breakpoint counts as neither an escalation nor friction, but `plugins/tempergraph/engine/src/tempergraph/improve/causes.py` (lines 166 to 190) derives `escalation:breakpoint`, a fault, from a breakpoint's pause record. SIL-B28 takes in the findings that exist, so a fixture for AC 2 should pause at a gate on a real cause such as `retries_spent`, as the scenarios of SIL-B28 do; the scenarios hold whichever way the cause is settled.
- The `stop` verb on a paused thread is unchanged (RCT-B3, RCT Purpose: a stop never decides a gate). The `stop` of the issue's "next `status`, `stop` or `attention`" is read as a verb that finds a lost runner, which it answers with exit 2 as before.
- "Killed" and "timed out" are one case. The timeout of R-160 F7 is the caller's, and the engine sees only a free lock and a segment with no `run_exit`, which RDD-B14 already calls orphaned. No grace period: the loop reads records that are complete at the kill, and a later resume has its own exit.
- Observers write once, which the acceptance criteria require (they rank above the specs): DUR-B4, CLI-B6, CLI-B8, OVR-B15 and RCT-B3 each take one clause pointing at SIL-B29, and OVR-B15's scenario and a new RCT-B3 scenario say what stays true. The acceptance criteria of those specs (DUR-AC3, RCT-AC5 and the criterion that every read-only verb leaves a fixture's hash unchanged) are not edited: they hold for fixtures with no lost runner. SIL-B32 keeps the verbs' output and exit code unchanged and says they start no session.
- The engine writes no `run_exit` for a lost segment. That keeps `health.orphaned` true (RDD-B5, RDD-B14; the monitor shows it), and fires neither the run-exit hooks nor the central stats row. The segment's settlement is its ledger row (exit 5, reason `runner_lost`) with the records of SIL-B8, so `finding_recorded` is written without a `run_exit`; EVT-B14 does not forbid it and SIL-B8 asks for it on every exit.
- "Once per thread" is read per trigger: the first lost runner of a thread starts the loop, a later lost segment of the same thread is recorded and starts none (SIL-B31), and for a stop the findings of a pause are judged once, by the first loop that follows them (SIL-B28). A later final exit starts its loop as every final exit does, so a thread lost once and then finished has two tickets. The alternative, once per end, is option E of the ADR and an open question below.
- The window of 7 days (`lost_runner.window_days`, provenance `default_no_data`) is an assumption of this step, to keep the first `status` after an upgrade from starting a loop for every old dead thread. IMD-AC3 asks every threshold named in SIL to exist as a parameter record, so the code step adds one.
- In stable mode a lost runner follows the lens rules of its mode and is no signal of its own (SIL open question); in dev mode, the default, a lost runner's exit 5 gets a ticket when its friction lens fires or its review plan has a depth, which `session_review: auto` gives in dev mode.
- Not edited, and why: SIL-B1, SIL-B9, SIL-B10 (a lost runner and a stop join them as final exits; their text holds), SRV-B13 to SRV-B16 (the plans are the same; the stop feeds them more findings), RDD-B5 and RDD-B14 (the flag stays), HUM-B12 and FLX-B10 (the decision and its exit code), the monitor's own documents `plugins/tempergraph-monitor/docs/adr/0002-poll-files-and-read-only-verbs.adr.md` and `plugins/tempergraph-monitor/docs/specs/01-data-sources.spec.md` (they call `status` read-only and the monitor polls it, so its first poll after a runner dies now hands the thread to the loop; flagged for the monitor's owner, outside this task's gaps), the guide `plugins/tempergraph/docs/guides/improving-workflows.guide.md` (line 7 says what happens "after every run") and two skills that name `status` as free of effects (`plugins/tempergraph/skills/run/SKILL.md`, lines 50 to 53, says it "spends nothing"; `plugins/tempergraph/skills/troubleshoot/SKILL.md`, lines 9 to 15 and 23, is "read-only, always" and runs `status`), all three of which the code step updates.
- No "Not built yet" line concerns this issue. SIL has none, and the one in the session review spec concerns corroboration (SRV-B7), which this task does not touch; nothing was removed.
- Size: spec 16 has no non-ASCII character and, measured from line lengths since this step has no shell, lies between 23 KB and 30.0 KB, most likely near 27 KB, against the 30 KB budget test; a later edit of it has little room.
- Left for the plan and code steps, where the code differs from the documents today: `run/runner.py` (the breakpoint stop returns before any record; `_drive` and `_loop` are the only path to a ticket), `improve/record.py` and `improve/child.py` (a ticket carries the stop's own fingerprints only, and the friction lens needs a fault in them; SIL-B28 needs a record of what an earlier loop judged), `improve/review.py` (`_signal_findings` reads the ticket's fingerprints), `improve/params.py` (the new parameter), `durability/status.py`, `observe/attention.py` and `cli/main.py` (the three verbs find a lost runner; the thread's run lock, taken without waiting, is the natural claim, since a second verb then finds it held, DUR-B10), `tests/conftest.py` (sets the loop `off` for every test, so a ticket test sets it back as `tests/test_loop_child.py` does) and `tests/test_detail.py` (its orphan fixture, a stand-in judge that raises, is a lost runner).

## Open questions

None blocks planning; each has the default the documents already use.

- Is "once per thread" once per trigger and thread (the default), or once per end? Options: (a) once per thread, so a thread lost again after a resume is recorded and starts no loop, which bounds cost and keeps repeated reviews of the same sessions out; (b) once per end, so every lost segment starts a loop, with the review plan reading the whole thread each time. Recommended: (a), as the criterion says.
- Is 7 days the right window for a lost runner? Options: (a) 7 (the default); (b) none, so the first look after an upgrade starts a loop for every old dead thread in the state root; (c) another figure. Recommended: (a) until a first run shows how many old threads a state root holds.
- Should a lost runner be a stable-mode signal of its own? Options: (a) no, it starts a loop only when its segment holds a signal (the default); (b) yes, which adds it to the stable-mode friction triggers of SIL-B10 and to the signals of SRV-B16. Recommended: (a); the runs of R-160 F7 were dev-mode runs.
- Should `resume` and `wait` also find a lost runner? Options: (a) no, only `status`, `stop` and `attention` (the default), so a thread resumed first is skipped; (b) `resume` settles the lost previous segment before its own start. Recommended: (b) if the owner often resumes without looking first; (a) keeps to the issue.
- Should the monitor's documents say that `status` writes once? Options: (a) leave them (the default); (b) amend ADR-0002 and the data-sources spec of the monitor. Recommended: (b), by the monitor's owner.
- Should a paused thread that is resumed with `proceed` and then ends also have its earlier pauses judged? Options: (a) no, since no criterion asks (the default); (b) extend SIL-B28 to every final exit after a pause. Recommended: (b) as a follow-up issue, since the same hole exists there.
