# Hand-off: i6-8

## Problem

GitHub issues #6 and #8: a session review result reaches neither filing nor the proposer. Only a category kept in three sessions of one run becomes a finding (a `review_repeat` finding), nothing counts runs, a kept observation never adds its category to an issue (SRV-B7, SIL-B16), and the proposer never reads kept observations (SRV-B10, PRP-B4). Spec 44 was at 30,281 of its 30,720 bytes, so the repeat behaviours moved to a split-off spec and the new criteria fit.

## Decisions

- Split by capability. Spec 44 measured 30,277 characters plus 4 bytes for two three-byte characters, 30,281 bytes of the 30,720 cap. The criteria for SRV-B7 and SRV-B10 alone would pass it. The repeat behaviours and their two criteria are the one capability the task already edits, and the only moved ids that another document links by path are in one decision record. The split-off spec keeps the prefix `SRV` as `judge-read-share.spec.md` does (the engine's spec-form test allows one criteria prefix per spec). SRV-B31, SRV-AC13 and SRV-AC14 belong to `judge-read-share.spec.md`, so the new ids are SRV-B32, SRV-AC15, SRV-AC16, SRV-AC17 and SRV-AC18
- G3 default (the task states it, and the triage note's `Owner decisions` gives option a): a repeat across 3 or more runs reaches the proposer and files no issue by itself. The prompt gave no conversation value (`⟨missing:settings.conversation⟩`), but the triage note has the sorted gap rows and the `Owner decisions` section of an unattended run, so the unattended rule applied: the default's behaviour is in SRV-B28, the spec holds no open question for it, and no decision record was written. The triage note's own suggestion to record the assumption in spec 44's open questions and in the decision record was not followed for that reason. The owner sees the assumption in the triage note's `Owner decisions`. The existing record stays true: it files nothing in the run that records the finding or in any later run
- What counts as a run: a run of the workflow in the local run store, counted once however many of its sessions kept the category. A kept observation counts, one the citation check rejected counts for nothing, and units count apart. Nothing in the task names a version or an age limit, so every run of the workflow counts (see the open question)
- Where the cross-run finding goes: the run whose reviews reach the count records it, and so does each later run that keeps the category on the unit; it names its runs. It has the cause and fingerprint of the finding of SRV-B26, so both kinds share one cluster and SRV-B28 covers both: a repeat inside one run reaches the proposer too, which goes one step past the task's text but changes nothing the cluster could tell apart. `improve backlog` counts the runs that hold the finding, so it shows two runs after a fourth. Earlier runs' records are not rewritten, so their observations are not `corroborated` (third scenario of SRV-B27)
- "Reaches the proposer" means the loop's own proposal of PRP-B23 (stable mode, every other condition of PRP-B23 unchanged) at autonomy `propose` or `trial`, and `improve propose` by a person at any level (PRP-B11). At `record` and `file` the cluster is only listed. PRP-B23 and PRP-B11 are not edited: "this run's findings" already reads as every finding recorded for the run, the review's included. The code is narrower today (see the reading list)
- Corroboration (SRV-B7): ADR-0119 (A1) takes any model-free finding on the same unit and run as a fair corroboration "even when the two describe the problem differently", so no table pairs categories with causes. A finding whose issue the friction judge does not file still carries `review:<category>` and `review_weight`. An observation never lifts a finding over the judge's floor: SIL-B16 and SIL-AC8 stay as they are
- Scope of the proposer's reading (SRV-B10): criterion 4 says "the kept observations of that unit" and PRP-B4 says "its member runs' kept observations". They agree as: the kept observations of the cluster's unit, every category, from the runs the cluster's findings belong to or name. A cross-run finding sits in one run and names the others, so naming matters. PRP-B4 is not edited
- The child's order (SIL-B17) is not edited, but the plan must settle one thing: SRV-B7 puts the category word in the issue body, so the run's kept observations must exist when the issue is written, and `process` files before it reviews today. SIL-B17 lists the child's duties without a clear order. If the code step reads its list as an order, it edits that line in the same pull request
- The canary criterion (SRV-AC5) counts as changed, since it names SRV-B7 and SRV-B10, which changed. Its canary test names `AC-5` in a comment, not `SRV-AC5`, so the code step adds the id there

## Open questions

None blocks planning; each has the default in force.

- Should old runs stop counting toward a repeat across runs? Options: (a) no, every run of the workflow in the local store counts, as the task says "runs of a workflow"; (b) only runs of the current workflow version, as the saturation rule of SRV-B5 counts; (c) only runs inside a window of days. Until answered: (a). Under (a) a run of a new version that keeps the category once, after a fix merged, records the finding at once, because the old runs still count. Changing it is one clause of SRV-B32 and the count in the code
- The owner decision G3 of the triage note: may a review category kept on one unit in N runs file an issue or reach the proposer with no model-free corroboration? Options: (a) it reaches the proposer at 3 or more runs and files nothing; (b) it reaches the proposer and files at 3 or more runs; (c) it stays a record only. Until answered: (a), the default in force in SRV-B28 and SRV-B32. A change to (b) or (c) is one edit of SRV-B28 and SRV-B32 and their two criteria, and a small code change
