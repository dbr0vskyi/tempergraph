## Acceptance criteria

1. A friction finding whose fingerprint meets the pattern rule files by the count only when at least two answers are recorded for that fingerprint inside `pattern_rule.window_days` (the `answers[]` of the `loop_judged` records of the workflow's runs, this run's answer included) and more than half of them are `attributed: true`; a tie does not file. With one recorded answer only, the finding is recorded with reason `few_answers` and files by the count at no confidence; it still files when that answer is attributed at or above `friction.file_confidence`. SIL-B18 states it, and a fixture proves each case: answers (true, false, true) file, (false, true) and (true, false) do not, one attributed answer at 0.5 does not, one attributed answer at 0.8 does.
2. The friction judge's brief says that an answer `attributed: true` can file the finding by the count whatever its confidence, and a test asserts the sentence is in the prompt the judge session receives.
3. The loop adds at most `seen_again.max_per_issue_per_day` (1, a loop parameter with provenance `default_no_data`) "seen again" comments to one issue in one UTC day, counted from the `issue_commented` records of the workflow's runs in the state root; a comment over the bound is not sent and leaves one `loop_result` record with op `comment_capped`, the issue's number and no text. `loop-issues` states the behaviour. A fixture of three exits on one day with one open issue leaves one comment and two `comment_capped` records, and an exit on the next day adds a second comment.
4. A loop issue closed with state reason `duplicate` mutes its cause as `not_planned` does (ISS-B3): inside `mute.days` no issue is opened and no comment added, and the result is `muted`. A test against the memory code host proves it, and the closed-reason cases already tested (`not_planned`, `completed`, none) keep their results.
5. A friction finding that does not file is recorded with exactly one of these reasons: `not_judged` (no answer), `not_attributed` (this run's answer is `attributed: false`, at any confidence and any count), `few_answers` or `not_attributed` by the majority of criterion 1 (the spec says which), `below_count` (attributed, the count not met, confidence below the floor), `below_floor` (kept only if a case remains for it; if none remains it is removed from code and specs). A test names each reason once.
6. Every decision for a friction finding of class `fault` that reached the judge carries the runs, requests and machines counted, and its `loop_result` record holds them as numbers; an `issue_filed` and an `issue_commented` record hold the decision's reason (`pattern_met` or `fault`). A test reads the records of a fixture loop child.
7. A request digest counts once per thread in the pattern rule, for both lenses: a fixture of three runs of which two share a request and one holds two digests does not meet `pattern_rule.min_distinct_requests`, and three runs with three requests still do. SIL-B3 states how runs and requests are counted.
8. An operator can make every run of a workflow on a machine record and not file without an environment variable: a setting the engine reads at each final exit, from the settings file an operator already uses for run settings, lowers the workflow's autonomy to `record` for runs started before the setting was written as for later ones. `self-improvement` or `engine-cli` states the key, and a test proves that a thread started without the setting and ending after it was written files nothing and records reason `autonomy_record`.
9. `tempergraph resume` accepts `--dry-run` with the meaning it has on `run` (the thread's loop files nothing and records `would_file`), `resume --help` shows it, and a test resumes a paused fixture thread with it and finds no issue, no comment and a `would_file` record.
10. `docs/guides/improving-workflows.guide.md` has a section on holding filing that names the three ways (the setting of criterion 8, `--dry-run` on `run` and `resume`, `TEMPERGRAPH_AUTONOMY=record`), says what each still runs and records, and says that closing a loop issue as not planned or as duplicate mutes its cause for `mute.days`; the guide's commands are the CLI's.
11. A replay test on an engine fixture, with a scripted judge and the memory code host, of five runs with five requests of a fixture workflow whose records hold, in each of at least three runs: a pause answered by an agent (cause `agent_decided:escalation`), a check failure at a step whose check ran the repository's suite and failed for the environment (recorded as `check_fail` for that step), and `retries_spent` after the executor reported a usage limit; the judge answers each as the review measured (attributed false in most runs, true in one).
