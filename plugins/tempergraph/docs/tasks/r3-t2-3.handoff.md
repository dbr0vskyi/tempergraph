# Hand-off: r3-t2-3

## Problem

A sub-workflow child must be learned from and measured as its own workflow (SWF-B9), and a parent run carried on a branch and paused inside its child must resume on a second state root and finish (SWF-AC3). Spec 99 already stated both, but SWF-B9 had one scenario for four results and SWF-AC1's statement covered only SWF-B1 to SWF-B6, so acceptance criteria 1 to 4 could not be proved from it; SWF-AC3 did not say what "finishes, the child's state intact" shows. The short visits also left open whether a child's outcome record counts in the child's promotion window.

## Gaps closed

- G1: `plugins/tempergraph/docs/specs/99-subworkflow-unit.spec.md`, SWF-B9 scenarios 1 and 2 and SWF-AC1. A child gate's `judge_state` is read from the child's own calibration cases and is not shared with a parent gate of the same name, and the child's judge session runs on the alias the child declares. JCL-B14 and JCL-B17 stay as they are.
- G2: `plugins/tempergraph/docs/specs/99-subworkflow-unit.spec.md`, SWF-B9 scenario 3 and SWF-AC1. A workflow-side friction finding on a child unit goes to the child's `issue_repository` with `sides: [workflow]` and `workflow: <child>` and names the parent. SIL-B18 stays as it is: for a child's unit, the workflow it files to is the child.
- G3: `plugins/tempergraph/docs/specs/99-subworkflow-unit.spec.md`, SWF-B9 scenarios 4 and 5 and SWF-AC1. The child's outcome record counts in `outcome show <child> --runs` carrying `origin: subworkflow:<parent>`, and ten such records with no run of the child's own leave the child's promotion window empty. This answers the point the short visits left open by reading PRO-B8 (`plugins/tempergraph/docs/specs/95-promotion-check.spec.md`, line 53) as it stands: the window takes the last finished runs of the workflow itself, and a child's outcome record from inside a parent is a record of the parent's run (the child has no `run_started` of its own, SWF-B8), so it is outside the child's window unless a window is told to read it, and none can be yet. Spec 95 is not edited.
- G4: `plugins/tempergraph/docs/specs/99-subworkflow-unit.spec.md`, SWF-B9 scenario 6 and SWF-AC1, with VER-B17, WUP-B6 and WUP-B16 (`61-version-metadata.spec.md`, `63-workflow-upgrade.spec.md`), which already define the child's notes, the `rename_field` item and the plan's reading of a sub-workflow's notes. The shape of the child's `changes/<version>.json` is VER-B9's entry narrowed by VER-B17; which detect rule finds a parent's reference to a produced key is the plan's to choose, and the scenario needs only the item and its hit.
- G5: `plugins/tempergraph/docs/specs/99-subworkflow-unit.spec.md`, SWF-B8's second scenario and SWF-AC3. A carried parent paused inside its child resumes on a second state root, the child continues where it paused, its earlier units do not run again, and the run finishes. CAR-B1 and CAR-AC1 (`96-run-state-on-a-branch.spec.md`) stay as they are: they carry a thread's checkpoint rows by thread, which holds a child's.

## Changed documents

- `plugins/tempergraph/docs/specs/99-subworkflow-unit.spec.md`: edited in place; SWF-B8 gains one scenario (a carried resume), SWF-B9 gains five scenarios and keeps its statement, SWF-AC1's statement covers SWF-B9's scenarios, SWF-AC3 says the run finishes with the child continuing where it paused; no behaviour or criterion id is added, removed or renumbered
- `plugins/tempergraph/docs/tasks/r3-t2-3.handoff.md`: rewritten; the short visit's hand-off had left G3 open

## Decisions

- A child's records from inside a parent stay out of the child's promotion window in this release: ADR-0133 assumption A2 and the task's "only when that window says so" give the default, and no window has a way to say so yet (see the open question).
- Spec 95 is not edited. PRO-B8 already takes only a workflow's own finished runs, and an edit would put every old criterion of spec 95 under the outcome gate's trace, among them PRO-AC5, a live criterion no offline test carries. Specs 16, 50, 61, 63 and 96 are not edited either: JCL, SIL and CAR state no child rule because spec 99 owns it, and VER-B17, WUP-B6 and WUP-B16 already state the change-notes behaviour with scenarios.
- SWF-B9 keeps its id and its one-sentence statement: acceptance criteria 1 to 4 cite it for all four results, so each result gets scenarios in place and no behaviour was split or renumbered.
- `origin: subworkflow:<parent>` marks a child's record, not a thread, so DUR-B11's list of thread origins is unchanged.
- The "Not built yet" line of spec 99's Open questions is true until the code exists and states what is built, so it is left for the code step's docs row, as in R3-T2.1 and R3-T2.2. That row also removes "and a sub-workflow's change notes in the plan" from the Not built yet line of `63-workflow-upgrade.spec.md`, which becomes false once the plan reads a child's notes (WUP-AC7 gets its test from scenario 6, while WUP-AC1 and WUP-AC4 are named by no test today and the task says old criteria of an edited spec need no new test ids), changes `test_subworkflow_docs.py` with the spec, and records R3-T2.3 and track R3-T2 as built in the release 3 plan.

## Open questions

- How does a child's promotion window say that it counts the child's records from inside a parent (SWF-B9, PRO-B8)? It does not block planning: until answered, no window counts them. Options: (a) never, as now, so a child that only ever runs inside parents cannot reach `local-stable` by its own window; (b) an option of `promote-check` that counts them, which changes PRO-B6 and PRO-B8 and puts spec 95's old criteria under the outcome gate's trace; (c) a declaration in the child workflow that its window counts them, which changes the workflow model. Owner: owner.
