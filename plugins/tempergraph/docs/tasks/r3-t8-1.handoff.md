## Decisions

Judge MCP views (G3):

- `judge_mcp` becomes true on `claude` in the change that builds the proxy and passes ECC-AC7 to ECC-AC9. The offline test can be built: a stand-in MCP server is a short stdio script, and `tests/fixtures/standin_cli.py` already shows the pattern of a recorded stand-in that writes its argv and prompt. If the code step finds it cannot, criterion 3 says the spec records why the flag stays false: it then undoes ECC-AC9, the `judge_mcp` word of ECC-B6, the EXI-B19 scenario and the open-question default of spec `executor-interface`, and states the reason in spec `executor-claude-code`'s Open questions.
- The proxy fronts only a local (stdio) server that the operator's own MCP configuration defines. A server found only in a repository (SEC-B3), a server not configured on the machine, a remote server (the open question of spec `executor-interface` says no until answered) and a server whose proxy fails to start are deferred (ECC-B15). The public documentation (https://code.claude.com/docs/en/mcp) says user and local scope are stored in `~/.claude.json`, project scope in `.mcp.json`, and an entry without a `type` is a stdio server. The plan confirms the file shape before it relies on it and may take user scope first.
- The engine must not rest on the CLI's report of a failed server. The same page says a skipped `--mcp-config` entry appears in `mcp_server_errors` and does not say a connection failure does. The judge prompt is rendered before the session starts (`run/nodes.py` lines 887-894 from `views.deferred`), so a failed start has to be known before the prompt is rendered, which means the engine checks each proxy itself before the launch. ECC-B13's `system/init` clause stays as a second signal; it is consistent with ECC-B15 and is not edited.
- A judge's MCP views come from the view catalog (GRD-B1, GRD-B7, GRD-AC6). `run/guard.py` (`view_set`) today adds a step's own `mcp:` tool to its judge's views as soon as `judge_mcp` is true, so a step's write tool would reach the judge. The catalog work comes first and GRD-AC6 must pass before the flag is set. The catalog's first entries are the plan's to fix from the names GRD-B7 states, keyed by full tool name; a tool it does not list stays deferred. See open question 2.
- Tests that pin the old outcome on `claude` change: `tests/test_preflight.py` (lines 124-132, a view of `mcp:tracker/get_issue` deferred on `claude`) and `tests/test_validate.py` (line 71, `judge-view-unavailable` for a `wiki_page` artifact). The new EXI-B19 scenario needs a judge executor that restricts judge tools and declares `judge_mcp` false; the `antigravity` set cannot be it, because its judge moves to `claude` (EXI-B24), so the test builds a stand-in and replaces its capabilities as `tests/test_preflight.py` lines 105-115 do. `judge_argv` (`executors/claude.py` lines 143-154) is called by `test_judge_launch_is_read_only` (`tests/test_claude_executor.py` lines 78-86) with a `ViewSet`, a model and `isolated=`, so a new parameter for the private configuration must be optional.
- Grants stay as they are: `views.add` of an `mcp:` capability is refused with `judge-view-unclassified` (`settings.py` lines 233-244, pinned by `tests/test_settings.py` lines 82-89). The message there says "release 1 has no read-only MCP catalog" and has to be reworded. See open question 3.
- The private configuration follows WSP-B5 and SEC-B12 (owner-only folder under the state root, removed on every exit path, never in argv, a log or an error text) and is proved by SEC-AC5; ECC-AC7 does not restate it.
- A pass against stand-ins proves the capability built, not live-proven (docs README, Readiness). A live check against the pinned CLI is the owner's.

Script cache (G1):

- Only a run that finished and succeeded is recorded in the cache: exit 0 or `ok`, every `produces` key present, not environmental. A failed run, a timeout and an environmental exit are never recorded, so a RETRY after a failure and a resume after the environment is fixed run the script again (SCR-B7, SCR-B2). This reads SCR-B9's "recorded result" of a finished run narrowly; no spec edit is needed. A test for it carries `AC 1` of the task, since no spec criterion names it.
- A restore replaces the run of the script only. The unit's gate (check, author's check, judge) runs as for any unit, as ADR-0067 requires of a judge ("run fresh on each subject").
- Only the `not_in_release` refusal goes from `model/validate.py` (lines 126-130). The refusals of SCR-B6 already exist (`script-cache-side-effects`, line 756-757), as does the `cached` field of the `script` record (`run/nodes.py` lines 539-540 writes `cached=False` today; `observe/detail.py` line 231 shows it).
- LOS-B8's list of the run folder does not name `cache/`, nor `scripts/`, which the code already writes; SCR-B9 owns `<thread folder>/cache/`, so LOS is not edited.

Sampled audit judge (G2):

- The draw is deterministic: the plan keys it on the thread, unit, item and attempt plus a seed, so a resume repeats the same decision for a gate attempt; at 1.0 every judged gate is audited and at 0 none, whatever the seed. Tests fix the seed through a hook such as the fields of `RunSettings` (`run/runner.py` lines 86-105, where `sleep` and `infra_tries` are already test hooks). The spec states the probability only.
- The audit judge's session is a `judge` session. `SessionKind` (`contracts.py` line 520), the request kinds of SSN (spec `session-contract` line 18) and the `session_opened` kinds of EVT (spec `run-events` line 41) are closed lists with no audit kind, and a new kind would edit those two specs. The session is told apart by a session key of its own, which must not collide with the gate judge's folder `sessions/<unit>.<attempt>.judge` (the key format is in spec `run-events` line 11), and by the `audit_judge` record.
- The record carries what OBS-B9 names (executor, alias, per-criterion agreement, usage) and the `statuses` list (`id`, `status`) that `improve/reliability.py` (lines 143-155) already reads and `tests/test_reliability.py` (lines 80-83) pins, so the reliability figures read it unchanged. A failed audit session, or one the guard discards, writes no `audit_judge` record (its `agent_run` is logged like any session's) and changes nothing.
- The two settings leave `NOT_IN_RELEASE` (`settings.py` lines 53-58); their catalog entries exist (lines 209-210). Removal puts them into `targets()` (lines 673-680), so `config show` and the resolved-settings rows change; the tests that count rows follow.

## Open questions

None blocks planning. Each has the default the plan reads.

1. Does the audit judge's cost count toward the run cost cap? BUD-B9 counts "every session's reported cost", JDG-B7 says the audit "never change[s] the verdict, the route or a budget", and JDG-AC7 compares every counter with the run without audit. Options: (a) the cost is logged like any judge's (`agent_run`, the `audit_judge` record) and added to no counter or cap, so a run near its cap is never drained by an audit, and the cap can be passed by the audit's spend; (b) the cost enters the run's spend, and a run at the cap can drain earlier than it would without audit. Until answered: (a), because it is the reading under which JDG-AC7 holds exactly. Owner: owner.
2. Which real MCP servers' tool names should the first catalog hold? GRD-B7 states only the generic rule (a tracker's create or update tool to its `get_issue`, a wiki's update tool to its `get_page`). Options: (a) only those two read views and the stand-in server's names for the tests, so every other MCP tool stays deferred; (b) also the tool names of the servers the owner uses. Until answered: (a); the safe state is out of reach, and a name added later is a data-only change. Owner: owner.
3. Should a person be able to grant a judge a catalogued read-only MCP view (`--grant judge:<unit>=mcp:...`)? RST-B13 says it applies only when the catalog classifies the tool read-only, and RST-B28 says it is refused while no read-only MCP catalog exists; the catalog now exists for derivation, and the grant path does not read it. Options: (a) leave it refused with `judge-view-unclassified` and reword the message; (b) let `views.add` accept the read-only entries of the catalog, with its tests. Until answered: (a). Owner: owner.
