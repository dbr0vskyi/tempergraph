## Decisions

- `defaults` is a word, read before a unit name as `escalate` and `stop` are (`validate.py` line 170, `flow.py` lines 207 and 237). A forward unit named `defaults` cannot be a deadline target. No rule on unit names is added: the same limit already holds for the other two words.
- The marking is in the artifact, not in the run log (the task allowed either): a list of question names under `defaulted`, written only when an applied deadline lets the run continue. A person's `proceed` that takes defaults (ASK-B8) stays as it is and is not marked. The spec says "under `defaulted` in the `answers` artifact"; the recommended placement is a top-level key beside `answers` in the file, so a reader that walks `answers` sees no change.
- A deadline whose defaulted answers fail the author's `check` keeps the run asking, as the task says ("as it would on a person's answers"). Nothing from defaults is stored (the person's still-asking path stores only given answers, `runner.py` lines 1057-1058, and `status.py` counts unanswered questions from that file), the pause stays overdue, and the exit is 3 with the check's problems. The apply is still an accepted resume, so it writes its `deadline` row as a person's still-asking answer writes its row (HUM-B6). The refusal before the deadline (exit 2, nothing written) is unchanged and is pinned for this value by a scenario that names the answers file.
- The refusals for `defaults` hold with or without `deadline_s`. The setting `<unit>.deadline_s` lets an operator add a deadline to a unit that declares none (`settings.py` lines 802-806, `run-settings-and-overrides.spec.md`), so a declaration that validates without a deadline must already be complete. The code's `_deadline` returns early when `deadline_s` is `None` (`validate.py` lines 166-167); the new refusals sit outside that early return.
- A list read from a step (`from`) cannot be checked at validation, so the same rule moves to the entry of the ask (ASK-B13) and stops the unit before the pause, as ASK-B2 does for a malformed list (run exit 4, reason `ask`). The task states the rule for "any required question"; extending it to a list read at entry is derived from AC 1 and ASK-B2, not stated by the task. Consequence: the Markdown list form cannot carry a `default` or `required: false` (`asking.py` lines 73-81), so an ask that declares `on_deadline: defaults` over a Markdown list always stops at entry; the step that writes the list must write the JSON form.
- Falsy defaults count: a `default` of `false` or `0` is a default (`asking.py` lines 170 and 177 test `is not None`), and ASK-B10's first scenario uses `false`.
- An ask with no `check` passes (`asking.py` line 184), so ASK-B10 covers it by its second scenario.
- The diagram needs no new edge for `defaults`: the applied deadline re-enters the ask's human node as `escalate` does (`flow.py` lines 161-162) and proceeds along the unit's PROCEED edge as a person's complete set does. What the code must do is stop `deadline_node` and `reachable_units` from reading the word as a unit name (`flow.py` lines 204-209, 237).
- No research note and no decision record: the triage lists no `research needed` or `decision needed` gap. ADR `flow-extensions-for-langgraph-parity` decision 3 still holds (a deadline is applied only by an explicit `resume --apply-deadline`, never by the supervisor, which `runner.py` lines 890-892 enforce for every value); it lists three values and is not edited, since a record is not edited.
- No changelog file and no version bump are planned: the engine is at 0.2.0 with changelog files for 0.0.1 and 0.2.0 only, release 3 has none yet, an added value asks nothing of a consumer (VER-B9), and the repository check that VER-B6 describes has no implementation in the engine's tests or in any script (searched the non-document files for it). The checks of AC 4 are the ones the code gate has.
- Left for the plan's Docs to update and the code step, because they say what is built: the release 3 plan row I3-15 (drop "(if the owner agrees)", record it as built in the form R3-T1.1 uses), and the id ranges "ASK-B5 to ASK-B9" in the docstrings of `api.py` (line 309), `asking.py` (line 1) and `test_ask_wait.py` (line 1), which may now end at ASK-B13. research `release-three-readiness-and-gaps` line 53 ("listed in the plan as I3-15 for the owner to accept", "FLX-B8 offers escalate, stop or a forward unit") is a finding of its time and is left as written; the plan may list it as a docs row if it wants it to say the owner accepted. The how-to guide `plugins/tempergraph/docs/guides/running-workflows.guide.md` (line 81, "take an overdue wait's declared way out") stays true.

## Open questions

1. A question's `default` is not checked against its kind (does not block planning). `asking.parse` runs only on answers a person gives, so a person's `proceed` already takes a default as declared, and `on_deadline: defaults` now does the same with no person present. A default its kind refuses (a `number` question with the default `n/a`, a `choice` default not among its choices, a `file` default outside the workspace, which ASK-B9 refuses from a person) reaches the `answers` artifact as written. The sharpest case is a list a model wrote for `from`. The task and the specs say nothing about it, so the specs state nothing. Options:
   - (a) leave it: a default is the author's text.
   - (b) refuse a default its kind refuses when `on_deadline: defaults` is declared, at validation for declared questions and at entry for a list read from a step (adds a clause to FLX-B11 and ASK-B13).
   - (c) refuse it for every ask (changes ASK-B5 and the person's `proceed`).
   - Recommended: (b) when the owner wants it; until answered, planning reads (a).
