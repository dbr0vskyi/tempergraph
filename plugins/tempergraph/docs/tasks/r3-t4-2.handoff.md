## Problem

Release 3 phase R3-T4.2 replaces the `not_in_release` refusal of a `contest` unit: slots run up to `concurrency` at once, each slot's check runs before its judge, a fixed rule picks the winner, and `concurrency` and `attempt_cost_cap_usd` are settable. CTS-B1 to CTS-B10 were written ahead of the code, but no behaviour said what the run detail shows for a slot or a winner, no scenario or criterion proved contest slots under the reserving cap, and the per-attempt cap had two names with no statement of how they relate. This step closes those three, and the few spec sentences the build makes false.

## Decisions

- Slots in the run detail are entries of a visit's `attempts` with `item` the slot's name, since the Purpose of spec 31 already says contest slots are items. `keys` are the three numbers the pick compares after the verdict (unmet warnings, criteria met, confidence); `cost` is its own field and the order is the entries' order. A slot's cost is the cost of every session whose key starts `<unit>.<slot>.` (its step sessions and its judge), which is the figure the pick compares and the detail shows. A slot put out by its check has a null verdict and null keys, because no judge ran. The unit's own gate record names no item, so by RDD-B10 it lands on the attempt's entry with no item.
- RDD-B10 had to change because slots run at once. `observe/detail.py` keeps one open attempt for a unit (`current`, `_open`) and puts `check` and `judgement` records there, which misplaces interleaved slots; the builder must place by the record's `item`.
- The run-log record is `contest`, not `contest_pick`. CTS-B7, the audit's reader (`audit/history.py` line 347) and its test fixture say `contest`; only EVT-B15 said `contest_pick`, so EVT-B15 is the one spec changed to settle it. The record holds `winner` and, per slot, the place `slot` from 1, `name`, check result, derived verdict, rank keys and cost, or `skipped`. The place numbers matter: the audit rule `contest-no-gain` reads `slot` and `winner` through `int(...)` (`audit/history_rules_more.py` lines 199 to 208), which a name such as `s1` does not convert, and its fixture (`test_audit_history_rules_more.py` lines 38 to 41) is already shaped that way.
- The declared ranges are refused in CTS-B10 because the settings code range-checks only the operator layers (`settings.py` `validate_layers`, lines 604 to 620). A unit's own value is the `workflow:unit` layer of the same key and nothing else would check it. A map's `concurrency` is checked the same way in `validate.py` `_map` (lines 379 to 380).
- Reservations: BUD-B12 already covers contest slots, so there is a scenario and a criterion and no behaviour. The share is the remaining cap divided by the slots that may run at once, the lower of `concurrency` and the number of slots, as `_hold` does for a map (`run/nodes.py` lines 290 to 293). The scenarios speak of slot sessions only; the judges start after every slot has run (CTS-B7), and if the plan runs them at once they take reservations too.
- WFM-B13 and RST-B32 are edited because the build makes them false, as the sub-workflow task did for WFM-B13 (`plugins/tempergraph/docs/tasks/r3-t2-1a.handoff.md`); they are not collateral.

## Open questions

None of these blocks planning; each says what the plan does until the owner answers.

- What should preflight show for a contest's projected cost range, the last clause of CTS-B10? The stats hold one projection per workflow and none per unit (`observe/rows.py` `projection`, CST-B15). Options: (a) the workflow's median and 90th percentile with the contest's slot count beside them; (b) the slot count times the base step's per-session cost cap where one is declared; (c) both. Recommended: (a), the literal reading of "from the stats projection". Until answered the plan builds no range, CTS says so under Open questions, and the code report names it. Owner: owner.
- What happens when a slot of a contest with `writes: false` changes the run's worktree? CTS-B6 and WSP-B11 do not say; the slots share the run worktree, and a sequential run of them would let one see another's files. Options: (a) fail the slot as a read-only branch or map item fails (`branch_changed_the_workspace`, WSP-B11's fingerprint rule); (b) refuse at validation a `writes: false` contest whose step declares `write` or `edit`; (c) leave it. Recommended: (a), which adds no new refusal. Until answered the plan does (a) and the code report names it. Owner: owner.
- What does a second attempt of a writer contest do about the first attempt's slot worktrees? WTR-B20 names them by slot only, CTS-B7 discards the others and merges the winner, and the Open questions of spec 82 keep every merged branch. Under `retry_scope: all`, or a trip back into the contest, the same names meet branches that still exist. Options: (a) remove every slot worktree and branch at the pick, the winner's after its merge, so the next attempt cuts afresh from the run branch; (b) keep the branches and add the attempt to the name after the first (changes WTR-B20); (c) reuse a slot's worktree. Recommended: (a). Until answered the fixtures of CTS-AC4 cover a writer merge on one attempt only, a second attempt of a writer contest ends blocked rather than overwrite a branch, and the code report names it. Owner: owner.
