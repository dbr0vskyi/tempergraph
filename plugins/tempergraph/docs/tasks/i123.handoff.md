# Hand-off: i123

## Problem

The improvement loop judges how a run went but never what the run delivered: no run records the pull request it led to, and nothing reads a person's review of it, so a `met` run that a reviewer sends back is invisible to the loop. The specs now say that a run records its pull request, that the loop reads it after delivery into `later[]` entries of counts and kinds, that a review asking for changes or a person's follow-up commit on a file the run wrote makes a `met` run an escape, and what an escape does: it fires the outcome lens, becomes a finding, can file an issue and is a harvest candidate. Review text stays in the run's local evidence.

## Decisions

- The triage note lists no owner decision, so none was answered or taken by default
- The conversation value and the owner's answers reached the step as unfilled placeholders; the step treated the run as unattended (`never`), took no decision that only a person can take, and gave each open question below an `Until answered:` default
- The loop does the reading, at its final exits and by the rules of PRP-B26 and PRP-B28; no new verb is specified (the task allows a later command or the loop, and a verb is a later addition)
- The record is on the run's ledger row and holds the code host, the repository and the number; the `finalize` event keeps the url as before
- An escape keeps the population the task and OUT-B19 name (`met`); the signals are the rerun the code already counts, changes requested, and a person's follow-up commit on a file the run wrote
- The finding of an escape is `outcome_escape`, the cause code the audit rule `outcome-escapes` already uses (ARC-B14), so ARC-B4 clusters the two by side, workflow, unit and cause

## Open questions

- Does a run graded `met_with_open` count as an escape? OUT-B19, OUT-B26 and the task say `met`; the code counts both (read `run/outcome_record.py` 159-160 and `audit/history_rules_more.py` 126). Options: a) `met` only; b) `met` and `met_with_open`. Until answered: a for the new signals, and the rerun counting in the code is left as it is
- Two runs can record one pull request (a finalizer that reuses an open one, or a rerun): the commits of the later run are follow-up commits of the earlier run. Options: a) they count as a person's follow-up commits; b) commits that another run of the workflow recorded for the same pull request are left out. Until answered: a
- How long is an open pull request read? Options: a) until it is merged or closed; b) also stop after 30 days, the figure the `pr_state` open question uses. Until answered: a, so an abandoned open pull request costs a few reads at each final exit
- Is a person's outcome label, or a pull request closed without a merge, an escape signal? This is the second open question of `plugins/tempergraph/docs/specs/run-outcome.spec.md` as it stands. Options: a) neither is; b) either is. Until answered: a
- Does the repository name of a recorded pull request count as the remote URL that SEC-B2 keeps out of a ledger row? Options: a) no: the repository comes from the url the finalizer returned, which the `finalize` event already holds, and SEC-B9 allows names in a ledger row; b) yes: the ledger row holds the host and number only, and the loop takes the repository from the workspace's git remote when it reads. Until answered: a
