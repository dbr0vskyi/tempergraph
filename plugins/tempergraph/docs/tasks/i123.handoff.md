# Hand-off: i123

## Problem

The improvement loop judges how a run went, never what the run delivered: no run records the pull request it led to, and nothing reads a person's review of it, so a `met` run that a reviewer sends back is invisible to the loop. The specs now say that a run records its pull request, that the loop reads it after delivery into `later[]` entries of counts and kinds, that changes requested or a person's follow-up commit on a file the run wrote makes a `met` run an escape, and what an escape does (the outcome lens, filing, harvest, corroboration). Review text stays in local evidence.

## Decisions

- No owner decision is listed in the triage note, so none was answered or taken by default.
- The loop does the reading, at its final exits and by the rules of PRP-B26 and PRP-B28; no new verb is specified (the task allows a later command or the loop, and a verb is a later addition).
- The record is on the run's ledger row and holds the code host, the repository and the number; the `finalize` event keeps the url as before.
- An escape keeps the population the task and OUT-B19 name (`met`); the signals are the rerun the code already counts, changes requested, and a person's follow-up commit on a file the run wrote.
- The finding of an escape is `outcome_escape`, the cause code the audit rule `outcome-escapes` already uses, so ARC-B4 clusters the two by side, workflow, unit and cause.

## Open questions

- Does a run graded `met_with_open` count as an escape? OUT-B19, OUT-B26 and the task say `met`; the code counts both (`run/outcome_record.py` 159-160, `audit/history_rules_more.py` 126). Options: a) `met` only; b) `met` and `met_with_open`. Until answered: a for the new signals, and the rerun counting in the code is left as it is.
- Two runs can record one pull request (a finalizer that reuses an open one): the commits of the later run are follow-up commits of the earlier run. Options: a) they count as a person's follow-up commits; b) commits that another run of the workflow recorded for the same pull request are left out. Until answered: a.
- How long is an open pull request read? Options: a) until it is merged or closed; b) also stop after 30 days, the figure the `pr_state` open question uses. Until answered: a, so an abandoned open pull request costs a few reads at each final exit.
- A person's outcome label and a pull request closed without a merge are not escape signals; this is the open question left in `run-outcome.spec.md`, with `Until answered: neither does`.
