# Triage: i196

## Task

`batch-queue/tasks/i196.md` (GitHub issue #196): a loop issue closed as a duplicate binds its cause to the issue it duplicates; later sightings comment there and open no new issue.

## Acceptance criteria

1. The code host client reads, by REST only and with list-argv calls (SEC-B7): the comments of one issue (for each its text and its author kind, as `_kind` classes it) and one issue by number (state, state reason, close time, whether it is a pull request), whatever labels the issue carries. The memory code host gains the same two reads, issues without the loop's label, and comments with an author kind, so a test can seed a person's issue and a closing comment. A test proves each read on the memory host, and a test of `GhCodeHost` with a replaced `gh` proves the two calls, that no search and no GraphQL call is made, and that a bad repository or number is refused.
2. A finding that would file, matches no open loop issue, and whose loop issue closed most recently was closed as `duplicate` with a target named as the design says, opens no issue and adds one comment to the target, inside `mute.days` as after it. The result is `commented` with the target's number, so its `issue_commented` record counts toward the bound of criterion 4. The first learning leaves one `loop_result` record with op `bound` that holds the cause key, the source's number and the target's number and no text. A fixture run proves: closed 10 days ago and 31 days ago both comment on the target and open nothing; the loop issue reopened takes the comment itself (an open issue wins, SIL-B2); a comment by an author without standing binds nothing; with two numbers in the comment the first is the target; a newer comment by a person with standing replaces the target.
3. With no target named, or a target that is the source itself, a pull request, or a number the host does not hold (`HTTP 404`), nothing is bound and ISS-B3 applies unchanged: `muted` inside `mute.days`, a new issue after it. When the read of the comments or of the target fails twice for another reason, no issue opens and no comment is sent, and one `loop_result` record with op `binding_unreadable` holds the cause key and no text. A test proves each case on the memory host, and the closed-reason cases already tested (`not_planned`, `completed`, a duplicate with no target, none) keep their results.
4. The comment on a target begins with a sentence that says it comes from tempergraph's improvement loop, names the cause, the workflow and the units, names the loop issue whose close as a duplicate sends the comment there (`#<n>`), and says that reopening that issue ends it; the sections of a "seen again" comment follow (ISS-B8, ISS-B11, ISS-B12, ISS-B14, ISS-B15) and no request text or free text of a run is in it (ISS-B10: the canary test covers this body). A target gets at most `seen_again.max_per_issue_per_day` comments of the loop in one UTC day, counted over every cause bound to it; a comment over the bound leaves one `comment_capped` record with the target's number. A fixture of two causes bound to one target and two exits on one day leaves one comment and `comment_capped` records for the rest, and an exit on the next day adds a second.
5. A closed target decides by its state reason, read at each filing of the cause: `completed` opens one new loop issue whose `## Summary` names the target as a possible regression, and later sightings comment on that new issue; `not_planned` or `duplicate` mutes the cause for `mute.days` from the target's close time and a new issue opens after it; no reason or another reason opens a new issue that names no regression. A target reopened takes the comments again. A chain (a target that is itself closed as a duplicate of a third issue) is not followed. A test proves each of the five cases on the memory host.
6. The binding record is in the state root, written owner-only, keyed by repository and cause key, and holds ids, numbers and times only. A fixture proves: a second state root with no record (another machine) and the same host comments on the same target and writes the same record; a record whose source issue was reopened is not used; a record whose source has a newer comment naming another number is replaced; an unreadable record file is rebuilt from the host and never stops a filing.
7. A waiting outbox entry that would open an issue, whose cause is bound, is delivered as one comment on the target within the bound of criterion 4 and opens no issue; it is not dropped as muted (ISS-B16, ISS-B17). A test proves it with an entry queued before the close and delivered 31 days after it.
8. A replay test on an engine fixture, driven through the loop child with a scripted judge and the memory code host: three causes of a fixture workflow each have a person's issue without the loop's label and a loop issue closed as a duplicate 31 days earlier, with closing comments in the three shapes of this batch (one number; two numbers in one sentence; two numbers of which the first is also the target of another cause), a fourth cause has a loop issue closed as a duplicate 10 days earlier with no comment, and a fifth has no issue. Over five exits on two UTC days no issue opens for the first four causes, each target gets at most one comment a day, the fourth cause is `muted`, and the fifth opens one issue at the exit where the pattern rule is met.
9. A decision record in the ten-section form of `.claude/rules/temperspec/decision.rule.md` (Context, Current state, Forces, Options considered, Decision, Decision rationale, Consequences, Risks, Assumptions, Revisit when) records how a binding is learned and where it is kept. It links `docs/adr/a-close-as-a-duplicate-mutes-a-loop-issues-cause.adr.md` in its Context as the record it extends, compares at least: the comment text (chosen), a hidden marker line a person pastes, the host's duplicate-of relation through GraphQL, and no local record (read the host at every filing). Its Risks name a comment such as "not a duplicate of #5" on an issue closed as a duplicate, and its Assumptions name the unchecked REST event of GitHub's own close-as-duplicate control. The earlier record is not edited.
10. The behaviours are stated in a new spec named for the capability (bindings of a cause to an issue the loop did not open), with its own prefix, its `## Depends on` rows for every spec its behaviours and criteria link (`loop-issues.spec.md`, `self-improvement.spec.md`, `improvement-data.spec.md`, `local-observability-store.spec.md` as used), and its path added to the Purpose of `overview.spec.md`. `loop-issues.spec.md` (26.5 KB of 30 KB) changes only where ISS-B3 and ISS-B17 would be false (a duplicate with a target is not muted), with a link to the new spec and its `Depends on` row; `self-improvement.spec.md` and `session-review.spec.md` (both above 30 KB) get no new text. LOS-B7 names the record's file if it is at the state root's top level. Every spec stays within 400 lines and 30,720 bytes, and no spec line names a workflow, an issue number of this repository or what the loop did before.
11. `docs/guides/improving-workflows.guide.md` says, where it describes close reasons: closing a loop issue as a duplicate with a comment that says `Duplicate of #<n>` sends the cause's later sightings to that issue as comments, at most one a day; without such a comment the cause is muted for `mute.days`; reopening the loop issue ends the binding; what a closed target does. A test asserts the sentences the guide must hold, as `tests/test_hold_filing_guide.py` does for the hold.
12. The criteria above are numbered 1 to 12 with no gap and are the whole slice: the run adds no criterion of another issue. For each criterion at least one test drives a real fixture run (a fixture workflow run to its exit and its ticket handled by the loop child, as `blocked_run` with `child.drain` or `child.process` in `tests/test_loop_child.py` do, against the memory code host), no test writes by hand a record or a host answer in a shape the engine or the host never emits, each new test carries the id of the spec criterion it proves, any new parameter is in `improve/params.py` with its source, and the tests of runs i171b and i170c still pass, changed only where a criterion above changes the fact they assert (`tests/test_loop_issues.py` `test_a_close_as_duplicate_mutes_as_not_planned_does`, `tests/test_outbox_delivery.py`).

## Intent

- Goal: a cause a person has already filed, and closed the loop's own issue against as a duplicate, stops producing new loop issues; its later sightings reach the person's issue as bounded comments.
- In scope: reading a closing comment's target by REST; a local binding record; a comment on the target; the target's state deciding (completed / not planned or duplicate / other); outbox delivery for bound causes; a new spec, a decision record, edits to `loop-issues`, `overview` and `local-observability-store` specs, the guide, and tests.
- Out of scope: binding without a first loop issue; a binding per unit; detector base rates and consequence causes; grouping a gate's criteria; the filing policy (#208); outbox defects of the i170c review; a lock around read-then-write; following chains, targets in other repositories, a dry run naming the target.
- Assumptions:
  - A1: the new spec's owner is a new capability and not a section of `loop-issues`, since criterion 10 says so and that spec has 3.5 KB left. If wrong: behaviours move into `loop-issues` and break its size limit.
  - A2: "a person with standing" means author association `OWNER`, `MEMBER` or `COLLABORATOR` as `_kind` classes it. If wrong: the standing test of criterion 2 changes.
  - A3: the design section of the task is binding, as the owner decided it on #196. If wrong: criteria 2 to 7 are rewritten.
