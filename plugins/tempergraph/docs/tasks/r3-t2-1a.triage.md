## Acceptance criteria

1. A workflow can declare `Subworkflow(workflow=…, requires=…, inputs=…, produces=…, gate=…, summary=…)`; the blueprint records each field as SWF-B7 reads it (`inputs` values as `request`, `<unit>.<key>` or a quoted literal; `produces` keys exposed under the unit's name to later units, so `{<unit>.<key>}` validates as a reference), and the child is resolved from the registry at run start.
2. Validation refuses, before any session starts and with no spend, each case of SWF-B6 with its code: `subworkflow-recursive` (the child names the parent, directly or through another child), `subworkflow-depth` (nesting deeper than three), `subworkflow-input-missing` (a required child input left unmapped), `subworkflow-version` (the child's version outside `requires`), `subworkflow-unknown` (child not registered or does not load, naming it), `subworkflow-produces` (a `produces` key the child declares no producer for), `needs_git` (a child that needs git under a parent outside git) and a built-in workflow marked `builtin` used as a child.
3. Each refusal is proved by an offline test with engine fixture workflows (a parent and one or more children registered in a test state root) that carries the id SWF-AC1, and a valid parent with a child passes validation.
4. Until R3-T2.2 is built, starting a run of a valid parent with a sub-workflow unit stops before any spend with one clear message that running a child is not built yet; a test shows it.
5. The spec's "Not built yet" line under Open questions names only what is left (running a child, measures and carrying), the release 3 plan records R3-T2.1 as built, and the engine's offline suite, `ruff check src tests` and `mypy` pass.
