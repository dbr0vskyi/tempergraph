# Hand-off: i54b

## Problem

The code check fails any verification command that does not exit 0, so a failure present before the change (an environment fault, or a failure the step noted and reported as `tests_passed: no`) costs retries that no code change can win back: four retries and about 2 USD in run `r3-t1-1b`. The task asks the check to run the commands itself, compare each failure with the run's base commit, and escalate as environmental a failure that was there before the change or that no changed file touches. The check cannot do this today because a command runs only in the workspace, so the engine needs a way to run a command at the base, and the check needs a rule for what the comparison means.

## Decisions

- The base run is an engine capability: `run(cmd, at_base=True)` in the check context. A package routine would be a second launcher with none of CHK-B12's safeguards and no reuse. The engine spec names no workflow (ADR-0129). The engine already escalates a check FAIL marked environmental with no judge and no retry (HUM-B7, BUD-B11), so nothing changes there.
- The comparison is the workflow's policy: a command that finished at the gate with a non-zero exit is run once at the base. It is environmental when the base run finished with a non-zero exit and either the exit code is the same or no path the run changed appears in the last lines the command printed at the gate. Everything else is a retry: the base exits 0, the base or the gate run did not finish, or the base could not be run. The two overlapping criteria are read this way: criterion 1 is the same-exit case, criterion 2 adds the changed-path test for exit codes that differ; the narrowing of criterion 1 is the open question below.
- A step's `tests_passed: no` no longer ends the check before any command runs (`code_check` does that today). The code prompt tells the step to report a failure present before its first change and to leave it unrepaired, so the shortcut hid the case of the task. The gate runs the commands itself (ts-code-verify).
- The check is environmental only when every failing finding is such a command. With another finding failing it stays an ordinary failure, the environmental command is named in the evidence and not listed as something to fix, and the next attempt escalates if nothing else fails (ts-code-mixed).
- A result at the base is reused within one visit of the unit, keyed on the base commit, the unit and the visit (CHK-B20). The task says "per gate visit"; a new visit also picks up an environment a person has repaired. A person who repairs it and resumes inside the same visit gets the kept result.
- The base checkout is a throwaway clone sharing the repository's objects, detached at the base commit: it has a `.git` and registers no worktree, so nothing is left in the repository (CHK-B21). The plan may choose another way with the same observable result.
- The code check runs on a limit of 1800 s (`check_timeout_s` in `workflow/temperspec/__init__.py`). The base run shares it. A run that cannot start in the time left (`min_start_s` can be the gate run's duration) or cannot finish is not compared and is retried as before. The plan decides whether to raise the limit.
- Scope is the code gate. `_verify` is also called by the outcome check (`ts-verify`, `checks.py` line 947); the plan keeps the outcome gate as it is, for example with a parameter.
- `_reuse` (ts-code-reuse) flags a command started twice on one tree. A base run has the same argv on another tree, so `_reuse` must skip runs marked `at_base`.
- The rows of the package spec are in its earlier layout, as the `speedup-runs` run left them; each row is mirrored into `outcome.json` with the same text, verified by the code check or a judge as the plan chooses.
- The specs hold no "Not built yet" line for issue 54, so none was removed. The specs now say what the code will do when this run's pull request is merged.
- `ts-traced` at the outcome gate asks for a test that names each criterion the run added or reworded and each old one that proves a behaviour it changed: CHK-AC8 to CHK-AC11, and CHK-AC1, CHK-AC2, CHK-AC4, CHK-AC5 and CHK-AC7, because CHK-B10, CHK-B12 and CHK-B14 changed. Only CHK-AC6 is named in the engine's tests today.
- The log's `check` record clips the evidence to 200 characters (`nodes.py` line 1388). The finding of an environmental command should carry the command, both exits and the reason in its first 200 characters.

## Open questions

- Is criterion 1 read literally, or as the rule reads it? Read literally, any command that also fails at the base is environmental. The rule retries one case: the base run fails with a different exit code than the gate run and the gate's output names a changed path, as when a command names a test file the change creates (pytest exits 4 at the base, 1 at the gate). Options: (a) as written; (b) environmental whenever the base fails, which would escalate every real failure of such a command. Until answered: (a). It does not block planning.
- Should a run at the base put the base checkout ahead of an installed copy of the code under test? Without it, a Python package installed in editable mode can exercise the workspace's code at the base, and a base failure caused by that reads as the same failure. Options: (a) the workspace's environment, unchanged (taken, listed in the check contract's open questions); (b) the engine sets the search path for the base run, which is language-specific. Until answered: (a). It does not block planning.
