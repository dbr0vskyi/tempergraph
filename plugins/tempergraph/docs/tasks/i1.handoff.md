# Hand-off: i1

## Problem

The loop files an issue with a fixed pair of labels and a free-form body, looks only at open issues when it de-duplicates, and names a cluster's issues in a pull request only by URL, so the owner's triage (labels, close reasons) is invisible to it and its trial results never reach the issue (R-160 F7, issue 1). The documents now say that a loop issue carries the repository's triage labels and four fixed sections, that a close as not planned mutes its fingerprint for 30 days and a close as completed makes the next occurrence a new issue that links the old one as a possible regression, and that a proposal's pull request writes `Closes #<n>` while a trial's result is one agent-format comment on the cluster's issue. No code, test or plan was touched.

## Decisions

- Where the behaviours live. SIL has about 4,200 bytes of its 30,720 left, and the six SIL-side behaviours with their criteria and open questions come to about 8,000 bytes (the whole new spec is between 9,000 and 10,000), so they are a new sibling spec, `loop-issues.spec.md` (ISS), like SRV and IMD beside SIL. No behaviour of SIL moved, so no id changed. The prefix has three capital letters because `test_spec_form.py` reads only those. A new prefix also keeps this task from colliding on ids with the other issues that touch SIL (#3, #6, #8). PRP has room and takes behaviour 3 in place. The task text says "SIL (spec 16) and PRP (spec 40) state" the behaviours: SIL states them by its Purpose pointer and SIL-AC3, and ISS holds the text; if the owner wants the text in SIL, SIL must first be split
- `issue_labels` is declared as `improvement.issue_labels` in the package's `tempergraph.json`, as `improvement.autonomy` is (PRP-B11). It is not a run-settings key: that would change RST-B20 and its catalog tests. "A workflow's or the engine's setting" is read by the finding's side: a workflow-side finding takes the workflow's list, an engine or executor finding takes the engine's own list, and both default to `["tempergraph-loop", "needs-triage"]`. A value that is not a list of names is ignored, as an invalid `improvement.autonomy` is. A finding of a child workflow (the finding record carries the child's `issue_repository`, `record.py` lines 128 to 141) takes the child's own declaration; the plan reads it where that repository is read
- `tempergraph-loop` and the side label are always added, because the task says a filed issue carries the triage labels "as well as" them. The executor side label stays `executor:<name>` (SIL-B11 and `filing.py` lines 115 to 117), not `side:executor:<name>`
- The hidden line stays the first line of the body (SIL-B18 says "opening"), so the four sections follow it. `## Fingerprint` shows the fingerprint as text and must not repeat the hidden line itself: the de-duplication match is the exact line (`filing.py` line 174, `test_filing.py` line 61)
- Closed issues are read only for a finding that would file and matches no open issue; an open issue wins, and a person ends a mute by reopening the issue. The latest close decides. The mute counts from the host's close time. A close as completed has no age limit and no version check. The reasons are the two the guide names; any other reason or none is read as no signal and the finding files as a new issue with no link, which is what the loop does today. A failed search of closed issues files anyway after one retry, as SIL-B2 does for open ones (a failed search usually fails the create too, which goes to the outbox)
- The possible-regression link is a link only. It records nothing on a proposal: `regressed_after_release` stays with PRP-B9's own comparison, which waits on #9. The task text names both in one sentence; the acceptance criterion says only that the new issue links the old one
- `mute.days` (30, provenance `default_no_data`) is the length of the pattern rule's window, so a new issue after a mute rests on runs made after the owner's close. IMD-AC3 asks every threshold to be a parameter record, so the code step adds one (`params.py`)
- `Closes #<n>` names each issue of the cluster in the pull request's repository, whatever its state, since GitHub's own handling of a closed issue is not a loop behaviour; an issue of another repository stays linked by URL as PRP-B8 says. The plan reads `_issues` (`proposals.py` lines 141 to 149), which lists the cluster's issue URLs from the loop's own records
- The trial comment is posted when the trial ends, in any decision, at autonomy `file` or above (PRP-B11 gives `record` no issue writes), on each issue of the cluster. It carries no pull-request link: GitHub links a pull request that says `Closes #<n>` to its issue by itself. It uses kind `result` (CONTRIBUTING.md 5.2) and `agent=loop`, the name 5.1 gives as an example. The plan decides where the post is made (`trial` has no code host today; its callers are `improve trial` and the loop's own trial in `autonomy.py`)
- A dry run (SIL-B6) makes no code host call today (`filing.py` lines 166 to 168), so its would-file list can show a finding that a real run would mute. Left alone: the task does not ask for it
- IMD-B9 names `noise` (closed as not planned) and `fixed` for the loop's metrics, and its open question asks who reads issue state on a team. The read here is made at filing, on the machine that files, so IMD-B9 and its question are not edited
- No "Not built yet" line names this issue (SIL has none; the one in PRP is PRP-B9, issue 9), so none was removed or edited
- Checked against what the new and edited behaviours link: SIL-B2, SIL-B3, SIL-B11, SIL-B18, SIL-B19, PRP-B8, PRP-B9, PRP-B11, PRP-B12, PRP-B23, IMD-B9, IMD-B23, RST-B20. No behaviour contradicts; SIL-AC3 was the one criterion that would have, and it is reworded
- Outside the gaps and left alone: `CONTRIBUTING.md` 5.1 says every agent comment carries the marker and footer and that loop comments carry the fingerprint line, but the "seen again" comment (`filing.py` line 181) carries neither. The code step also updates what the documents say is pending: `CONTRIBUTING.md` lines 57 and 148 call #1 future work, and the guide `improving-workflows.guide.md` (line 7) says what the loop files

## Open questions

None blocks planning; each has the default the documents already use.

- Is 30 days the right mute period? Options: (a) 30 (the default, the pattern rule's window); (b) 7, so a worsening fault resurfaces soon and the owner declines it weekly; (c) 90, the fewest repeats and a long silence. Recommended: (a) until real runs show how often a declined fingerprint returns
- Should a close as a duplicate mute like a close as not planned? Options: (a) no, the reason is unread and the finding files as a new issue (the default); (b) yes, since the owner said it is tracked elsewhere. Recommended: (a); the loop cannot see the issue it duplicates
- Should a recurrence after a close as completed also record `regressed_after_release` on the merged proposal that closed the issue? Options: (a) no, link only (the default); (b) yes, once `pr_state` is derived (#9). Recommended: (a)
- Should an operator set `issue_labels` per machine, as a run setting? Options: (a) no, only the workflow's declaration and the engine's own list (the default); (b) yes, a key in RST-B20. Recommended: (a)
- Should the loop's own proposals skip a cluster whose issues were closed as not planned? Options: (a) no, PRP-B23 unchanged (the default); (b) yes, a new behaviour in PRP. Recommended: (b) if the owner enables autonomy `propose` or `trial`; at the default `file` it has no effect
- Should the "seen again" comment carry the agent marker and footer of CONTRIBUTING.md 5.1? Options: (a) leave it (the default; outside this task); (b) one-line change in `filing.py`, with a test. Recommended: (b), as a follow-up issue
