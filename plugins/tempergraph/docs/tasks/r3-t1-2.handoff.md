# Hand-off: r3-t1-2

## Problem

Release 3 phase R3-T1.2 makes a step or judge that the `claude` executor launches from inside a host Claude Code session reach only what it declares. ECC-B14 already states the three reach rules, but ECC-B8 still sent `--tools` only under the operator's enforcement setting, ECC-B14 left the names that survive the environment drop loose ("the credentials the probe needs"), and no criterion proved the rules by argv and environment scans of a step, a retry and a judge launch.

- G1: `plugins/tempergraph/docs/specs/executor-claude-code.spec.md` (ECC-B8): the `--tools` clause now says every launch, whether or not the enforcement setting is on; three scenarios cover a shell step, the check preview and a step with no tool; proved by ECC-AC6
- G2: `plugins/tempergraph/docs/specs/executor-claude-code.spec.md` (ECC-AC6, new; ECC-B14 made exact for a step, a retry and a judge)

## Decisions

- ECC-B14 keeps its id and its three reach rules in one behaviour. The task, ADR-0132, R-140 F4 and the release 3 plan all cite ECC-B14 for the whole capability, so splitting it would leave those links pointing at a third of it. ECC-B8's argv recipe now agrees with it instead of stating a second, conflicting rule.
- The actor of ECC-B14 changed from "the launcher" to "the executor". The behaviour is about the `claude` executor's launches; the launcher serves every executor, and EXI-B22 already states what it strips for all of them. The plan may place the filter in the launcher or have the executor request it per launch; either meets ECC-B14. The model-free probes (EXI-B23) and the check worker also start through the launcher; ECC-B14 says nothing about them (see open question 1, option d).
- The environment rule holds for every step, retry and judge launch, not only when a host marker is present, because the task says every launch. With no host names in the environment it removes nothing. A retry is a fresh launch (ECC-B9) and carries the same rules; the session request has no attempt field, so a retry test calls the executor a second time.
- Names are matched by prefix (`CLAUDECODE` and `CLAUDE_`): the task lists what stays, and the names a host sets for its children change between CLI versions.
- "The engine's own overlay" is read as: the engine lays its names after the base environment is filtered, so they always reach the session. For a step that is ECC-B9's pair: `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR` keeps the host's own value when the host sets one (ECC-B9 says "unless the host already sets it", and `test_step_env` pins it), while a host's `CLAUDE_CODE_SUBAGENT_MODEL` never passes, only the engine's value does (the task: "when the engine sets it"). For a judge it is the credentials profile of ECC-B10 and SEC-B12; ECC-B9 is step-only, but the task's wording covers it by meaning.
- ECC-B8's `--tools` is built from the declared tools by ECC-B7's map. A declared `shell` maps to `Bash`. The check preview (CHK-B17) grants a `Bash` allow rule on `claude` even when the step declares no `shell`, so the shell tool joins `--tools` for it, as the executor already does under enforcement. A step that declares nothing sends an empty value (R-001 F12: an empty value means no built-in tool). The enforcement setting keeps its other effects: the strict MCP config in ECC-B8 and the preflight refusal of an executor that cannot enforce (EXI-B1, EXI-B12).
- Judge launches: ECC-B10 already sends `--tools` on every judge launch, so it is unchanged. No launch sends `--add-dir` today (searched the whole engine, source and tests); ECC-AC6 pins it.
- Not edited, on purpose: TSA-B3 (its "enforced only with `--enforce-tools`" is the audit's notion of enforcement, and no code for its `not-enforced` rule exists to disagree); the CLI's listing of probe facts (the code lists P-CC-1 to P-CC-9; adding P-CC-10 and P-CC-11 as `not run` is for the plan to decide, nothing pins the count); ECC-B13's probe list; TCK-B19 (see open question 1).
- Left for the code step, because they say what is built and are true only once the code lands (task AC 5): the "Not built yet" line under ECC's Open questions, which names ECC-B14 today and is to name only the live probes P-CC-10 and P-CC-11, and the R3-T1.2 record in the release 3 plan, in the form R3-T1.1 uses. Both belong in the plan's Docs to update.
- A step that calls a built-in it did not declare (for example reading files without declaring `read`) no longer has it once `--tools` is always sent. That is the intended reach. The plan runs the whole offline suite, which loads every workflow package under `plugins/` (CLAUDE.md).

## Open questions

1. Which credential and gateway names beyond the task's list must still reach a step or judge? The prefix rule of ECC-B14 also drops `CLAUDE_CODE_OAUTH_TOKEN` (the token `claude setup-token` makes for scripts), `CLAUDE_CONFIG_DIR` (a relocated configuration folder, where a sign-in file can live) and the `CLAUDE_CODE_SKIP_*_AUTH` switches that gateway setups set beside `CLAUDE_CODE_USE_BEDROCK` or `CLAUDE_CODE_USE_VERTEX`. The task keeps only the three `CLAUDE_CODE_USE_*` switches and `ANTHROPIC_*`, and the operator checked sign-in without any `CLAUDE_*` name on the cloud container alone. A launch whose only credential is one of these names would sign out or fail mid-run while the preflight probe still passed, because `auth status` starts through the launcher with the full environment. The token matters most: TCK-B19 accepts `oauth_token` for `claude` schedules, R-150 calls the script token the recommended unattended path, and a step has no credentials profile to carry it (only a judge has, ECC-B10), so ECC-B14 as the task words it leaves that kind unusable for steps. TCK-B19 is not edited. The names come from the public Claude Code docs (https://code.claude.com/docs/en/env-vars, https://code.claude.com/docs/en/authentication, https://code.claude.com/docs/en/llm-gateway-connect), read through search summaries and not run against a CLI. This does not block planning: the task states the rule, and the answer changes one clause of ECC-B14 and the names a test plants. Options:
   - (a) keep the task's list.
   - (b) also keep `CLAUDE_CODE_OAUTH_TOKEN` and the `CLAUDE_CODE_SKIP_*_AUTH` switches: they carry credentials or the gateway, not a host's session or directories.
   - (c) as (b), and `CLAUDE_CONFIG_DIR`, accepting that a host's configuration folder then reaches the step too.
   - (d) any of these, and the same filtered environment for the model-free probes, so preflight reports what a step will see.
   - (e) drop only when `CLAUDECODE` is in the engine's environment, so unattended fires keep their token.
   - Recommended: (b), plus (d) if the probe should predict the step. Until answered, planning reads (a).
2. Built-in `--tools` does not restrict MCP tools (R-001 F12), and ECC-B8 sends the strict MCP config only under enforcement with an MCP tool declared. If the host's user configuration registers MCP servers, a step's `system/init` still lists their tools and P-CC-10 ("lists only its `--tools`") would fail on them. The task and ECC-B14 name built-in tools only, so nothing was changed. It does not block planning. Options:
   - (a) leave it and read P-CC-10's result first.
   - (b) send the strict MCP config, and `--disallowedTools "mcp__*"` when no MCP tool is declared, on every step launch, as ECC-B10 does for a judge.
   - Until answered, planning reads (a).
