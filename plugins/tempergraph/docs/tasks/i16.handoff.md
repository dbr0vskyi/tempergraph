# Hand-off: i16

## Problem

A `writes: true` contest cuts one worktree and branch per slot when its slots first run (`--s-<slot>`). A gate RETRY runs the slots again, and the cut refuses a slot that already has its worktree, so the run ends with `workspace_refused` (#16). A BACK to the unit before the contest meets the same names when the contest runs again (the R3-T4.2 code report names both cases). No spec said where a later attempt's slots run, what becomes of the first attempt's branches, or which branch is merged.

## Decisions

- Acceptance criterion 1's default is taken, because no spec states reuse or fresh worktrees. Searched `72-contest-unit.spec.md`, `82-worktree-mode.spec.md` and `13-workspace-and-concurrency.spec.md` for "second attempt", "retry", "slot" with "worktree" and "branch": CTS-B8 says which slots run again, CTS-B5 and CTS-B7 what a pick merges and discards, WTR-B20 and WTR-B24 the names and the record; none says where a later attempt runs. A later attempt cuts fresh slot worktrees and branches from the run branch's head after the checkpoint commit, leaves the earlier attempts' branches, worktrees and records as they are, and merges only its own winner's branch.
- The head a later attempt starts from already holds the first attempt's winner. `_contest_judge` merges a writer winner at the pick whatever its verdict (`run/nodes.py` line 869), so a RETRY or BACK leaves that work on the run branch. CTS-B11's first scenario states it: the retried slot's worktree holds the files the first attempt's merge put there. Under `retry_scope: all` every slot therefore starts from that head too. The criterion's words "cut from the current head" are what this follows.
- Under `retry_scope: best` the retry cuts a worktree for the one slot that runs (CTS-B11 says "each slot that runs in that attempt"). Slots that do not run get none.
- Names. The first attempt keeps `--s-<slot>` (`tests/test_workspace.py` line 148 and `tests/test_contest_writers.py` pin it); the n-th attempt, for n above 1, takes `--s<n>-<slot>` on the folder and the branch. `--s-` never equals `--s<digits>-`, so no name repeats; it is the device of the map's `--i<n>-<item>`. Rejected: a number after the slot (a slot `x-2` of the first attempt would meet slot `x` of the second); reusing or resetting the first attempt's branch (the criterion leaves those branches as they are and WTR-B23 deletes none).
- What the number counts. It is the contest's own attempt number, the one in the `attempt` field of its `contest` run record: `_contest_step` adds 1 to the unit's last attempt (`run/nodes.py` line 741) and a BACK keeps the unit's attempt record (`clear_from`, `run/gate.py` lines 25-40), so it rises across visits (BUD-B3). It is not the slot's count in a session key: a slot's own count is `n:<slot>` in the map record (`_concurrent_item`, lines 669-677), and a slot that did not run in an attempt, by the cost cap or a `best` retry, stays behind it. Read in the code, not run.
- The first run after a BACK is therefore an attempt after the first and is covered by the same rule (CTS-B11, third scenario; CTS-AC9). That closes the other half of the R3-T4.2 known limit ("a new visit meeting the slot children"), at little extra cost: the one name rule separates both, and the plan adds one test (CTS-AC9). If the plan finds the BACK case costs more than that, it says so in the plan and does not drop it silently.
- Where each rule lives. CTS states what a later attempt does with its slots (the attempt is the contest's own idea); WTR-B20 owns names and is edited in place. WSP-B11 and WSP-B19 name parallel blocks and maps and not the contest, whose checkpoint and worktrees the code (`git.py` `commit_all` cites WSP-B19) and CTS-B6 already tie to them; CTS-B11 links WSP-B19 as MAP-B14 does, and WSP is not edited. WTR-B23 and WTR-B24 already hold for a later attempt (cleanup and the listing read the workspace record, which keeps both attempts' children). No spec stated "ends blocked"; R-150 did, and is edited. The plans and task notes that record the limit stay as records.
- Spec 77 (MAP) is not touched, as the task asks. The WTR-B20 sentence is edited by appending the contest clause after the map clause, which keeps its words.
- The task's criteria map to the documents. Criterion 1: CTS-B11 to CTS-B13, WTR-B20. Criterion 2: CTS-AC7 and CTS-AC11 (a regression test in `tests/test_contest_writers.py` that carries both ids). Criterion 3: CTS-B11 to CTS-B13 and WTR-B20 state it, and R-150 no longer says the opposite. Criterion 4: the plan's verification.
- No decision record and no research note: no gap asks for one, and criterion 1 leaves one workable option.
- The run's conversation setting arrived unresolved (the placeholder `⟨missing:settings.conversation⟩`). The triage note lists no owner decision, so nothing here needs a person before planning.

## Open questions

None of this blocks the task. The plan leaves it as it is until the owner answers.

- A stop between an attempt's cut and the end of its step node. `_contest_step` cuts the slot worktrees (`run/nodes.py` line 732) and checks the boundary (line 740) before it returns the attempt's state (line 770). A drain at the boundary (cost cap, attempt cap, a person's stop) or a crash after the cut leaves worktrees and branches the state does not list, and the resume runs the same attempt number again (DUR-B2), meets its own names and ends `workspace_refused`. That holds for a first attempt today and will hold for later ones. Read in the code, not run. Options: (a) a task of its own: check the boundary before the cut and write the workspace record with it, or let a resumed attempt reuse its own cut; (b) leave it. Until answered: (b).
