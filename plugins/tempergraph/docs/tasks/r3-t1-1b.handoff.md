## Decisions

- The record is defined in BUD, the owner of reservations. OBS-B7 only lists the kind and links to it, as it does for `map_items`, `self_check` and `finalize`, so nothing is defined twice.
- One kind, `reservation`, with an `action` of `held`, `waiting` or `refused`, the way EVT-B15 uses `action` for `workspace`, `grant` and `ruling`. A new kind is additive: every reader skips a kind it does not know (OBS-B7).
- Each record carries the figures the decision rested on (amount, source, spend, what the other running sessions hold, cap), so an operator can redo the sum against the cap from the record alone and see why a branch started late.
- A `refused` record exists because a drain under BUD-B12 can come with spend below the cap (3.00 of 5.00 USD with a 2.50 USD reservation). `run_exit` with reason `cost_cap` alone would not explain that.
- A wait is recorded once, when it begins. Its end is the session's `held` record, or a `refused` one, so there is no seconds-waited field: the `ts` of the two records gives it.
- "Over the cap" is strictly more than the cap. A reservation that brings spend plus reservations to exactly the cap fits. The third tier needs this: it divides the remaining cap by the width, so the last branch always lands exactly on the cap (BUD-B13, second scenario).
- The behaviours say "a session that takes a reservation", as BUD-B12 does, so maps, contests and councils reuse the records later. Which session kinds reserve in this build (step, retry, judge, re-ask) is left to the plan: BUD-B12 says "a starting session" and the task says "each session of a parallel read-only block". Only parallel read-only branches are built (task AC 5).
- Left for the code step, because they say what is built and are true only once the code lands (task AC 5): narrowing the "Not built yet" line under BUD's Open questions, and recording R3-T1.1 as built in the release 3 plan. The line names BUD-B12 only; its rewrite should cover BUD-B13 to BUD-B15 as well.
- BUD-AC2 is left as written, since the task gives it to the BUD-B12 tests. The log checks of AC 4 are BUD-AC5 to BUD-AC7, which the log-reading tests carry.
- No other document found is made false: searching the engine's guides and specs for record kinds found no guide that names one, and OBS-B7 is the only list of them that the new kind has to join (EVT adds kinds and never renames, and IMD's canary test covers only kinds that reach a sink, which this one does not).

## Open questions

- The second reservation tier, "the projection of its unit from the central run stats" (BUD-B12, task AC 1), has no per-unit source. CST-B15 projects per workflow and per finished run (median and 90th percentile), and no spec or code derives a figure for one unit, though the `session` rows of CST-B9 hold each session's unit and cost. BUD-B13 records the tier as `source` `projection` and leaves the figure open. This is not a gap of the triage note, so CST was not edited.
  - (a) Leave it: the tier applies when the stats hold a projection of the unit, which they do not today, so reservations fall to the per-session cap or the share, and the code step reports the skipped tier under Deviations.
  - (b) Add a per-unit projection to CST first (for example the median estimated cost of one session of the unit over its `session` rows, `thin` under 5 rows) and build the tier on it.
  - (c) Drop the middle tier from BUD-B12 and from the task until (b) exists.
  - Recommended: (b) as a task of its own, since the concurrent map, contest and council of release 3 reserve the same way. It does not block planning: the other two tiers and BUD-B13 to BUD-B15 are fully stated, and the task's two tests need only them. Until answered, planning reads (a).
