# Triage: r3-t3-2

## Task

Engine release 3 plan, track R3-T3, phase R3-T3.2 "Concurrent map" (`plugins/tempergraph/docs/plans/third-release.plan.md`): a map with `mode: concurrent` runs its items concurrently, a writing map gives each item its own worktree, and the map is verified after the merge. Code task against behaviours already written in spec `map-unit`, spec `workspace-and-concurrency` and spec `budgets-and-failures`.

## Acceptance criteria

1. A map with `mode: concurrent` validates and runs up to `concurrency` items at once; items that declare neither `write` nor `edit` run read-only in the run worktree and fail when they change it.
2. A writing concurrent map runs each item in its own sibling worktree cut after a checkpoint commit, merges the items into the run branch without fast-forward in item order at the join, and a merge conflict resets the run branch and blocks the join with the conflicting paths and no model call.
3. After the merge, the map's verification (its gate's check over the joined result) runs once on the run worktree before the next unit.
4. Concurrent items keep their own retry budgets; a spent item pauses addressed by unit and item while the others keep their results; with two pending item pauses, a resume without an item is refused with both exact commands and a named item's `retry` reruns only that item (MAP-B6, MAP-B10).
5. Concurrent items stay under the run cost cap through the reservations (no item starts when the reserved spend would cross the cap).
6. Offline tests on stand-ins prove 1 to 5 and carry the MAP, WSP or BUD criterion ids that state them (add a MAP criterion for the concurrent mode when none states it); the `not_in_release` refusal of the concurrent map is gone from code and specs, and the "Not built yet" line of spec `map-unit` names only what is left; the release 3 plan records R3-T3.2 and track R3-T3 as built; the offline suite, `ruff check src tests` and `mypy` pass.
