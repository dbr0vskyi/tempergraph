- Why this design: the engine owns the run at the base (`run(cmd, at_base=True)`: one launcher with CHK-B12's limits, one reuse store, nothing left in the repository), and the package owns what a base result means (the same exit code, or no changed path in the output). The package's tests go in a new file, `tests/test_code_base.py`, that builds its own scratch repository and so passes alone; the engine's go in a new `tests/test_check_at_base.py`. This keeps the 996-line `test_temperspec.py` out of the rows. The five acceptance criteria are `AC 1` to `AC 5` of the triage note.
- Complexity: `simple`. Three phases, 11 task rows, 4 test rows, 9 files, 3 verification commands, no heavy phase, and about 165,000 bytes in the files the rows name (estimated from line counts, with no shell here: package `checks.py` about 950 lines, `outcome.json` about 1,160, the four engine source files 145 to 242 lines each, the README; the new test files have no size yet).
- Assumptions, each from a spec, a decision record or the hand-off:
  - Criterion 1 is read as the package decision record reads it (a base failure with another exit code and a changed path in the output is retried); the engine's editable-install question stays as the spec has it: the base run has the workspace's environment.
  - The base checkout is `git clone --shared --no-checkout` of the workspace and a detached checkout of `git.base`, made through the git reader (the sanctioned launch site) inside a folder the engine allots outside the workspace and the main checkout. `run_doc` allots that folder before the worker starts and removes it after the worker ends (which covers a worker ended at its limit); `run_check` also removes what the context made when the check returns or raises, so a check run in process (the package's tests) leaves nothing either. One checkout serves every base run of one check. The engine's decision record lets the plan pick another way with the same observable result.
  - A base commit that is not a full commit id is refused, and the run is `not_started`.
  - The base reuse key is argv, the resolved program path, the command's folder, the base commit, the unit and the visit; a record in the store carries `at_base`, and a workspace key is never looked up for a base run or the other way round.
  - A base run asks for `min_start_s` equal to the gate run's duration, so a base run that cannot finish in the time left is `not_started` and the command is retried as before (ts-code-nobase). The check's limit stays 1800 s.
  - A base run's `tail` and `program_path` show both the workspace and the base checkout as `<workdir>` (CHK-B12, CHK-AC4), because a command at the base can print a path of either.
  - An environmental command is a `fail` finding when no other finding fails (the result is then marked `environmental`), and a `maybe` finding otherwise, so the retry lists only what the step can fix (ts-code-mixed). Its line leads the evidence, so the log's 200-character clip keeps the command, both exits and the reason.
  - The outcome gate's own `_verify` call keeps its behaviour: the comparison is a parameter that only the code gate passes (the task names the code check).
  - The step's `tests_passed: no` no longer ends the code check before a command runs; no test pins the shortcut (searched `tests_passed` in both test folders and the evals).
  - Tests carry the ids the outcome gate's `ts-traced` asks for: CHK-AC8 to CHK-AC11, and CHK-AC1, CHK-AC2, CHK-AC4, CHK-AC5 and CHK-AC7 on a test that asserts the part of that criterion this run changed.
