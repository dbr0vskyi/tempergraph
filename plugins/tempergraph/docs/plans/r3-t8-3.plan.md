- Why this design: the audit gains a history reader that turns the workflow's local run records (run log, activity journals, digests) in `--window` and `--version` into per-unit facts, and every history rule reads those facts only; the tool surface is built once per session from the executors' tool maps, the manifest and (when present) the same facts, and both the C4 rules and the `audit tools` matrix read that one surface, so the matrix and the findings cannot disagree. Rules join the catalog with their `min_n` and `built` release; a rule whose input is missing is listed as skipped with its reason, never as passed (ARC-B7).
- Council and contest history rules: `council-rounds-no-gain`, `council-conformity` and `contest-no-gain` (ARC-B15) read run records only, so they are built in this task although the `council` and `contest` units are not built yet (`api.py` still declares them as later). Each has a raising fixture and a clean fixture made of synthetic run records, shaped by the records the specs state: a council's positions with their round history and `changed` flags (CNL-B10, CNL-B2, CNL-B12 in `plugins/tempergraph/docs/specs/council-unit.spec.md`) and a contest's run event that holds every slot's keys and names the winner (CTS-B7 in `plugins/tempergraph/docs/specs/contest-unit.spec.md`, read for the record shape only). When a workflow has too few such records the rule is skipped with its `n` and `min_n`, as ARC-B7 states. No history rule of the catalog is left without a raising fixture.
