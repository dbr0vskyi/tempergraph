# Plan: a sub-workflow child is learned from and measured as its own workflow, and a parent paused inside a child can be carried

## 0. Hand-off

- Triage note: `plugins/tempergraph/docs/tasks/r3-t2-3.triage.md`; hand-off: `plugins/tempergraph/docs/tasks/r3-t2-3.handoff.md`
- Specs read: `plugins/tempergraph/docs/specs/99-subworkflow-unit.spec.md` (SWF-B8, SWF-B9, SWF-AC1, SWF-AC3), `plugins/tempergraph/docs/specs/61-version-metadata.spec.md` (VER-B17), `plugins/tempergraph/docs/specs/63-workflow-upgrade.spec.md` (WUP-B6, WUP-B16, Open questions), and the specs of the hand-off's reading list (JCL, LAD, SIL, EVT, OUT, PRO, CAR) for the ids they define. - Code read from the hand-off's reading list: `run/subrun.py` (applied, build, run_child), `improve/filing.py`, `improve/calibration.py` (current_binding), `run/outcome_record.py` (_latest, measures), `package/changelog.py` (entries_between, detect, compatibility), `package/upgrade.py` (plan, upgrade). No file outside the list was opened.
- Why this design: spec 99 already states every behaviour, so the plan adds none. A child runs under a spec renamed to the parent (`subrun.applied` sets `name=parent.name`), so every lookup keyed by `spec.name` (judge binding and grade, causes, finding lines, filing, measures) reads the parent inside a child. Each phase finds the lookup that serves one result and makes it read the child, with an engine fixture parent and child and stand-in executors, never a shipped workflow (ADR-0129). The plan is `complex`: more than 3 phases, more than 6 test rows and more than 10 files.
- Choices left to the plan by the hand-off: (1) the child's `changes/<version>.json` follows VER-B9's entry shape narrowed by VER-B17 and is read by `package/changelog.py` for each sub-workflow unit of the parent, from the child's registered package, between the version the parent was last stamped against and the child's current version; (2) its detect rule for a parent's reference to a produced key is `template_key` on `<unit>.<key>`, with the `rename_field` item pointing at that reference (the item needs an action that renames a produced key in the parent's templates, since the shipped `rename_field` renames a builder keyword); (3) no promotion window counts a child's records from inside a parent in this release (ADR-0133 assumption A2). The hand-off's open question about how a window could say so stays with the owner and blocks nothing.

## 2. Phases

### Phase 1: The child's own judges

Goal: a child gate and a parent gate of one name each judge on their own bindings and calibration cases (R1), proved on a fixture parent and child whose parameters (`issue_repository`, calibration cases, judge alias) the shared fixture module takes, which the later phases reuse.
Weight: medium

### Phase 2: Findings filed to the child

Goal: a friction finding on a child unit is recorded and filed under the child's workflow name, version and `issue_repository`, naming the parent (R2).
Weight: medium

### Phase 3: Measures and the promotion window

Goal: the child's outcome record from inside a parent counts in `outcome show <child> --runs` with `origin: subworkflow:<parent>`, and stays outside the child's promotion window (R3, R4).
Weight: medium

### Phase 4: The parent's upgrade reads the child's change notes

Goal: `upgrade <parent> --check` reads a child's `changes/<version>.json` and plans a `rename_field` item at the parent's reference to a renamed produced key (R5).
Weight: medium

### Phase 5: Carrying a parent paused inside its child

Goal: a parent carried on a branch, paused inside its child, resumes on a second state root and finishes, the child continuing where it paused (R6).
Weight: light

### Phase 6: Documents and release record

Goal: the documents say what is built: spec 99 loses its Open questions section, spec 63 loses the clause about a sub-workflow's change notes, the release 3 plan records R3-T2.3 and track R3-T2 as built, and `test_subworkflow_docs.py` follows; the offline suite, lint and types pass (R7, R8).
Weight: light
