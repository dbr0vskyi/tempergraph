  - `plugins/temperspec-tgraph/rules/plan.rule.md`: the plan format.
  - `plugins/tempergraph/engine/src/tempergraph/model/subworkflow.py`: the child reader of phase R3-T2.1 that this task builds on (`read_child`, `Child`, `exposed_keys`, `stop_message`).
  - `plugins/tempergraph/engine/src/tempergraph/compiler/graph.py` and `compiler/state.py`: the graph has four nodes per unit and no handling of a `subworkflow` kind; run state is one `RunState` whose channels are keyed by unit name.
  - `plugins/tempergraph/engine/src/tempergraph/run/nodes.py`: `EngineNodes` and `RunContext` are bound to one spec (`ctx.spec`); `step` dispatches on the unit kind, `_boundary` reads the run cost cap from `ctx.spec` and the cost from state, `_session` and `step` write session keys, the gate funnel (`gate`, `human`) is per spec.
  - `plugins/tempergraph/engine/src/tempergraph/run/runner.py`: `_drive` writes `run_started`, the engine record and `workflow_changed`; `_start` holds the interim stop (`subworkflow_stop`); `_resume` compiles the thread with inert nodes, checks the decision with the parent spec and breaks on a changed version.
  - `plugins/tempergraph/engine/src/tempergraph/durability/checkpoint.py`: `snapshot` reads a pause from the parent's tasks, so a child's pause surfaces as the parent's.
  - `plugins/tempergraph/engine/src/tempergraph/run/log.py`: `RunLog.write` is the one writer of `run.jsonl`; the unit of a record is split from its `session_key` when absent.
  - `plugins/tempergraph/engine/src/tempergraph/run/gate.py` (names only), `run/outcome.py` (`with_outcome`), `run/outcome_record.py` (`build`), `engine/tests/fixtures/subworkflows.py` (the fixture parents and children of phase R3-T2.1).
- Why this design: the child runs as a LangGraph subgraph that the sub-workflow unit's step node invokes, so it shares the parent's checkpointer, thread, workspace and lock (ADR-0133). It gets its own compiled graph, its own `EngineNodes` and its own run state, because `EngineNodes` and every state channel are keyed to one spec's unit names and a child's `work` must not meet the parent's `work`. The child's context shares the parent's log, registry, state root, drain check and run cost cap, and starts from the parent's cost so the one cap holds; its log writer adds `child: <unit>` and its session keys are prefixed `<unit>/`. The unit's step node hands back only what `produces` exposes (artifacts and values under the unit's name), the cost the child added and the child's outcome verdict, so the parent's existing gate, judge and template reading work unchanged. The step node never calls the child's finalizer. The checks of each phase settle how the child's pause payload, checkpoint namespace and per-child engine record are named.

## 2. Phases

### Phase 1: Running a child

Goal: a parent run that reaches a sub-workflow unit runs the child's units in the parent's workspace and thread as a subgraph with its own nodes and state, with `child: <unit>` on its records, `<unit>/` session keys, its declared defaults, its outcome gate, one `run.jsonl`, one thread and one ledger row, the child's version in `run_started.children` and the engine file, `children[<unit>]` in the outcome record, the finalizer never called, and `{<unit>.<key>}` read by later units; the interim `not_in_release` refusal and its code are removed from `run` and `run --check`.
Weight: heavy (large-context)

### Phase 2: One cap

Goal: a child attempt that would start at or over the parent's run cost cap drains the run with exit 5 `cost_cap`, the child's spend counts against the parent's run and daily caps and is shown on its own line in reports and not summed into the parent's own steps.
Weight: medium

### Phase 3: A child's pause and a changed child

Goal: a child pause pauses the parent with `unit` reading `<unit>/<child unit>` and a resume answers it as any pause with no later parent unit started; a parent paused inside a child whose version changed resumes with one `workflow_changed` record naming `child: <unit>`, and a resume whose child was removed is refused with exit 2 naming the child.
Weight: medium

### Phase 4: The unit's gate on the child's result

Goal: a child's upstream defect in a key mapped into `inputs` sends the parent back to the unit that made it when it is a back target, else asks a person; a child outcome of `unmet` or `needs_person` fails the unit's gate with the child's failing final criteria as blockers within the child's own budgets; the child's finalizer never runs and its outcome gate is never skipped, with the `subworkflow-finalizer-skipped` warning once at validation.
Weight: medium

### Phase 5: Documents and the gate

Goal: SWF-B11 and SWF-AC4 are removed from spec 99, its Open questions line names only measures and carrying, the release 3 plan records R3-T2.2 as built, the tests that pinned the refusal and the old Open questions line are changed, and the engine's offline suite, `ruff check src tests` and `mypy` pass.
Weight: light
