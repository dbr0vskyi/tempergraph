Spec 44 has no "Not built yet" bullet any more (discovery removed it), so AC 5 asks for a test that keeps it out.
- Files opened beyond the reading list, and why: `engine/src/tempergraph/improve/record.py` (how findings are read and written, for the corroboration write); `engine/tests/test_loop_child.py` (`blocked_run`, `judge_says`, `outcome_ticket`, the fixtures of the child's tests); `engine/tests/test_cli.py` (the `cli` helper that runs `improve backlog`); `engine/tests/test_loop_summary.py` (it builds on `build_code_run` and counts a `review_repeat` finding as recorded; it stays true); `docs/guides/improving-workflows.guide.md` (it states no repeat or corroboration rule, so no guide is false).
- Why this design: the cross-run count sits beside the in-run count in `repeat.record`, which already runs after the last review, so both kinds share one finding, one cause and one cluster (SRV-B32, SRV-B28). The loop's own proposal matches clusters to the ticket's fingerprints, fixed before the review runs, so the child hands `act` a ticket copy whose fingerprints add this run's `review`-lens findings. Corroboration needs the run's kept observations when the issue body is written, so the child runs the review after the friction judge and before it decides and files; executor call order does not change.
- Choices the specs leave open, settled here: (1) a model-free finding is any finding of the run whose lens is neither `review` nor `outcome`; (2) when several categories were kept on its unit, the finding takes the category with the most kept observations (ties: first in alphabetical order) and `review_weight` is that count, as SRV-B27 counts; (3) the issue body names the category code only, checked against the catalog's names; (4) the proposer's reading is the kept observations of the cluster's unit, every category, from the runs that member findings sit in (`thread`) or name (`runs`), notes included, datamarked and fenced as the review view does. The code report states each of these.
- Tests that pin what changes: no test constructs by position or compares a signature that changes. `build_code_run` in `tests/test_review_repeat.py` gains a defaulted `keys` parameter, and its callers (`tests/test_loop_summary.py`) pass two arguments. The filing step moves after the review in `child.process`, so the phase 3 expand step runs the whole suite for tests that read `loop.jsonl` by position.
