- Why this design: the cross-run count sits beside the in-run count in `repeat.record`, which already runs after the last review, so both kinds share one finding, one cause and one cluster (SRV-B32, SRV-B28). The loop's own proposal matches clusters to the ticket's fingerprints, fixed before the review runs, so the child hands `act` a ticket copy whose fingerprints add this run's `review`-lens findings. Corroboration needs the run's kept observations when the issue body is written, so the child runs the review after the friction judge and before it decides and files; executor call order does not change.
- Choices the specs leave open, settled here: (1) a model-free finding is any finding of the run whose lens is neither `review` nor `outcome`; (2) when several categories were kept on its unit, the finding takes the category with the most kept observations (ties: first in alphabetical order) and `review_weight` is that count, as SRV-B27 counts; (3) the issue body names the category code only, checked against the catalog's names; (4) the proposer's reading is the kept observations of the cluster's unit, every category, from the runs that member findings sit in (`thread`) or name (`runs`), notes included, datamarked and fenced as the review view does. The code report states each of these.
- Tests that pin what changes: no test constructs by position or compares a signature that changes. `build_code_run` in `tests/test_review_repeat.py` gains a defaulted `keys` parameter, and its callers (`tests/test_loop_summary.py`) pass two arguments. The filing step moves after the review in `child.process`, so the phase 3 expand step runs the whole suite for tests that read `loop.jsonl` by position.

## 2. Phases

### Phase 1: A category kept in several runs is a finding

Goal: three runs that keep one category on one unit give the third run one `review_repeat` finding naming the runs, which `improve backlog` lists, and two runs give none. Tests first in `tests/test_review_repeat.py` (SRV-AC17: the 3-run and 2-run backlog through `cli(repo, None, "improve", "backlog", "demo", "--json")`, a rejected third run, another unit, the sessions-in-runs and four-run scenarios, the `infra` class of `environment_fault`, the parameter record; `build_code_run` gains the defaulted `keys` parameter), then `improve/params.py` (`review.repeat_runs`, 3, source SRV-B32), `improve/repeat.py` (a run store reader of kept runs and the cross-run branch of `record`, one finding per unit and category and run, carrying `runs` and the weight of this run's kept observations) and `improve/causes.py` (the remedy text names sessions or runs).
Weight: medium

### Phase 2: A review repeat reaches the proposer and files nothing

Goal: at autonomy `propose` the loop child proposes on the cluster of the repeat finding its own run's review recorded, and at `file` it proposes nothing, with no issue and no comment at any run count. Tests first in `tests/test_autonomy.py` (SRV-AC18, on `_fake`, with runs 1 and 2 written by `write_reviews` and the third reviewed by the child) and in `tests/test_review_repeat.py` (SRV-AC11 at one, two and three runs through `child.process`, extending `test_a_review_alone_files_nothing_in_any_run`), then `improve/child.py` (after the review, `act` gets a ticket copy whose fingerprints add those of this run's fault findings with lens `review`).
Weight: light

### Phase 3: Corroboration files

Goal: a model-free finding with a kept observation on its unit in its run carries `review:<category>` and `review_weight` and files an issue whose body names the category and no note text; without a kept observation, or with one of an earlier run only, it files as before and names no review category, a kept observation with no finding files nothing, and a finding below the friction floor stays unfiled. Tests first in a new `tests/test_review_corroboration.py` (SRV-AC15, with `ticket`, `session`, `bash`, `rec` of `tests/test_session_review.py` and `build_code_run` or a session of repeated failing calls so that `tool_thrash` is kept), then `improve/record.py` (a helper that rewrites the findings document), `improve/review.py` (a function that sets `review` and `review_weight` on the run's model-free findings), `improve/filing.py` (`body` names the category code of a `review` field), `improve/child.py` (review after the friction judge and before deciding and filing, candidates read after it) and `16-self-improvement.spec.md` (SIL-B17 lists the review before the decision and filing).
Weight: medium

### Phase 4: The proposer reads kept observations

Goal: the proposer's prompt for a cluster carries the kept observations of the cluster's unit, with notes, from the runs its findings belong to or name, datamarked and fenced, and nothing of another unit or of a rejected observation, while only `review.py` and `proposals.py` name the evidence folder. Tests first in `tests/test_proposals.py` (SRV-AC16, on `proposer_ex` capturing `req.prompt`, with member findings written for two runs that each kept `tool_thrash` on `code`, one also keeping `prompt_misread` on `plan` and a rejected `instruction_ignored` on `code`), then `improve/review.py` (a reader of kept observations with notes for one unit and run) and `improve/proposals.py` (`propose` appends the datamarked block to the proposer's prompt).
Weight: medium

### Phase 5: Close-out

Goal: the canary test of SRV-AC5 carries the id `SRV-AC5`, a test pins that spec 44 has no "Not built yet" line and that its text names no unbuilt SRV-B7 or SRV-B10, and the engine suite, `ruff check src tests` and `mypy` pass. Tests first (`tests/test_session_review.py`), then no source change.
Weight: light
