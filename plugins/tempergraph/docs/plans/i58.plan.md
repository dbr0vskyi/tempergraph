## 2. Phases

### Phase 1: The code host reads closed issues

Goal: `MemoryCodeHost` and `GhCodeHost` answer a read of the closed issues of a fingerprint with number, URL, body, close reason and close time, and `mute.days` is a parameter record.
Weight: light

### Phase 2: A loop issue sits in the triage queue

Goal: a filed issue carries the labels of `issue_labels` and the four fixed sections, for workflow, engine, executor and child-workflow findings.
Weight: medium

### Phase 3: The loop reads close reasons back

Goal: a finding that would file mutes after a close as not planned, links a possible regression after a close as completed, files plainly for an unread reason or a failed read, and a `muted` result is recorded but never counted as filed.
Weight: medium

### Phase 4: Proposals and trials link their issue

Goal: a draft pull request writes `Closes #<n>` for the cluster's issues of its repository, and a finished trial leaves one agent-format `result` comment on each of them, through the outbox when the host is down.
Weight: medium

### Phase 5: Documents say what is built

Goal: `CONTRIBUTING.md`, the improving-workflows guide and the live-check runbook stop calling #58 pending and describe the labels, sections, mute, regression link, `Closes #<n>` and the trial comment, with the L-17 closed-as-not-planned case added and not run.
Weight: light
