- Why this design: the run's `run_segment` ledger row is written once at each exit and never rewritten (IMD-B13), so the pull request is a field of that row (FIN-B11) and each `later[]` entry (OUT-B24) is a new appended ledger row of its own kind, which the readers of a run's outcome join by thread. Review text is written only to the run's local evidence by a module that `filing.py` and `codehost.py` never import (FBK-B15, the source test of `tests/test_filing.py`). The read, the finding and the filing sit in the loop child beside the proposal read (PRP-B26, PRP-B28), so they inherit its conditions: autonomy `file` or above, no dry run, a host that cannot be reached changes nothing.
- Detail that serves OUT-B24 and adds no behaviour: "the commits the run's branch did not hold when it ended" needs the commit the branch held at the run's end, so the pull request record on the ledger row also holds that commit id (no text); "the files the run wrote" and "the units that wrote them" come from the run log's `agent_run` records, which name the paths each session changed.
- Tests use fixture workflows from `tests/fixtures/`; none names a shipped workflow (`tests/test_source_rules.py`).

## 2. Phases

### Phase 1: The run records its pull request

Goal: a finalizer url that names a pull request leaves its code host, repository, number and the run's end commit on the run's ledger row, and the text-to-pull-request rule gives the host as well.
Weight: light

### Phase 2: The code host reads a pull request's reviews, comments and commits

Goal: the code host clients (the `gh` client and the in-memory one) answer read-only questions about a pull request's reviews with their state and author kind, review comments, and commits with author kind and changed files, as constant argv with the repository checked, and fail as `CodeHostError` when the host cannot be reached.
Weight: light

### Phase 3: A read of a recorded pull request appends a `later[]` entry

Goal: at each final exit the loop child reads the pull requests that runs of the workflow recorded, appends counts-and-kinds entries to a run's `later[]` as ledger rows, writes review text only to the run's local evidence, and a ticket is written for a workflow that has a recorded pull request still to read.
Weight: heavy (large-context)

### Phase 4: Escapes are counted from reviews

Goal: one function counts the escapes of a workflow from reruns, `changes_requested` reviews and follow-up commits on files the run wrote, and `outcome show`, `outcome candidates` and the audit rule `outcome-escapes` all read it.
Weight: light

### Phase 5: An escape fires the lens, is a finding and files by the pattern rule

Goal: a read that shows an escape records an `outcome_escape` finding for each unit that wrote a changed file (or the `outcome` unit), fires the outcome lens in stable mode with no model call, files by the pattern rule, and is corroborated by kept review observations of the same unit and run.
Weight: heavy (large-context)

### Phase 6: An escape is a harvest candidate

Goal: `evals harvest <workflow> outcome` writes one local candidate per escape with the pull request's identity, counts and kinds and the suggested `UNMET`, and no text.
Weight: light

### Phase 7: The canary, the no-workflow check and the documents

Goal: one test shows review text reaches no record but the local evidence, one test shows the specs name no shipped workflow, the stale statement that no run records its pull request is gone, and the guide and the skill say what the loop and `evals harvest` now do.
Weight: light
