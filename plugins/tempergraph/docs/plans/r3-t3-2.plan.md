A session that works from this plan starts from the hand-off's reading list and opens another file only for what the list does not answer.
- Why this design: the map's four nodes keep the item in hand in channels keyed by unit (`attempts`, `judgements`, `feedback`, `counters`, `route`, `pause`), which is right for one item at a time and wrong for several at once. The work is therefore ordered so each phase is testable alone: validation first, then per-item state with read-only concurrent items (the heavy phase, a refactor of what the sequential map also uses, so every sequential map test in `tests/test_map.py` must keep passing unchanged), then the writing shape by reusing R3-T3.1's `cut_writers`, `fork` and `_merge_writers` for items, then pauses addressed by item, then reservations and the check after the merge, then documents. A sequential map keeps compiling to the same graph, so the diagrams that workflow packages commit do not change.
- Choices taken from the hand-off's Open questions, none of which blocks planning: a failed check after the merge ends the map blocked and not retried with the merge kept (MAP-B13); a second entry into a writing concurrent map by a trip back is outside this task and the code report names it under Deviations; no `needs_git` reason is added for a map and the code report names it; the plain key after a concurrent map holds the last item of the list. These follow the specs as written and add no behaviour.
