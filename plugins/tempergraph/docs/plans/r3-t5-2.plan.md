## 2. Phases

### Phase 1: Who may create a schedule, and the fire token

Goal: `add`, `edit`, `resume` and `fire` need a person (`schedule_not_by_person`, `--relayed`); a fire token is made at `add` and stored as `token_digest`; the run's caller classification accepts a valid token as caller `scheduler` and refuses `schedule_token_invalid` and `schedule_reserved` before anything is written.
Weight: light

### Phase 2: Unattended credential kinds and the per-executor check

Goal: each executor declares its unattended credential kinds as a capability, and a model-free check resolves each executor and judge binding of a schedule at `add`, `edit` and each fire, filling `executors_checked` and giving `credential_unattended`, `judge_credential`, `credential_may_expire` and the fire-time `credential` refusal.
Weight: medium

### Phase 3: The scheduled-run ledger and `schedule runs`

Goal: every handled fire is one row of `~/.tempergraph/schedules/runs.jsonl`, updated by an `ended` row, kept when its schedule, state root or repository is gone, and read by `schedule runs` from any directory.
Weight: light

### Phase 4: The tick

Goal: `schedule tick` is the lock-guarded, idempotent, model-free routine that settles, decides through the R3-T5.1 functions and launches `run` detached through an injectable launcher with the token, `--schedule` and a hand-off ticket, within 4 runs and 20 s, with `deferred`, `repo_missing` and a heartbeat.
Weight: heavy (many-tests)

### Phase 5: `schedule fire` through the tick's path

Goal: `schedule fire <id>` starts one fire now through the tick's launch path with a manual fire id, no catch-up and the person-only rule, and `NOT_IN_RELEASE` shrinks to the verbs of the later phases and then to none.
Weight: light

### Phase 6: What a scheduled run adds elsewhere

Goal: a scheduled run carries `origin: schedule` and the schedule block in its status document, `run_started`, the stats row and the sink row; `report --by schedule`, the attention items, `blocking_schedule`, `trigger_stale`, the `schedule_paused` hook event and the supervision counts follow, proved end to end with scripted runs (SCH-AC5, SCH-AC7).
Weight: heavy (large-context)

### Phase 7: The portable loop and the `host` adapter

Goal: `schedule loop [--detach|--stop]` runs the tick on a sleep that ends on a wall-clock jump, one per user, re-executing through the shim after an engine update; the SessionStart hook starts it when `schedule.loop_autostart` is on; `schedule add` warns when no trigger is alive.
Weight: medium

### Phase 8: The `os` adapter and `schedule trigger`

Goal: `schedule trigger install|status|remove` writes, reports and deletes one per-user entry (LaunchAgent, systemd user unit, Task Scheduler task, crontab fallback) that names only the shim and `schedule loop` or `schedule tick`, checked against golden files and never installed for real, with `no_os_scheduler`, `broken` and the rewrite after an `update`.
Weight: medium

### Phase 9: Pipeline export

Goal: `schedule export <id> --for github-actions|gitlab-ci|crontab` prints the snippet of TCK-B20 with the UTC cron rule, and `export_needs_utc` and `--pin-offset` for a moving offset.
Weight: light

### Phase 10: The `tempergraph:schedule` skill

Goal: the skill drives the verbs with no state and its eval cases cover the five cases of TCK-AC7.
Weight: light

### Phase 11: Documents, probes and the final checks

Goal: specs 83 and 84, the release 3 plan, the live-checks plan and the tests that pin their wording say what is built and what waits; P-SCH-1 to P-SCH-4 are listed; no engine file names a workflow package; the three checks pass.
Weight: light
