- Why this design: the applied deadline reuses the person's path. `runner.resume` meets `--apply-deadline` on an `input` pause whose `on_deadline` is `defaults`, merges the stored answers with each unanswered question's default and runs the author's `check` the way `_answers_step` does; a pass hands the complete set to the human node, which routes it exactly as a person's `proceed` with answers does (artifact `answers`, step values), with `by: deadline`. A refusal keeps the ask open with exit 3 and stores only the given answers. The refusals at validation and at entry share one helper in `run/asking.py`, so the rule is stated once in code.
- Default text is the author's text (owner's delegate, option (a) of the hand-off's open question): no row checks a default against its question's kind, and no row adds such a check.
- The pre-deadline refusal (exit 2, nothing written) and the supervisor refusal are untouched; a test pins the first for this value.
- No version bump and no changelog file (hand-off, Decisions; VER-B9).

## 2. Phases

### Phase 1: Validation and the entry check

Goal: `on_deadline: defaults` is accepted only on an ask whose required questions all have a default, refused on a wait and on an incomplete ask with its own finding codes (R1), and an ask that reads its list from a step stops before its pause when a required question has no default (R2); the shared rule is one helper in `run/asking.py`, and the value comment of `AskSpec` in `contracts.py` names `defaults`.
Weight: light

### Phase 2: Applying the deadline

Goal: `resume --apply-deadline` after the deadline completes the ask from its defaults, runs the check, continues with an `answers` artifact that lists `defaulted` and writes the `deadline` row (R3, R5), keeps the ask open with exit 3 and only the given answers when the check refuses (R4), still refuses before the deadline with exit 2 and nothing written (R6), and `defaults` is no longer read as a unit name by the deadline target, reachable units and diagram (R7).
Weight: heavy (large-context)

### Phase 3: Plan row and checks

Goal: the release 3 plan row I3-15 records the feature as built (R8), and the offline suite, lint and types pass (R9).
Weight: light
