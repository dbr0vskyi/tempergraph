Beyond the list I searched the engine source for callers of `deadline_node`, `deadline_of`, `apply_deadline` and `ask_fault` (it found `model/diagram.py`, `run/outcome.py` and `api.py`, where `on_deadline` is already a free string, so none needs a change beyond `flow.deadline_node`), and read lines 296-320 of `run/gate.py` where an `ask_fault` stops the unit.
- The specs already state the new value with scenarios and ids (discovery wrote FLX-B8, FLX-B11, FLX-AC6, FLX-AC7, ASK-B10 to ASK-B13, ASK-AC5 to ASK-AC8), so this plan edits no spec.
- Why this design: the applied deadline reuses the person's path. `runner.resume` meets `--apply-deadline` on an `input` pause whose `on_deadline` is `defaults`, merges the stored answers with each unanswered question's default and runs the author's `check` the way `_answers_step` does; a pass hands the complete set to the human node, which routes it exactly as a person's `proceed` with answers does (artifact `answers`, step values), with `by: deadline`. A refusal keeps the ask open with exit 3 and stores only the given answers. The refusals at validation and at entry share one helper in `run/asking.py`, so the rule is stated once in code.
- Default text is the author's text (owner's delegate, option (a) of the hand-off's open question): no row checks a default against its question's kind, and no row adds such a check.
- The pre-deadline refusal (exit 2, nothing written) and the supervisor refusal are untouched; a test pins the first for this value.
- No version bump and no changelog file (hand-off, Decisions; VER-B9).
