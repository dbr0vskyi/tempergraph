- Why this design: the applied deadline reuses the person's path. `runner.resume` meets `--apply-deadline` on an `input` pause whose `on_deadline` is `defaults`, merges the stored answers with each unanswered question's default and runs the author's `check` the way `_answers_step` does. A pass hands the complete set to the human node, which routes it as a person's complete answers are routed (artifact `answers`, step values) with `by: deadline`. A refusal keeps the ask open with exit 3 and stores only the given answers. The refusals at validation and at entry share one helper in `run/asking.py`, so the rule is stated once in code.
- Default text is the author's text (option (a) of the hand-off's open question): no row checks a default against its question's kind.
- The pre-deadline refusal (exit 2, nothing written) and the supervisor refusal are untouched; a test pins the first for this value.
- No version bump and no changelog file (hand-off, Decisions; VER-B9).
- ASK-AC4 and FLX-AC2 are criteria of the two specs this plan depends on, and no test carries either. Neither follows from this task's criteria, and neither can be carried truthfully by this change. ASK-AC4 asks for the monitor's documents to show kind `input` with question counts; the spec's own Open questions say that holds only in the status document and waits on the monitor's documents. FLX-AC2 asks that every scenario of FLX-B6 (selective parallel) hold offline; the spec's Open questions say selective parallel is not built and stays in release 3, and the engine refuses it `not_in_release`. ## 2. Phases

### Phase 1: Validation and the entry check

Goal: `on_deadline: defaults` is accepted only on an ask whose declared required questions all have a default, and is refused on a wait and on an incomplete ask with its own finding codes (R1); an ask that reads its list from a step stops before its pause when a required question has no default (R2). The rule is one helper in `run/asking.py` that validation (`model/validate.py`, outside the early return on a missing `deadline_s`) and the entry of `_person_unit` in `run/nodes.py` both call; the `on_deadline` comment of `AskSpec` in `contracts.py` and the id-range docstrings name `defaults` and ASK-B13. Tests carry FLX-AC7 and ASK-AC8.
Weight: light

### Phase 2: Applying the deadline

Goal: `resume --apply-deadline` after the deadline completes the ask from its defaults, runs the check, continues with an `answers` artifact that lists `defaulted` and writes the `deadline` row (R3, R5); keeps the ask open with exit 3 and only the given answers when the check refuses (R4); still refuses before the deadline with exit 2 and nothing written (R6); and `defaults` is no longer read as a unit name by the deadline target, the reachable units and the diagram (R7). The work is in `run/asking.py` (the defaulted names; `store` writes `defaulted` only when given), `run/runner.py` (the `--apply-deadline` branch of `resume` and a deadline answers step beside `_answers_step`), `run/gate.py` (`apply_deadline` takes the completed answers and routes them as a complete set with `by: deadline`) and `model/flow.py` (`deadline_node`, `reachable_units`). Tests carry ASK-AC5, ASK-AC6, ASK-AC7, FLX-AC6 and FLX-AC5.
Weight: heavy (large-context)

### Phase 3: Plan row and checks

Goal: the release 3 plan row I3-15 in `plugins/tempergraph/docs/plans/third-release.plan.md` records the feature as built (R8), every new test carries its criterion id, and the offline suite, lint and types pass (R9).
Weight: light
