- Why this design: the files a run wrote come from its own repository, the diff between the branch start (the `base_commit` of the run log's `workspace` record) and the end commit on the ledger row (OUT-B28), read in the main checkout that holds the state root, which shares the worktrees' objects. The unit that wrote a file comes from a new list on the `agent_run` record of each step session: the files changed since the commit the session started from, committed or not, by any tool or command (SIL-B33). A judge's `changed_paths` keeps its meaning. The read returns a result for every pull request it read, appended or not, so the finding follows the state (OUT-B32), and an OS lock around the decision to append and to record makes overlapping reads leave one entry and one finding per unit (OUT-B30).
- Choices of the plan that no spec fixes, all inside OUT-B25, OUT-B29 and OUT-B31: a host answer holds `author_kind` `person` only for an account of type user that the host gives as owner, member or collaborator (a review and a comment carry `author_association`; a commit author's standing is one read-only GET of the repository's collaborator check for each distinct author of a commit after the end commit, none for a commit with no account or with other than one parent); the `loop_skipped` record of a pull request that cannot be read holds `thread` (the run's thread id), `number` and `error` (the type name), with `step` `pull_request_read` and `reason` `error` as the whole-read record has; `MemoryCodeHost` keeps the shas whose files it was asked for, so a test counts them.
- No spec line changes: the new `wrote_paths` field of a step's `agent_run` record is the record SIL-B33 reads and no spec lists the fields of that record. No behaviour is cut: the rest of the cost of a read, the recorded code host with the url pattern, and the watch-only ticket are named out of scope by the task, to be filed as follow-up issues and named in the code report.
- Open questions of the hand-off keep their `Until answered` defaults: a run that is an escape only by a rerun gets no finding at a read (option a); a later run's commits on a pull request another run recorded count as a person's follow-up commits (option a).
- Tests use fixture packages and a fake host built in the tests; none names a shipped workflow (`engine/tests/test_source_rules.py`). The fixture steps are scripted replies that write a file in the request's workdir and commit it, one through a tool call and one through a shell command with no tool call.

## 2. Phases

### Phase 1: The run's files and the unit that wrote each

Goal: a step session records the files it changed since the commit it started from, the loop takes the run's files from the diff between branch start and end commit, and a fixture run whose steps commit gets its entry and its finding for the writing unit.
Weight: medium

### Phase 2: What a read asks, counts and skips

Goal: the host client asks for the files of follow-up commits only, counts a person only by the host's standing and one parent, and a pull request that cannot be read leaves one `loop_skipped` record.
Weight: medium

### Phase 3: One entry and one finding for one state

Goal: a read returns every pull request it read, the finding is recorded from the run's state at the end of each read for each unit not holding one, and overlapping reads leave one entry and one finding per unit.
Weight: medium

### Phase 4: Review text is never carried

Goal: `evidence/pull_request.jsonl` is in no carried set, and the canary test covers a carried thread.
Weight: light

### Phase 5: Test ids, the status field and the first request's criteria

Goal: every test of the pull request reads carries the criterion it proves, a test names DUR-AC7 on real status rows, each of criteria 1 to 5 of the first request has a test on a real fixture run, and the guide says who counts as a person.
Weight: medium
