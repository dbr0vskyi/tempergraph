A loop issue closed as a duplicate binds its cause to the issue it duplicates: later sightings comment there and open no new issue (GitHub issue #196)

The improvement loop finds the issue of a cause only among issues that carry its label `tempergraph-loop` and its hidden lines, so it opens an issue for a cause a person has already filed. The owner decided on 2026-11-26 (comment on #196): closing the loop's issue as a duplicate binds its cause to the target; later sightings comment on the target and open no new issue. The area is the engine (`plugins/tempergraph`): spec `loop-issues` (ISS-B3, ISS-B4, ISS-B5, ISS-B7, ISS-B9, ISS-B13, ISS-B16, ISS-B17), `self-improvement` (SIL-B2, SIL-B18, SIL-B19), `improvement-data` (IMD-B23), `local-observability-store` (LOS-B7), the decision record `docs/adr/a-close-as-a-duplicate-mutes-a-loop-issues-cause.adr.md` (its `Revisit when` names this decision) and the guide `docs/guides/improving-workflows.guide.md`. The engine names no workflow (ADR `the-engine-names-no-workflow`), so every behaviour is stated for any package and tested with an engine fixture.

What the code does today, on the trunk at `790bd25c`:

- `improve/codehost.py` (`GhCodeHost.loop_issues`) reads `repos/<repo>/issues` with `labels=tempergraph-loop`, page by page, and keeps `number`, `url`, `body`, `state_reason`, `closed_at`, `created_at`. `improve/filing.py` (`file`, `_match_open`, `_holds`) matches the lines `<!-- tempergraph:fp=<fingerprint> -->` and `<!-- tempergraph:cause=<key> -->` (`cause_key`: a digest of side, workflow and cause) in the bodies of those issues only. An issue without the label is never read.
- A loop issue closed as `not_planned` or `duplicate` mutes its cause for `mute.days` (30, `improve/params.py`): `file` at `filing.py:618`, the outbox at `filing.py:537` (ISS-B3, ISS-B17, built by run i171b). After the 30 days the cause opens a new issue. A close as `completed` links a possible regression (ISS-B4, `filing.py:622`).
- A "seen again" comment is bounded by `seen_again.max_per_issue_per_day` (1), counted per repository and issue number from the `issue_commented` records (`comments_by_day`, ISS-B13).
- What the code host gives without GraphQL, checked on #198, #199 and #200 on 2026-11-27 with read-only `gh api` calls: the issue object holds `state_reason: "duplicate"` and no field for the target; the `closed` event of `issues/<n>/timeline` holds `state_reason` and no target; no `marked_as_duplicate` event exists on any of the three. The target is named only in the text of the person's closing comment ("Closing as a duplicate of #172, whose …"; "Closing as a duplicate of #189 for … and of #134 for …"; "Closing as a duplicate of #134 (…) and #157 (…)"), which `repos/<repo>/issues/<n>/comments` returns with the author's `author_association` (`codehost.py` `_kind` already classes an author from it). Whether a close through GitHub's own "close as duplicate" control leaves a REST event that names the target was not checked; GraphQL's `MarkedAsDuplicateEvent` is not used (ISS-B9 keeps the loop on REST).
- A hand-written issue already collects a cause's findings when a person gives it the label and the cause line of a loop issue (ISS-B7, `_match_open`; the guide says so). That way stays as it is and is not this run's work.

Evidence: the replay in the review of run i170c (comment of 2026-11-26T22:56Z on #170; the engine's own functions over one machine's records, 17 threads and 296 recorded judge answers, an in-memory code host seeded with the seven real loop issues): 25 issues would open, 28 when the mutes of #198 to #200 end on 2026-12-26; 11 to 13 of the 25 repeat an issue a person filed (#148, #149 and #212, #192, #197, #134, #204). #198, #199 and #200 were closed as duplicates of #172, of #189 and #134, and of #134 and #157: two of the three closes name two targets, and one target (#134) is named by two causes.

The design this run builds (one slice; the decision record of criterion 9 weighs it against the alternatives):

- **Learned from** the loop issue of the cause that was closed most recently, when its state reason is `duplicate`: the newest comment on it by a person with standing (`OWNER`, `MEMBER` or `COLLABORATOR`) that holds the words `duplicate of #<n>` (any case), and in that comment the first such number. It is GitHub's own comment form and the form of this batch's three closes, so no new marker has to be taught and the three real closes bind as they are. The duplicate-of relation is not used because REST does not give it. With no such comment the close mutes as today (ISS-B3).
- **Stored** as a local record keyed by repository and cause key (source issue, target issue, the source's close time), a cache of what the host says: a machine with no record learns the binding from the host at its first filing of the cause, and a record whose source issue was reopened, closed anew or commented on since is learned again.
- **A later sighting** adds one comment to the target, within the bound of ISS-B13, whose first lines stand on their own on a person's issue.
- **The target's state decides** when it is closed: as completed, a new loop issue links it as a possible regression (as ISS-B4); as not planned or as a duplicate, the cause is muted from the target's close (as ISS-B3); with another or no reason, a new issue opens (as ISS-B5).

Acceptance criteria:

1. The code host client reads, by REST only and with list-argv calls (SEC-B7): the comments of one issue (for each its text and its author kind, as `_kind` classes it) and one issue by number (state, state reason, close time, whether it is a pull request), whatever labels the issue carries. The memory code host gains the same two reads, issues without the loop's label, and comments with an author kind, so a test can seed a person's issue and a closing comment. A test proves each read on the memory host, and a test of `GhCodeHost` with a replaced `gh` proves the two calls, that no search and no GraphQL call is made, and that a bad repository or number is refused.
2. A finding that would file, matches no open loop issue, and whose loop issue closed most recently was closed as `duplicate` with a target named as the design says, opens no issue and adds one comment to the target, inside `mute.days` as after it. The result is `commented` with the target's number, so its `issue_commented` record counts toward the bound of criterion 4. The first learning leaves one `loop_result` record with op `bound` that holds the cause key, the source's number and the target's number and no text. A fixture run proves: closed 10 days ago and 31 days ago both comment on the target and open nothing; the loop issue reopened takes the comment itself (an open issue wins, SIL-B2); a comment by an author without standing binds nothing; with two numbers in the comment the first is the target; a newer comment by a person with standing replaces the target.
3. With no target named, or a target that is the source itself, a pull request, or a number the host does not hold (`HTTP 404`), nothing is bound and ISS-B3 applies unchanged: `muted` inside `mute.days`, a new issue after it. When the read of the comments or of the target fails twice for another reason, no issue opens and no comment is sent, and one `loop_result` record with op `binding_unreadable` holds the cause key and no text. A test proves each case on the memory host, and the closed-reason cases already tested (`not_planned`, `completed`, a duplicate with no target, none) keep their results.
4. The comment on a target begins with a sentence that says it comes from tempergraph's improvement loop, names the cause, the workflow and the units, names the loop issue whose close as a duplicate sends the comment there (`#<n>`), and says that reopening that issue ends it; the sections of a "seen again" comment follow (ISS-B8, ISS-B11, ISS-B12, ISS-B14, ISS-B15) and no request text or free text of a run is in it (ISS-B10: the canary test covers this body). A target gets at most `seen_again.max_per_issue_per_day` comments of the loop in one UTC day, counted over every cause bound to it; a comment over the bound leaves one `comment_capped` record with the target's number. A fixture of two causes bound to one target and two exits on one day leaves one comment and `comment_capped` records for the rest, and an exit on the next day adds a second.
5. A target reopened takes the comments again. A chain (a target that is itself closed as a duplicate of a third issue) is not followed. A test proves each of the five cases on the memory host.
