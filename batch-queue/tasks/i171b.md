The pattern rule for friction findings is safe to switch on: finish the change after its review (GitHub issue #171)

Since merge `b546268e` a friction finding of the improvement loop files when its fingerprint is recorded in `pattern_rule.min_runs` runs with `pattern_rule.min_distinct_requests` distinct requests and its judge attributed it, at any confidence (SIL-B18), a finding its judge gave no answer for stays `not_judged` (SIL-B35), and `loop.jsonl` records what the judge answered (`answers[]` of `loop_judged`, SIL-B36). The area is the engine (`plugins/tempergraph`): specs `self-improvement` (SIL-B2, SIL-B3, SIL-B18, SIL-B35, SIL-B36), `loop-issues` (ISS-B3, ISS-B7, ISS-B12), `improvement-data` (IMD-B23, the parameters), `engine-cli` and the guide `docs/guides/improving-workflows.guide.md`. The engine names no workflow (ADR `the-engine-names-no-workflow`), so every behaviour is stated for any package and tested with an engine fixture.

A first run built the rule; its plan and notes are `plugins/tempergraph/docs/plans/i171.plan.md` and `plugins/tempergraph/docs/tasks/i171.triage.md`, `i171.handoff.md` and `i171.report.md`; this run writes its own plan and notes and leaves those as the record. Its code met its criteria. An independent review (`batch-queue/tasks/i171.review.md`, with a replay script in its appendix) then replayed the engine's filing functions over one machine's real records: 8 threads, 19 friction clusters that meet the count, 63 judge answers of which 20 were `attributed: false`. The rule would open 9 to 11 issues there, about four of them noise and three repeating issues a person filed, and would add 3 to 9 "seen again" comments at every run exit. The findings below are the work of this run:

1. The attribution gate is one draw of an unstable flag. `improve/filing.py` (`decide`) reads only this run's `attributed`, at any confidence. For 8 of the 19 clusters the judge answered false at least once, and for 6 it gave both answers across runs; an earlier `false` is not held against the count, so a cause such as a pause an operator's agent answered files on one "true" at 0.5 after a "false". The judge brief (`improve/child.py`, `BRIEF`) does not say that an attributed answer can file whatever its confidence.
2. No bound on "seen again" comments. `improve/filing.py` (`file`) adds one full-body comment per cause to an open issue at every exit; a cause present in 7 of 7 runs is commented 7 times. The daily cap (SIL-B20) is in USD and holds in stable mode only.
3. A loop issue closed as `duplicate` is filed again at the next exit: `file` mutes a cause only for `not_planned` (ISS-B3) and links only `completed` (ISS-B4).
4. The reason `below_floor` covers three cases: not attributed (also at 0.9), below the count, and below the floor. A decision below the count carries no counts, and an `issue_filed` record carries no reason, so `loop.jsonl` does not say why a finding filed or did not.
5. Requests can be reached inside one thread: `_pattern` counts every digest of the history, and a thread whose request changed between segments holds two (5 runs, 7 requests for one cluster). A request edited within one run can stand in for a missing distinct request.
6. An operator cannot hold filing for a machine. `improve/params.py` is constants; `run --dry-run` holds one thread and `resume` does not take the option; `TEMPERGRAPH_AUTONOMY=record` is an environment variable of the process that reaches the final exit, which a run already started cannot be given, and the guide does not name it as a hold.

Acceptance criteria:

1. A friction finding whose fingerprint meets the pattern rule files by the count only when at least two answers are recorded for that fingerprint inside `pattern_rule.window_days` (the `answers[]` of the `loop_judged` records of the workflow's runs, this run's answer included) and more than half of them are `attributed: true`; a tie does not file. With one recorded answer only, the finding is recorded with reason `few_answers` and files by the count at no confidence; it still files when that answer is attributed at or above `friction.file_confidence`. SIL-B18 states it, and a fixture proves each case: answers (true, false, true) file, (false, true) and (true, false) do not, one attributed answer at 0.5 does not, one attributed answer at 0.8 does.
2. The friction judge's brief says that an answer `attributed: true` can file the finding by the count whatever its confidence, and a test asserts the sentence is in the prompt the judge session receives.
3. The loop adds at most `seen_again.max_per_issue_per_day` (1, a loop parameter with provenance `default_no_data`) "seen again" comments to one issue in one UTC day, counted from the `issue_commented` records of the workflow's runs in the state root; a comment over the bound is not sent and leaves one `loop_result` record with op `comment_capped`, the issue's number and no text. `loop-issues` states the behaviour. A fixture of three exits on one day with one open issue leaves one comment and two `comment_capped` records, and an exit on the next day adds a second comment.
4. A loop issue closed with state reason `duplicate` mutes its cause as `not_planned` does (ISS-B3): inside `mute.days` no issue is opened and no comment added, and the result is `muted`. A test against the memory code host proves it, and the closed-reason cases already tested (`not_planned`, `completed`, none) keep their results.
5. A friction finding that does not file is recorded with exactly one of these reasons: `not_judged` (no answer), `not_attributed` (this run's answer is `attributed: false`, at any confidence and any count), `few_answers` or `not_attributed` by the majority of criterion 1 (the spec says which), `below_count` (attributed, the count not met, confidence below the floor), `below_floor` (kept only if a case remains for it; if none remains it is removed from code and specs). A test names each reason once.
6. Every decision for a friction finding of class `fault` that reached the judge carries the runs, requests and machines counted, and its `loop_result` record holds them as numbers; an `issue_filed` and an `issue_commented` record hold the decision's reason (`pattern_met` or `fault`). A test reads the records of a fixture loop child.
7. A request digest counts once per thread in the pattern rule, for both lenses: a fixture of three runs of which two share a request and one holds two digests does not meet `pattern_rule.min_distinct_requests`, and three runs with three requests still do. SIL-B3 states how runs and requests are counted.
8. An operator can make every run of a workflow on a machine record and not file without an environment variable: a setting the engine reads at each final exit, from the settings file an operator already uses for run settings, lowers the workflow's autonomy to `record` for runs started before the setting was written as for later ones. `self-improvement` or `engine-cli` states the key, and a test proves that a thread started without the setting and ending after it was written files nothing and records reason `autonomy_record`.
9. `tempergraph resume` accepts `--dry-run` with the meaning it has on `run` (the thread's loop files nothing and records `would_file`), `resume --help` shows it, and a test resumes a paused fixture thread with it and finds no issue, no comment and a `would_file` record.
10. `docs/guides/improving-workflows.guide.md` has a section on holding filing that names the three ways (the setting of criterion 8, `--dry-run` on `run` and `resume`, `TEMPERGRAPH_AUTONOMY=record`), says what each still runs and records, and says that closing a loop issue as not planned or as duplicate mutes its cause for `mute.days`; the guide's commands are the CLI's.
11. A replay test on an engine fixture, with a scripted judge and the memory code host, of five runs with five requests of a fixture workflow whose records hold, in each of at least three runs: a pause answered by an agent (cause `agent_decided:escalation`), a check failure at a step whose check ran the repository's suite and failed for the environment (recorded as `check_fail` for that step), and `retries_spent` after the executor reported a usage limit; the judge answers each as the review measured (attributed false in most runs, true in one). No issue and no comment is made for any of the three causes at any of the five exits, and a fourth cause of the fixture that the judge attributes in every run files one issue at the third exit and is commented within the bound of criterion 3.
12. The specs changed by this run state what the code does without naming any workflow, every new parameter is in `improve/params.py` with its source, and each new test carries the id of the spec criterion it proves.

Out of scope, each to be filed as a follow-up issue and named in the report:

- Mixed engines on one ticket queue: the loop child is started with the interpreter of the run that exited and claims every waiting ticket, so a ticket written by a run on one engine build can be decided by another build's rules (review finding 5).
- No lock around "read the open list, then create": two loop children filing the same cause within seconds can open two issues (review finding 6).
- Dedup against issues a person filed: the loop matches only issues that carry its label and its hidden lines, so it opens an issue for a cause a person has already filed.
- `tests/test_loop_open_questions.py` asserts the prose of two open questions and fails when the owner answers one (review finding 8).
- The open question on `review_repeat` clusters lives in `review-repeats.spec.md` and not in `self-improvement` (review finding 9).
