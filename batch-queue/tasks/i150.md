temperspec: a spec wording finding at the outcome gate goes back to discovery, never to triage (GitHub issue #150)

In run `temperspec/i144` of 2026-11-25 the outcome gate's check passed and its judge wrote that every task criterion was achieved with tests. It graded `ts-spec-sync` PARTIAL with the fix in one sentence (add one clause to a scenario of a linked behaviour) and named no `defect_in`. The gate answered BACK with `route_target: triage.step` (cause `outcome_serves`), so the run did triage, three reading sessions, discovery, the plan and the code again for one line of a spec. With an earlier trip back of the same run this reached the attempt cap and the run stopped.

The cause is in the package (`plugins/temperspec-tgraph`), not in the engine. The engine sends a failing final criterion back to the earliest unit on the run's path whose own criterion `serves` it (engine spec `run-outcome`, OUT-B3; `run/outcome.py` `derived_back`). In the package's `outcome.json` four criteria serve `ts-spec-sync`: `ts-set-links` (setup), `ts-tri-gaps` (triage), `ts-dis-links` (discovery) and `ts-code-related` (code). Triage is the earliest of them on an ordinary path, and setup on a path that ran the setup. A spec sentence that disagrees with a linked spec is discovery's product: the package's overview gives the specs to discovery, sends every return to discovery from a later gate to the full visit (decision record `short-discovery-visit`), and the decision record `ts-spec-sync` has the criterion judged at the outcome gate only.

Wanted: a failing `ts-spec-sync` with no `defect_in` reaches the step that owns the spec, with the judge's fix in its hands. The engine's rule stays as it is; the package changes which of its criteria serve `ts-spec-sync`, or how its outcome gate names the place of the defect.

Acceptance criteria:

1. An outcome judgement with `ts-spec-sync` PARTIAL or UNMET and no `defect_in`, on a path that holds the full discovery, routes to `discovery`; neither `triage`, `setup` nor a reading step (`read_gap`, `read_component`) is entered again.
2. On a path that does not hold the full discovery (the short visit, the quick lane, triage straight to the plan) the same judgement routes to a step a package spec names for that path, and that step is never `triage` or `setup`.
3. The step the run goes back to is given the judge's fix as the judge wrote it (the `fix` and the place of the failing criterion), in the reason of its visit.
4. A test of the package proves 1 and 2 with the engine's own routing (the loaded workflow and `outcome.json`, not a copy of the rule), and one fixture run shows the units entered after the judgement.
5. A spec of the package states where each final criterion that a judge grades sends the run when it names no `defect_in`, and the decision record `ts-spec-sync` agrees with it.
6. `outcome.json` carries a new revision with its `revisions` entry, and `tempergraph author verify plugins/temperspec-tgraph` passes its model-free rungs.

Out of scope: any change to the engine's back-target rule (OUT-B3); `ts-traced` and a criterion that only a live check proves (#151); what the run's exit says after a stop at the attempt cap (#172); `workflow_changed` after a trip back (#152).
