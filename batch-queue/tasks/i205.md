Run control: the attempt cap stops a loop and not a healthy run, a stop request is cleared by the stop it caused, and a stop by request records for the improvement loop and files nothing (GitHub issue #205)

Three small things seen on 2026-11-26 (`batch-queue/observations.md`, "The second session's runs"). The area is the engine (`plugins/tempergraph`): specs `compiler-and-flow` (CMP-B5), `run-settings-and-overrides` (the setting `run.attempt_cap`), `map-unit`, `run-control` (RCT-B7, RCT-B9), `durability-and-resume`, `runs-without-a-final-exit` (SIL-B27, SIL-B28) and the guide `docs/guides/improving-workflows.guide.md`. The engine names no workflow (ADR `the-engine-names-no-workflow`), so every behaviour is stated for any package and tested with an engine fixture.

1. The attempt cap in a healthy run. A run stopped with exit 4 and reason `attempt_cap` at the retry of its first map item after one step, eight items of a reading map, three more steps, one of them retried once, and the item: 15 attempts in one invocation, with no trip back. `_boundary` in `run/nodes.py` compares `attempts_started`, which counts every attempt of every unit and every item, with the setting (default 15, `settings.py`). `resume` went on, so the cap cost only a person's time; nothing in the exit tells such a stop from a loop.
2. A stop request outlives the stop it caused. A run was asked to stop (`tempergraph stop`, mode drain) and stopped at its boundary with exit 4 and reason `stopped_by_request`. The next plain `resume` ended at once with exit 4, reason `stopped` and the message "stopped at None", and the one after it was refused: "a stopped thread re-opens with retry, back:<unit> or rewind:<unit>" (`run/runner.py`). Only `--decision retry` re-opened the thread. RCT-B7 says the request file is removed when the engine acts on it and RCT-B9 that a stale one is cleared at a resume; what made the first resume stop is not known and is the run's to find (the operator's logs show only the two exits).
3. A stop is an exit the loop files at. SIL-B9 makes every exit that is not a pause final, so a stop by request started a loop child that judged and filed three issues while the thread was going to be resumed. Whether such a stop files is stated nowhere.

Parts 1 and 2 (criteria 1 to 6) touch no file of the improvement loop. Part 3 (criteria 7 to 9) does, and it rests on what i170b and i170c state for pause findings and for a ticket that only recorded: it is built only when both are on the batch head this run starts from. If the operator starts this run earlier, criteria 7 to 9 are cut and become a request of their own.

Acceptance criteria:

1. A run that only moves forward is never stopped by the default cap, whatever the number of its units and of a map's items. `compiler-and-flow` (CMP-B5) states what the cap counts so that this holds (for example: an attempt counts when it repeats, as a retry or as a visit after a trip back; or a map's items count once for the map), and `run-settings-and-overrides` says the same of the setting. A fixture run of one step, a map of twenty items and three more steps, each passing on its first attempt, ends with exit 0 under the default settings.
2. A run that repeats is still stopped: a fixture run whose two units send each other back until the cap, and one whose step fails its gate until the cap with a retry budget above it, each stop cleanly before the next attempt with exit 4 and reason `attempt_cap`, at the count the spec states. The recursion limit of the graph stays a backstop that no fixture reaches.
3. The exit at the cap says what repeated: the `run_exit` record and the exit's JSON payload hold the number of attempts counted, and for each unit (and item) that was attempted more than once its attempts and the trips back that entered it. A test reads both from the fixture of criterion 2. Where i172 (`batch-queue/tasks/i172.md`) already puts the trips back of an invocation on the finding of this exit, the same numbers are used and not counted twice.
4. A thread that stopped at the cap during an item of a map resumes at that item with the passed items not run again (MAP's rule stands), and the count starts anew for the invocation; the existing tests of `tests/test_run.py` and `tests/test_map.py` on the cap still pass, changed only where criterion 1 changes the number they set.
5. A thread stopped by a request, in mode drain at a boundary and in mode now inside a session, continues with a plain `tempergraph resume <workflow> <task>`: no decision is asked for, the run goes on from the attempt the stop interrupted or preceded, and the thread ends as the same run without the stop would. After the stop no request file is left, and nothing in the thread's stored state makes a later invocation stop again. `run-control` states it; one parametrised test for the two modes proves it and reads the exit of the resume.
6. The cases beside it keep their meaning: a request written while no engine runs the thread is removed at the next resume and recorded as stale, and the run is not stopped by it (RCT-B9); a second request during a stop keeps the stronger mode (RCT-B8); a thread stopped by a person's decision or by a spent budget still re-opens only with `retry`, `back:<unit>` or `rewind:<unit>`, and the refusal's message says which kind of stop it is. `status` shows a thread stopped by request as resumable with the command to type.
7. An exit with reason `stopped_by_request` records for the improvement loop and acts on nothing: the segment's findings are derived and stored as at any exit, no judge session and no session review is started, no issue is opened and no comment added, and `loop.jsonl` gains one record that says the exit was a stop by request, with the count of findings held and no text. `runs-without-a-final-exit` states it beside SIL-B27 (a person's stop at a pause stays an exit that is judged). A fixture thread with a fault in its segment, stopped by request, leaves no ticket for a judge, no call to the memory code host and that one record.
8. The findings of a segment that ended in a stop by request are handed to the loop at the thread's next final exit, once, as SIL-B28 hands those of a segment that ended in a pause, and by the rule i170c states for a ticket that only recorded. A fixture thread stopped by request, resumed and finished files for a fault of its first segment exactly once and asks the judge once; a thread stopped by request and never resumed leaves its findings recorded only, and the spec says so.
9. `docs/guides/improving-workflows.guide.md` lists, in its paragraph on final exits, what the loop does at each exit that is not a pause: finished, stopped at the attempt cap, stopped by a budget, stopped by a person's decision, stopped by request, failed, lost. Its commands are the CLI's.
10. The specs changed state what the code does without naming any workflow and stay within the spec budget (`self-improvement.spec.md` is at 27.3 of 30 KB and four other requests add to it: the text of criteria 7 and 8 goes to `runs-without-a-final-exit.spec.md`); each new test carries the id of the spec criterion it proves.
