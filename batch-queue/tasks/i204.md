A judge that says it did not read is asked again once, with its own fix line, before a person is paused; the judge briefs say a row's file is opened before the row is graded (GitHub issue #204)

Twice on 2026-11-26 a judge that had the read tools ended its judgement by saying what it had not opened, and the run paused for a person. Run `temperspec/i123b`, outcome judge: "I did not read the code or test bodies for AC 1 to 4 and AC 7", `ts-accepted` PARTIAL with `gap`, pause `unresolved_gap`; the operator's `retry` with "read them, then grade" passed in one minute. Run `temperspec/i153`, judge of phase `p3`: rows "were seen only as search output", with the fix "Read status.py around lines 160-175 and the 3.1 test body"; the operator opened the two places and answered `proceed`. Run `temperspec/i173` met it a third time at phase `p3` ("Rows 3.1, 3.2 and 3.4 were not read", fix "Read the files of rows 3.1, 3.2, 3.4, 3.7 and 3.9 around the change lines"). In each case the judge named the lines it needed, and the only thing a person added was "read them".

The task has two parts, in two areas.

The engine part (`plugins/tempergraph`, spec `judge-and-verdict`). Today `derive` (`run/judging.py`) turns a judgement with `gap: true`, or a blocker graded UNVERIFIABLE, into ESCALATE with reason `unresolved_gap`, and a blocker graded PARTIAL into RETRY of the step, which runs the step's session again for something the step cannot change. The judge node (`run/nodes.py`) already runs one second judge session when the first answer has no parsable block (kind `judge_reask`, JDG-B2); nothing asks the judge again when the block is valid and its gap is the judge's own. The engine names no workflow (ADR `the-engine-names-no-workflow`): the capability is stated for any judge of any package and tested with an engine fixture.

The package part (`plugins/temperspec-tgraph`, spec `judge-reading`). JRD-B6 already has every brief say that search lines alone are PARTIAL, and JRD-B3 has the code judge open the listed files. No brief of the other gates says that the file a row or a criterion names is opened before that row or criterion is graded, and no brief tells the judge how to say that a failing grade is about its own reading.

Acceptance criteria:

1. A judgement can say, for each criterion it grades PARTIAL or UNVERIFIABLE and for its `gap`, that the grade rests on something the judge itself did not open, with the places it needs in the finding's `fix`. `judge-and-verdict` states the field of the judgement block that carries it and how a judge is told of it in the answer format every judge receives; a judgement without the field reads as it does today.
2. When every failing blocker of a judgement, and its gap if it has one, is marked as the judge's own reading, the judge node runs exactly one more judge session for that attempt before any verdict is derived. Its prompt holds the first judgement's fix lines for the marked criteria and tells the judge to open those places and then grade the full rubric; it is the same judge (executor, model, tools, views) on the same subject. The verdict is derived from the second judgement alone. A fixture judge whose first answer marks its gap and whose second has none lets the run go on with no pause, no retry of the step and no retry spent.
3. The re-ask is bounded to one per attempt: a second judgement that still marks its own reading, has no parsable block (after the re-ask of JDG-B2) or times out is derived as a first judgement is today (an unresolved gap pauses, a PARTIAL blocker retries the step). A fixture proves that two judge sessions and no third run in that case.
4. A judgement in which at least one failing blocker is not marked is derived as today, with no extra session: a real defect is never hidden behind a re-read. A fixture proves it with one marked and one unmarked failing blocker.
5. The re-ask is recorded: the second session has a session kind of its own in the run log and the session records, the `judgement` record of the attempt says that a re-ask ran and which criteria it was for, and the run report and the run detail document count the session with the judge's sessions. The cost of the re-ask is in the run's cost. `judge-and-verdict` and the spec that owns the session kinds state it.
6. The guard, the usage-limit handling and the risk rules of a judge session hold for the re-ask as for the first session: a re-ask refused for a usage limit pauses as JDG-B14 says, and a re-ask the guard discards is an unparsed judgement. One test for each.
7. Every judge brief of the package (`judges/*.md`, and the outcome judge's stance in `outcome.json`) says that the file a row or a criterion names is opened with the read tool before that row or criterion is graded, that lines a search printed are not a reading (JRD-B6 stands), and that a grade that fails only because the judge did not open a place is marked as criterion 1 says, with the path and lines to open as its fix. `judge-reading` states the three rules for every judge of the workflow, and a test of the package asserts each sentence in each brief the loaded workflow hands a judge, as the tests of JRD-AC4 and JRD-AC5 do.
8. A stand-in run of the package on the `phases` arm, whose phase judge first answers with a marked gap and then with every blocker MET, passes the phase gate on its first attempt with no pause.
9. The specs changed by this run state what the code does, the engine's without naming any workflow; each stays within the spec budget; each new test carries the id of the spec criterion it proves; JDG-AC and JRD-AC tests still pass, changed only where a criterion above changes the fact they assert. `outcome.json` carries a new revision if a criterion or the outcome judge's stance changed.

The plan holds no row that runs `tempergraph author verify` or `tempergraph upgrade-check --stamp` and no row that edits a digest of `stamp.json` or `authoring.json` by hand: a step session may not run those commands (#203). If the package's files changed, the report names the files left for the operator to stamp after the merge; the one number the package's tests read (`outcome_revision` in `stamp.json`) may be set by a row.
