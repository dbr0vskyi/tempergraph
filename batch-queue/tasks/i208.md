The loop's filing is on by default, a dry run by its own setting, and one run can turn the dry run on or off with an argument (GitHub issue #208)

The owner decided on 2026-11-26 (issue #208): filing is on by default; one run can override either way with a parameter, on `run` and on `resume`; a machine-wide hold reaches runs already started; `status` and the loop's summary say which of these was in force. On 2026-11-27 the owner replaced one point: the workflow's mode does not control a dry run and controls other things; a dry run has its own setting and its own CLI argument; and the argument for real filing wins, for that run, over a declared autonomy level of `record`. The area is the engine (`plugins/tempergraph`): specs `self-improvement` (SIL-B6), `improvement-proposals` (PRP-B11, PRP-B31), `run-options` (ROP-B9, ROP-B14), `run-settings-and-overrides`, `loop-summary-and-review-retries` (SIL-B22), `runs-without-a-final-exit` (SIL-B47), and the guide `improving-workflows`. The engine names no workflow.

What exists today, on the trunk at `93de7ae9` (paths under `plugins/tempergraph/engine/src/tempergraph`):

- The declared autonomy level defaults to `file` (`improve/proposals.py:75-92`), so a workflow that declares nothing files. That part of the decision already holds.
- `--dry-run` is on `run` and `resume` as a switch that can only turn a dry run on (`cli/main.py:269`, read at `:404`). It sets `RunSettings.dry_run` (`run/runner.py:108`) and is written on `run_started` and in the run's meta (`run/runner.py:416`, `:829`).
- At a final exit the thread is a dry run when this call or any earlier `run_started` of the thread had it (`run/runner.py:567-569`). The ticket carries it (`improve/child.py:147`) and `filing.file` writes `would_file` and files nothing (`improve/child.py:524`, `improve/filing.py:570`).
- A dry run is not a real run for the promotion and release counts (`improve/promotion.py:92`, `improve/release.py:25`). Trials, eval suites and authoring trials start their runs as dry runs in code (`improve/trials.py:291`, `improve/suites.py:296`, `author/trial.py:229`).
- The machine-wide hold exists: the run setting `loop_autonomy` (`settings.py:203`), read from the settings files at each final exit (`run/runner.py:561`, PRP-B31), lowers the level and never raises it. `TEMPERGRAPH_AUTONOMY` does the same (`improve/child.py:138`).
- The mode (`dev` or `stable`, `contracts.py:546`) decides the session review and the daily cap (`improve/child.py:126-136`). It decides nothing about filing, and this run keeps it so.

What is missing:

- A dry run is not in the settings catalog (`settings.py`), so no workflow and no settings file can declare it, and there is no declared default to print.
- Nothing turns a dry run off for one run: no `--no-dry-run`, and a thread that once had `--dry-run` stays dry to its end.
- The `loop_summary` record (`improve/loop_summary.py:50-56`: `recorded`, `filed`, `top[]`) and `status` (`observe/detail.py:561`) do not say whether an exit filed, ran dry or was held, or where that came from.

The design this run builds:

- One run setting, `loop_dry_run` (true or false, default false), in the catalog at scope `run`. A workflow declares it among its own setting defaults, a settings file or a profile sets it, like any run setting. The field `RunSettings.dry_run` and the records it writes stay; they take their value from the setting.
- `--dry-run` and a new `--no-dry-run`, on `run` and on `resume`, are spellings of `--set run.loop_dry_run=true` and `=false`. The thread keeps the value like any flag (RST-B26), so the value given last is the one in force.
- `--no-dry-run` given on the command line asks for real filing, and it wins over a level of `record` that the workflow declares: that thread files as at level `file`, and no higher. The declared level is not changed, so every other run of the workflow still records only. A `loop_dry_run` of false from a workflow, a file or a profile does not do this; only the argument does.
- The operator's hold still wins over the argument: `loop_autonomy` or `TEMPERGRAPH_AUTONOMY` at `record` files nothing.

Acceptance criteria:

1. A workflow that declares nothing about filing, run with no argument, files; a test proves it at mode `dev` and at mode `stable` against the memory code host, and no code path reads the mode to decide a dry run.
2. `loop_dry_run` is in the settings catalog at scope `run` with the values true and false and the default false; `config show` prints its value and the layer it came from. Any other value is refused before any spend, in the same words on `run` and `resume`.
3. A workflow that declares `loop_dry_run` true writes `would_file` results with titles, and makes no issue and no comment, at every final exit of its threads; the same holds when a settings file sets it. A fixture run proves both.
4. `run --help` and `resume --help` list `--dry-run` and `--no-dry-run`; each is recorded as the flag `run.loop_dry_run`, and a call that gives both is refused before any spend.
5. The argument overrides in both directions: a thread of a workflow that declares a dry run, started with `--no-dry-run`, files; a thread of a workflow that declares nothing, started with `--dry-run`, files nothing. A fixture run proves both.
6. The value given last wins: a thread started with `--dry-run` and resumed with `--no-dry-run` files at its final exit, and the reverse files nothing. A resume that gives neither keeps the value the thread holds, and `resume --unset run.loop_dry_run` returns the thread to the declared value.
7. A thread started before this change, whose log has `run_started` with `dry_run` and no value of the setting, is a dry run until a later call gives `--no-dry-run`.
8. `run_started` holds `dry_run` when the value in force for that segment is a dry run, from any source, so the counts of real runs (PRO-B8) leave out a run that a declared setting made dry.
