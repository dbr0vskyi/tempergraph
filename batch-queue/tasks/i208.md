The loop's filing is on by default, a dry run where the workflow's mode says so, and one run can override it either way (GitHub issue #208)

The owner decided on 2026-11-26 (issue #208): filing is on by default; a workflow's improvement mode can make it a dry run; one run can override either way with a parameter, on `run` and on `resume`; a machine-wide hold reaches runs already started; `status` and the loop's summary say which of these was in force. The area is the engine (`plugins/tempergraph`): specs `self-improvement` (SIL-B6), `improvement-proposals` (PRP-B11, PRP-B31), `run-options`, `run-settings-and-overrides`, `loop-summary-and-review-retries` (SIL-B22), `runs-without-a-final-exit` (SIL-B47), and the guide `improving-workflows`. The engine names no workflow.

What the code does today, on the trunk at `7fd52537`:

- The declared autonomy level defaults to `file` (`improve/proposals.py`, `autonomy`), so a workflow that declares nothing files. That part of the decision already holds.
- `--dry-run` exists on `run` and `resume` (`cli/main.py`) and only turns filing off. `run/runner.py` holds it for the whole thread: any segment that started with it makes every later exit a dry run, and no option turns it back.
- The improvement mode (`dev` or `stable`, `contracts.py`) decides the session review and the daily cap. It does not decide whether filing is a dry run.
- The machine-wide hold exists: the run setting `loop_autonomy`, read from the settings files at each final exit (PRP-B31), lowers the level and never raises it. The environment variable `TEMPERGRAPH_AUTONOMY` does the same.
- The `loop_summary` record holds `recorded`, `filed` and `top[]`. Neither it nor `status` says whether the exit filed, ran dry or was held, or why.

The design this run builds:

- A workflow may declare, in `improvement` of its `tempergraph.json`, the modes in which its filing is a dry run (a list of `dev` and `stable`, empty by default). With nothing declared the loop files in both modes.
- A run setting `loop_filing` with the values `file` and `dry_run` overrides the workflow's declaration for one thread. It is given on `run` and on `resume` with `--set` or its own option; `--dry-run` stays as the spelling of `dry_run`. The value given last on the thread is the one in force.
- The override changes the dry run only. It never raises the autonomy level: at `record`, declared or held, the loop records and files nothing whatever `loop_filing` says.

Acceptance criteria:

1. A workflow that declares nothing about filing files at `dev` and at `stable`; a test proves both against the memory code host.
2. A workflow that lists a mode as a dry run writes `would_file` results with titles, and makes no issue and no comment, at every final exit of a thread in that mode; in the other mode it files. A fixture run proves both.
3. A declared mode list that holds any other word is refused when the package is loaded, with a message that names the key and the allowed words.
4. `loop_filing` is in the settings catalog at scope `run` with the values `file` and `dry_run` and no default; `run` and `resume` accept it, and any other value is refused before any spend in the same words on both verbs.
5. A thread of a workflow whose mode is a dry run, started with `loop_filing=file`, files; a thread of a workflow that files, started with `loop_filing=dry_run` or `--dry-run`, files nothing. A fixture run proves both.
6. The value given last wins: a thread started with `--dry-run` and resumed with `loop_filing=file` files at its final exit, and the reverse files nothing. A resume that gives no value keeps the value the thread holds.
7. The hold wins over the override: with `loop_autonomy` set to `record` in a settings file before the final exit, a thread started with `loop_filing=file` makes no issue and no comment and records each decided finding with the reason `autonomy_record`.
8. The `loop_summary` record holds what was in force at the exit: `filing` (one of `file`, `dry_run`, `held`) and `filing_source` (one of `default`, `workflow_mode`, `run_setting`, `machine_hold`, `declared_record`). A test proves each of the five sources on a fixture thread.
9. `status` shows the same two words for a thread's latest final exit, in its text and in `--json`.
10. A finding of an exit that ran dry is handed again at the thread's next final exit, as SIL-B47 says today; the test of that behaviour covers a dry run caused by the workflow's mode.
11. `docs/guides/improving-workflows.guide.md` states the whole rule in one section: the default, the workflow's mode list, the per-run override, the hold and their order. A test asserts the sentences the guide must hold.
12. The specs changed by this run state what the code does without naming any workflow and stay within the spec budget. Each new test carries the id of the spec criterion it proves, and the tests of runs i171b and i170c still pass, changed only where a criterion above changes the fact they assert.
