A friction judge session of the loop that fails is a finding the loop files: first slice (GitHub issue #209)

The owner decided on 2026-11-26 (issue #209): a judge that fails is a critical fault and must not be silent. Each failure is a finding of its own with the judge's unit, the kind of failure, the executor and model, and counts; it files by the pattern rule like any fault. This slice covers the loop's own friction judge. The area is the engine (`plugins/tempergraph`): specs `self-improvement` (SIL-B35, SIL-B36), `friction-causes`, `friction-filing-decisions`, `loop-issues` (ISS-B2, ISS-B12). The engine names no workflow.

What the code does today, on the trunk at `7fd52537`:

- `improve/child.py` runs one friction judge session for the findings that have no recorded answer. Its `loop_judged` record holds `ok`, `parsed`, the executor, alias, effort, usage and the answers. When the session fails, or its reply cannot be read, or the reply leaves findings out, each unanswered finding is recorded `not_judged` (SIL-B35) and nothing else is written.
- No finding is made for the judge itself, so a judge that fails at every exit leaves no trace a person is shown. `improve/causes.py` has `judge_unparsed` for a gate's judge and no cause code for the loop's judge.
- A session result says how it failed: `ok`, `timed_out`, `error_kind`, `infra_cause`, `usage_limit` (`contracts.py`, `SessionResult`).

The design this run builds:

- One kind per failed judge session, from a fixed list: `session_failed`, `timed_out`, `refused`, `unparsed`, `findings_left_out`, `usage_limit`. A session that fails in more than one way takes the first of them in that order of the list that applies, `usage_limit` first.
- One finding per failed session, cause `loop_judge:<kind>`, on a fixed unit name for the loop's friction judge, class `fault` and side `engine` for every kind but `usage_limit`, which is class `infra`, side `host`, and recorded only.
- The finding is not handed to the friction judge. It files by the count of the pattern rule alone.

Acceptance criteria:

1. The kinds are one list in the code with a cause code each in `improve/causes.py`; a test asserts the list, each kind's class and side, and that no other kind can be recorded.
2. A friction judge session that fails, for each of the six kinds, leaves one finding with the judge's unit, the kind, the executor, the model alias and the effort, the number of findings handed to the judge, the number it answered and the number left unjudged, and no text of the session. A fixture run through the loop child with a scripted judge proves each kind.
3. The `loop_judged` record of a failed session holds the same kind, so the finding and the record agree; a test compares them for each kind.
4. A session that answers every finding it was handed leaves no such finding.
5. A reply that answers half of the findings handed leaves one finding of kind `findings_left_out` whose counts hold the half that went unjudged; the answered half is decided as today.
6. A session the usage limit refused leaves a finding of class `infra` that is never filed, at any count.
7. A fault finding of this slice files when its fingerprint meets the count of the pattern rule, without an answer of the friction judge, and its decision record holds the numbers counted. A fixture over three threads proves it files at the count and not below it.
8. The finding is never handed to the friction judge: a test proves the judge's prompt of a later exit does not hold its fingerprint.
9. The issue filed for it goes to the engine's repository, and its body says the kind, the executor and model, and how many findings went unjudged because of it, summed over the sightings the body shows. The canary test for free text covers this body.
10. The findings the failed judge left out stay `not_judged` and are handed again at the thread's next final exit, as today.
11. The specs changed by this run state the behaviours without naming any workflow and stay within the spec budget (`self-improvement.spec.md` is over 30 KB and gets no new text: the behaviours go in `friction-causes.spec.md` or a new spec named for the capability). Each new cause is in the cause table with its remedy text, each new test carries the id of the spec criterion it proves, and the tests of runs i171b, i170c and i172 still pass, changed only where a criterion above changes the fact they assert.
