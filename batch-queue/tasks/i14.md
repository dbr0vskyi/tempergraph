A complexity switch in an example workflow, and guides for the release 3 features (GitHub issue #14)

Release 3 track R3-T10.1 (item I3-14, moved from R2-T9.1). New users learn the engine from the two example workflows (`plugins/release-notes-tgraph`, `plugins/doc-refresh-tgraph`) and from the user guides (`plugins/tempergraph/docs/guides/*.guide.md`: getting started, running, authoring and improving workflows, linked from the root README). Neither example has a complexity switch: a measured switch that picks between a simple and a detailed shape of the same job from model-free measures and a rules file in the package, the most detailed arm being the safe one (spec `complexity-routing`, CXR). The guides describe that switch in one paragraph ("Route by size" in the authoring guide) and have no section on what release 3 built: sub-workflows, writer branches, the concurrent map, council and contest units, and schedules. The pull-request gate is not built (issues #11 and #12), so its guide is not part of this task. The areas are the examples and the engine's guides (`plugins/tempergraph`). The engine names no workflow (ADR `the-engine-names-no-workflow`): the example's tests live in its own package, and the engine's suite finds them through `tests/test_workflow_packages.py`.

Acceptance criteria:

1. One of the two example workflows declares a complexity switch (CXR) that picks between a simple and a detailed shape of its job.
2. That example's own tests cover the switch and pass through the engine's `tests/test_workflow_packages.py`.
3. The guides say what a sub-workflow is for and how a workflow declares one.
4. The guides say what writer branches and the concurrent map are for and how a workflow declares each.
5. The guides say what the council and contest units are for and how a workflow declares each.
6. The guides say what a schedule is for and how to add one.
7. Every `tempergraph` command that a guide shows is a verb with flags that the CLI accepts.
