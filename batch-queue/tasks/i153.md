A session refused for the account's usage limit spends no retry and pauses the run until the reset (GitHub issue #153)

At 14:25 UTC on 2026-11-25 the account's usage limit was reached while three runs were live. Each refused session was recorded as an ordinary model error (`agent_run` with `ok: false`, `error_kind: model`, `infra_cause: null`, about 2 s long) and retried at once. One run spent its retry budget of 2 in four seconds and ended with exit 5 (`budget`); another paused on `retry_budget`; a third lost one retry. Both stopped threads went on with a plain `resume` once the limit was lifted.

The executor already reports the fact: a session that ends because the allowance is spent returns `usage_limit` true and `usage_limit_resets_at` (specs `session-contract` SSN-B11, `executor-claude-code` ECC-B17; `contracts.py`, `executors/session.py`). The run does not read it. `budgets-and-failures` BUD-B1 spends the retry budget on `error_kind: model`, and BUD-B11 names causes that escalate at once and spend no counter (`auth`, `refused`; `run/nodes.py` sets `escalate` for them). The loop's own reviews already stop on a usage limit (`session-review` SRV-B30). The area is the engine (`plugins/tempergraph`); the engine names no workflow (ADR `the-engine-names-no-workflow`).

Wanted: a refusal for the usage limit is a cause of its own. It charges nothing, pauses the run with the reset time, and a plain `resume` after the reset is all the run needs.

Acceptance criteria:

1. A step, retry or judge session that ends not ok with `usage_limit` true spends no retry and no infra try, and `budgets-and-failures` states it as a cause of its own.
2. The run then pauses (exit 3) with a pause reason of its own. The pause record and the run's `status` row carry `usage_limit_resets_at` (null when the executor reported none).
3. A plain `resume` continues at the same unit and the same attempt number, with every counter as it was before the refused session.
4. The run-log record of the refused session carries `usage_limit` and the reset instant, so a reader can tell it from a model error.
5. A fixture with a stand-in executor whose sessions end not ok with `usage_limit` true and a reset one hour ahead, on a step with a retry budget of 2: after three refused sessions (the first run and two resumes) the retry counter is 0 and the thread is paused, not ended with `budget`.
6. A fixture in which the judge session of a gate is refused the same way: the gate's verdict is not derived from it, nothing is spent, and `resume` runs the judge again without running the step again.
7. A session that fails with `usage_limit` false is counted as before the change.
8. The specs that define the pause reasons and the status row state the new reason, and every new rule has a test that carries its criterion id.

Out of scope: waiting for the reset and resuming without a person; a cause code of the improvement loop for the refusal (#172); how an executor recognises the limit (ECC-B17 stands); the loop's own review retry (SIL-B25, SIL-B26). A refused session that is one item of a map or one member of a council or contest follows the same rule; a fixture for those unit kinds is not asked for.
