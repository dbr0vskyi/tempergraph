temperspec: a review unit after the code step reads the diff and the acceptance criteria with nothing of the run's own reasoning (GitHub issue #173, without its live run)

Twice on 2026-11-25 a run of the temperspec workflow (`plugins/temperspec-tgraph`) passed every gate and an independent reader then found a defect that blocks the change's use. In `temperspec/i141` (outcome `met`, 11.64 USD) a reader given the diff and the criteria found in about three minutes a lookup that never ends when all its places fail; the code judge had graded the code's alignment MET. In `temperspec/i144` the reader found a plugin loaded before the suite's own path setup. A review cost about 120,000 to 170,000 tokens; sending the fix back after the run cost a second run each time (11.58 and 7.80 USD). The run's own judges cannot fill this place: they are given the step's products and reasoning to check against.

Wanted: a review unit after the code step (after both arms meet at `code_join`) and before the outcome gate. Its reader is independent and read-only. It is given the run's diff since the run's base, the task's acceptance criteria and the repository to read. It is never given the plan, the hand-off, the code report, an earlier judgement or the text of a step session. What it finds goes back as numbered feedback, and the run goes on to the outcome gate only when no blocking finding is left.

Neighbours, so the unit is not confused with them: #124 is a lens of the engine's improvement loop that reads after the run has ended and never changes the run's diff; #155 says how a step answers each numbered point of feedback; #105 separates the tests from the code session. The engine names no workflow (ADR `the-engine-names-no-workflow`). If the unit cannot be built with what the engine offers today (for example a session that is refused the run's own documents), the run writes that need in the package's docs as a general capability, builds no engine change, and says so in its report.

Acceptance criteria:

1. A spec of the package states the unit: where it sits, what the reader is given and what it is never given, as listed above.
2. The reader's prompt and the values it reads hold none of the plan, the hand-off, the code report, an earlier judgement or a step session's text; a test of the package proves it on the loaded workflow.
3. The reader's findings are numbered, each with a file and a line, each marked blocking or not blocking, and are written to a document on the run's branch; a model-free check refuses a finding without a file and a line or without its mark.
4. A blocking finding sends the run back once, to the plan step or to the code step, with the findings as numbered feedback; the spec says which step for which kind of finding.
5. The unit has a budget of one trip back: when a blocking finding is left after it, the run pauses and the pause shows the findings left.
6. Findings that are not blocking are in the draft pull request's description and block nothing.
7. The spec states a lane or a size of change under which the unit does not run, with its reason; a fixture run under that bound does not enter the unit.
8. The findings document also records, for each finding of a first review, whether the visit it started built it or refused it, as far as the engine's "every point is addressed" blocker (engine spec `reruns-and-feedback`, RRN-B14) gives that.
9. A fixture run whose diff holds a planted defect that every other gate passes is sent back by the unit; a fixture run with a clean diff passes it with no trip back.
10. `outcome.json` carries a new revision, `tempergraph author verify plugins/temperspec-tgraph` passes its model-free rungs, and the package's README, overview spec and diagram show the unit.

Out of scope: the live run that records the unit's cost and what it found (the operator makes it after the merge); the rule of #155 for how a step accounts for each feedback point; the loop's lens of #124; any engine change; a second reader or a council of readers.

Likely files: `plugins/temperspec-tgraph/workflow/temperspec/__init__.py` (the units after `code_join`), `workflow/temperspec/checks.py`, `workflow/temperspec/routing.py` (`finalize`, the pull request's description), `blueprint.json`, `outcome.json`, `authoring.json`, `stamp.json`, a new prompt and judge file under `prompts/` and `judges/`, `diagram/`, `README.md`, `docs/specs/overview.spec.md`, `docs/specs/code-join.spec.md`, `docs/specs/outcome-gate.spec.md`, a new spec for the unit, and a new test file under `tests/`.
