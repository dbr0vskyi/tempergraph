The loop's cause codes name a tool-access pause, a trip back, a stop at the attempt cap, an undelivered last stage and a usage-limit refusal (first slice of GitHub issue #172)

The improvement loop makes its findings from run-log records (`improve/causes.py` `derive`) and from session digests. On 2026-11-25 the costliest events of nine real threads had no cause code, or a code whose fixed remedy points at the wrong thing.

A code that says the wrong thing:

- A tool-access pause. The live record has `pause_kind: escalation` and `reason: tool_access`; `derive` tests `pause_kind == "tool_access"`, so the finding is `escalation:tool_access` with the remedy "An escalation with an unlisted reason". SIL-B14 says `tool_access:<refusal class>`, and stable mode's friction triggers (`improve/lenses.py`) list `tool_access`, which this finding does not match. The test of the cause types a record with `pause_kind: tool_access` that the engine's gate (`run/gate.py`) never writes.
- A pause of an ask unit (`pause_kind: input`) becomes `escalation:input`, class `fault`.
- `tool_repeat`: 96 of the day's 97 `repeats[]` entries have no error class (edits of one file, reads). The remedy says "The step repeated the same failing call", and SRV-B2's scenario is four failing calls.

No code at all:

- A trip back: five gates answered `BACK`. `derive` reads no `BACK` verdict; `loop_budget_spent` exists only for a pause. After one trip back a run spent 21 more sessions.
- A stop at the attempt cap: `run_exit` with reason `attempt_cap` (exit 4). `derive` knows the reasons `budget`, `person` and `cost_cap`.
- A last stage that did not deliver: `finalize` records whose outcome leaves a manual step or is `skipped`, on exit 0, with no finding.
- A session refused for the usage limit: recorded as `retries_spent`, a fault of the workflow.

This task is the part of the issue that reads run-log records. It starts after the usage-limit task (#153) is merged, which puts the refusal on the session's record. The area is the engine (`plugins/tempergraph`), spec `self-improvement` (SIL-B11, SIL-B12, SIL-B14, SIL-B23, SIL-AC7), `session-review` SRV-B2. The engine names no workflow (ADR `the-engine-names-no-workflow`): a code is made from what the engine's records say (a verdict, an exit reason, a finalizer outcome), never from the name of a unit or an outcome of one package.

Acceptance criteria:

1. A tool-access pause written by the engine's gate yields `tool_access:<refusal class>` (SIL-B14) and matches stable mode's friction trigger. The fixture's pause record is produced by a fixture run, not typed into the test.
2. `self-improvement` states a cause code for a gate's trip back, with a class, a side and a remedy. The finding names the unit the run left and the unit it went to, and counts the sessions run again after it.
3. `self-improvement` states a cause code for a final exit at the attempt cap; the finding says how many trips back the invocation held.
4. `self-improvement` states a cause code for a run that ends with exit 0 and whose finalizer outcome leaves a step to a person or did nothing, read from what the finalizer contract records; the spec says which recorded facts count.
5. `self-improvement` states a cause code for a session refused for a usage limit: class `infra`, never a fault of the workflow, and such a session yields no `retries_spent`.
6. A pause of an ask unit is classed `designed`.
7. `tool_repeat` is made only from repeats that failed; repeated calls that did not fail give a second code with a remedy of its own, or none, and SRV-B2 says which.
8. Each new or corrected code is produced by an engine fixture (SIL-AC7), and the remedy of each names a kind of change that fits a unit with no step and no prompt.
