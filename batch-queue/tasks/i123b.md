The improvement loop reads the person's review of a run's pull request as a later outcome signal: finish the change after its review (GitHub issue #123)

A person who reviews a delivered pull request finds in minutes what every gate let through, and the improvement loop did not hear them: the only later signals were an engine ruling, a rewind or rerun, `label <thread> outcome`, and a pull request closed unmerged that no run could derive, because no run recorded its pull request. Evidence: research `does-the-improvement-loop-find-what-a-reviewer-finds` F9, F10, conclusion 5. The area is the engine (`plugins/tempergraph`): specs `run-outcome` (OUT-B18, OUT-B19, OUT-B23 to OUT-B26), `feedback-and-judge-reliability` (FBK-B15), `self-improvement` (SIL-B10, SIL-B33, SIL-B34), `finalizer-contract` (FIN-B11), `lifecycle-and-evals` (LIF-B17), `durability-and-resume` (DUR-B11). The engine names no workflow (ADR `the-engine-names-no-workflow`), so the capability is stated for any package and tested with an engine fixture package. The code host is reached through `gh`; an unreachable host or a `gh` that is not signed in records nothing and fails nothing.

A first run built this on the branch this run starts from (`tg/temperspec/i123`): the pull request on the run's ledger row (`run/finalize.py`, `run/runner.py`), the reads of reviews, review comments and commits (`improve/codehost.py`), the `later[]` entry and the local evidence file (`improve/pr_later.py`), the escape rule and the model-free `outcome_escape` finding (`run/outcome_record.py`, `improve/escape.py`), the harvest candidate (`improve/harvest.py`), the `finalizer` field of the status row, the behaviours named above with their criteria, and tests. Its plan and notes are `plugins/tempergraph/docs/plans/i123.plan.md` and `plugins/tempergraph/docs/tasks/i123.triage.md`, `i123.handoff.md` and `i123.report.md`; this run writes its own plan and notes and leaves those as the record. The first run's code passed its gates. An independent review of it (`batch-queue/tasks/i123.review.md`, with four failing probe tests in its appendix) then found one defect that blocks its use and smaller ones; they are the work of this run:

Blocking:

1. "Files the run wrote" is empty for real runs, so a person's follow-up commit never makes an escape. `improve/pr_later.py` (`_wrote`) reads `changed_paths` from `agent_run` records; the engine writes that field only on judge sessions, from `git status` with no base, which is empty once a step has committed, and a step session's record holds none. In three real runs, 64 judge records hold an empty list and 57 step records hold none. The tests pass because they hand-write step records with `changed_paths`. `improve/escape.py` (`_writers`) matches against the session digests' `_wrote`, which holds edit and write tool calls only (8 of the 42 files the first run itself changed). Take the run's files from git or from the code host (the files of the pull request's commits up to the recorded end commit, or the diff from the run's base to its end commit), and attribute a file to a unit from that unit's commits or sessions in a way that holds for a step that writes through the shell.

Not blocking:

2. A review followed by a fix commit never names the writing unit: `escape.record` returns unless the run became an escape at this read (`_is_new`), and after a `changes_requested` review the run is one already. Decide on "is an escape now, and this unit holds no finding".
3. A failure or a race between the ledger row and the finding loses the signal for good: the `outcome_later` rows are appended first, the findings written after, and the next read sees an equal entry and returns nothing. Two loop children at two final exits both append the same row, and neither records a finding. Derive "needs a finding" from the state, not from the append, and let no equal entry be appended twice by two children.
4. `pull_commits` makes one GET for each commit, those before the end commit included, whose files are never used. Fetch files only for commits after the recorded end commit. A pull request that cannot be read is skipped with no record: write one `loop_skipped` record for it, with ids and an error kind only.
5. "A person" is any account that is not a bot: on a public repository any user can make a `met` run an escape and put text in the state root; a commit with no account counts as a person's; a merge commit that brings the base branch in can hit a file the run wrote. Count only an author the host gives as `OWNER`, `MEMBER` or `COLLABORATOR`, no commit with no account and no commit with more than one parent, and keep no text of any other author in the local evidence.
6. `evidence/pull_request.jsonl` is local by FBK-B15, and the carry filter (`durability/carry.py`) would push it with a carried thread. Never carry it.
7. Specs disagree with the code: FIN-B11 and FIN-AC5 do not name the end commit the row holds; OUT-B26 and OUT-AC10 say `met` where a rerun also counts for `met_with_open`; OUT-B24 does not say that an end commit no longer among the pull request's commits gives no follow-up commit; SIL-B10 says the outcome lens runs for the earlier run where the code writes one `loop_lens` record and the finding. Bring each line in line with what the system does after this run.
8. Test ids: the six tests of `tests/test_pr_reads.py` carry PRP-AC11 and prove the reads of OUT-AC8 and OUT-AC9; `tests/test_specs_name_no_workflow.py` carries a behaviour id; no test names DUR-AC7.

Acceptance criteria:

1. A run of a fixture package whose steps commit and whose finalizer returns a pull request url, read against a fake code host that shows a person's follow-up commit on a file the run wrote, gets a `later[]` entry with one file, is an escape in `outcome show`, and holds an `outcome_escape` finding for the unit that wrote the file, also when the step wrote it through the shell; no test of this criterion hand-writes a run-log record.
2. A run whose pull request a first read shows with a `changes_requested` review and a later read shows with a follow-up commit on a file unit `a` wrote holds a finding for the `outcome` unit and one for `a`, and a third read adds none.
3. A read whose finding could not be written leaves the finding to the next read, and two reads of the same pull request that overlap leave one `later[]` entry and one finding per unit.
4. A read asks the code host for the files of the commits after the recorded end commit and of no other, proved by a count on the fake host, and a pull request that cannot be read leaves one `loop_skipped` record with no text and changes no exit code.
5. A review, a review comment and a commit of an author the host does not give as owner, member or collaborator, a commit with no account, and a commit with more than one parent are in no count of an entry, make no escape, and leave no text in the local evidence; OUT-B25 and OUT-AC9 state it.
6. `evidence/pull_request.jsonl` is in no carried set, and the canary test of FBK-AC7 also covers a carried thread.
7. FIN-B11, FIN-AC5, OUT-B24, OUT-B26, OUT-AC10 and SIL-B10 state what the code does, without naming any workflow, and every test of the pull request reads carries the criterion it proves.
8. A test that names DUR-AC7 asserts on `status --json` rows of fixture threads that a finalizer that returned manual steps gives `finalizer` equal to the `finalize` event's `outcome`, `reason` and `manual_steps`, one that raised gives `outcome` `error` and no steps, a published or quietly skipped run has no `finalizer` key, the row holds the other fields of DUR-B11 that apply, and `status` left the state root unchanged.
9. For each acceptance criterion of the first request (`batch-queue/tasks/i123.md`, criteria 1 to 5), at least one test drives a real fixture run (steps that commit, a finalizer that returns a pull request url) and not hand-written ledger or log records.

Out of scope, each to be filed as a follow-up issue and named in the report:

- The rest of the cost of a read: no read of a pull request whose head commit and update time are unchanged, a cap by age or count of open pull requests, a minimum interval between reads, and a reopened pull request read again.
- The code host: the recorded host is not used by the read, and the pattern that takes it from a url admits credentials.
- A watch-only ticket that finds an escape does a whole ticket's work under the clean thread.
