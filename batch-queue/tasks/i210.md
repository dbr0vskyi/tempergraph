A loop issue holds the run's and the steps' metrics, and a redaction level decides what an issue in the engine's repository may show: first slice (GitHub issue #210)

The owner's direction of 2026-11-26 (issue #210): nobody who triages an issue has the machine that ran it, so the issue must hold enough to confirm it and to see an anomaly. This slice builds the metrics block (item 2 of the issue) and the redaction level (item 3). They go together because the level decides which rows of the block may leave the machine. The area is the engine (`plugins/tempergraph`): spec `loop-issues` (ISS-B2, ISS-B8, ISS-B10, ISS-B11), `local-observability-store`, `central-run-stats`. The engine names no workflow.

What the code does today, on the trunk at `7fd52537`:

- `improve/filing.py` (`body`) writes Summary, Environment, Run, Steps to reproduce, Run log, Evidence, Fingerprint and Suggested remedy. `RUN_NAMES` gives the run's cost so far, the cost of the finding's units and the attempts per unit; `improve/issue_context.py` (`run_facts`) derives them from the finding's segment.
- The body has no sessions, wall time, time waiting on commands, tokens, retries or trips back, for the run or for a step, and nothing to compare a figure with.
- A finding on the engine's or an executor's side files to the engine's repository (`filing.py`, `repository`). Its body shows the workflow's name, its unit names, its version and its costs, whoever owns the workflow. No setting limits that.
- The body holds ids, enums, numbers and versions only (ISS-B10), and a canary test proves no request text or run text reaches it.

The design this run builds:

- A `## Metrics` section after `## Run`: one row for the run and one row for each step the finding's segment ran, with sessions, wall time, time waiting on commands, tokens, reported cost, retries and trips back. Beside each figure stands the median of the same figure over the workflow's recent runs on this machine, with the number of runs it is taken from.
- A redaction level the workflow declares in `improvement` of its `tempergraph.json`: `full` (the default) or `engine_only`. It applies to an issue filed in a repository other than the workflow's own issue repository.

Acceptance criteria:

1. The body of a filed issue holds a `## Metrics` section whose first row is the run's: sessions, wall time, time waiting on commands, input and output tokens, reported cost, retries and trips back. A fixture run proves each figure against the records of that run.
2. One row follows for each step the finding's segment ran, with the same figures, in the order the steps first ran.
3. Each figure shows the median over the workflow's runs on this machine that reached a final exit, the most recent ones up to a loop parameter (in `improve/params.py` with its source), and the number of runs counted. With fewer than three such runs the row says so and shows no median.
4. A figure the records do not hold is shown as not recorded, never as zero; a test proves it for a session whose executor reported no cost.
5. The section holds numbers, unit names and enums only; the canary test for free text (ISS-B10) covers it.
6. The redaction level is read from the package when it is loaded; any word other than `full` and `engine_only` is refused with a message that names the key and the allowed words.
7. At `engine_only`, an issue filed in a repository other than the workflow's own shows no workflow name, no unit name, no workflow version, no cost and no token count. Its Metrics section holds the run's row only, with sessions, wall time, retries and trips back; its steps to reproduce name no unit.
8. At `engine_only` that body ends with one line that lists, by fixed words, which kinds of fact were withheld. A test asserts the line and searches the whole body for the fixture workflow's name and each of its unit names.
9. At `engine_only` an issue filed in the workflow's own repository is unchanged, and at `full` every issue is unchanged except for the new section. A test proves both.
10. A "seen again" comment follows the same level as an issue in the same repository.
11. The hidden lines the loop matches on (fingerprint, cause) are the same at both levels, so de-duplication is unchanged; a test files the same cause at both levels and finds one issue.
12. `loop-issues.spec.md` (26.5 KB of 30 KB) gains only a link; the behaviours go in a new spec named for the capability, with its `Depends on` rows and its path in the Purpose of `overview.spec.md`. The guide `improving-workflows` names the level and what it withholds. Each new test carries the id of the spec criterion it proves, and the tests of runs i170b, i170c and i171b still pass, changed only where a criterion above changes the fact they assert.
