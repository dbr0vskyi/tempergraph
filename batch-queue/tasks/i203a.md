temperspec: generated files of a repository's workflow packages (stamps, diagrams) are regenerated by a script step after the code step, in a worktree too, and a failed regeneration goes back to the code step as findings (first slice of GitHub issue #203)

Every run that changes a workflow package's outcome record, a unit or a brief, or an engine input of the packages' diagrams, has to refresh the package's `stamp.json`, `authoring.json` and `diagram/`. Those files are written by two engine commands, `tempergraph upgrade-check <package> --stamp` and `tempergraph author verify <package>`. No step session may run them (the workflow's `VERIFY` list in `plugins/temperspec-tgraph/workflow/temperspec/__init__.py` holds read-only git and the commands of the repository's `tempergraph.commands.json`), so a plan row that asks for them cannot be built. Seen on 2026-11-25 and 26:

- Run `temperspec/i153`, rows 4.9 to 4.11, and run `temperspec/i150`, row 3.3: the session built the rest, left the rows unmarked and the run paused for a person, who ran the command.
- Run `temperspec/i173`, rows 3.7 and 3.8: four pauses at phase `p3`. The operator ran the two commands three times and wrote each failure back to the phase by hand: `author verify` rung 2 `summary-too-long` (a unit summary over 60 characters in `blueprint.json`), then `blueprint-difference` (the unit and `blueprint.json` disagreed on what the unit reads); `upgrade-check` V4 with `validate:check_without_pass_case`, `validate:check_without_fail_case` and `outcome-unverified-blocker` for each new blocker. The session fixed each in one visit once it was told. A phase judge also failed the rows because `outcome_revision` had been edited by hand and the digests had not.
- In a worktree `author verify` fails at its register rung while the workflow's name is registered from the main checkout: `register` in `plugins/tempergraph/engine/src/tempergraph/package/registry.py` refuses `name-taken` for a second path. The operator's way round is a throwaway `TEMPERGRAPH_HOME`. `upgrade-check --stamp` takes a path and has no such refusal.

Wanted: no plan row and no model for the regeneration. After the code step has passed its gate (after both arms meet at `code_join`, and before the review unit that i173 adds and the outcome gate, so both read the regenerated files) a script unit regenerates what the repository says is generated, when its inputs changed in the run, and commits the result. When a regeneration fails, what it reported goes back to the code step as numbered findings, inside a budget; a person is paused only when that budget is spent.

What was checked before this request was written, so the run does not have to find it again:

- A script unit may run a `call` (a callable of the package, in the engine's process, as `prepare` and `commit_step` in `workflow/temperspec/routing.py` are) or a `run` whose prefix is on the workflow's allow-list (engine spec `script-units-and-hybrid-steps`, SCR-B5 and SCR-B6; `security` SEC-B5). The regeneration has to run with the engine of the run's own worktree when the repository holds the engine, so it is a command started in the worktree and not a call into the engine that runs the workflow.
- A script unit's failure retries the script (SCR-B7) and then pauses. No check finding can send a run back: `CheckFinding` (`contracts.py`) has no field for a unit at fault, a judge's `defect_in` is the only line back at an ordinary gate, and the outcome gate derives its target from `serves`. So "back to the code step with the findings" is not buildable with what the engine offers today.
- The package knows no stamp: which commands regenerate what is a fact of the repository. The repository already declares the commands a run may use in `tempergraph.commands.json` (engine `check-contract-and-command-runs` CHK-B11; package spec `repository-commands`).

The engine names no workflow (ADR `the-engine-names-no-workflow`). Before any engine change the run writes each need in the package's docs as a general capability; the engine change is then stated in the engine's specs without the workflow and tested with an engine fixture. Two needs are expected: (a) `author verify` of a package at a path, in a linked worktree of the checkout its name is registered from, passes or skips its register rung without a second home and without changing the registry entry of the main checkout; (b) a gate with no judge can send the run back to a declared back target when its check, or its script, fails with findings, the findings being the reason of the visit. If the run finds a way to meet a criterion below with no engine change, it takes it and says so.

Acceptance criteria:

1. A spec of the package states the unit: where it sits, what it reads to know which regenerations a repository has and what the inputs of each are, when it runs one (an input of it is among the paths the run changed since its base), that it starts no session, and that it commits what it wrote on the run's branch with the step's commits. A repository that declares no regeneration, and a run that changed no input, pass the unit with nothing run and nothing written; a fixture run for each proves it.
2. The declaration is the repository's, in a file the package's spec names (the commands file or one beside it); a regeneration command is run through the engine's command runner under the launch rules (SEC-B5), never through a shell, and a command the declaration does not hold is refused. The prepare step does not invent regenerations for a repository.
3. This repository declares its own: the stamp and diagram of each workflow package under `plugins/` whose files, or whose engine inputs, changed, and the authoring record where `author verify` writes one. After a fixture run in a linked worktree whose code step changed a unit's summary and a brief of a fixture package, the package's stamp, authoring record and diagram are the ones the two engine commands write, the main checkout's registry entry and files are unchanged (a tree digest before and after), and the run did not pause.
4. `tempergraph author verify <path>` run in a linked worktree, while the workflow's name is registered from the main checkout, passes its model-free rungs with the default home. The engine spec that owns the register rung states what the rung does for a path that is another checkout of the registered package; an engine fixture proves it and proves that a different package claiming a registered name is still refused `name-taken`.
5. A regeneration that fails sends the run back to the code step once, with one numbered finding for each thing the command reported (for the two engine commands: the rung or check, the finding's code, the unit and the message, as their JSON output gives them), and the code step's visit is told to fix those and nothing else. The four failures of run i173 are the fixture: a summary over 60 characters, a check with no pass case and no fail case, a blocker no case verifies, and a blueprint difference each come back as a finding that names the file to change; the stand-in code step fixes them, the regeneration passes on the second visit, and the run reaches the outcome gate with no pause.
6. The trip back has a budget of one: a regeneration that still fails after it pauses the run, and the pause shows the findings left. A regeneration that fails for the environment (the command does not start, a timeout) pauses at once and sends nothing back. A fixture for each.
7. On the arm `phases` the trip back runs the code step (the join) and not the phases again, unless the run shows in its plan why that cannot be had with the engine's back-edges; then the spec says what runs again and the fixture of criterion 5 counts the sessions.
8. The plan and expand prompts, and the plan rule if it must, say that a generated file the repository declares gets no task row and that `outcome_revision`, digests and diagrams are never edited by hand; the phase and code checks do not count a declared generated file the unit wrote against the scope of a phase or of the change (`ts-phs-scope`, `ts-code-scope`), and the code gate's reading list leaves them out.
9. If an engine capability of need (b) is built: a workflow declares it on a gate with no judge, validation refuses it on a map's gate (MAP-B11 stands) and on a gate that has a judge, the loop budget bounds it (BUD), the visit reason holds the findings' criterion, place, message and fix and nothing else, and an engine fixture with a script unit that fails once proves the trip back, the second pass and the budget. The engine specs changed say it without naming any workflow.
10. `outcome.json` carries a new revision, the package's README, overview spec and diagram show the unit, the specs changed stay within the spec budget, and each new test carries the id of the spec criterion it proves. The package's own stamp, authoring record and diagram at the end of this run are written by the unit this run built, in this run's worktree, or the report says why not and names the files left for the operator.
