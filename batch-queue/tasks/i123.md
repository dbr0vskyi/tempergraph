The improvement loop reads the person's review of a run's pull request as a later outcome signal (GitHub issue #123)

Record the pull request a run led to, and read its review state, review comments, requested changes and the person's own follow-up commits on the run's branch as later outcome signals (OUT-B18 `later[]`). A `met` run contradicted this way is an escape (OUT-B19): it fires the outcome lens, keeps the comment text as local evidence only, and becomes a harvest candidate for a labelled case.

Why: a person reviewing a delivered pull request found, in minutes, that a workflow's step wrote specs as a literal account of each task instead of the general rule. Every gate passed, and the loop, which ran on the same runs, filed only process findings. Today the only later signals are an engine ruling, rewind or rerun, `label <thread> outcome`, and a pull request closed unmerged, and even that last one is not derived because no run records its pull request (open question in spec `feedback-and-judge-reliability`). The person who merges is the cheapest reviewer there is, and the loop does not hear them. Evidence: research `does-the-improvement-loop-find-what-a-reviewer-finds` F9, F10, conclusion 5.

The area is the engine (`plugins/tempergraph`): specs `run-outcome` (OUT-B18, OUT-B19), `feedback-and-judge-reliability`, `self-improvement` (SIL-B10, SIL-B13). The engine names no workflow (ADR `the-engine-names-no-workflow`). The code host is reached through `gh`, as the loop's issue filing and a proposal's pull-request state already are; an unreachable host or a `gh` that is not signed in records nothing and fails nothing.

Acceptance criteria:

1. A run records the pull request it opened or pushed to (its number and code host), with no text of the pull request.
2. A later command, or the loop, reads that pull request's review state, review comments and follow-up commits by a person through the code host, and appends a `later[]` entry with counts and kinds only; comment text stays in local evidence.
3. A `met` run with changes requested, or with a person's follow-up commits that change files the run wrote, counts as an escape in `outcome show` and fires the outcome lens in stable mode.
4. An escape is a harvest candidate (`evals harvest outcome`) and a corroborating finding for review observations on the units that wrote those files.
5. Nothing in a filed issue or a ledger row carries review comment text, proved by a canary test.
6. The specs `run-outcome`, `feedback-and-judge-reliability` and `self-improvement` state this without naming any workflow.
