temperspec: the outcome gate sends no run back for a fact that no step can change (first slice of GitHub issue #197)

When a final criterion fails, the outcome gate sends the run back to the earliest step whose criterion serves it (engine spec `run-outcome`, OUT-B3 and OUT-B16; the targets come from `serves` in `plugins/temperspec-tgraph/outcome.json`). For two failures no step of the run can do anything, and the trip back still runs most of the run again and then stops on a budget:

- `ts-spec-fresh` fails when the base branch changed a spec the run edited (`_fresh` in `plugins/temperspec-tgraph/workflow/temperspec/checks.py`, package spec `side-by-side-runs`). Its own fix line says "start the task again from the head of the base branch", which no step session can do. In this batch a finished run is merged into the batch branch straight away while other runs are live, so the failure is common: runs `temperspec/i21b` and `temperspec/i153` were both sent back for it.
- `ts-verify` fails when a verification command fails for the machine (a cached sign-in, an environment variable, a full temporary folder; #185). The code gate compares a failing command with the run's base commit and marks the same failure there environmental, which pauses with no retry (`_compared`, `_run_commands` with `compare=True`; criteria `ts-code-base`, `ts-code-touch`, `ts-code-nobase`, `ts-code-spend` in `docs/specs/code.spec.md`; engine `check-contract-and-command-runs` CHK-B14, CHK-B18 to CHK-B20). The outcome check calls `_verify` without the comparison, so the same failure is recorded `environmental: false` and routed back; in run i21b the `expand` step then spent its retries on no change.

Runs sent back from the outcome gate on 2026-11-25 and 26: i144 twice, i21, i21b, i123, i153; four of them then stopped on a budget or the attempt cap. A trip back from the outcome gate runs about 85 percent of a run again (step costs of run i123b: about 15.7 of 18.1 USD).

This task is the part of the issue that stops those two trips. The area is the package (`plugins/temperspec-tgraph`): specs `outcome-gate` and `side-by-side-runs`. The engine names no workflow (ADR `the-engine-names-no-workflow`); a check result marked environmental already pauses any gate with no retry (engine `gate-and-human` HUM-B7), and this request expects no engine change. If a stand-in run shows that the engine's outcome gate routes back before it reads that mark, the run writes the need in the package's docs and makes the engine change as a general statement of OUT-B16 with an engine fixture.

Acceptance criteria:

1. A failing `ts-spec-fresh` never sends the run back. The outcome gate pauses with the cause: the pause shows each spec that changed on the base branch, the base commit and the head it was compared with, and the one action that clears it (bring the base branch's head into the run's branch, then answer `retry`; SBS-B2 already passes a run that merged the head). `side-by-side-runs` states it, and the criterion's fix line says the same. A stand-in run whose base branch gains a commit to a spec the run edited ends its first invocation paused at the outcome gate with no step entered again, and after a merge of the head made by the test and a `retry` it reaches the finalizer.
2. The outcome check compares a failing verification command with the run's base commit exactly as the code gate does (the same function, the same four cases: exits 0 at the base, fails the same, fails differently and names a changed file, fails differently and names none; not compared when there is no base or the command does not finish). A failure that is environmental by that comparison never sends the run back: the gate pauses with the command, its exit at the gate and at the base and the reason, as the code gate's pause does. `outcome-gate` states it. A stand-in run whose command fails the same at the base ends paused at the outcome gate with no step entered again.
3. A verification command that exits 0 at the outcome gate is never run at the base, and a failing one is run there once per visit of the gate; a test counts the started commands (as the test of `ts-code-spend` does).
4. A failure the change caused still goes back as today: a stand-in run whose command exits 0 at the base and 1 at the head is sent to the step OGT and `serves` name today, with the command's output in the reason.
5. When a fact no step can change fails beside a failure a step could repair, the run pauses and goes nowhere: a trip back cannot make the gate pass while the first fact stands. The pause lists both, the unchangeable one first. A stand-in run with a moved base and a failing `ts-traced` proves it. After the operator clears the first and answers `retry`, the gate runs again and the second failure is routed as today.
6. The outcome judge is not started when the check paused the run for criteria 1, 2 or 5 (CHK-B1 holds for the outcome gate); a test counts the judge sessions.
7. `outcome-gate` states, as one behaviour, which final criteria name a fact no step can change and what the gate does for each; the wording of `ts-spec-fresh` and `ts-verify` in `outcome.json` and their `check_method` say the same; `outcome.json` carries a new revision.
8. The specs changed stay within the spec budget, each new test carries the id of the spec criterion it proves, and the tests of OGT-AC, SBS-AC and the code gate's base comparison still pass, changed only where a criterion above changes the fact they assert.

The plan holds no row that runs `tempergraph author verify` or `tempergraph upgrade-check --stamp` and no row that edits a digest by hand. If i203a (`batch-queue/tasks/i203a.md`) is merged before this run starts, its unit writes the stamp; if not, the report names the files left for the operator to stamp, and the one number the package's tests read (`outcome_revision` in `stamp.json`) may be set by a row.
